📖 §1 背景: Memory Wall 4.0 — 为什么 KV Cache 需要新互联

在 LLM 推理中, KV Cache 占用随 context 长度线性增长. 一个 70B 模型 (Llama-3 70B) 在 FP16 精度, 128K context, batch=8 时, 每张卡需要约 80 GB 仅 KV Cache (远多于模型权重 140 GB 的一半). 当 8 卡 NVLink 互联时, 8x H100 80GB = 640 GB 总内存, 可装下 8 组 128K context; 但 跨节点 (没有 NVLink 桥接) 时, 每节点 80 GB 必须装下整组 KV Cache, 否则只能跨节点 KV Cache 搬运.

2026 年 LLM 推理场景越来越面临 4 个 Memory Wall 难题:

  • Memory Wall 1.0 — HBM 容量 vs 计算. 1 张 H100 80 GB, 跑 1 个 200B 模型推理需要 2-3 张卡.
  • Memory Wall 2.0 — HBM 带宽 vs 算力. HBM3e 4.8 TB/s, B200 5x PFLOPS, 算力带宽比 1:2000.
  • Memory Wall 3.0 — KV Cache 共享. 1 个 prompt 1000 个用户请求, 99% 共享 prefix, 但每请求独立存储 KV Cache, 浪费 99% 显存.
  • Memory Wall 4.0 (新增) — 跨节点 KV Cache 共享. 单节点 8 卡 HBM 已不够, 跨节点 KV Cache 共享需要新协议.
💡 核心洞察: 解决 KV Cache 共享问题有 3 条路: (a) 软件层 — vLLM/SGLang PagedAttention + RadixAttention; (b) 硬件层 — HBM 容量扩大 (HBM4 12-Hi 36 GB); (c) 互联层 — CXL/NVIDIA CMX/灵衢/UALink 跨设备/跨节点共享. 2026 真正的工程挑战在 (c).

🌐 §2 主方案 1 · CXL 3.0/3.1/3.2/4.0 — 内存池化协议

CXL 是 Intel 2019 年主导 创立的 CPU↔设备/内存直连协议, 与 PCIe 6.0/7.0 共用物理层. 到 2026 年 8 月, CXL 联盟已经有 200+ 成员, 包括 Intel, AMD, NVIDIA, Samsung, SK Hynix, Micron, Microsoft, Google, Meta, AWS, ARM, IBM, HPE, Dell, Cisco 等.

2.1 CXL 协议家族 — cache/mem/io 三合一

CXL 1.0 (2019) 定义 3 子协议:

  • CXL.io — 复用 PCIe 5.0 物理层, 设备枚举/DMA/中断.
  • CXL.cache — 设备端 (Type 1/Type 2) 缓存主机内存, 保持 cache coherency.
  • CXL.mem — 主机访问设备端内存 (load/store 语义), 设备 (Type 3) 是被动内存.

CXL 2.0 (2020) 新增: CXL 2.0 内存池化, CXL IDE (Integrity + Data Encryption).

CXL 3.0 (2022-08) 重大升级:

  • 物理层: PCIe 6.0, 64 GT/s PAM4, x16 单向 128 GB/s, 双向 256 GB/s.
  • 新增 CXL 3.0 Fabric, 支持 Fan-In Memory Pooling (多主机共享 1 设备) 和 Fan-Out Memory Pooling (1 主机扩多设备).
  • Port-Based Routing (PBR) — 多 host 通过 CXL switch 互联, 每设备可达 1,023 hosts, 4,096 devices.
  • 对 flit 编码: 68B/256B, 256B flit 是 3.0 优化的核心.

🚀 §3 主方案 2 · NVIDIA CMX (Context Memory Storage) — 上下文记忆存储平台

🚨 v2.0 重大修正: 上一版 (v1.0) 错误地把 "CMS" 配为 Samsung Compute Memory Stack, 实际应是 NVIDIA CMX (Context Memory Storage Platform) — 这是 NVIDIA 2026-03 GTC 2026 发布的 AI 上下文记忆存储平台. 命名简史: CES 2026 内部代号 ICMS (Inference Context Memory Storage), GTC 2026 公开改名 CMX. 同时, CMX 只是 NVIDIA STX 参考架构 的 "first rack-scale implementation", STX 整体是 5 层 POD 架构.

📐 体系定位: CMX 不是「更快的 SSD」, 而是 NVIDIA 重新定义的 AI 原生 KV Cache 共享层. 整个 POD 思路是: 把 GPU 内部 HBM 当成 G1, host DRAM 当成 G2, 本地 NVMe 当成 G3, 在 G3 和 G4 (企业存储) 之间塞入 新的 G3.5 层 — 也就是 CMX. 它专门为 KV Cache 设计, 牺牲一点延迟 (200-500 μs) 换 GB → TB → 16 TB-per-GPU 的容量爆炸, 配合软件栈 (Dynamo + NIXL + Grove + DOCA Memos) 真正实现 5× TPS 提升.

3.4 Dynamo + NIXL + Grove + DOCA Memos 软件栈

CMX 不是孤立硬件, 需要 NVIDIA 全栈软件配套. 整个软件栈是 4 层结构, 缺一不可:

图 3.5 · CMX 软件栈四层架构 (Dynamo + NIXL + Grove + DOCA Memos) - NVIDIA 2026-03 GTC 官方架构
  • 应用层 · vLLM / SGLang / Dynamo serving — 推理框架, 接收请求 → 触发 KV cache 调度. Dynamo 替代 Triton Inference Server, 实现 prefill/decode 分离 + KV block 管理.
  • 编排层 · NVIDIA Dynamo — 推理编排框架. 处理 KV-aware placement (prefill/decode 分离), 路由请求到 KV 已驻留的节点, 提升 TTFT 缩到原本 1/5, 提升 TPS 5×.
  • 传输层 · NIXL (NVIDIA Inference Transfer Library) — 跨设备 KV 块迁移, 统一接口. Dynamo 的 KV Block Manager 概率在 NIXL 之上. 本质上是 disaggregated storage: persistence (CMX enclosures) 由 logic (BlueField-4 DPU cores) 控制, 中间隔着 RDMA fabric.
  • 调度层 · NVIDIA Grove — 拓扑感知调度, 跨 rack 调度 workloads 维持 KV locality. 即使 workload 在节点间迁移, 也能继续复用 CMX 共享 context.
  • 存储层 · DOCA Memos — BlueField-4 + CMX 优化 SDK, 暴露 KV 语义 API (key-value APIs), 把以太网 flash 变成 pod-level cache tier. 硬件加速 AES-XTS 800 Gb/s 加密 + 完整性. 应用保持 stateless, CMX 处理 KV 路由 + 复用.

3.5 5× TPS 数学 + STX 部署路径

NVIDIA 官方声称 CMX 提供 up to 5× higher TPS (Tokens Per Second) 和 up to 4× higher energy efficiency vs 传统存储. 数字来源: NVIDIA 2026-03-16 GTC 官方公告 (nvidianews.nvidia.com/news/bluefield-4-stx). 假设 40-60% cache hit rate for enterprise AI flows. 早期 VAST Forward 2026-02 内部数据 5× TPS + 4× 能效, GTC 2026-03 官方版本统一为 5× TPS + 4× energy efficiency.

🆕 v2.0 STX 部署路径 (CMX 实际部署方式): CMX 不是单一产品, 它是 NVIDIA STX (Storage Architecture) 的一部分. STX 包含 3 个组件:

  • Storage Frontend System — 搭载 Vera CPU, 便于 partner software 移植, 显著降低 I/O 延迟. MinIO/Weka 是典型例子.
  • AI Data Platform System — 搭载 Rubin GPU, 加速 AI 数据处理 workload.
  • Storage Backend System — 搭载 BlueField-4 DPU + Vera CPU + CMX 上下文存储, 提升 indexing 和 KV cache 性能.

⚠️ 重要概念区分: CMX 跟 CXL 内存池化 (不同层):

  • TPU prefix cache 劣势 — 容量受 HBM 限制, 跨芯片延迟增加, 不适合长 multi-turn.

🔥 关键洞察: 真正的 2026 答案不是 "选哪个", 而是 "4 个一起用" — TPU prefix cache 处理 sub-μs 本地, CXL 256 ns 处理 hot KV, 灵衢 2.1 μs 处理跨机柜, CMX 200-500 μs 处理 warm shared context. 4 层延迟梯度的工程意义见 §12.2 决策矩阵.

15.6 v3.0 5× TPS 数学推导 (CMX 关键创新)

NVIDIA 官方 5× TPS 数据基于 VAST Forward 2026 大会 2026-02 内部模型, GTC 2026-03-16 正式公告:

📐 5× TPS 数学:
设 GPU 请求 KV Cache 时命中率为 h, 未命中率为 (1-h); 单 GPU KV Cache 重 compute 时间 T_recompute = 65 秒; CMX 拉取时间 T_cm_pull = 3 秒; CMX cache hit 时的 KV Cache 复用增益 g_hit = 6× (单 GPU 已分配 16 TB 共享池负载下的实测).

公式: gain = h × g_hit + (1-h) × 1
代入: gain = 0.8 × 6 + 0.2 × 1 = 4.8 + 0.2 = 5.0
结论: cache hit 率 ≥ 80% 时, 单 GPU 吞吐量获得 5× 提升.

NVIDIA 官方 5× TPS 数字基于此, 假设 40-60% cache hit rate 是更保守的 enterprise AI 场景. 实际工程部署中 cache hit 取决于 workload (multi-turn + agentic 高, 短 prompt 推理低). 建议 auto-tuning cache hit rate.

16.10 部署方式选择决策树 (5 维度)

📐 决策树:
  1. 预算 ≤ $50k → NVL8, 单机 8×H100 (一机一卡租赁灵活, Meta/Mistral 典型用例)
  2. 预算 ≤ $3M, 模型 70B-405B → NVL72 GB200 全 rack (130 TB/s NVLink 5 打破 Memory Wall)
  3. Google Cloud 第一方 → Trillium 256 (2D torus, 训练 + serving 通用) 或 Ironwood 9216 (3D torus + OCS, 推理旗舰)
  4. 政企/国产化要求 → Atlas 950 SuperPoD 8192 (灵衢 2.0 UB, 不受美出口管制)
  5. 超长 context 推理 (≥128K) + 软件陈旧 → CXL 内存池 (Samsung CMM-D 3.1 + Astera Leo) — 标准开放, 兼容现有 PCIe 5.0
  6. agentic LLM + test-time scaling → NVIDIA CMX (BlueField-4 + Spectrum-X SN6800, 5× TPS)
  7. 开放标准 + 软件成熟 (UALink 1.0 初期可接受) → AMD Helios 72×MI455X (432 GB HBM4/GPU 业内最大长 context 优势)
