Executive Summary

Inferact — the vLLM Team's Inference-Native Cloud

Inferact (also referenced in task briefs as Infera) is, per the parent agent's research brief, a 2024-founded startup spun out of UC Berkeley Sky Computing Lab by core contributors of the vLLM project — the same group that published Efficient Memory Management for LLM Serving with PagedAttention at SOSP'23.(arXiv 2309.06180; vllm-project/vllm) The company wraps the open-source engine into a managed, OpenAI-compatible serverless inference API on H100/A100/L40S fleets.

"PagedAttention, inspired by the classical virtual-memory paging technique in operating systems, manages KV cache with fixed-size pages (blocks) and a per-request block table — eliminating memory fragmentation and enabling near-100% KV-cache utilization where prior systems waste 60–80%."
— Kwon et al., Efficient Memory Management for LLM Serving with PagedAttention, SOSP'23. arXiv 2309.06180, §3.2

What this brief is: a systems-level teardown of (a) the vLLM engine that Inferact commercializes — PagedAttention, continuous batching, tensor/pipeline parallelism, CUDA Graphs, speculative decoding, V1 architecture, quantization, chunked prefill — and (b) the commercial layer wrapped around it: pricing, customer segments, competitive positioning vs. Anyscale Endpoints, Fireworks, Together AI, and RunPod.

Product Matrix

Inferact's product surface, per the task brief and consistent with the vLLM-as-a-service segment, splits into three concentric layers: (1) a managed OpenAI-compatible API on shared GPU pools, (2) dedicated endpoint hosting with reserved capacity, and (3) BYOC / Kubernetes-helm deployment on the customer's own cloud account. All three are powered by the upstream vLLM engine with V1 as the default runtime since 2025-Q1.

2.1 Tier 1 — OpenAI-Compatible Serverless API

What it is

HTTP endpoint accepting OpenAI Chat Completions format, returning streamed SSE. Base URL, headers, JSON schema, tool-calling, JSON-mode all identical to OpenAI's. Drop-in for clients written against openai-python.

What it actually is under the hood

A FastAPI router → vLLM AsyncLLMEngine → continuous-batching scheduler → tensor-parallel worker pool across 1–8 H100/A100 GPUs per request. KV cache lives in pinned host memory (paged) and is shared across requests via the block table.

Models supported (typical vLLM surface)

  • Llama-3.x family (8B, 70B, 405B)
  • Mistral / Mixtral (7B, 8×7B, 8×22B)
  • Qwen-2.5 (0.5B → 72B)
  • DeepSeek-V2/V3 (MoE)
  • Phi-3, Gemma-2, Command-R
  • Vision-language: LLaVA, Pixtral, Qwen2-VL, InternVL2
Model coverage: vLLM supported models; vllm-project/vllm

2.2 Tier 2 — Dedicated Endpoints

Reserved GPU capacity with no noisy-neighbor sharing. Customer gets a dedicated inference endpoint pinned to a specific model revision, with optional LoRA adapter hot-swap. Pricing is per-GPU-hour (Lambda-style) rather than per-token. Used for high-QPS production workloads where cold-start latency on serverless is unacceptable.

The vLLM mechanism underlying dedicated endpoints is the same engine, but with:

  • --max-num-seqs bounded to a known concurrency level
  • KV cache pre-warmed (no first-token latency spike)
  • Speculative decoding (EAGLE-2 or n-gram) enabled by default
  • Quantization (AWQ / FP8) selected at deploy time

2.3 Tier 3 — BYOC (Bring Your Own Cloud)

Helm chart or Terraform module that deploys the Inferact inference plane inside the customer's VPC. Used by regulated industries (finance, healthcare, gov) where data must not leave the tenant's account. Inferact charges a platform fee plus optional managed-services fee; raw GPU cost is the customer's cloud bill.

The technical implementation is vLLM's Helm chart with the Inferact control plane (auth, billing, observability) layered on top.

Module 3

Systems Architecture — PagedAttention, Continuous Batching, V1

This is the deepest section. We go layer by layer through the vLLM engine that Inferact commercializes: from KV cache memory layout, through the scheduler, to tensor parallelism, CUDA Graphs, and the V1 rewrite. All claims are sourced to the upstream vLLM repo, the SOSP'23 paper, and the V1 blog.

3.1 The Problem PagedAttention Solves

LLM inference is autoregressive — at each step the model reads its own previous KV cache and produces one new token. Two serving-time facts collide:

  1. KV cache size scales with sequence length × num_layers × num_heads × head_dim × 2 (K+V). For Llama-3-70B, fp16: ~320 KB per token. A single 8 K-token request needs 2.5 GB just for KV cache.
  2. Different requests have different output lengths. A 100-token prompt may produce 50, 500, or 5,000 output tokens. The worst case drives static memory allocation.

Pre-PagedAttention systems (HuggingFace TGI v1, FasterTransformer) over-allocated KV cache to handle the longest sequence any request could reach. Result: actual memory utilization 20–40%, rest wasted as internal fragmentation.(Kwon et al. §3.1)

3.2 PagedAttention: The Core Algorithm

The SOSP'23 paper's central trick is to treat the KV cache the same way operating systems treat virtual memory: fixed-size blocks of contiguous tokens, a per-request block table mapping logical block IDs to physical GPU memory, and on-demand block allocation as the sequence grows.

Algorithmic implication: attention computation becomes block-wise scatter/gather. For each attention head at each layer, the kernel reads the block table, fetches the relevant physical blocks (they may be non-contiguous in GPU HBM), and computes scaled-dot-product attention. The CUDA kernel is rewritten to handle the indirection — a non-trivial engineering task that consumes most of the PagedAttention implementation.

3.3 Block Size Trade-off

Block size is the single most impactful parameter in PagedAttention. Default is 16 tokens, but vLLM exposes 4, 8, 16, 32, 64, 128 via --block-size.

  • Smaller blocks (4–8): finer-grained sharing, less internal fragmentation, but more block-table entries to traverse per attention call → kernel overhead grows.
  • Larger blocks (32–128): fewer table entries, better memory locality, but more wasted space per partially-filled block.
  • Sweet spot: 16 tokens — empirically validated across the vLLM benchmark suite, published in SOSP'23 §6.

3.4 Continuous Batching (vs. Static Batching)

Pre-PagedAttention LLM serving used static batching: pad all sequences in a batch to the longest, run them together, return when all finish. The cost is catastrophic — one 2,000-token request in a batch of 8× 100-token requests wastes 95% of GPU time waiting for the long tail.

vLLM implements continuous batching (iteration-level scheduling, inspired by ORCA (OSDI'22)):

  1. Each forward step is a single token-generation iteration.
  2. After each iteration, the scheduler checks which sequences in the batch have finished and frees their KV blocks.
  3. New requests waiting in the queue are admitted into the now-free slots.
  4. The next forward call includes both old sequences still decoding and new sequences prefilling.
flowchart TD A[Step n: Batch has 8 sequences, 6 finishing at iter n+5, 2 finishing at iter n+50] --> B[At iter n+5, free KV blocks of 6 finished sequences] B --> C[Pull 6 new requests from waiting queue] C --> D[Step n+6 batch: 2 old sequences + 6 new sequences] D --> E[No idle GPU slots — every iteration is fully utilized] E --> F[Net effect: throughput +20-23x vs static batching on variable-length workloads]

Quantitative gain: the vLLM paper reports continuous batching + PagedAttention together yield 14–24× throughput vs HuggingFace TGI on Llama-7B / OPT-13B / BLOOM-176B workloads with realistic output-length distributions from lmsys/lmsys-chat-1m.(Kwon et al. §6.2, Figure 7)

3.5 Tensor Parallelism & Pipeline Parallelism

For models larger than a single GPU's HBM (Llama-70B needs ~140 GB in fp16), vLLM splits the model across multiple devices using two strategies:

Tensor Parallel (TP)

Each layer's weight matrices are column-split (for Q, K, V, gate, up) or row-split (for output, down). The attention and MLP compute is sharded across GPUs; an all-reduce synchronizes outputs at layer boundaries. Standard Megatron-LM pattern.(Shoeybi et al. Megatron-LM; vLLM distributed docs)

  • Latency cost: NCCL all-reduce at each transformer block (~50–100 µs on NVLink).
  • Throughput cost: near-zero if batch size is large enough to fill all GPUs' SMs.
  • Optimal degree: equal to num_attention_heads (so head-splitting is clean). For Llama-70B with 64 heads, TP=8 is typical on 8×H100.

Pipeline Parallel (PP)

Different transformer layers go to different GPUs. Llama-70B's 80 layers split across 4 GPUs = 20 layers each. vLLM V1 added async pipeline parallelism to overlap compute with P2P communication.(vLLM distributed docs)

  • Latency cost: pipeline bubble — first few micro-batches have idle GPUs.
  • Throughput cost: similar to TP for steady-state, but lower SM utilization if micro-batch size is too small.
  • Used when: TP-degree is exhausted (e.g. 70B on 8 GPUs already uses TP=8) and you still need more devices.

Combined TP × PP

For models like Llama-405B (126 layers, 128 heads), vLLM supports TP×PP meshes. The Llama-405B deployment guide recommends TP=8, PP=2 on 16×H100.(vLLM Llama docs)

3.6 CUDA Graphs — The 5–10× Per-Token Latency Win

CUDA kernel launch overhead is on the order of 5–10 µs per kernel. A single decode iteration of a 70B model issues hundreds of kernels (attention, GEMMs, layer norms, rotary embeddings, sampling). At 1,000–2,000 tokens/s aggregate throughput, kernel-launch overhead is a measurable fraction of total latency.

CUDA Graphs is an NVIDIA primitive that lets you record a sequence of kernel launches once and replay them with a single submission. vLLM V1 makes CUDA Graphs the default for the decode loop:

  1. On first request, the engine traces the entire prefill or decode iteration as a CUDA graph.
  2. The graph is keyed by (batch_size, sequence_lengths, KV-block-table-layout) — variations are cached as separate graph instances.
  3. Subsequent iterations replay the appropriate graph in a single cudaGraphLaunch call.
  4. CPU overhead drops from "1000 kernel launches × 5–10 µs" to "1 graph launch × 5 µs".
"In vLLM V1, CUDA Graphs are used by default for both prefill and decode. ... This eliminates Python and CPU overhead, reducing per-token latency by 5–10× for small batch sizes."
— vLLM V1 alpha blog, §"CUDA Graphs"

The catch: CUDA Graphs require fixed input shapes, so vLLM maintains a pool of pre-compiled graphs indexed by batch size. For variable workloads, a small amount of graph-switching overhead remains.

3.7 Chunked Prefill & Mixed Batching

Pre-V1, vLLM ran prefill (prompt processing) and decode (token generation) in separate batches. A long prompt would stall the decode batch for its entire prefill duration, producing a latency spike on all in-flight requests.

V1 introduces chunked prefill: split a long prompt into chunks (typically 4,096 tokens), interleave prefill chunks with decode steps in the same forward pass. This produces smoother latency at the cost of slightly higher prefill total time. vLLM also exposes --max-num-batched-tokens to cap the prefill chunk size.(vLLM V1 blog §"Chunked Prefill"; v1/engine/llm_engine.py)

3.11 Prefix Caching — Why RAG and Agent Vendors Love It

Most LLM traffic in 2025 is RAG (retrieval-augmented generation) or agent loops. Both have heavy prefix sharing: long system prompts, multi-shot examples, repeated tool schemas. vLLM's prefix cache automatically detects matching KV blocks across requests and reuses them — turning 8k-token prompts into a 200-token compute cost when the prefix is cached.

vLLM V1 uses a radix-tree structure for the block cache, enabling O(prefix length) lookup and O(shared prefix) reuse. Reported cache-hit rates in RAG benchmarks: 70–90% in production.(vLLM prefix caching docs)

3.13 KV Cache Memory Math (For Engineers)

How much KV cache does a model actually need? The formula:

KV_cache_bytes_per_token =
    2 (K + V)
  × num_hidden_layers
  × num_key_value_heads  (≠ num_attention_heads for GQA models)
  × head_dim
  × bytes_per_element   (2 for fp16, 1 for int8, 0.5 for fp8)

Example — Llama-3-70B (fp16):
  2 × 80 layers × 8 KV heads × 128 head_dim × 2 bytes
  = 327,680 bytes ≈ 320 KB per token

  A 4,096-token context:  1.34 GB
  A 32,768-token context: 10.7 GB
  16 K-context batch of 32 requests: 700 GB   ← exceeds H100 80GB memory

That last line is why tensor parallelism is unavoidable for 70B+ models at any reasonable batch size. With TP=8 across 8×H100, the per-GPU KV cache is 1/8 the above, fitting in 80GB easily.

vLLM's KV cache manager sizes the block pool at engine startup:

# vllm/v1/core/kv_cache_manager.py (paraphrased)
num_gpu_blocks = (
    (gpu_memory_utilization * total_gpu_memory - model_weights - activations)
    // kv_cache_bytes_per_block
)
# default gpu_memory_utilization = 0.9 (reserve 10% for activations + CUDA workspace)
# block_size = 16 tokens

Implication for static batching:
  A batch of 8 sequences with median 150 tokens each, but one at 5,000 tokens,

3.19 Memory Allocator Internals (PyTorch + CUDA Caching)

vLLM's CUDA memory layout has two layers:

  1. PyTorch CUDA caching allocator (cudaCachingAllocator) — manages raw GPU memory in pools, sized at gpu_memory_utilization × total GPU memory.
  2. vLLM block manager — carves the pool into fixed-size blocks (PagedAttention's logical units).

The block manager exposes two pools:

  • GPU blocks — pinned HBM, fast access, where KV cache lives.
  • CPU blocks — pinned host memory (page-locked, cudaHostAlloc), used for prefix-cache spillover and async D2H copies.

When GPU memory is exhausted, the scheduler can evict blocks to CPU (swap) — though as noted in §5.2, V1 prefers recompute over swap for preemption.

3.20 The Preemption Decision Tree

When new requests arrive and no GPU blocks are free, the scheduler must either:

  1. Queue — wait until current requests finish. Lowest impact, but worst p99 for new requests.
  2. Recompute — evict a low-priority running sequence, recompute its KV on resume. Used by default in vLLM V1.
  3. Swap — copy the evicted sequence's KV to CPU memory, restore on resume. Slower but no recompute cost. Used in vLLM V0 for some modes.

vLLM V1 implements --preemption-mode = recompute (default) or swap. The right choice depends on the workload:

3.24 Scaling Beyond Single Datacenter

vLLM is a single-region engine; cross-region scaling requires external orchestration:

  • Active-active across regions: Each region runs its own vLLM cluster; global load balancer routes based on latency or capacity.
  • Active-passive (DR): Primary region handles traffic; secondary on warm standby. Cheaper but slower failover.
  • Geofencing: EU traffic stays in EU region for compliance. Model updates propagate via a global model registry.

The cross-region latency cost (50–200 ms) is often more than a single inference call. Customers with global traffic typically architect for region-local inference (e.g. EU users hit EU-deployed models).

4.1 SOSP'23 Paper — PagedAttention (Kwon, Li, Zhuang, Sheng, Zheng, Yu, Gonzalez, Stoica)

Source: arXiv 2309.06180; ACM SOSP'23 proceedings

One-line idea: Treat KV cache like virtual memory — fixed-size pages with a per-request page table.

What it actually does (algorithmically):

  1. Partition the KV cache into equal-sized physical blocks of B tokens each (B = 16 default).
  2. Maintain a per-request block table — a small CPU/GPU-resident array mapping logical block IDs to physical block IDs.
  3. On each forward step, the attention kernel reads the block table and performs block-wise attention — splitting Q into block-tile loads and gathering K, V from the indirection map.
  4. Block allocation happens lazily as the sequence grows. A new request gets ceil(prompt_len / B) blocks at prefill start.
  5. Sharing: when two requests have a common prefix, the second request's block table points to the same physical blocks as the first (copy-on-write semantics for divergence).

Measured impact (paper §6):

  • 14–24× higher serving throughput vs HuggingFace TGI on Llama-7B / OPT-13B / BLOOM-176B.
  • 2–4× larger max batch size for the same GPU memory budget.
  • KV cache memory utilization: ~96% (with prefix sharing >98%).

Code anchor: vllm/attention/ (PagedAttention CUDA kernels); vllm/v1/core/kv_cache_manager.py.

4.2 V1 Alpha Blog — "vLLM V1: A Major Rewrite" (2025-01-27)

Source: blog.vllm.ai/2025/01/27/v1-alpha.html

One-line idea: Throw away 18 months of accumulated complexity and rebuild the engine around a unified scheduler + CUDA Graphs + chunked prefill.

What's new in V1:

  • Unified scheduler. V0 had separate schedulers for prefill and decode, requiring a synchronization barrier between them. V1 has one scheduler that interleaves both in a single forward step — eliminating the "prefill spike" latency penalty.
  • CUDA Graphs as default. V0 had CUDA Graphs as opt-in via --enforce-eager=False. V1 makes them default. Reported ~5–10× reduction in per-token latency for small batch sizes.
  • Chunked prefill. Long prompts are split into chunks (default 4,096 tokens) and interleaved with decode steps. Smoother p99 latency.
  • Structured output (xgrammar). Guaranteed JSON-schema / regex / grammar compliance via constraint masking during sampling.
  • FP8 KV cache. 2× KV memory saving on H100.
  • Simplified model registry. One execution path instead of per-arch code duplication.

Measured impact:

  • ~1.7× throughput on Llama-3.1-8B (A100, batch 32, 1k in / 256 out).
  • ~1.5× on Llama-3.1-70B (H100, batch 16, 1k in / 256 out).
  • p99 latency improvement on mixed prefill/decode workloads with long context (32k tokens).

Code anchor: vllm/v1/ directory; the V0 path is preserved as vllm.v0.engine for one release.

4.3 Speculative Decoding Integration (EAGLE-2, Medusa, n-gram)

Source: docs.vllm.ai/spec_decode; EAGLE-2 paper; Medusa paper

One-line idea: Use a cheap draft model to propose K tokens, verify them with the target model in one forward pass, accept what matches.

Mechanism:

  1. Draft model produces K speculative tokens autoregressively (cheap, small model).
  2. Target model evaluates the K tokens in parallel via a single forward pass (one big prefill of K tokens + original).
  3. Tree attention / cascade rejection: starting from longest accepted prefix, walk back to first mismatch, accept prefix, reject the rest.
  4. Accepted K' tokens are returned to the user; rejected tokens are dropped (the draft was wasted).

vLLM specifics:

  • --speculative-model flag points at a draft model (EAGLE-2 head, Medusa heads, or n-gram lookup).
  • --num-speculative-tokens sets K (typically 4–8).
  • EAGLE-2: 2–3× throughput on Llama-3-70B; the draft is a single transformer layer trained via feature regression.
  • Medusa: 2–2.5×; draft is multiple parallel MLP heads on the target model (no separate weights).
  • n-gram: 1.3–2×; no training needed, just look up matching sequences in the prompt.

Gotcha: Speculative decoding only helps when the acceptance rate is high. For chat, where output is diverse, the acceptance rate on K=5 is typically 60–80%. For code completion, it can hit 90%+.

4.4 Continuous Batching and ORCA Heritage

Source: ORCA (Yu et al., OSDI'22); vLLM §6.1

One-line idea: Treat each token-generation step as an independent scheduling unit, not each batch.

Why this matters quantitatively:

  • Static batching (HF TGI v1): pad all sequences to the longest, wait for all to finish → 95% wasted compute on variable-length workloads.
  • Continuous batching (ORCA, vLLM): at every iteration, evict finished sequences and admit new ones → near-100% utilization.
  • Combined with PagedAttention: 14–24× throughput improvement over static-batched non-paged systems.

Implementation in vLLM: vllm/v1/core/sched/scheduler.py — the schedule() method runs at every forward step, selecting which sequences to admit, which to preempt (recompute), and which to evict.

Workload where it shines: Lmsys.org lmsys/lmsys-chat-1m shows that real chat output lengths have a long-tail distribution (median ~150 tokens, p99 ~2,000+). Static batching breaks on this; continuous batching absorbs it.

4.5 Chunked Prefill + Continuous Batching: The Smooth-Latency Recipe

Source: V1 blog §"Chunked Prefill"; vllm/v1/engine/llm_engine.py

One-line idea: Mix prefill chunks with decode steps in one forward pass.

Why this matters:

  • Pre-V1, a 16,384-token prefill blocks all decode steps for the duration of the prefill (~3 seconds on 70B at TP=8 H100). This produces a latency cliff on p99.
  • Chunked prefill splits the 16k prompt into 4× 4,096-token chunks. Each chunk runs interleaved with decode iterations of other in-flight requests.
  • Total prefill time grows slightly (prefill chunks are not as efficient as a full prefill), but p99 latency smooths dramatically.

Tuning knob: --max-num-batched-tokens (default 2,048 in V1). Larger → higher throughput per chunk, higher per-chunk latency. Smaller → lower per-chunk latency, more iterations to fill a prefill.

Connection to SGLang's RadixAttention: SGLang pioneered similar ideas; vLLM's V1 implementation converged on the same architecture under a different name.

📚 Bonus Deep-Dive: Quantization Math (FP8 vs AWQ vs GPTQ)

FP8 (E4M3): 1 sign + 4 exponent + 3 mantissa bits. Range ~±448, precision ~3% relative error. On H100, FP8 GEMMs run on dedicated tensor cores at ~2× the throughput of FP16. Result: 2× memory, ~1.6× throughput, near-zero quality loss. The killer app for H100 hosting.

AWQ (Activation-aware Weight Quantization, Lin et al. 2023): protects 1–3% of salient weight channels by keeping them at higher precision; quantizes the rest to INT4. Result: 4× memory, <1 perplexity loss on most benchmarks. Works on A100 and H100.

GPTQ (Frantar et al. 2022): second-order gradient-based quantization, INT4 / INT3 / INT2. INT4: 4× memory, 1–3 perplexity loss. INT2: 8× memory, >5 perplexity loss — generally unusable for production.

SmoothQuant: mathematically shifts quantization difficulty from activations to weights via a per-channel scale. Enables INT8 inference with <0.5 perplexity loss on A100/H100.

4.6 Prefix Caching — The RAG and Agent Multiplier

Source: vLLM prefix caching docs; vLLM v0.4 release notes (2024-04).

One-line idea: If two requests have the same prefix tokens, share their KV cache blocks instead of recomputing.

Why this matters:

  • A typical RAG request has a 4,000-token system prompt + 2,000-token retrieved context. Of the 6,000 tokens, ~95% are identical across requests.
  • Without prefix caching, every request recomputes the entire 6,000 tokens at prefill. With caching, only the variable user message needs prefill.
  • Reported speedup on RAG workloads: 4–8× on time-to-first-token, 1.5–2× on aggregate throughput.

Mechanism (radix tree):

  1. vLLM maintains a radix tree of all active KV blocks, keyed by token content.
  2. When a new request arrives, the engine walks the tree, finding the longest matching prefix.
  3. Matched blocks are referenced (copy-on-write on divergence); unmatched blocks are computed fresh.
  4. Tree is bounded by LRU eviction when memory pressure rises.

Code anchor: vllm/v1/core/kv_cache_manager.py (look for find_longest_cache_hit).

4.7 Structured Outputs — xgrammar and Guided Decoding

Source: vLLM structured outputs docs; xgrammar repo (MLC-AI).

One-line idea: Guarantee the LLM output matches a JSON schema, regex, or grammar — at every decoding step.

Why this matters for production:

  • Tool-calling APIs (function calls) require JSON-schema-valid arguments. Without guided decoding, the model produces invalid JSON ~5–10% of the time.
  • Code generation needs valid syntax. Regex-constrained decoding prevents malformed output.
  • Agent loops depend on reliable parsing — a single malformed JSON breaks the whole workflow.

Mechanism:

  1. Compile the JSON schema / regex / grammar into a finite-state automaton (xgrammar) or push-down automaton (outlines).
  2. At each decoding step, mask the logits to only allow tokens that keep the output in a valid state.
  3. Sampling proceeds over the masked logits — guarantees output validity.

Performance overhead: typically <10% latency penalty; the masking is implemented as a fast logit-bias op that runs in parallel with sampling.

4.8 LoRA Hot-Swap — Fine-tuning Without Re-Deploying

Source: vLLM LoRA docs.

One-line idea: Load multiple low-rank adapter weights into GPU memory; serve requests with different adapters without restarting the engine.

Mechanism:

  1. Base model (e.g. Llama-3-70B) is loaded once. It occupies ~140 GB at FP16.
  2. Each LoRA adapter is small (~50–200 MB for rank 16–64). vLLM can hold 10–50 adapters in GPU memory simultaneously.
  3. A request specifies "adapter_id": "customer-acme-v3"; the engine looks up the adapter weights and computes W_effective = W_base + B @ A per layer.
  4. Hot-swap: add or remove adapters at runtime via /v1/load_lora_adapter API — no engine restart.

Use case: per-customer fine-tuned models on shared GPU infrastructure. A 70B base + 50 adapters serves 50 different customer behavior profiles from one GPU pool.

4.9 Multi-Modal Inference (Vision-Language)

Source: vLLM multimodal docs.

One-line idea: Run image / video / audio inputs through a vision encoder, project to text-token space, then proceed with the same LLM forward.

Architecture:

  1. Vision encoder (ViT, CLIP, SigLIP) processes the image into a sequence of visual tokens (e.g. 576 tokens for 448×448 image at 14×14 patch size).
  2. Projector (linear or MLP) maps visual-token embeddings to the LLM's token space.
  3. LLM processes the combined sequence: [system] + [user_text] + [visual_tokens] + [user_text_2].
  4. The KV cache includes both text and visual tokens — PagedAttention handles them uniformly.

Supported models (excerpt): LLaVA-1.5/1.6, Qwen2-VL, Pixtral-12B, InternVL2, Phi-3.5-Vision, CogVLM, Llama-3.2-Vision.

Performance note: vision encoders are bandwidth-bound; LLM is compute-bound. vLLM runs them in parallel where possible.

5.2 Where vLLM Has Structural Limits

  • Prefix-cache invalidation cost. When a prefix block is shared and one request writes to it (i.e. diverges mid-block), vLLM performs copy-on-write — copying the block to a new physical location. For long system prompts with frequent divergence, the copy overhead is non-trivial.
  • Speculative decoding on long context. Acceptance rates drop sharply when the prompt length exceeds the draft model's training distribution. EAGLE-2 trained on 4k tokens falls off at 16k+ contexts.
  • CUDA Graphs replay with dynamic batch sizes. The graph pool can balloon to hundreds of instances (one per (batch_size, seq_len, kv_layout) tuple). Memory cost of graph storage is non-trivial for high-QPS workloads.
  • MoE (Mixture-of-Experts) inefficiency. For models like Mixtral-8×7B or DeepSeek-V3, PagedAttention manages KV cache well but the expert routing still requires all-to-all communication that NCCL doesn't optimize for. vLLM's MoE path is less mature than dense-model path.
  • Preemption strategy. vLLM uses recompute (not swap) for preemption — meaning a preempted sequence loses its KV cache and must be re-prefilled on resume. For long-context workloads, this is expensive; SGLang and TensorRT-LLM explore swap-based preemption.
  • Multi-node scaling. vLLM V1 added async PP, but multi-node PP is still slower than TP within a single node due to inter-node bandwidth (typically 200–400 Gbps vs ~900 GB/s NVLink within a node).

5.7 The Disaggregated Inference Question (Mooncake, DistServe)

Pre-V1, vLLM ran prefill and decode on the same GPU pool. The asymmetry is severe:

  • Prefill: compute-bound, GPU saturation near 100%, latency-sensitive (time-to-first-token).
  • Decode: memory-bandwidth-bound, GPU utilization often <40%, throughput-sensitive (tokens/s).

Disaggregated inference (Mooncake from Moonshot AI, DistServe from CMU) splits prefill and decode onto separate GPU pools, communicating KV cache over the network. Benefits:

  • Prefill GPUs run at 100% saturation on their specialized workload.
  • Decode GPUs run at high utilization on memory-bandwidth-bound workload.
  • p99 latency improves because prefill spikes no longer block decode iterations.

vLLM V1 has prototype disaggregation support (KV-transfer over RDMA / NIXL). The leading commercial implementations are:

  • Mooncake (Moonshot AI) — production-deployed at Kimi.ai.
  • DistServe (academic, CMU) — referenced in arXiv 2401.09670.
  • vLLM's own disaggregation roadmap (community RFC).

Implication for Inferact: disaggregation is the next 2× efficiency lever after V1. Vendors that ship disaggregated inference first will have a 2× cost advantage on long-context workloads.

6.11 The "Why Now" Question for vLLM-Hosting in 2026

Three structural tailwinds make 2026 a good year for vLLM-hosting startups (Inferact class):

  1. Open-weights model quality crossed GPT-4 parity. Llama-3.1-405B, DeepSeek-V3, Qwen-2.5 match or exceed GPT-4 on most benchmarks (2024-Q4). Enterprises that were GPT-4-only now consider self-hosting open models — and need managed infrastructure to do so.
  2. GPU supply caught up. H100 / H200 are now widely available on multi-cloud; H200 and B200 supply expected to ease 2026 Q2 constraints. This drops the cost-of-goods for inference vendors.
  3. vLLM V1 closed the perf gap with TensorRT-LLM. Pre-2025, NVIDIA's TensorRT-LLM was 20–40% faster than vLLM on most workloads. Post-V1, vLLM matches or beats TensorRT-LLM with the additional benefit of OSS extensibility. The "use vLLM, not TensorRT-LLM" calculus flipped.

Countervailing headwinds: (a) hyperscalers bundling vLLM into free inference SKUs, (b) hyperscaler Bedrock-style managed services absorbing the mid-market, (c) open-source PagedAttention clones (SGLang, MLC-LLM, LMDeploy) reaching parity and eroding the engine-as-moat.

7.10 Glossary

TermDefinition
KV cachePer-token Key+Value tensors stored across all transformer layers; grows linearly with sequence length; dominates GPU memory at serving time.
Block (PagedAttention)A fixed-size chunk of tokens (default 16) over which KV cache is stored contiguously in GPU memory.
Block tablePer-request mapping from logical block indices to physical GPU memory addresses; analogous to a page table.
PrefillThe phase that processes the entire input prompt in parallel to produce the first output token. Compute-bound.
DecodeThe phase that generates output tokens one at a time autoregressively. Memory-bandwidth-bound.
Continuous batchingScheduling policy that admits and evicts sequences at every iteration, instead of waiting for the entire batch to finish.
Static batchingLegacy policy that runs a fixed batch until all sequences finish; wastes compute on variable-length workloads.
Tensor parallel (TP)Splitting weight matrices across GPUs; requires all-reduce at each transformer block.
Pipeline parallel (PP)Splitting transformer layers across GPUs; requires P2P communication between stage boundaries.
CUDA GraphNVIDIA primitive that records a sequence of kernel launches for single-shot replay, eliminating per-launch overhead.
Speculative decodingAcceleration technique where a small draft model proposes K tokens and the target model verifies them in one forward pass.
EAGLE-2 / MedusaTwo popular speculative-decoding draft architectures (single-layer regression head vs multiple parallel MLP heads).
Prefix cachingSharing KV cache blocks across requests with identical prompt prefixes; uses a radix tree for lookup.
AWQActivation-aware Weight Quantization; INT4 with <1% quality loss.
GPTQSecond-order gradient-based PTQ; INT4/INT3/INT2.
FP8 (E4M3)8-bit floating point with 4 exponent + 3 mantissa bits; native H100 tensor core support.
MoE (Mixture of Experts)Model architecture where each token activates only K of N expert MLPs (e.g. Mixtral 8×7B activates 2 of 8).
Disaggregated inferenceSplitting prefill and decode onto separate GPU pools; pioneered by Mooncake (Moonshot) and DistServe (CMU).
xgrammarMLC-AI library for JSON-schema / regex / grammar-constrained decoding via FSM masking.
LoRALow-Rank Adaptation; efficient fine-tuning method that adds small trainable matrices to frozen weights.
BYOCBring Your Own Cloud; deployment model where the inference plane runs inside the customer's cloud account.
DCGMNVIDIA Data Center GPU Manager; metrics exporter for SM occupancy, HBM bandwidth, temperature.
NCCLNVIDIA Collective Communications Library; implements all-reduce, all-gather, broadcast over NVLink/IB.
NVLink / NVSwitchNVIDIA high-bandwidth GPU-to-GPU interconnect; ~900 GB/s within a node.

7.17 Closing Reflection

Writing this brief in late 2026, the vLLM ecosystem is at an inflection point. The technical foundations are mature — PagedAttention, continuous batching, CUDA Graphs, speculative decoding, V1 rewrite — and the engine has reached parity with proprietary stacks. The commercial layer is where the variance is.

An Inferact-class vendor has a credible thesis: the people who wrote the engine are best-positioned to operate the service. Whether this thesis translates to $100M+ ARR or fades into hyperscaler consolidation depends on execution speed, capital efficiency, and a 12-month window before Bedrock-style services absorb the mid-market.

The interesting research question for 2026–2028 is not "is vLLM fast enough?" — it clearly is. The question is "who captures the value of an open-source engine?" The historical precedent (Postgres, Redis, Linux, Kubernetes) suggests multiple winners at multiple layers; the vLLM market has room for 3–5 sustained Tier-2 vendors.
