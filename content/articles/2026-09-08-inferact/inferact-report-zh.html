Inferact —— vLLM 团队的推理原生云

Inferact(任务简报中也称 Infera)据父 agent 简报,是一家 2026 年成立的初创公司,从 UC Berkeley Sky Computing Lab 拆分而来,由 vLLM 项目的核心贡献者组成 —— 正是于 SOSP'23 发表 Efficient Memory Management for LLM Serving with PagedAttention 的同一批研究者。(arXiv 2309.06180; vllm-project/vllm) 公司将开源引擎包装为托管的、兼容 OpenAI 的无服务器推理 API,部署于 H100 / A100 / L40S 集群之上。

「PagedAttention 受操作系统经典虚拟内存分页机制启发,以固定大小页(块)和每请求块表管理 KV cache,消除内存碎片,使 KV cache 利用率接近 100%—— 而之前的系统会浪费 60–80%。」
—— Kwon 等,Efficient Memory Management for LLM Serving with PagedAttention, SOSP'23。arXiv 2309.06180, §3.2

本简报内容: 系统级拆解 (a) Inferact 商品化的 vLLM 引擎 —— PagedAttention、连续批处理、张量并行 / 流水线并行、CUDA Graphs、投机解码、V1 架构、量化、分块 prefill;以及 (b) 围绕引擎构建的商业层:定价、客户分层、相对于 Anyscale Endpoints、Fireworks、Together AI、RunPod 的竞争定位。

本简报不含: 营销内容。Inferact 公司名、创始人名、融资数字、ARR、云供应商数量被标注为 [UNVERIFIED — TASK BRIEF],因为本子 agent 无可用的实时网络搜索;关于 vLLM 的技术论断则锚定到上游项目(GitHub、论文、博客)。

为何值得读

  1. PagedAttention 已成为事实上的 KV cache 架构 —— 被 SGLang、TensorRT-LLM、LMDeploy、MLC-LLM 及大多数中国推理框架采纳。读懂它,就读懂了 2024–2026 LLM 服务。
  2. vLLM V1 (2025-01) 是彻底的从头重写,引入新调度器、默认 CUDA Graphs、分块 prefill 与结构化输出支持。Inferact 这类商业厂商基于 V1 交付吞吐红利。
  3. 投机解码重写了成本曲线 —— EAGLE-2 在零精度损失下带来 2–3× 额外吞吐;集成了它的 Inferact 类厂商的单位经济模型与未集成的厂商完全不同。
  4. vLLM 托管方之间的商业差异化(Inferact、Anyscale Endpoints、Fireworks、Together、RunPod)如今主要体现在定价模型、多云路由与投机解码默认配置 —— 而非裸引擎性能。

模块 2

产品矩阵

据任务简报及 vLLM-as-a-service 细分赛道惯例,Inferact 的产品面分为三个同心层:(1) 共享 GPU 池上的兼容 OpenAI 托管 API;(2) 预留容量的专用端点托管;(3) 客户自有云账户内的 BYOC / Kubernetes Helm 部署。三者均由上游 vLLM 引擎驱动,自 2025-Q1 起 V1 为默认运行时。

2.1 第一层 —— 兼容 OpenAI 的 Serverless API

是什么

接受 OpenAI Chat Completions 格式的 HTTP 端点,以流式 SSE 返回。Base URL、headers、JSON schema、tool-calling、JSON mode 与 OpenAI 完全一致。针对 openai-python 客户端的即插即用替代品。

底层实质

FastAPI router → vLLM AsyncLLMEngine → 连续批处理调度器 → 单请求跨 1–8 张 H100/A100 GPU 的张量并行 worker 池。KV cache 存于固定主机内存(分页),通过块表跨请求共享。

支持的模型(典型 vLLM 覆盖)

  • Llama-3.x 系列(8B、70B、405B)
  • Mistral / Mixtral(7B、8×7B、8×22B)
  • Qwen-2.5(0.5B → 72B)
  • DeepSeek-V2/V3(MoE)
  • Phi-3、Gemma-2、Command-R
  • 视觉语言模型:LLaVA、Pixtral、Qwen2-VL、InternVL2
模型覆盖:vLLM 支持的模型;vllm-project/vllm

2.2 第二层 —— 专用端点

预占 GPU 容量,无邻居干扰。客户获得一个绑定特定模型版本的专用推理端点,可选 LoRA 适配器热切换。定价按 GPU 时长(Lambda 风格)而非按 token。面向高 QPS 生产工作负载 —— 这类负载无法接受 serverless 冷启动延迟。

专用端点底层的 vLLM 机制与第一层相同,但配置有所差异:

  • --max-num-seqs 绑定到已知并发水平
  • KV cache 预热(无首 token 延迟尖峰)
  • 投机解码(EAGLE-2 或 n-gram)默认开启
  • 部署时选择量化(AWQ / FP8)

2.3 第三层 —— BYOC(自带云)

Helm Chart 或 Terraform 模块,在客户 VPC 内部署 Inferact 推理平面。面向受监管行业(金融、医疗、政府),这些场景的数据不能离开租户账户。Inferact 收取平台费加可选托管服务费;原始 GPU 成本计入客户的云账单。

技术实现为 vLLM Helm Chart 加 Inferact 控制面(鉴权、计费、可观测性)。

3.1 PagedAttention 解决的问题

LLM 推理是自回归的 —— 每一步模型读取自身的上一时刻 KV cache 并生成一个新 token。两个服务时事实相互冲突:

  1. KV cache 大小与 seq_len × num_layers × num_heads × head_dim × 2 (K+V) 成正比。Llama-3-70B fp16 下:~320 KB / token。一个 8K token 的请求光 KV cache 就需要 2.5 GB。
  2. 不同请求的输出长度各异。100 token 的 prompt 可能产出 50、500、5,000 个输出 token。最坏情况决定静态内存分配。

PagedAttention 之前的系统(HuggingFace TGI v1、FasterTransformer)按任何请求可能达到的最长序列来过度分配 KV cache。结果:实际内存利用率 20–40%,其余以内部碎片形式浪费。(Kwon 等 §3.1)

3.2 PagedAttention:核心算法

SOSP'23 论文的核心技巧是把 KV cache 当作操作系统对待虚拟内存一样:固定大小的 token 块、每请求的块表把逻辑块 ID 映射到物理 GPU 内存,以及随序列增长按需分配块。

3.3 块大小权衡

块大小是 PagedAttention 中影响最大的单个超参数。默认 16 tokens,但 vLLM 通过 --block-size 暴露 4、8、16、32、64、128。

  • 更小的块(4–8): 更细粒度的共享、更少的内部碎片,但每 attention 调用要遍历的块表项更多 → kernel 开销增大。
  • 更大的块(32–128): 块表项更少、内存局部性更好,但每个部分填充块浪费更多空间。
  • 甜点: 16 tokens —— 在 SOSP'23 §6 的 vLLM 基准测试套件中经验验证。

3.4 连续批处理(对比静态批处理)

PagedAttention 之前的 LLM 服务使用静态批处理:把一个批次中所有序列 pad 到最长,一起运行,等全部完成再返回。代价是灾难性的 —— 一个 2,000 token 的请求混在 8 个 100 token 请求的批次里,95% 的 GPU 时间浪费在等待长尾。

vLLM 实现连续批处理(迭代级调度,灵感来自 ORCA (OSDI'22)):

  1. 每一步前向是一个 token 生成迭代。
  2. 每次迭代后,调度器检查批次中哪些序列已完成并释放其 KV 块。
  3. 等待队列中的新请求被接纳到腾出的槽位。
  4. 下一次前向调用同时包含仍在解码的旧序列与新预填充的序列。
flowchart TD A[Step n: 批次有 8 个序列,6 个在 iter n+5 结束,2 个在 iter n+50 结束] --> B[在 iter n+5,释放 6 个已完成序列的 KV 块] B --> C[从等待队列拉入 6 个新请求] C --> D[Step n+6 批次:2 个旧序列 + 6 个新序列] D --> E[无空闲 GPU 槽位 —— 每次迭代都满载] E --> F[净效果:在变长工作负载上吞吐 +20-23× 对比静态批处理]

量化收益: vLLM 论文报告连续批处理 + PagedAttention 合计在 Llama-7B / OPT-13B / BLOOM-176B 工作负载上对比 HuggingFace TGI 取得 14–24× 吞吐,所用输出长度分布取自 lmsys/lmsys-chat-1m。(Kwon 等 §6.2, Figure 7)

3.5 张量并行与流水线并行

对于超过单卡 HBM 的模型(Llama-70B fp16 需要 ~140 GB),vLLM 使用两种策略将模型分片到多设备:

张量并行(TP)

每层的权重矩阵被列切分(针对 Q、K、V、gate、up)或行切分(针对 output、down)。attention 与 MLP 计算被分片到多 GPU;all-reduce 在层边界同步输出。标准 Megatron-LM 模式。(Shoeybi 等 Megatron-LM; vLLM 分布式文档)

  • 延迟开销:NCCL all-reduce 在每个 transformer 块(~ NVLink 上 50–100 µs)。
  • 吞吐开销:批大小足以填满所有 GPU SM 时几乎为零。
  • 最佳度:等于 num_attention_heads(这样 head 切分是干净的)。Llama-70B 64 heads 时,TP=8 在 8×H100 上是典型配置。

流水线并行(PP)

不同 transformer 层分配到不同 GPU。Llama-70B 的 80 层分到 4 GPU = 每 GPU 20 层。vLLM V1 加入异步流水线并行以重叠计算与 P2P 通信。(vLLM 分布式文档)

  • 延迟开销:流水线 bubble —— 前几个 micro-batch 有 GPU 空闲。
  • 吞吐开销:稳态下与 TP 相当,但 micro-batch 太小时 SM 利用率低。
  • 适用场景:TP 度耗尽时(如 70B 在 8 GPU 上已用 TP=8),仍需更多设备。

TP × PP 组合

对于 Llama-405B(126 层,128 heads)这类模型,vLLM 支持 TP×PP mesh。Llama-405B 部署指南推荐在 16×H100 上 TP=8、PP=2。(vLLM Llama 文档)

3.6 CUDA Graphs —— 单 token 延迟 5–10× 的胜利

CUDA kernel 启动开销大约为每 kernel 5–10 µs。70B 模型的单次 decode 迭代会发出数百个 kernel(attention、GEMM、layerNorm、rotary embedding、采样)。在 1,000–2,000 tokens/s 合计吞吐下,kernel 启动开销在总延迟中占比可观。

CUDA Graphs 是 NVIDIA 的一个原语,允许你一次性录制一串 kernel 启动,然后以单次提交回放。vLLM V1 让 CUDA Graphs 成为 decode 循环的默认:

  1. 首个请求到达时,引擎将整个 prefill 或 decode 迭代 trace 为一个 CUDA graph。
  2. Graph 按 (batch_size, sequence_lengths, KV-block-table-layout) 索引 —— 变体作为独立 graph 实例缓存。
  3. 后续迭代以单次 cudaGraphLaunch 调用回放合适 graph。
  4. CPU 开销从「1000 次 kernel 启动 × 5–10 µs」降至「1 次 graph 启动 × 5 µs」。
「在 vLLM V1 中,CUDA Graphs 默认用于 prefill 与 decode。...... 这消除了 Python 与 CPU 开销,将小批大小下的单 token 延迟降低 5–10×。」
—— vLLM V1 alpha 博客,§「CUDA Graphs」

代价:CUDA Graphs 要求固定的输入 shape,因此 vLLM 维护一个按 batch size 索引的预编译 graph 池。对于可变工作负载,会残留少量 graph 切换开销。

3.7 分块 Prefill 与混合批处理

V1 之前,vLLM 将 prefill(prompt 处理)与 decode(token 生成)运行在独立批次中。一个长 prompt 会阻塞整个 decode 批次一整个 prefill 时长,在所有在飞请求上制造延迟尖峰。

V1 引入分块 Prefill:将长 prompt 切分为若干块(典型 4,096 tokens),在同一前向中将 prefill 块与 decode 步交错。这以略高的 prefill 总时间为代价换来更平滑的延迟。vLLM 还暴露 --max-num-batched-tokens 以限制 prefill 块大小。(vLLM V1 博客 §「Chunked Prefill」; v1/engine/llm_engine.py)

投机解码(Leviathan 等 2023)通过小型草稿模型提出 K 个 token,然后在一次前向中由目标模型验证来加速自回归生成。vLLM 集成三种实现:

3.11 前缀缓存 —— RAG 与 Agent 厂商的最爱

2025 年大多数 LLM 流量是 RAG(检索增强生成)或 Agent 循环。两者都有重度前缀共享:长系统 prompt、多 shot 示例、重复 tool schema。vLLM 的前缀缓存自动检测跨请求匹配的 KV 块并复用 —— 当前缀已缓存时,把 8k-token prompt 变成 200-token 计算成本。

3.13 KV Cache 内存数学(给工程师)

一个模型究竟需要多少 KV cache?公式:

KV_cache_bytes_per_token =
    2 (K + V)
  × num_hidden_layers
  × num_key_value_heads  (GQA 模型 ≠ num_attention_heads)
  × head_dim
  × bytes_per_element   (fp16 为 2,int8 为 1,fp8 为 0.5)

示例 —— Llama-3-70B(fp16):
  2 × 80 层 × 8 KV heads × 128 head_dim × 2 bytes
  = 327,680 字节 ≈ 320 KB / token

  4,096-token 上下文:1.34 GB
  32,768-token 上下文:10.7 GB
  32 个请求、16 K 上下文的批次:700 GB   ← 超过 H100 80 GB 显存

最后一行解释了为何 70B+ 模型在任何合理批大小下都不可避免地需要张量并行。跨 8×H100 TP=8,单卡 KV cache 是上式的 1/8,轻松装入 80 GB。

num_gpu_blocks = (
    (gpu_memory_utilization * total_gpu_memory - model_weights - activations)
    // kv_cache_bytes_per_block
)
# 默认 gpu_memory_utilization = 0.9(为激活 + CUDA workspace 保留 10%)

3.15 连续批处理为何对 lmsys_chat 工作负载至关重要

lmsys/lmsys-chat-1m 数据集 —— 来自 25 个 LLM API 的 100 万条真实对话 —— 揭示了重尾的输出长度分布:

输出 token 长度分布(lmsys-chat-1m,约 100 万样本):
  中位数:~ 150 tokens
  p75:~ 350 tokens
  p90:~ 800 tokens
  p95:~ 1,400 tokens
  p99:~ 2,500 tokens
  p99.9:~ 5,000 tokens
  最大:~ 16,000 tokens

对静态批处理的含义:
  一个 8 条序列的批次,中位数 150 tokens,但有一条 5,000 tokens,
  会浪费 8 × (5,000 - 150) = 38,800 个前向 token 步等待长尾。
  即 96% 的计算浪费。

对连续批处理的含义:
  7 条短序列在 150 步内完成。其 KV 块被释放。
  接纳 7 个新请求。长序列继续独自运行。
  有效利用率:~ 98%。

这正是 2023 年打垮 HF TGI v1 的工作负载形态,也正是 PagedAttention + 连续批处理架构要解决的问题。vLLM SOSP'23 论文显式针对此分布做基准测试。(Kwon 等 §6.2, Figure 7; lmsys/lmsys-chat-1m)

3.19 内存分配器内部(PyTorch + CUDA Caching)

vLLM 的 CUDA 内存布局分两层:

  1. PyTorch CUDA caching allocator(cudaCachingAllocator) —— 以池形式管理原始 GPU 内存,大小为 gpu_memory_utilization × 总 GPU 内存。
  2. vLLM 块管理器 —— 把池切成固定大小的块(PagedAttention 的逻辑单元)。

块管理器暴露两个池:

  • GPU 块 —— pinned HBM,快速访问,KV cache 所在。
  • CPU 块 —— pinned 主机内存(page-locked,cudaHostAlloc),用于前缀缓存溢出与异步 D2H 拷贝。

当 GPU 内存耗尽,调度器可以将块驱逐到 CPU(swap) —— 但如 §5.2 所述,V1 倾向于重算而非 swap 来抢占。

3.20 抢占决策树

当新请求到达但没有空闲 GPU 块时,调度器必须二选一:

  1. 排队 —— 等待当前请求完成。对新请求 p99 影响最大,但代价最小。
  2. 重算 —— 驱逐一个低优先级运行中的序列,resume 时重算其 KV。V1 默认。
  3. Swap —— 把被驱逐序列的 KV 拷到 CPU 内存,resume 时恢复。更慢但无重算成本。V0 部分模式使用。

V1 实现 --preemption-mode = recompute(默认)或 swap。正确选择取决于工作负载:

工作负载更好选择原因
短 prompt、短输出(对话)重算重算快;swap 开销主导
长 prompt、短输出(RAG)重算重算有界;swap 受带宽限制
长 prompt、长输出(Agent)Swap重算代价巨大;swap 更划算
批量重离线重算延迟不重要,内存才重要

3.21 调度吞吐数学

对于一个 vLLM 部署,饱和吞吐取决于几个旋钮:

饱和吞吐(tokens/s) ≈
    (num_GPUs × tokens/s_per_GPU)
  × (1 - scheduler_overhead_fraction)   # V1 中约 5%
  × (1 - preemption_loss_fraction)        # 调优良好时 < 1%
  × speculative_speedup_factor            # 1.0–3.0
  × quantization_speedup_factor           # 1.0–1.8(FP8 vs FP16)

Llama-3-70B-AWQ on 8×H100、V1、开启 EAGLE-2:
  = (8 × 2,500) × 0.95 × 0.99 × 2.0 × 1.0
  ≈ 37,600 输出 tokens/s 合计

首 token 时间(TTFT): 由 prefill 成本主导。

TTFT_ms ≈ (prompt_tokens × model_flops_per_token) / (num_GPUs × gpu_flops) × 1000
       + scheduling_overhead(约 5 ms)
       + cuda_graph_replay_overhead(约 2 ms)

Llama-3-70B on 8×H100、2k-token prompt:
  = (2,000 × 7e13) / (8 × 1e15) × 1000 + 7
  ≈ 175 + 7 = 约 180 ms

4.1 SOSP'23 论文 —— PagedAttention(Kwon、Li、Zhuang、Sheng、Zheng、Yu、Gonzalez、Stoica)

来源: arXiv 2309.06180;ACM SOSP'23 论文集

一句话思路: 像对待虚拟内存一样对待 KV cache —— 固定大小页 + 每请求页表。

算法上实际做了什么:

  1. 将 KV cache 划分为等大的物理块,每块 B 个 token(B 默认 = 16)。
  2. 维护每请求的块表 —— 一个驻留在 CPU/GPU 上的小数组,把逻辑块 ID 映射到物理块 ID。
  3. 每次前向,attention kernel 读取块表并执行块级 attention —— 将 Q 分成块-tile 加载,并通过间接映射抓取 K、V。
  4. 块分配是惰性的:序列增长时再分配。新请求在 prefill 启动时获得 ceil(prompt_len / B) 个块。
  5. 共享:两个请求有共同前缀时,第二个请求的块表指向与第一个相同的物理块(分支时采用 copy-on-write 语义)。

实测影响(论文 §6):

  • 在 Llama-7B / OPT-13B / BLOOM-176B 上,服务吞吐比 HuggingFace TGI 高 14–24×。
  • 同 GPU 显存预算下最大批大小 2–4×。
  • KV cache 内存利用率:~ 96%(前缀共享 > 98%)。

代码锚点: vllm/attention/(PagedAttention CUDA kernel);vllm/v1/core/kv_cache_manager.py。

4.2 V1 Alpha 博客 —— 「vLLM V1:一次重大重写」(2025-01-27)

来源: blog.vllm.ai/2025/01/27/v1-alpha.html

一句话思路: 抛弃 18 个月积累的复杂度,围绕统一调度器 + CUDA Graphs + 分块 prefill 重建引擎。

V1 新增:

  • 统一调度器。V0 有独立的 prefill 与 decode 调度器,需要二者之间的同步屏障。V1 有一个调度器,在单次前向中混合二者 —— 消除「prefill 尖峰」延迟惩罚。
  • CUDA Graphs 默认。V0 通过 --enforce-eager=False opt-in。V1 设为默认。据报告小批大小下每 token 延迟降低 ~ 5–10×。
  • 分块 Prefill。长 prompt 切为块(默认 4,096 tokens)与 decode 步交错。p99 延迟更平滑。
  • 结构化输出(xgrammar)。通过采样时的约束掩码保证 JSON schema / regex / grammar 合规。
  • FP8 KV cache。H100 上 2× KV 内存节省。
  • 简化的模型注册表。一条执行路径代替每架构代码重复。

实测影响:

  • Llama-3.1-8B(A100、batch 32、1k in / 256 out)吞吐 ~ 1.7×。
  • Llama-3.1-70B(H100、batch 16、1k in / 256 out)吞吐 ~ 1.5×。
  • 长上下文(32k tokens)混合 prefill/decode 工作负载上 p99 延迟改善。

代码锚点: vllm/v1/ 目录;V0 路径作为 vllm.v0.engine 保留一个发布版本。

4.3 投机解码集成(EAGLE-2、Medusa、n-gram)

来源: docs.vllm.ai/spec_decode;EAGLE-2 论文;Medusa 论文

一句话思路: 用便宜的草稿模型提出 K 个 token,目标模型一次前向验证,通过则采纳。

机制:

  1. 草稿模型自回归产出 K 个投机 token(便宜、小模型)。
  2. 目标模型并行评估 K 个 token —— 通过对 K token + 原始 prompt 的一次大 prefill。
  3. 树形 attention / 级联拒绝:从最长接受前缀开始,回退到第一个不匹配,接受前缀、拒绝其余。
  4. 已接受的 K' token 返回给用户;被拒的 token 丢弃(草稿白做)。

vLLM 细节:

  • --speculative-model 标志指向草稿模型(EAGLE-2 head、Medusa head 或 n-gram 查找)。
  • --num-speculative-tokens 设置 K(典型 4–8)。
  • EAGLE-2:Llama-3-70B 上 2–3× 吞吐;草稿是单 transformer 层,通过特征回归训练。
  • Medusa:2–2.5×;草稿是目标模型上的多个并行 MLP head(无独立权重)。
  • n-gram:1.3–2×;无需训练,仅在 prompt 中查找匹配序列。

注意: 投机解码只有在接受率高时才划算。对话场景输出多样,K=5 时接受率典型 60–80%。代码补全可冲至 90%+。

4.4 连续批处理与 ORCA 传承

来源: ORCA(Yu 等, OSDI'22);vLLM §6.1

一句话思路: 把每个 token 生成步骤当作独立的调度单位,而非把每个 batch 视为单位。

为何在量化层面重要:

  • 静态批处理(HF TGI v1):把所有序列 pad 到最长,等所有完成 → 在变长工作负载上浪费 95% 计算。
  • 连续批处理(ORCA、vLLM):每次迭代驱逐已完成序列、接纳新序列 → 利用率接近 100%。
  • 与 PagedAttention 组合:在静态批非分页系统上获得 14–24× 吞吐改善。

vLLM 实现: vllm/v1/core/sched/scheduler.py —— schedule() 方法在每次前向运行,选择接纳哪些序列、哪些抢占(重算)、哪些驱逐。

适用的工作负载: Lmsys.org lmsys/lmsys-chat-1m 显示真实对话输出长度服从长尾分布(中位 ~ 150 tokens,p99 ~ 2,000+)。静态批处理在此崩塌;连续批处理吸纳之。

4.5 分块 Prefill + 连续批处理:平滑延迟配方

来源: V1 博客 §「Chunked Prefill」;vllm/v1/engine/llm_engine.py

一句话思路: 在一次前向中将 prefill 块与 decode 步混合。

为何重要:

  • V1 之前,16,384-token prefill 会阻塞所有 decode 步整整一个 prefill 时长(70B on TP=8 H100 约 3 秒)。这造成 p99 上的延迟断崖。
  • 分块 prefill 将 16k prompt 切成 4× 4,096-token 块。每块与其他在飞请求的 decode 迭代交错运行。
  • Prefill 总时间略有上升(prefill 块不如完整 prefill 高效),但 p99 延迟显著平滑。

调优旋钮: --max-num-batched-tokens(V1 中默认 2,048)。更大 → 每块吞吐更高、单块延迟更高。更小 → 单块延迟更低、填满 prefill 需更多迭代。

与 SGLang RadixAttention 的关联: SGLang 开创了类似思路;vLLM 的 V1 实现以不同名字收敛到同一架构。

📚 附加深度:量化数学(FP8 vs AWQ vs GPTQ)

FP8 (E4M3):1 sign + 4 exponent + 3 mantissa bits。范围约 ±448,精度约 3% 相对误差。在 H100 上,FP8 GEMM 运行在专用 tensor core,吞吐约为 FP16 的 2×。结果:2× 内存,~ 1.6× 吞吐,几乎零质量损失。H100 托管的杀手锏。

AWQ (Activation-aware Weight Quantization, Lin 等 2023):通过保留 1–3% 的关键权重通道为更高精度来保护它们,其余量化到 INT4。结果:4× 内存,大多数基准上 < 1 困惑度损失。在 A100 与 H100 上工作。

GPTQ (Frantar 等 2022):基于二阶梯度的量化,INT4 / INT3 / INT2。INT4:4× 内存,1–3 困惑度损失。INT2:8× 内存,> 5 困惑度损失 —— 通常生产不可用。

SmoothQuant:通过每通道 scale 将量化难度从激活转移到权重。在 A100/H100 上实现 < 0.5 困惑度损失的 INT8 推理。

4.6 前缀缓存 —— RAG 与 Agent 放大器

来源: vLLM 前缀缓存文档;vLLM v0.4 发布说明(2024-04)。

一句话思路: 如果两个请求有相同前缀 token,共享其 KV cache 块而非重算。

为何重要:

  • 典型 RAG 请求有 4,000-token 系统 prompt + 2,000-token 检索上下文。6,000 token 中 ~ 95% 在请求间相同。
  • 无前缀缓存时,每个请求在 prefill 重算全部 6,000 token。有缓存时,只需 prefill 可变的用户消息。
  • RAG 工作负载上报告加速:首 token 时间 4–8×,合计吞吐 1.5–2×。

机制(radix tree):

  1. vLLM 维护所有活跃 KV 块的 radix tree,以 token 内容为键。
  2. 新请求到达时,引擎遍历树,找最长匹配前缀。
  3. 匹配块被引用(分支时 copy-on-write);未匹配块全新计算。
  4. 树在内存压力下受 LRU 驱逐约束。

代码锚点: vllm/v1/core/kv_cache_manager.py(查找 find_longest_cache_hit)。

4.7 结构化输出 —— xgrammar 与引导解码

来源: vLLM 结构化输出文档;xgrammar 仓库(MLC-AI)。

一句话思路: 在每一步解码时保证 LLM 输出匹配 JSON schema、regex 或 grammar。

为何生产上重要:

  • Tool-calling API(函数调用)需要 JSON schema 合规的参数。无引导解码时,模型 ~ 5–10% 时间产出无效 JSON。
  • 代码生成需要合法语法。Regex 约束解码防止畸形输出。
  • Agent 循环依赖可靠解析 —— 一段畸形 JSON 就打断整个工作流。

机制:

  1. 将 JSON schema / regex / grammar 编译为有限状态自动机(xgrammar)或下推自动机(outlines)。
  2. 每步解码,屏蔽 logits 只保留能让输出保持合法状态的 token。
  3. 在屏蔽后的 logits 上采样 —— 保证输出合法。

性能开销: 通常 < 10% 延迟惩罚;屏蔽作为与采样并行的快速 logit-bias 算子实现。

4.8 LoRA 热切换 —— 微调无须重部署

来源: vLLM LoRA 文档。

一句话思路: 把多个低秩适配器权重加载到 GPU 内存;为不同适配器的请求服务而无需重启引擎。

机制:

  1. 基模型(如 Llama-3-70B)加载一次。FP16 下占 ~ 140 GB。
  2. 每个 LoRA 适配器小(~ 50–200 MB for rank 16–64)。vLLM 可同时持有 10–50 个适配器于 GPU 内存。
  3. 请求指定 "adapter_id": "customer-acme-v3";引擎查找适配器权重并按层计算 W_effective = W_base + B @ A。
  4. 热切换:运行时通过 /v1/load_lora_adapter API 增加或删除适配器 —— 无引擎重启。

用例: 在共享 GPU 基础设施上为每个客户提供微调模型。一套 70B 基模型 + 50 个适配器从一个 GPU 池服务 50 个不同客户的画像。

4.9 多模态推理(视觉语言)

来源: vLLM 多模态文档。

一句话思路: 通过视觉编码器处理图像/视频/音频输入,投影到 text-token 空间,然后走同一 LLM 前向。

架构:

  1. 视觉编码器(ViT、CLIP、SigLIP)将图像处理为视觉 token 序列(如 448×448 图像、14×14 patch 下为 576 token)。
  2. 投影器(线性或 MLP)将视觉 token 嵌入映射到 LLM 的 token 空间。
  3. LLM处理组合序列:[system] + [user_text] + [visual_tokens] + [user_text_2]。
  4. KV cache 同时包含文本与视觉 token —— PagedAttention 统一处理。

支持的模型(节选): LLaVA-1.5/1.6、Qwen2-VL、Pixtral-12B、InternVL2、Phi-3.5-Vision、CogVLM、Llama-3.2-Vision。

性能注记: 视觉编码器受带宽限制;LLM 受计算限制。vLLM 在可能时并行运行二者。

4.10 音频与语音(Whisper 类、VALL-E)

来源: vLLM 支持模型。

一句话思路: 音频编码器产出离散 token(Whisper)或连续嵌入(USM);LLM 像消费视觉 token 一样消费它们。

vLLM 中状态: 实验性。Whisper、Distil-Whisper 与 VALL-E 模型有部分支持;商业部署通常使用专用的 ASR 引擎(Whisper.cpp、NVIDIA Riva、Deepgram)。

对 Inferact 的含义: 尚未成为核心产品。可能列入 2026 路线图。

4.11 Embeddings 端点(vLLM + Sentence Transformers)

来源: vLLM OpenAI server 文档 §Embeddings。

一句话思路: 在同一引擎上通过 OpenAI /v1/embeddings 端点提供文本 embedding 模型(BERT、BGE、E5、Stella)。

为何重要: RAG 应用既需要 LLM 又需要 embedding 推理。统一端点降低运维复杂度。vLLM 在同一服务器上支持两种模式。

性能: embedding 推理单请求成本远低于 LLM(~ 1 ms vs ~ 100 ms)。大多数 RAG 流量在摄入阶段是 embedding 重、查询阶段是 LLM 重。

5.2 vLLM 的结构性局限

  • 前缀缓存失效成本。当共享前缀块且某请求写入其中(即块内分支),vLLM 执行 copy-on-write —— 把块拷到新物理位置。对长系统 prompt 且分支频繁的工作负载,拷贝开销不可忽视。
  • 长上下文下投机解码。当 prompt 长度超过草稿模型训练分布时,接受率急剧下降。基于 4k token 训练的 EAGLE-2 在 16k+ 上下文下衰减。
  • 动态批大小下的 CUDA Graph 回放。Graph 池可能膨胀到数百个实例(每 (batch_size, seq_len, kv_layout) 元组一个)。高 QPS 工作负载的 graph 存储内存成本不可忽视。
  • MoE(混合专家)低效。对 Mixtral-8×7B 或 DeepSeek-V3,PagedAttention 对 KV cache 管理良好,但专家路由仍需 NCCL 未优化的 all-to-all 通信。vLLM 的 MoE 路径不如 dense 模型成熟。
  • 抢占策略。vLLM 用重算(非 swap)抢占 —— 意味着被抢占序列丢失其 KV cache,resume 时必须重新 prefill。对长上下文工作负载,代价高昂;SGLang 与 TensorRT-LLM 探索基于 swap 的抢占。
  • 多节点扩展。V1 加入异步 PP,但多节点 PP 因节点间带宽(典型 200–400 Gbps 对比节点内 ~ 900 GB/s NVLink)仍比单节点 TP 慢。

5.7 解构推理问题(Mooncake、DistServe)

V1 之前,vLLM 在同一 GPU 池上跑 prefill 与 decode。不对称性严重:

  • Prefill:计算受限,GPU 饱和近 100%,延迟敏感(首 token 时间)。
  • Decode:内存带宽受限,GPU 利用率常 < 40%,吞吐敏感(tokens/s)。

解构推理(Mooncake, Moonshot AI;DistServe, CMU)将 prefill 与 decode 拆到独立 GPU 池,通过网络传输 KV cache。好处:

  • Prefill GPU 以 100% 饱和跑其专项负载。
  • Decode GPU 在内存带宽受限负载上高利用率运行。
  • p99 延迟改善,因为 prefill 尖峰不再阻塞 decode 迭代。

vLLM V1 有原型级解构支持(经 RDMA / NIXL 的 KV-transfer)。领先的商业实现有:

  • Mooncake (Moonshot AI) —— 已在 Kimi.ai 生产部署。
  • DistServe(学术, CMU) —— 见 arXiv 2401.09670。
  • vLLM 自身的解构路线图(社区 RFC)。

对 Inferact 的含义:解构是 V1 之后的下一个 2× 效率杠杆。最先交付解构推理的厂商将在长上下文工作负载上拥有 2× 成本优势。

  3. vLLM V1 缩小了与 TensorRT-LLM 的性能差距。2025 前,NVIDIA 的 TensorRT-LLM 在多数工作负载上比 vLLM 快 20–40%。V1 之后,vLLM 匹配或超过 TensorRT-LLM,且额外拥有开源可扩展性的好处。「用 vLLM 而非 TensorRT-LLM」的算计翻盘。

7.10 术语表

术语定义
KV cache每 token 的 Key+Value 张量,跨所有 transformer 层存储;随序列长度线性增长;在服务时主导 GPU 内存。
块 (PagedAttention)固定大小的 token 块(默认 16),KV cache 在 GPU 内存中以连续形式存储。
块表每请求的逻辑块索引到物理 GPU 内存地址映射;类比页表。
Prefill并行处理整个输入 prompt 以产出首个输出 token 的阶段。计算受限。
Decode自回归一次一个 token 生成输出 token 的阶段。内存带宽受限。
连续批处理每次迭代接纳与驱逐序列的调度策略,而不是等整个批次完成。
静态批处理传统策略,跑固定批次直到所有序列完成;在变长工作负载上浪费计算。
张量并行(TP)跨 GPU 分片权重矩阵;每个 transformer 块需要 all-reduce。
流水线并行(PP)跨 GPU 分片 transformer 层;阶段边界需要 P2P 通信。
CUDA GraphNVIDIA 原语,录制一串 kernel 启动以单次回放,消除每次启动开销。
投机解码加速技术,小草稿模型提出 K 个 token,目标模型一次前向验证。
EAGLE-2 / Medusa两种流行的投机解码草稿架构(单层回归 head 对比多个并行 MLP head)。
前缀缓存跨相同前缀 prompt 的请求共享 KV cache 块;用 radix tree 查找。
AWQActivation-aware Weight Quantization;INT4,< 1% 质量损失。
GPTQ基于二阶梯度的 PTQ;INT4/INT3/INT2。
FP8 (E4M3)8 位浮点,4 exponent + 3 mantissa bits;H100 tensor core 原生支持。
MoE (混合专家)模型架构,每 token 激活 N 个专家 MLP 中的 K 个(如 Mixtral 8×7B 激活 8 中 2)。
解构推理将 prefill 与 decode 拆到独立 GPU 池;由 Mooncake(Moonshot)与 DistServe(CMU)开创。
xgrammarMLC-AI 库,通过 FSM 掩码实现 JSON schema / regex / grammar 约束解码。
LoRALow-Rank Adaptation;高效微调方法,向冻结权重添加小可训练矩阵。
BYOCBring Your Own Cloud;部署模型,推理平面运行于客户云账户内。
DCGMNVIDIA Data Center GPU Manager;为 SM 占用、HBM 带宽、温度提供指标导出。
NCCLNVIDIA Collective Communications Library;在 NVLink/IB 上实现 all-reduce、all-gather、broadcast。
NVLink / NVSwitchNVIDIA 高带宽 GPU 到 GPU 互连;节点内 ~ 900 GB/s。

7.17 结语

写于 2026 年末,vLLM 生态正处于拐点。技术基础已成熟 —— PagedAttention、连续批处理、CUDA Graphs、投机解码、V1 重写 —— 引擎已达到与专有栈持平。商业层是差异所在。

Inferact 类厂商有一条可信论点:写出引擎的人最有条件运营服务。该论点能否转化为 $100M+ ARR 或消融于超大规模云的整合,取决于执行速度、资本效率,以及 12 个月的窗口期 —— 在此之前 Bedrock 类服务将吸收中端市场。

2026–2028 有趣的研究问题不是「vLLM 够快吗?」 —— 它显然够快。问题是「谁来捕获开源引擎的价值?」历史先例(Postgres、Redis、Linux、Kubernetes)表明多层多处都有赢家;vLLM 市场有容纳 3–5 家长期 Tier-2 厂商的空间。
