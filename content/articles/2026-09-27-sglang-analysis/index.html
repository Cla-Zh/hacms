CH.00研究背景与方法

0.1 分析对象：sgl-project/sglang

SGLang 是由 李墨 (LMSYS-org) 团队主导的开源 LLM 服务框架，与 vLLM、TensorRT-LLM 并列为 LLM serving 三大主流方案。SGLang 的核心差异化在于：

  • RadixAttention — 基数树结构的 prefix cache，比 vLLM 静态 hash cache 命中率显著提升
  • SGLang DSL — 前端编程语言层 (类似 Lisp 的 S-expression)，支持 fork/generate/select 等并行原语
  • 双层架构 — 解释器层 + SRT 运行时层，前端可控后端高效
  • Composed FSM — 结构化输出引擎，与 vLLM Outlines 同源但更高效

CH.01维度一：双层架构解构与端到端执行流

SGLang 最具辨识度的设计是双层架构：一个面向 LLM 程序的前端语言层 (DSL) 与一个面向高吞吐的后端运行时层 (SRT)。这种分层让 SGLang 同时具备编程语言的表达力与推理引擎的高性能。

1.1 前端语言层（Frontend Language & Program Runtime）

SGLang 的前端由 python/sglang/lang/ 模块构成，是其与传统 LLM 服务框架最显著的差异化设计。它允许用户像编写 Python 一样定义结构化 LLM 程序，并自动获得 fork/parallel/structured-output 等高级能力。

1.1.4 Tracing 与 Fork/Join 状态机

lang/tracer.py 实现了 SGLang DSL 的执行追踪，核心类: Tracer。SGLang 的 fork 语义允许一次函数调用复制其执行状态并产生多个候选输出，结合 cache 基础调度器实现 branch search、parallel sampling 等 Agent 模式。

示例 DSL 代码:

import sglang as sgl

@sgl.function
def multi_sample(s, question):
    s += sgl.user(question)
    forks = s.fork(3)  # fork 产生 3 个候选状态
    samples = [f(s) for f in forks]
    return samples

这段代码展示了 SGLang 的核心威力：一次 fork 操作复制状态，三次独立 rollout，而 prefix 部分共享同一 KV Cache（RadixAttention 收益）。

CH.02维度二：核心关键技术原理与代码实现

2.1 RadixAttention 与基数树缓存管理

RadixAttention 是 SGLang 最具创新性的核心设计之一。与 vLLM 静态 hash-based prefix cache 不同，SGLang 采用基数树（Radix Tree / Prefix Tree） 来组织 KV Cache 的前缀共享。

2.1.3 RadixAttention vs vLLM Hash-Based Prefix Cache

维度RadixAttention (SGLang)Static Prefix Cache (vLLM)
数据结构Radix Tree（多分支前缀树）Hash Map（key→KV 块）
多轮对话共享✅ 自动递归复用任意前缀⚠️ 需显式预热
Few-shot Prompt 复用✅ 同 prompt 多分支各算一次❌ 每次单独算
Tree Search / Beam Search✅ 天然支持（fork 语义）❌ 不支持
多模态 prefix✅ 跨模态前缀共享❌ 仅文本
LRU 淘汰粒度节点级（子树）Block 级
管理开销中（树遍历 O(log N)）低（哈希 O(1)）
实现复杂度高（分裂/合并/引用计数）低

设计权衡：RadixAttention 以更高的管理复杂度换取 prefix 命中率显著提升，特别在 multi-turn chat、agent loop、tree search 场景下收益巨大。

CacheAwarePolicy 优先调度 prefix cache 命中度高的请求，最大化 RadixAttention 复用收益。具体策略包括：

  • cache hit 优先: prefix matching length 高的 request 排前面
  • running queue eviction: 显存不足时按优先级驱逐
  • chunked prefill: 长 prompt 分块执行 prefill
  • decode batch 合并: 多 decode 请求合并 forward

2.4 结构化输出引擎（XGrammar / Compressed FSM）

SGLang 的结构化输出引擎 XGrammar 与 vLLM 的 Outlines 同源（皆出自 guidance 团队），但 SGLang 做了 Compressed Finite State Machine (CFSM) 优化，在 mask 构造效率上有显著优势。

2.4.1 XGrammar 后端

srt/constrained/xgrammar_backend.py 实现了 XGrammarGrammar 类 (L77)。

xgrammar_backend.py L77

2.4.2 工作原理

  1. 预编译: JSON Schema / Regex → Compressed Finite State Machine (CFSM)，XGrammar 引擎将 DFA 压缩为 token 级别的 mask 树
  2. 逐 Token 掩码: 每个 decode step，scheduler 调用 accept_token 更新 FSM 状态，mask_logits 计算当前允许 token 集合，置为 -inf 屏蔽其他 token
  3. 零开销推理: structured output 几乎不增加延迟（实测 < 5% overhead）

4.1 代码级瓶颈与技术债务

4.1.1 Radix Tree 锁竞争与并发瓶颈

radix_cache.py 中所有 prefix 操作（insert, match_prefix, evict）均在全局锁保护下，所有请求的 prefix 操作串行化。在 100+ QPS 高并发下，tree mutation 可能成为 throughput 瓶颈。

改进方向:

  • Lock striping（按 hash bucket 分锁）
  • Lock-free radix (CAS-based)
  • Epoch-based reclamation

4.1.2 Python 解释器瓶颈

scheduler.py (6111 LOC) 调度核心全部 Python 实现；model_runner.py (2428 LOC) 包含大量 dispatch + forward 调度逻辑。

⚠ GIL 限制下的 Python overhead

每次 request 调度都有 Python overhead，在 32+ GPU 部署下，scheduler 单进程可能成为调度瓶颈。

改进方向:

  • 用 Cython/Rust 重写 hot path（schedule_policy.py 中 _calc_priority_weight 等）
  • 用 Python 3.12+ sub-interpreters 绕过 GIL
  • Scheduler 进程横向扩展（DP scheduler）

4.1.3 多进程 IPC 开销

Ch通道机制序列化开销高并发下瓶颈
HTTP→Tokenizerasyncio.Queue0低
Tokenizer→SchedulerZMQ IPCJSON pickle (~200µs)中
Scheduler→TP WorkerNCCL collective0 (GPU direct)低
TP Worker→DetokenizerZMQ PUB/SUBmsgpack (~300µs)中
Detokenizer→Clientasyncio.Queue0低

优化建议:

  • 用 Apache Arrow / FlatBuffers 替代 JSON 序列化（实测 5-10x 加速）
  • 用 CUDA IPC / NVLink shared memory 跨进程共享 KV Cache metadata
  • 在 TP group 内启用 fused broadcast（避免多次 collective call）

4.1.4 动态长文本 Prefill 与显存碎片

srt/mem_cache/memory_pool.py 是 KV Cache 分配器。核心问题：

  1. 变长请求的连续 KV Cache 分配产生内部碎片 (intra-request fragmentation)
  2. 长 prompt + 突发并发下，Radix Tree 的反复 evict/insert 造成外部碎片
  3. CUDA Graph recapture 触发的 memory re-allocation 引发延迟毛刺 (latency spike)

典型症状: TTFT p99 偶发性 2-5x 抖动。

4.1.5 CUDA Graph Recapture 开销

CUDA Graph 需要 pre-warm + capture，当 batch shape 变化（新增请求类型）触发 recapture，单次 ~100ms 抖动。

改进方向:

  • 多 shape pool（预 capture 多种典型 batch shape）
  • Piecewise CUDA Graph（分段 capture + 拼接）

4.2.1 跨节点分布式 RadixAttention

预测路径: 2026-2027 实现

4.2.2 Prefill / Decode 物理节点分离架构

预测路径: 2025-2026 成为 SGLang 默认部署模式

当前状态:

  • 已支持 KV Cache 跨节点 RDMA 传输
  • 已支持 MoE + Mamba + Transformer 混合模型的 Disaggregation

下一步演进:

  1. 弹性扩缩容: Prefill 节点按 QPS 自动伸缩，Decode 节点按 active session 数伸缩
  2. SLO-aware 调度: 区分 TTFT-bound (Chat) vs TPS-bound (Completion) 请求路由到不同 pool
  3. 跨数据中心: 利用 WAN 链路跨 region 部署 Prefill Cluster

4.2.3 编译期计算图联合优化

预测路径: 2026 H2 起 SGLang 集成 torch.compile + TensorRT-LLM 双后端

技术潜力:

  • 前端 DSL 静态计算图（@sgl.function 编译为静态 IR）
  • 后端 Triton JIT / TensorRT-LLM 算子级图融合协同
  • 跨 kernel 边界 kernel fusion（如 attention + sampling + structured mask）

SGLang 已有基础:

  • python/sglang/compile_deep_gemm.py — DeepGEMM 编译入口
  • python/sglang/kernels/aot/ — AOT compiled kernels
  • 模型 export 路径支持 ONNX / TorchScript

预期收益:

  • Decode latency 降低 20-40%（kernel launch overhead 消除）
  • 显存占用降低 10-15%（memory planning 优化）
