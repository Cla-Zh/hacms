炼金工厂 · Agent Platform v0.1
软件设计文档 (主文档)

基于 micro VM 的多框架 Agent 开发与运行平台。从解决方案、产品形态、C/S 协议、VM 隔离、目录挂载、权限模型、安全、可观测性到价格策略,端到端的设计规范。当前文档完成 v0.1 的"先做一个主界面 + 单 VM + 双框架 (OpenClaw / Hermes) + 目录挂载"最小可用形态。

CH.01概述与背景

1.1 一句话定位

炼金工厂 · Agent Platform 是一个面向开发者与团队的 Agent 开发与运行托管平台:用户在浏览器中登录即可获得一个 隔离的 micro VM (轻量级虚拟机),VM 内预置或上传自选的 Agent 框架 (OpenClaw / Hermes / 自定义),Agent 通过目录挂载访问宿主机的数据,所有 LLM 调用、文件操作、网络访问都受平台 权限模型 约束,做到"开箱即用 + 强隔离 + 可观测"。

1.2 解决的痛点

  • 本地 Agent 跑不安全:开发者在自己的 Mac/PC 上跑 OpenClaw/Hermes 时,Agent 可读写 home 目录任何文件,误删/误传风险高。
  • 环境配置痛苦:每个 Agent 框架有不同的 Node/Python 依赖、API key 配置,MCP 服务器接入繁琐,团队内 5 个开发者 5 套环境。
  • 无统一观测:Agent 跑了什么、调了什么 API、花了多少 token、阻塞在哪里,本地终端一片黑。
  • 难分享与协作:团队成员间无法共享同一份"调试好的 Agent 配置",复制粘贴 = 版本漂移。
  • 商业 Agent 平台太贵:E2B/Modal/Daytona 起步价 $0.05/session,中小企业和独立开发者吃不下。

1.3 与市场同类产品的差异

CH.02目标 · 非目标 · 用户故事

2.5 关键场景:首次冷启动 VM (US-03 拆分)

  1. 00:00 用户点击 "启动 OpenClaw"
  2. 00:01 S 端 API 创建 VM 记录,DB 插入 row
  3. 00:02 VM Manager 从 OCI registry 拉取基础 rootfs (Alpine 3.20, 80MB) → 本地缓存
  4. 00:05 VM Manager 拉取 OpenClaw 框架镜像 (Node 22 + 依赖, ~300MB, 复用上次的 layer 缓存)
  5. 00:15 创建 libkrun 实例, 启动 micro VM
  6. 00:18 VM 内 systemd 启动 krun-agent
  7. 00:20 krun-agent 启动 OpenClaw 进程 (entrypoint.sh)
  8. 00:25 OpenClaw 在 VM 内的 :7777 端口 ready
  9. 00:26 S 端反向 tunnel 建立 (WebSocket frp),C 端收到 "VM ready" 信号
  10. 00:28 C 端 UI 切换到对话界面

冷启动目标 < 30 秒 (SSD 缓存命中时);热启动 < 3 秒 (VM paused → resumed)。

CH.03总体技术架构

3.1 一张图看清 (System Overview)

图 2 · 系统总体架构图 — 3 个区 (C 端浏览器 · S 端 Linux 服务器 · micro VM) + 5 横切关注

3.2 架构分层原则

  • C/S 边界:C 端是纯渲染层,所有业务逻辑 + 鉴权 + 资源调度都在 S 端;C 端从不直连 VM
  • VM 是黑盒:从 S 端看,VM 是一个拥有独立 IP/资源/生命周期的进程,它的内部 Agent 框架版本由 manifest 描述,S 端不解析框架内部状态
  • 事件驱动优先:所有 VM 状态变化通过事件总线 (Redis Streams) 广播,S 端内部模块解耦
  • 可观测先行:每个 VM 启动时自动注入 OpenTelemetry SDK,所有调用都有 trace_id
  • 权限最小化:S 端的 VM Manager 以非 root 用户运行,只通过 capabilities (CAP_SYS_ADMIN 子集) 操作 VM

4.2 REST 路由设计 (v0.1)

认证 (Auth)
  POST   /v1/auth/magic-links           { email }                  → 发送 Magic Link
  POST   /v1/auth/sessions               { token }                  → 兑换 JWT
  POST   /v1/auth/refresh                —                          → 刷新 access token
  POST   /v1/auth/logout                 —                          → 撤销

  POST   /v1/vms/{id}/start                                          → 启动
  POST   /v1/vms/{id}/pause                                          → 暂停
  POST   /v1/vms/{id}/resume                                         → 恢复
  DELETE /v1/vms/{id}                                                → 销毁

  GET    /v1/runtimes                                                → 预置 + 上传列表

用量与计费 [v0.2]

  GET    /v1/usage/history                ?from=&to=

管理员 (Admin)

4.4 WebSocket 事件协议 (流式响应)

VM 与 C 端通过 S 端 Stream Hub 转发 WebSocket 消息。每条消息是一个 JSON Lines 单行对象,基本 schema:

// C 端 → S 端 (控制)
{ "type": "subscribe", "vm_id": "vm_abc", "topics": ["events", "stream"] }
{ "type": "user_message", "vm_id": "vm_abc", "conv_id": "conv_xyz", "content": "..." }
{ "type": "tool_approval", "vm_id": "vm_abc", "tool_call_id": "...", "decision": "allow|deny" }
{ "type": "ping", "ts": 1737... }

// S 端 → C 端 (推送)
{ "type": "vm_state", "vm_id": "...", "state": "RUNNING", "ts": ... }
{ "type": "stream_token", "conv_id": "...", "delta": "你好", "seq": 42 }
{ "type": "tool_call", "id": "tc_...", "name": "read_file", "args": {...} }
{ "type": "tool_result", "id": "tc_...", "result": {...}, "duration_ms": 87 }
{ "type": "file_change", "path": "/workspace/main.py", "diff": "..." }
{ "type": "vm_metric", "cpu_pct": 23.4, "mem_mb": 412, "ts": ... }
{ "type": "error", "code": "...", "message": "...", "fatal": false }
{ "type": "pong", "ts": ... }

4.6 速率限制 (Rate Limiting)

  • 登录尝试:同 IP 5 次 / 分钟,同邮箱 3 次 / 小时
  • VM 创建:单用户 3 次 / 小时 (v0.1 限额;v0.2 按订阅放开)
  • WebSocket 消息:每连接 60 条 / 秒 (超过则断开重连)
  • 挂载变更:每 VM 10 次 / 分钟 (防误操作)

实现:Redis Token Bucket,中间件读取 X-RateLimit-* 响应头。

CH.05Micro VM 隔离层 (libkrun)

5.1 选型理由

我们没有选 Docker 容器 (共享内核,逃逸风险),也没选 Firecracker (Go 实现,二次开发门槛高),而是选了 containers/libkrun:

  • 真正的 VM 隔离:独立内核,通过 KVM 硬件虚拟化跑真 Linux guest
  • 启动速度:~100ms cold start,vs Docker 50ms 启动 vs Firecracker 125ms
  • vsock 通信:无需虚拟网卡,内核级转发,延迟 <1ms,适合流式响应
  • Rust 核心:可被 Python 通过 cffi 绑定 (我们封装了 agent_platform.infra.krun)
  • 维护活跃:containers 组织维护 (Podman 同源),与 OCI 生态兼容

5.4 三层隔离 (Defense in Depth)

Layer 1 · cgroups v2/sys/fs/cgroup/agent-platform/{vm_id}/CPU/MEM/DISK
  • cpu.max = 400000 1000000 (4 核绑定 40%)
  • memory.max = 4294967296 (4GB 硬上限)
  • memory.high = 3221225472 (3GB 软上限,触发回收)
  • io.max = rbps=209715200 wbps=209715200 (200 MB/s IO 限速)
  • pids.max = 1024 (进程数上限)
Layer 2 · Landlock/sys/kernel/security/landlock文件系统白名单
  • VM 进程启动前调用 prctl(PR_SET_NO_NEW_PRIVS)
  • 构造 Landlock ruleset:只允许读 /usr/lib、/etc/ssl、/workspace
  • 不允许写 /etc、/usr、/var/log
  • 挂载目录根据 mount.mode 决定 RO/RW
Layer 3 · seccompBPF program系统调用过滤
  • 默认 deny + 白名单 50 个安全 syscall (read/write/open/exit/clone/futex 等)
  • 禁止 ptrace、mount、reboot、kexec_load、init_module
  • 禁止 socket(AF_NETLINK)、setns (防逃逸)
  • 允许 vsock (AF_VSOCK) 用于与 S 端通信

5.5 网络隔离

v0.1 网络模型采用 slirp 用户态 NAT (无 TAP):

  • VM 内看到的 IP 是 10.0.2.15,gateway 10.0.2.2
  • 所有外出流量经 S 端的 slirp 进程,受 eBPF 出口白名单控制
  • 默认白名单:LLM API 域名 (api.openai.com、api.anthropic.com、generativelanguage.googleapis.com)、MCP 默认服务器
  • 用户自定义白名单需在 VM 设置里声明,保存到 isolation.net_egress
  • DNS 由 S 端 slirp 转发,过滤私有 IP (防 SSRF 攻击)

6.4 自定义上传流程 (US-06)

  1. 用户在主界面点击 "+" 按钮 → 弹窗显示上传对话框
  2. 选择本地 .tar.gz 文件 (≤100 MB,内含 manifest.json + rootfs 层)
  3. C 端 POST /v1/runtimes/upload (multipart/form-data) → S 端接收,存到临时目录
  4. S 端解析 manifest,校验 schema,验证 rootfs-layer.tar 完整性 (sha256)
  5. S 端在 sandbox 中试启动 (1 分钟超时),验证 entrypoint 能起 + 端口能开
  6. 通过 → 移入 runtimes/user_uploaded/{runtime_id}/ + 入库
  7. 失败 → 返回 422 + 详细错误 (缺 manifest/格式错/启动失败)
  8. C 端收到新 runtime_id,刷新主页,新卡片出现

6.5 框架与 LLM Provider 的解耦

每个 runtime 通过环境变量 OPENAI_API_KEY / ANTHROPIC_API_KEY 等获取 LLM 凭证。这些变量由 S 端在 VM 启动前从 用户密钥库注入:

  • v0.1 密钥存 PG,使用 SOPS 加密;v0.3 切 HashiCorp Vault
  • 用户在主界面"设置"里管理自己的 LLM API keys (仅本人可见)
  • VM 进程退出后,环境变量不持久化到磁盘

6.6 框架状态监测

S 端通过 vsock 周期性 ping (/healthz 端点) 检测 Agent 进程:

  • 每 30 秒发心跳
  • 3 次失败 → VM 置 FAILED 状态,触发告警 + 1 次自动重启
  • Agent 主动上报 agent_state (idle / busy / error) → C 端 UI 显示对应状态

7.4 配额 Enforcement

挂载目录的配额不是文件系统本身 (loop 文件),而是在 virtiofsd 进程层 enforce:

# virtiofsd 启动参数
virtiofsd \
  --shared-dir /home/calvin/projects/foo \
  --sandbox none \
  --cache always \
  --quota-size 5368709120  # 5 GB
  --quota-files 100000

当 VM 内 Agent 写文件总大小超过配额,virtiofsd 返 ENOSPC,Agent 进程收到 EIO 错误,S 端同步触发 mount_state = QUOTA_EXCEEDED 事件。

7.5 跨平台路径映射

用户主机的路径 (Windows/macOS/Linux) 与 VM 内路径 (Alpine Linux) 通过 路径转换器自动映射:

宿主用户路径S 端规范化VM 内路径
Linux~/projects/foo/home/calvin/projects/foo/workspace/foo
macOS~/projects/foo/Users/calvin/projects/foo/workspace/foo
Windows (v0.3)C:\Users\calvin\projects\foo/mnt/c/Users/calvin/projects/foo/workspace/foo

7.6 路径冲突检测

同一 VM 不允许两个挂载指向同一 VM 内路径。冲突检测算法:

def check_conflict(new_mount, existing_mounts):
    for m in existing_mounts:
        if paths_overlap(new_mount.vm_path, m.vm_path):
            return f"conflict with mount {m.mount_id} at {m.vm_path}"
    return None

子路径冲突: /workspace 已挂载,不允许再挂 /workspace/subdir。需要用户先卸载外层。

CH.10运维与可观测性

10.1 日志规范

  • 所有 S 端 Python 进程使用 structlog 输出 JSON,字段:ts, level, msg, trace_id, vm_id, user_id, action, duration_ms, error_code
  • VM 内 Agent 进程的 stdout/stderr 通过 vsock 转发到 S 端,经 S 端落盘到 /var/log/agent-platform/vms/{vm_id}/
  • 日志保留 7 天 (本地) / 90 天 (归档到 S3 [v0.3])
  • 结构化字段支持 grep/jq 查询,例:jq 'select(.vm_id=="vm_abc" and .level=="error")' /var/log/agent-platform/api.log

10.3 Tracing (OpenTelemetry)

所有 API 请求 + VM 操作都注入 traceparent header,后端用 OTLP exporter 发到 Jaeger / Tempo:

  • S 端 span 名:vm_manager.start_vm、mount_manager.apply 等
  • VM 内 krun-agent 通过 vsock 把 trace 数据推到 S 端
  • trace_id 跨 C → S → VM 全链路串联

10.5 备份与恢复

v0.1 备份策略:

  • PG 数据库:每日 pg_dump 到 /var/backups/agent-platform/pg-YYYYMMDD.sql.gz,保留 30 天
  • VM rootfs overlay:不备份 (临时状态,VM 销毁即丢);用户需要持久化的数据应放在挂载目录
  • 用户上传的 runtime:存 /opt/agent-platform/runtimes/user_uploaded/,跟随 PG 备份
  • 配置文件:/etc/agent-platform/ 整个目录 tar 到备份目录

恢复演练:每月一次,完整从备份恢复整个平台,目标 RTO < 2 小时,RPO < 24 小时。

10.6 升级策略

  • S 端服务:蓝绿部署 (旧实例 + 新实例,Nginx 切换),无停机
  • PG schema:Alembic 迁移,所有变更 forward + backward 兼容
  • VM base 镜像:每月一次新版本,旧版本保留 1 个 (用户可手动切换)
  • Runtime (OpenClaw/Hermes) 版本:固定 SHA 锁定,需运维手动升级并通知用户
