执行摘要

执行摘要 —— Ray + Anyscale:从伯克利研究项目到现代 AI 基底

Ray 是一款开源分布式计算框架,由 Robert Nishihara、Philipp Moritz、Ion Stoica 等人于 2017 年在 UC Berkeley 的 RISELab 创建(arXiv 1712.05889,发表于 NSDI'18)。它为 task、actor、placement group 以及分布式对象存储提供了一套统一的 Python API —— 形成一个统一基底。同一个实验室随后将其拆分出 Ray Train(分布式训练)、Ray Serve(模型服务)、Ray Tune(超参搜索)以及 RLlib(强化学习)。

Anyscale 是 Ray 的商业化主体。公司由 Ion Stoica(UC Berkeley 教授、Databricks 与 Apache Spark 联合创始人)、Robert Nishihara(Ray 论文第一作者)、Philipp Moritz 以及一批 RISELab 校友于 2019 年共同创立。公司运营 Anyscale Platform(托管 Ray-as-a-service)、Anyscale Workspaces(浏览器 IDE + 笔记本)以及 —— 直至 2024 年 3 月 —— Anyscale Endpoints(托管 LLM 推理 API,一种 vLLM 风格、与 OpenAI/Anthropic 直接 API 竞争的服务)。

⚠ 战略转向信号。2024-03-05,Anyscale 公开宣布 Anyscale Endpoints 弃用,把所有推理流量引导至基于开源 Ray Serve + vLLM 栈、由 anyscale.com 品牌化的路由。托管 LLM API 业务实质上已死;Anyscale 现在是一家平台型 / 托管 Ray 公司,收入来自算力、企业支持与平台费。(anyscale.com/blog/anyscale-endpoints-deprecation-notice)

为什么这份简报值得看。Ray 是除超大规模云厂内部栈之外,AI 领域占主导地位的开源分布式计算基底。OpenAI 使用 Ray 编排 ChatGPT 训练(anyscale.com/blog/anyscale-platform-supports-openai);Uber 用 Ray 做需求预测与货运定价;Shopify 在 Ray 上跑推荐系统;Pinterest 用 Ray 做内容审核与广告 CTR;蚂蚁集团、字节跳动、JPMorgan Chase 都运行着大规模的 Ray 集群。该论文在 Google Scholar 上有 4,000+ 引用,GitHub 仓库 star 数超过 30k。

为什么这篇研究简报值得读

  1. Ray 不是框架,而是一套分布式操作系统。Tasks、actors、Plasma/Arrow 对象存储、GCS 控制面以及 placement group 调度器共同组成一个连贯的运行时,而不仅仅是一个库。把它当成"只是 Python 装饰器"会错失它的深度。
  2. Plasma → Arrow-Flight 迁移(Ray 2.x)是 2018 年以来最具影响力的架构变更,而在第三方博客中几乎无人提及。
  3. Anyscale 的 Endpoints 关停是 AI 基础设施公司"自建 vs 转售"的经典案例:在超大规模云厂每个季度下调价格的背景下,推出与 OpenAI/Anthropic 直接竞争的薄利托管 API 业务,在结构上就赢不了。Anyscale 转向平台是正确的选择。
  4. Ray 与 Modal / E2B / RunPod / Baseten 的定位是 2026 年 AI 基础设施领域最重要的战略问题之一:Ray 是"分布式计算的 JVM",Modal 是"云上的 Python",未来的混合形态尚不明朗。

2.1 六大 Ray 库

Ray 由一个小型的 core 加上五个领域库组成。每个库本身都是一个独立开源项目;合在一起,覆盖 AI 工作负载的完整生命周期。

库范围一句话说明
Ray Core tasks、actors、objects、placement groups 分布式运行时:任意函数加一个装饰器即可在任意节点上运行。
Ray Train 分布式模型训练 封装 PyTorch / TensorFlow / HuggingFace Transformers,支持多 GPU、多节点训练,内置 checkpoint。
Ray Serve 模型服务与推理 框架无关的在线推理:带入任何 Python 模型,即可获得请求批处理、自动伸缩、多副本部署。
Ray Tune 超参优化 可扩展的 HPO,支持 Population-Based Training、HyperBand、ASHA,集成 Optuna。
RLlib 强化学习 生产级 RL:IMPALA、PPO、SAC、APPO;支持多智能体与离线 RL。
Ray Data 分布式数据处理 流优先的 Dataset API,用于预处理、ETL 与推理流水线。

2.3 Ray Core API —— Tasks、Actors、Objects

组成每个 Ray 工作负载的三个原语:

Tasks —— 无状态函数

@ray.remote
def f(x):
    return x * x

futures = [f.remote(i) for i in range(8)]
results = ray.get(futures)  # [0, 1, 4, 9, 16, 25, 36, 49]

Task 是工作调度的基本单位。每次 .remote() 调用都会把函数提交给 Ray 调度器选中的 worker 节点。Ray 立即返回一个 ObjectRef;实际工作在远程 worker 上异步执行;ray.get() 阻塞等待结果(也可以接受一个 ObjectRef 列表以批量取回)。

Actors —— 有状态 worker

@ray.remote(num_gpus=1)
class Counter:
    def __init__(self):
        self.n = 0
    def inc(self):
        self.n += 1
        return self.n

c = Counter.remote()
c.inc.remote()  # schedules a method call as a task on the actor

Actor 是 Python 类,其实例存活于单个 worker 上(可能配备 GPU),以顺序(per-actor)或并行(max_concurrency 下)的方式处理方法调用。Ray Serve 的底层就是 Actor:每个 replica 都是一个包裹模型的 Actor。

Objects 与对象存储

从 task/actor 返回的任何值都会被存进分布式对象存储。如果你把一个 ObjectRef 传给另一个 task,Ray 不会序列化对象本身 —— 它传递的是一个引用,消费者从生产者写入的对应对象存储位置取出字节。这种零拷贝模式是 Ray 的标志性特性之一。

2.4 Placement Groups —— 把 Gang Scheduling 做对

pg = ray.util.placement_group(
    [{"GPU": 1}] * 4,
    strategy="STRICT_PACK"
)
ray.get(pg.ready())

@ray.remote(placement_group=pg)
def train_shard(rank):
    ...

# All four train_shard tasks land on the same node
ray.get([train_shard.remote(i) for i in range(4)])

Placement group 是 Ray 作为整体调度的一组资源束。策略:PACK(单节点)、STRICT_PACK(单节点,资源不够则失败)、SPREAD(尽量分散到不同节点)、STRICT_SPREAD(每个 bundle 必须落在不同节点)。这就是 Ray Train 做分布式数据并行训练所用的机制 —— 同一台 H100 上的 8 块 GPU 被协同调度到一起,使 NCCL 建立连接时不必跨节点通信。

2.5 Ray Serve —— 推理基底

Ray Serve 从最初(v0.x,2019 年)的简单 HTTP 前端,演化到完整推理平台(v2.x,2022 年起)。当前架构:

  • Deployment:包裹模型的 Python 类。每个 deployment 拥有 num_replicas、ray_actor_options(GPU、CPU、内存)、max_concurrent_queries、autoscaling_config。
  • Replica:运行 deployment 类的 Actor。Replica 可以独立伸缩。
  • Router:HTTP 前端,负责在 replica 间做负载均衡;支持批处理、流式(SSE)、WebSocket。
  • Graph:通过 ingress 组合多个 deployment;支持 DAG 路由、模型链路。
@serve.deployment(ray_actor_options={"num_gpus": 1})
class Predictor:
    def __init__(self):
        self.model = load_model("...")
    async def __call__(self, request):
        data = await request.json()
        return self.model.predict(data["prompt"])

serve.run(Predictor.bind())

Ray Serve 上的 LLM 服务。开源集成:vLLM VLLMEngine(一个包裹 vLLM PagedAttention 引擎的 Ray Serve deployment)、Text Generation Inference(TGI)、HuggingFace Transformers pipelines、SGLang。Ray Serve 负责编排(replica、自动伸缩、请求路由);具体引擎可插拔。

2.6 Ray Train —— 分布式训练编排器

Ray Train 封装 PyTorch Lightning、HuggingFace Transformers(Accelerate)与 TensorFlow,提供:

  • 分布式启动器:单个 Trainer 跨 N 个 worker 运行;rank 0 是 driver,rank 1..N-1 是 worker。
  • Checkpoint:周期性 checkpoint 写入配置的存储后端(S3、NFS、本地)。
  • 容错:worker 可重启;Trainer 从最近 checkpoint 恢复。
  • 弹性训练:worker 可以随时加入/离开(例如 spot 实例被回收)。

这是 OpenAI 用来扩展 ChatGPT 训练的一层。(Anyscale × OpenAI 博客)

2.7 RLlib —— 生产级强化学习

RLlib 实现了经典算法(PPO、IMPALA、SAC、DQN、APPO、DreamerV3),底层复用同一套 Ray actor / placement-group 机制。每个 rollout worker 都是一个 actor;trainer 则是另一个 actor,负责收集 rollout 并更新策略。IMPALA / APPO 是与大批量分布式 RL 关系最密切的算法 —— 它们采用"中心化 learner + 大量 rollout actor"的模式,这正是 OpenAI Five(Dota 2)与 DeepMind AlphaStar 的同款结构。

2.8 KubeRay —— Ray on Kubernetes

KubeRay 是连接 Ray 与 Kubernetes 的桥梁,由 Anyscale 与 Ray 社区联合贡献。包含两个 operator:

  • RayCluster CRD:Ray 集群(head + worker 组)的声明式 spec;Kubernetes 负责协调实际的节点。
  • RayJob CRD:向运行中的 RayCluster 提交 Ray job;处理生命周期。
  • RayService CRD:长期运行的 Ray Serve deployment(Anyscale Platform 的 BYOC 部署基于它)。

KubeRay 是自托管 Ray 的主流部署方式。(github.com/ray-project/kuberay)

3.2 GCS —— 全局控制存储

GCS 是 Ray 的控制面:一个分片的、类 Redis 的键值存储,负责追踪:

  • 所有 actors:actor ID → 节点 ID、placement group、状态(ALIVE/DEAD/RESTARTING)、函数 spec。
  • 所有 tasks:task ID → 状态、依赖、返回 object ID。
  • 所有 objects:object ID → 位置(哪些 raylet 持有其字节)。
  • 所有 节点:节点 ID → 资源、IP、raylet 心跳。
  • 所有 jobs:job ID → driver、状态。

Ray 2.x 用自定义 C++ 实现(构建在一个名为 Core Workflow 的自定义 actor 框架之上)替代了原本由 Redis 支撑的 GCS,以提高吞吐,并避免 Redis 单点故障。GCS 是 Ray 控制面中最为关键的一环:GCS 故障会让整个集群宕机。

3.3 对象存储 —— Plasma → Arrow Flight

Plasma(Ray 0.x – 2.x)

最初,Ray 使用 Plasma,一个从 Apache Arrow 早期共享内存分配器 fork 而来的内存对象存储。Plasma 以不可变 Arrow buffer 形式把对象放在共享内存中(Linux 上是 /dev/shm);消费者可以通过 mmap 同一批页面而不发生拷贝。

  • 优点:节点内零拷贝;延迟极低。
  • 缺点:仅限 RAM;不持久;跨节点传输走 gRPC,且会序列化 Arrow buffer。

Arrow Flight(Ray 2.20+)

从 Ray 2.20 左右(2024 年)起,团队把跨节点的对象存储协议迁移到了 Arrow Flight,借助标准 Arrow RPC 框架,实现向量化、批量的传输。Plasma 的节点内共享内存路径仍然保留,但跨节点路径改为基于 Arrow Flight over gRPC。

  • 优点:大 tensor 上的吞吐更佳(Arrow 列式格式对 GPU 友好);标准协议;可与外部 Arrow Flight server 集成。
  • 缺点:仍然不持久;大对象(多 GB tensor)仍需仔细流式处理。

来源:Ray 数据传输博客;arrow.apache.org/flight;Ray 2.20.0 发布说明。

3.4 Ray 调度器 —— Gang Scheduling 与 Placement

每个 raylet 运行一个本地调度器;GCS 运行全局调度器。Task placement 分为两阶段:

  1. 本地调度:如果 task 的资源需求能在创建它的节点(本地 raylet)上满足,就在本地运行。
  2. 全局调度:否则,任务被转发到能匹配资源的节点。Ray 默认采用 spread 启发式(集群范围内的 best-fit),再叠加 placement-group 约束。

Gang scheduling 通过 placement groups 实现:把若干 bundle 声明为原子单位。STRICT_PACK 要求所有 bundle 落在同一节点;STRICT_SPREAD 要求每个 bundle 落在不同节点。指定了 placement group 的 task 会被强制放到对应节点。

资源模型。Ray 暴露一小套固定资源:CPU、GPU、内存(字节)、自定义资源(例如"TPU"、"rdma")。每个节点声明自身资源;每个 task/actor 声明自身需求;调度器负责满足。

3.5 Autoscaler

由 Anyscale 维护(且开源)的 autoscaler 监听挂起的 task/actor 需求,相应地增删 worker 节点。可按集群粒度配置:

  • 每种 worker 类型的 min_workers、max_workers。
  • 多种 worker 类型(如 "cpu-small"、"gpu-8xH100"、"gpu-1xA100")。
  • 扩容速度(默认激进,节点启动约 30s)。
  • 空闲超时(默认约 5 分钟)。

在 Kubernetes 上,autoscaler 与 K8s API 对接以创建新 pod(RayCluster CRD)。在 AWS/GCP/Azure 上,Anyscale Platform 与对应云厂的 API 对接。

Ray Serve 的 autoscaler 是一种基于队列的控制器:它观察每个 replica 上 in-flight 请求数,超出 target 时即扩容。Replica 启动通常需要 30–90 秒(把模型加载到 GPU),因此控制器使用扩容阈值以避免尾延迟飙升。

v2.x 中的动态批处理:Serve 可以在一个时间窗(默认 1ms)内收集 N 个请求,把它们作为一个批次分发给一个 replica —— 这是 GPU 推理吞吐的关键。

3.8 分布式推理 —— Ray 上的张量并行 & 流水线并行

Ray Serve 通过 deployment 组合支持模型并行推理:把模型拆分成多个 deployment,每个持有权重的某一片。

对于张量并行(如 Megatron 风格的 transformer 层内切分),Ray Serve 把这部分下放给底层引擎:vLLM 在单个 replica 内部跨 GPU 实现自己的张量并行;DeepSpeed-MII 暴露张量并行端点,可被 Serve deployment 包裹。Ray 的角色是调度多 GPU replica(通过 placement group)以及处理请求路由。

3.9 Ray 集群生命周期

  1. 引导启动:在 head 节点上 ray start --head。GCS 启动;worker 节点上的 raylet 通过 ray start --address=<head> 注册。
  2. 提交 Job:ray job submit --address=... -- python script.py 或从 driver 进程调用 ray.init(address=...)。
  3. 调度:GCS + raylet 根据资源和 placement group 调度 task/actor。
  4. 自动伸缩:集群 autoscaler 根据挂起需求增删节点。
  5. 关闭:在每个节点上执行 ray stop;autoscaler 终止所有 worker。

3.9b Ray Data —— 流优先的 Dataset API

Ray Data(2.0 加入,2.10+ 成熟)取代了 Ray 1.x 中较老的 ray.data.Dataset。它构建于同一套 actor + 对象存储原语之上,但暴露了一个流式、流水线的 API:

import ray

ds = ray.data.read_parquet("s3://bucket/data/*.parquet")
ds = ds.map_batches(preprocess, batch_format="numpy")
ds = ds.map_batches(tokenize, num_gpus=1)
ds.write_parquet("s3://bucket/out/")

关键设计选择:

  • Block 级执行:数据集是 Arrow block 流;操作以流水线方式执行,由固定大小的 worker actor 池执行。
  • GPU-aware map_batches:单个 map_batches 调用即可申请 GPU;operator 把每个 batch 分配给带有一块 GPU 的 worker。
  • 流式消费:iter_batches() 是一个生成器,逐批产出结果 —— 无需把整个数据集物化进内存。

Ray Data 是 Ray Train(加载 → 预处理 → 分片给 trainer)与 Ray Serve(加载 → 预处理 → 批推模型)的推荐 ETL 层。它替代了较老的 Modin + Pandas API。

3.10 为什么这套架构重要

Ray 的设计选择颇为独特,值得单独指出:

  • 单一 Python API 表面:tasks、actors、objects、placement groups 共用 @ray.remote —— 没有 DSL。
  • 零拷贝对象存储:节点内共享内存 mmap,跨节点 Arrow Flight —— 无 pickle-to-bytes 步骤。
  • 无显式集群配置:driver 上调用 ray.init() 后,通过 head address 自动发现 worker;在 K8s 上,KubeRay 连这一步也隐藏掉了。
  • 无强调度保证:调度是尽力而为;spot 实例丢失可能杀死 actor(由 RLlib / Ray Train 的容错机制处理)。

Ray Serve 在其上额外提供的能力

  • 可观测性:内置 dashboard,展示每副本请求延迟、吞吐、错误率。

  • 路由开销:每请求比原生 vLLM 多 ~5–10 ms p50。
  • 冷启动:replica 启动 30–90s(加载模型 + 预热 CUDA),而 vLLM standalone 同样慢,但没有路由需要预热。
  • 运维复杂度:比单进程 vLLM 多出 GCS + raylet + router + replica 等更多组件。

1. Ray: A Distributed Framework for Emerging AI Applications(NSDI'18)

作者:Philipp Moritz、Robert Nishihara、Stephanie Wang、Alexey Tumanov、Richard Liaw、Eric Liang、Melih Elibol、Zongheng Yang、William Paul、Michael I. Jordan、Ion Stoica · arXiv 1712.05889 · NSDI'18

问题陈述

现有分布式系统把 AI 工作负载强行塞进错误的抽象:MapReduce 做批量训练、MPI 做 HPC、Spark 做 ETL、各自定制的 actor 系统做服务。RL 工作负载正好处于训练 + 服务 + 仿真的交叉地带,没有单一框架能完整覆盖。

方案细节

  • 两个原语:无状态 tasks 与有状态 actors,二者都通过单一 API 分布。
  • 动态任务图:每个 task/actor 在运行时可以继续提交 task,从而支持静态 DAG(Spark、Airflow)无法表达的嵌套并行。
  • 分布式调度器:逻辑/物理时钟混合;自底向上调度(子节点先于阻塞的父节点调度)。
  • Plasma 对象存储:基于共享内存,使用 mmap 实现零拷贝;对象不可变。
  • 拓扑感知 placement:基于提示,非强制 —— 应用给出偏好,调度器在条件允许时满足。

基准

Python task 启动开销~1 ms(单节点,Spark 则 ~100 ms)
端到端 RL 训练(IMPALA)线性扩展到约 256 节点,效率 ~80%

2. Ray 2.0 架构(Anyscale 工程博客)

作者:Anyscale 工程团队 · 2022-10-13 · anyscale.com/blog/whats-new-in-ray-2-0

问题陈述

Ray 1.x 积累了技术债:各个 AI 库(Train、Serve、Tune、RLlib)以略有差异的方式构建在 Core 之上;actor API 是有状态的、隐式失败的;Serve v0.x 的前端只是一个薄薄的 Flask 包装。Core 需要被重做,以承载动态、容错、actor 密集型的工作负载。

方案细节

  • 新 Runtime:基于一个 C++ actor 框架("Core Workflow"),支持有状态、可重启、可监控的 actor。Python API 只是这一 C++ core 的薄封装。
  • Ray Serve v2:完全重写。Deployment 成为 GCS 中的一等公民;Replica 是 actor;Ingress 是单独的 router actor。支持基于 DAG 的 deployment 组合。
  • Ray Train:在新 runtime 之上重构。Trainer 是单个 actor,协调 N 个 worker actor;集成 PyTorch Lightning、HuggingFace Transformers、TensorFlow。
  • Ray Data:全新的流式 Dataset API;流水线执行;原生 Arrow 集成。

基准

  • Actor 启动延迟相比 Ray 1.x 减少约 10 倍
  • 高并发服务场景下 Serve 吞吐提升约 5 倍
  • GCS 吞吐提升,足以支撑单集群 10k+ actor

3. Ray 如何设置 Worker —— 生命周期深读(Anyscale 博客)

作者:Eric Liang · 2023-04-18 · anyscale.com/blog/ray-worker-lifecycle

问题陈述

为了调试 Ray 或优化基于 Ray 的系统,你需要理解 worker 进程的生命周期:Python driver 如何成为 worker,actor 运行在哪里,worker 与 raylet 之间是什么关系。

方案细节

  • Driver:调用 ray.init() 的 Python 进程。运行用户脚本;提交 task 和 actor。
  • raylet:每个节点上的 C++ 守护进程;本地调度器 + 对象存储管理器。
  • Worker 进程:由 raylet 按需拉起,用来执行 task/actor 方法。每个 worker 都是独立的 Python 进程;actor 的类实例在同一 worker 中存活整个 actor 生命周期。
  • Dashboard:一个独立的 JavaScript / React 进程,监听 8265 端口;通过 GCS 获取状态。

洞见

Worker 自身存在导入开销(冷启动 Python ~50–200 ms),因此 Ray 会在同一 worker 的多次 task 间缓存导入状态(runtime_env 机制)。

4. RLlib 的生产级分布式 RL(Anyscale 博客)

作者:Sven Mika · 2021-08-04 · anyscale.com/blog/scaling-reinforcement-learning-with-ray-and-rllib

问题陈述

RL 在结构上比监督学习更难扩展:episode 内部的 rollout 是顺序的;learner 在每个梯度步后都需要新的策略权重;探索 vs 利用会带来噪声梯度。

方案细节

  • IMPALA / APPO:中心化 learner 从大量 rollout worker 拉取轨迹;权重更新以异步方式广播回去(V-trace 离策略修正)。
  • Worker 即 Actor:每个 rollout worker 都是一个 actor,运行仿真器(如 Atari 环境、机器人环境);learner 是另一个独立的 actor。
  • Ray placement group:把 learner + GPU worker 紧凑调度在同一台高内存节点;把 rollout actor 分散到大量纯 CPU 节点以最大化仿真并行。

基准

  • ~1000 个 rollout actor、1 个 learner、1 块 GPU;相比单节点基线样本吞吐提升 ~10 倍
  • 被蚂蚁集团用于生产级 RL(论文:Ray + RLlib at Ant Group)

5. Ray Serve LLM 指南:在 Ray 上把 vLLM 落地生产

作者:Anyscale 工程团队 · 2024(持续更新) · docs.ray.io/serve/llm/serving-llms

问题陈述

vLLM 是当前最先进的开源 LLM 服务引擎(PagedAttention、连续批处理)。把 vLLM 跑到生产环境需要自动伸缩、请求路由、多副本部署、可观测性 —— 而这恰好是 Ray Serve 的强项。

方案细节

  • LLMServer Serve deployment:包裹 vLLM 的 LLM 引擎;支持任何 HuggingFace 模型;在单个 replica 内通过 vLLM 自身的 tensor_parallel_size 跨多 GPU 做张量并行。
  • 多 LoRA 服务:单个 replica 可以服务多个 LoRA 适配器;Ray Serve 的请求路由按请求挑选适配器。
  • 基于队列深度的自动伸缩:autoscaling_config.target_num_ongoing_requests_per_replica。
  • 流式响应:SSE;vLLM 的流式输出通过 Serve 的流式响应 API 暴露。

基准

  • Llama-3-70B + TP=4 + H100 上约 10–20k tokens/s/GPU
  • 与 standalone vLLM 服务相当;额外提供多副本 + 自动伸缩 + 可观测性
  • 冷启动:把 70B 模型加载到 8×H100 约 30–60 秒(瓶颈是模型加载,不是 Ray)

来源:Ray Serve LLM 指南;vLLM v0.2。

5.2 Ray 的独特优势

  1. 开源社区与贡献者基础。Ray 在 GitHub 上有 1,200+ 贡献者、30k+ stars、每年一度的 Ray Summit(1,500+ 与会者),已被十大科技公司中的 6 家采用。
  2. 跨 AI 生命周期的全覆盖:训练、服务、调参、RL、数据预处理 —— 共享同一运行时,共享同一套原语(actors、objects)。
  3. 零拷贝数据共享:Plasma / Arrow-Flight 对象存储使得模型、tensor、dataframe 在 task 间传递时无需额外序列化。
  4. 通过 KubeRay 原生集成 Kubernetes:同一份 Ray 代码可以在笔记本上、1000 节点集群上或托管 K8s 部署上运行。
  5. Spark 谱系背书:创始团队有构建分布式系统的经验;工程文化成熟。

5.3 Ray 的独特短板

  1. DX 不如 Modal 平滑:你仍然需要关心集群、placement group、runtime env。Modal 把这些全部隐藏。
  2. 服务侧冷启动差:Ray Serve 的冷启动(70B 模型 30–60s)远慢于 Modal 的 checkpoint snapshot 方式。Modal 直接以此为卖点。
  3. GCS 是单点:GCS 故障导致集群宕机。KubeRay + 冗余 raylet 可缓解,但无法根除。
  4. Anyscale Endpoints 的失败:证明托管 API 业务难做。Anyscale 现在的对手是超大规模云厂平台(AWS、GCP、Azure),而不是直接对标 OpenAI。
  5. 文档质量参差:Ray 库很多,每个库都有自己的文档;质量参差不齐。KubeRay 文档尤其落后于 Anyscale 产品文档。

6.5 战略判断

Ray 是除 Spark 之外最重要的 AI 开源分布式计算框架。Anyscale 是其天然的商业化托管者。Endpoints 关停是结构性纠偏,不是失败 —— Anyscale 现在处于以下几波浪潮的有利位置:

  1. 企业 AI:大企业希望在自己的云上自托管 LLM;Anyscale Private Endpoints 是对的产品。
  2. 基础模型训练:OpenAI 等持续把 Ray 用于 RLHF 与预训练的横向扩展。
  3. 规模化 RL:ChatGPT 之后的 RL 微调浪潮(RLHF、RLAIF、DPO)全部基于 Ray。
  4. 多云 AI:企业希望避免 AWS/GCP 锁定;Anyscale 是真正多云的。

风险:如果 Modal 补齐 Ray 类原语的速度,快于 Anyscale 补齐 Modal 式 DX 的速度,AI 基础设施的重心可能迁移。Anyscale 的防守之策是押注开源社区(Modal 没有)和企业自托管(Modal 也不提供)。
