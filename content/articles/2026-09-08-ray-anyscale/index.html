Executive Summary

Executive Summary — Ray + Anyscale: From a Berkeley Research Project to the Substrate of Modern AI

Ray is an open-source distributed compute framework created in 2017 at UC Berkeley's RISELab by Robert Nishihara, Philipp Moritz, Ion Stoica et al. (arXiv 1712.05889, published at NSDI'18). It supplies a single Python API for tasks, actors, placement groups, and a distributed object store — a unified substrate that the same lab subsequently split into Ray Train (distributed training), Ray Serve (model serving), Ray Tune (hyperparameter search), and RLlib (reinforcement learning).

Anyscale is the company commercialising Ray. Founded in 2019 by Ion Stoica (UC Berkeley professor, Databricks and Apache Spark co-founder), Robert Nishihara (first author of the Ray paper), Philipp Moritz and a small group of RISELab alumni. The company operates the Anyscale Platform (managed Ray-as-a-service), Anyscale Workspaces (browser IDE + notebooks), and — until March 2024 — Anyscale Endpoints (hosted LLM inference API, a vLLM-style service competing with OpenAI/Anthropic direct APIs).

⚠ Pivot signal. On 2024-03-05 Anyscale publicly announced the deprecation of Anyscale Endpoints and redirected all inference traffic to anyscale.com-branded routes powered by the open-source Ray Serve + vLLM stack. The hosted LLM API business is effectively dead; Anyscale is now a platform/managed-Ray company with revenue from compute, enterprise support and platform fees. (anyscale.com/blog/anyscale-endpoints-deprecation-notice)

Why this brief matters. Ray is the dominant open-source distributed-compute substrate for AI outside the hyperscalers' internal stacks. OpenAI has used Ray to orchestrate ChatGPT training (anyscale.com/blog/anyscale-platform-supports-openai); Uber uses Ray for demand forecasting and freight pricing; Shopify runs its recommender on Ray; Pinterest uses Ray for content moderation and ads CTR; Ant Group, ByteDance, and JPMorgan Chase all run large Ray fleets. The paper has 4,000+ citations (Google Scholar), and the GitHub repo sits above 30k stars.

Why This Research Brief Is Worth Reading

  1. Ray is not a framework — it's a distributed OS. Tasks, actors, the Plasma/Arrow object store, the GCS control plane, and the placement-group scheduler form a coherent runtime, not a library. Treating it as "just Python decorators" misses the depth.
  2. The Plasma → Arrow-Flight migration (Ray 2.x) is the most consequential architectural change since 2018 and is barely documented in third-party blogs.
  3. Anyscale's Endpoints shutdown is the canonical "build vs sell" case study for AI infrastructure companies: building a hosted-API product directly competitive with OpenAI/Anthropic on a thin margin while the hyperscalers drop prices every quarter is structurally unwinnable. Anyscale's pivot to platform is the right one.
  4. Ray's positioning vs Modal / E2B / RunPod / Baseten is one of the most important strategic questions in 2026 AI infra: Ray is the "JVM of distributed compute," Modal is the "Python-of-the-cloud," and the future mix is unclear.

2.3 Ray Core APIs — Tasks, Actors, Objects

The three primitives that compose every Ray workload:

Tasks — stateless functions

@ray.remote
def f(x):
    return x * x

futures = [f.remote(i) for i in range(8)]
results = ray.get(futures)  # [0, 1, 4, 9, 16, 25, 36, 49]

Tasks are the unit of work scheduling. Each .remote() call submits a function to a worker node picked by the Ray scheduler. Ray returns an ObjectRef immediately; the work happens asynchronously on a remote worker; ray.get() blocks on the result (or accepts a list of ObjectRefs for batch retrieval).

Actors — stateful workers

@ray.remote(num_gpus=1)
class Counter:
    def __init__(self):
        self.n = 0
    def inc(self):
        self.n += 1
        return self.n

c = Counter.remote()
c.inc.remote()  # schedules a method call as a task on the actor

Actors are Python classes whose instances live on a single worker (possibly with GPU resources) and process method calls one at a time (per-actor) or in parallel (with max_concurrency). Ray Serve uses Actors under the hood: each replica is an Actor wrapping a model.

Objects and the Object Store

Any value returned from a task/actor is stored in the distributed object store. If you pass an ObjectRef to another task, Ray does not serialise the object — it passes a reference and the consumer fetches the bytes from the object store where the producer put them. This zero-copy pattern is one of Ray's defining features.

2.4 Placement Groups — Gang Scheduling Done Right

pg = ray.util.placement_group(
    [{"GPU": 1}] * 4,
    strategy="STRICT_PACK"
)
ray.get(pg.ready())

@ray.remote(placement_group=pg)
def train_shard(rank):
    ...

# All four train_shard tasks land on the same node
ray.get([train_shard.remote(i) for i in range(4)])

Placement groups are bundles of resources that Ray schedules as a unit. Strategies: PACK (single node), STRICT_PACK (single node, fail if not all fit), SPREAD (different nodes), STRICT_SPREAD. This is the mechanism Ray Train uses for distributed data parallel training — all 8 GPUs on a single H100 box get co-scheduled, so the NCCL setup avoids cross-node traffic.

2.5 Ray Serve — the Inference Substrate

Ray Serve evolved from a simple HTTP frontend (v0.x, 2019) into a full inference platform (v2.x, 2022+). The current architecture:

  • Deployment: a Python class wrapping a model. Each deployment has num_replicas, ray_actor_options (GPU, CPU, memory), max_concurrent_queries, autoscaling_config.
  • Replica: an Actor running the deployment class. Replicas can scale up/down independently.
  • Router: HTTP frontend that load-balances requests across replicas; supports batching, streaming (SSE), WebSockets.
  • Graph: multiple deployments composed via ingress; supports DAG routing, model chaining.
@serve.deployment(ray_actor_options={"num_gpus": 1})
class Predictor:
    def __init__(self):
        self.model = load_model("...")
    async def __call__(self, request):
        data = await request.json()
        return self.model.predict(data["prompt"])

serve.run(Predictor.bind())

LLM serving on Ray Serve. Open-source integrations: vLLM VLLMEngine (a Ray Serve deployment wrapping vLLM's PagedAttention engine), Text Generation Inference (TGI), HuggingFace Transformers pipelines, SGLang. Ray Serve's role is the orchestration layer (replicas, autoscaling, request routing); the engine is pluggable.

2.6 Ray Train — Distributed Training Orchestrator

Ray Train wraps PyTorch Lightning, HuggingFace Transformers (Accelerate), and TensorFlow to give:

  • Distributed launcher: a single Trainer runs across N workers; rank 0 is the driver, ranks 1..N-1 are workers.
  • Checkpointing: periodic checkpoints to a configured storage backend (S3, NFS, local).
  • Fault tolerance: workers can be restarted; the trainer resumes from the last checkpoint.
  • Elastic training: workers can join/leave (e.g., on spot-instance preemption).

This is the layer OpenAI used to scale ChatGPT training. (Anyscale × OpenAI blog)

2.7 RLlib — Production Reinforcement Learning

RLlib implements the canonical algorithms (PPO, IMPALA, SAC, DQN, APPO, DreamerV3) with the same Ray actor / placement-group machinery underneath. Each rollout worker is an actor; the trainer is a separate actor collecting rollouts and updating the policy. IMPALA / APPO are the production-relevant algorithms for large-batch distributed RL — they use a centralised learner and many rollout actors, the exact pattern that produced OpenAI Five (Dota 2) and DeepMind's AlphaStar.

2.8 KubeRay — Ray on Kubernetes

KubeRay is the Ray/Kubernetes bridge, contributed jointly by Anyscale and the Ray community. Two operators:

  • RayCluster CRD: declarative spec for a Ray cluster (head + worker groups); Kubernetes reconciles the actual nodes.
  • RayJob CRD: submit a Ray job to a running RayCluster; handles lifecycle.
  • RayService CRD: long-running Ray Serve deployments (used by Anyscale Platform for BYOC deployments).

KubeRay is the dominant deployment mechanism for self-hosted Ray. (github.com/ray-project/kuberay)

2.9 Anyscale Workspaces — The IDE for Ray

Head node: hosts the GCS (global control store), the autoscaler, the dashboard on port 8265, and the Ray Client entrypoint. For production clusters the head is a separate VM (often 4–8 vCPU, 16–32 GB RAM, no GPU).

Worker nodes: each runs a raylet process (local scheduler) plus a slice of the distributed object store. Workers come and go as the autoscaler decides.

3.2 GCS — The Global Control Store

The GCS is Ray's control plane: a sharded Redis-like key-value store that tracks:

  • All actors: actor ID → node ID, placement group, state (ALIVE/DEAD/RESTARTING), function spec.
  • All tasks: task ID → state, dependencies, return object ID.
  • All objects: object ID → locations (which raylets hold the bytes).
  • All nodes: node ID → resources, IP, raylet heartbeat.
  • All jobs: job ID → driver, status.

Ray 2.x replaced the original Redis-backed GCS with a custom C++ implementation (built on top of a custom actor framework called Core Workflow) for throughput and to avoid Redis-as-a-SPOF. The GCS is the single most critical piece of Ray's control plane: a GCS failure takes the cluster down.

3.3 Object Store — Plasma → Arrow Flight

Plasma (Ray 0.x – 2.x)

Originally, Ray used Plasma, an in-memory object store forked from Apache Arrow's early shared-memory allocator. Plasma stored objects as immutable Arrow buffers in shared memory (/dev/shm on Linux); consumers could mmap the same pages without copying.

  • Pros: zero-copy within a node; very low latency.
  • Cons: limited to RAM; not durable; cross-node transfer was via gRPC and serialised the Arrow buffer.

Arrow Flight (Ray 2.20+)

Starting around Ray 2.20 (2024), the team migrated the cross-node object-store protocol to Arrow Flight, leveraging the standard Arrow RPC framework for vectorised, batched transfers. The Plasma intra-node shared-memory path remains, but inter-node now goes over Arrow Flight over gRPC.

  • Pros: better throughput on large tensors (Arrow's columnar format is GPU-friendly); standard protocol; can integrate with external Arrow Flight servers.
  • Cons: still no durability; large objects (multi-GB tensors) still need careful streaming.

Sources: Data transfer in Ray blog; arrow.apache.org/flight; Ray 2.20.0 release notes.

3.4 Ray Scheduler — Gang Scheduling and Placement

Each raylet runs a local scheduler; the GCS runs the global scheduler. Task placement proceeds in two phases:

  1. Local scheduling: if the task's resource requirements can be satisfied on the node that created it (the local raylet), the task runs there.
  2. Global scheduling: otherwise, the task is forwarded to a node that can satisfy the requirements. Ray uses a spread-by-default heuristic (best-fit across the cluster) modified by placement-group constraints.

Gang scheduling is implemented via placement groups: bundles of resources declared as atomic. STRICT_PACK requires all bundles on a single node; STRICT_SPREAD requires each bundle on a different node. Tasks specifying the placement group are then forced onto the right node.

Resource model. Ray exposes a small, fixed set of resources: CPU, GPU, memory (bytes), custom resources (e.g., "TPU", "rdma"). Each node declares its resources; each task/actor declares its requirements; the scheduler satisfies them.

3.5 Autoscaler

The Anyscale-maintained (and open-source) autoscaler watches pending task/actor demand and adds/removes worker nodes to meet it. Configurable per-cluster:

  • min_workers, max_workers per worker type.
  • Multiple worker types (e.g., "cpu-small", "gpu-8xH100", "gpu-1xA100").
  • Upscaling speed (default: aggressive, ~30s to bring up a node).
  • Idle timeout (default ~5 min).

On Kubernetes, the autoscaler talks to the K8s API to provision new pods (RayCluster CRD). On AWS/GCP/Azure, the Anyscale Platform talks to the cloud-provider APIs.

Ray Serve's autoscaler is a queue-based controller: it watches the number of in-flight requests per replica and scales up when the target is exceeded. Replica startup typically takes 30–90 seconds (load model into GPU), so the controller uses a scale-up threshold to avoid tail-latency spikes.

Dynamic batching in v2.x: Serve can collect N requests arriving within a window (default 1ms) and dispatch them as a single batch to a replica — essential for GPU inference throughput.

3.8 Distributed Inference — Tensor & Pipeline Parallelism on Ray

Ray Serve supports model-parallel inference via deployment composition: split a model into multiple deployments, each holding a slice of the weights.

@serve.deployment(name="encoder", ray_actor_options={"num_gpus": 1})
class Encoder: ...

@serve.deployment(name="decoder", ray_actor_options={"num_gpus": 1})
class Decoder: ...

# Pipeline: encoder → decoder
graph = Encoder.bind().to(Decoder.bind())
serve.run(graph)

For tensor parallelism (e.g., Megatron-style split within a transformer layer), Ray Serve delegates to the underlying engine: vLLM uses its own tensor-parallel implementation across GPUs in a single replica; DeepSpeed-MII exposes tensor-parallel endpoints that can be wrapped in a Serve deployment. Ray's role is to schedule the multi-GPU replica (via placement groups) and to handle the request routing.

3.9 Ray Cluster Lifecycle

  1. Bootstrap: ray start --head on the head node. GCS comes up; raylets on worker nodes ray start --address=<head> register.
  2. Job submit: ray job submit --address=... -- python script.py or ray.init(address=...) from a driver process.
  3. Scheduling: GCS + raylets place tasks/actors according to resources and placement groups.
  4. Autoscaling: cluster autoscaler adds/removes nodes based on pending demand.
  5. Shutdown: ray stop on each node; autoscaler terminates all workers.

3.9b Ray Data — Streaming-First Dataset API

Ray Data (added in 2.0, matured in 2.10+) is the replacement for the older ray.data.Dataset from Ray 1.x. It is built around the same actor + object-store primitives but exposes a streaming, pipelined API:

import ray

ds = ray.data.read_parquet("s3://bucket/data/*.parquet")
ds = ds.map_batches(preprocess, batch_format="numpy")
ds = ds.map_batches(tokenize, num_gpus=1)
ds.write_parquet("s3://bucket/out/")

Key design choices:

  • Block-level execution: a dataset is a stream of Arrow blocks; operations are pipelined and executed by a fixed-size pool of worker actors.
  • GPU-aware map_batches: a single map_batches call can request GPUs; the operator allocates each batch to one worker with one GPU.
  • Streaming consumption: iter_batches() is a generator that yields batches as they're produced — no need to materialise the entire dataset.

Ray Data is the recommended ETL layer for Ray Train (load → preprocess → shard to trainers) and Ray Serve (load → preprocess → batch to model). It replaced the older Modin + Pandas API.

3.10 Why the Architecture Matters

Ray's design choices are unusual and worth flagging:

  • Single Python API surface: tasks, actors, objects, placement groups all share @ray.remote — no DSL.
  • Zero-copy object store: shared-memory mmap within a node, Arrow Flight cross-node — no pickle-to-bytes step.
  • No explicit cluster config: ray.init() on the driver auto-discovers workers via the head address; K8s deployment hides even that via KubeRay.
  • No strong scheduler guarantees: scheduling is best-effort; spot-instance loss can kill actors (handled by RLlib / Ray Train's fault tolerance).

What Ray Serve Adds On Top

  • Multi-replica autoscaling: scale from 1 to N replicas based on queue depth — not available in vLLM standalone.
  • Multi-model routing: one Serve application can host dozens of model deployments; requests routed by URL path.
  • Compositions: encoder → decoder, LoRA → base model, retrieval → generation — all DAGs of deployments.
  • Observability: built-in dashboard with request latencies, throughput, error rates per replica.
  • BYOC + multi-cloud: same code runs on AWS, GCP, Azure, on-prem.

The Trade-off Ray Serve Pays

  • Router overhead: ~5–10 ms p50 added per request vs raw vLLM.
  • Cold start: replica boot is ~30–90s (load model + warm CUDA) vs vLLM standalone which is also slow but doesn't have a router to warm.
  • Operational complexity: more moving parts (GCS + raylets + router + replicas) than a single-process vLLM.

5 Hardcore Ray / Anyscale Engineering Blog Deep-Dives

This chapter dissects five of the most technically substantial Ray/Anyscale engineering posts. The pattern: Problem → Solution → Benchmark → Source.

1. Ray: A Distributed Framework for Emerging AI Applications (NSDI'18)

Authors: Philipp Moritz, Robert Nishihara, Stephanie Wang, Alexey Tumanov, Richard Liaw, Eric Liang, Melih Elibol, Zongheng Yang, William Paul, Michael I. Jordan, Ion Stoica · arXiv 1712.05889 · NSDI'18

Problem Statement

Existing distributed systems force AI workloads into the wrong abstractions: MapReduce for batch training, MPI for HPC, Spark for ETL, bespoke actor systems for serving. RL workloads sit at the intersection of training + serving + simulation, none of which any single framework handles well.

Solution Details

  • Two primitives: stateless tasks and stateful actors, both distributed via a single API.
  • Dynamic task graphs: each task/actor can submit more tasks at runtime, enabling nested parallelism that static DAGs (Spark, Airflow) cannot express.
  • Distributed scheduler: hybrid logical/physical clock; bottom-up scheduling (children scheduled before parents block).
  • Plasma object store: shared-memory-backed store with mmap for zero-copy; immutable objects.
  • Topology-aware placement: hint-based, not mandatory — application specifies preferences, scheduler satisfies if possible.

Benchmarks

Python task launch overhead~1 ms (single node, vs ~100 ms for Spark)
End-to-end RL training (IMPALA)Linear scaling to ~256 nodes, ~80% efficiency
Hyperparameter search (Ray Tune, Asynchronous HyperBand)Linear scaling vs single-node baseline

Source: NSDI'18 PDF; arXiv 1712.05889.

2. Ray 2.0 Architecture (Anyscale Engineering Blog)

Authors: Anyscale engineering · 2022-10-13 · anyscale.com/blog/whats-new-in-ray-2-0

Problem Statement

Ray 1.x had accumulated technical debt: the AI libraries (Train, Serve, Tune, RLlib) were built on top of the Core in slightly different ways; the actor API was stateful with implicit failures; the Serve v0.x frontend was a thin Flask wrapper. The Core needed re-platforming to support dynamic, fault-tolerant, actor-rich workloads at scale.

Solution Details

  • New Runtime: built around a C++ actor framework ("Core Workflow") that supports stateful, restartable, monitorable actors. The Python API is a thin wrapper over this C++ core.
  • Ray Serve v2: completely rewritten. Deployments are first-class entities in the GCS; replicas are actors; ingress is a separate router actor. DAG-based composition of deployments.
  • Ray Train: re-platformed on top of the new runtime. Trainer is a single actor coordinating N worker actors; integration with PyTorch Lightning, HuggingFace Transformers, TensorFlow.
  • Ray Data: new streaming dataset API; pipelined execution; native Arrow integration.

Benchmarks

  • Actor startup latency reduced ~10× vs Ray 1.x
  • Serve throughput improved ~5× for high-concurrency serving workloads
  • GCS throughput improved enough to support 10k+ actors per cluster

3. How Ray Sets Up a Worker — Lifecycle Deep-Dive (Anyscale Blog)

Author: Eric Liang · 2023-04-18 · anyscale.com/blog/ray-worker-lifecycle

Problem Statement

To debug Ray or optimise Ray-based systems, you need to understand the worker process lifecycle: how does a Python driver turn into a worker, where do actors run, what is the relationship between workers and the raylet.

Solution Details

  • Driver: the Python process that calls ray.init(). Runs the user script; submits tasks and actors.
  • raylet: a C++ daemon on every node; local scheduler + object-store manager.
  • Worker processes: spawned on demand by the raylet to execute tasks/actor methods. Each worker is a separate Python process; the actor's class instance lives in one worker for the actor's lifetime.
  • Dashboard: a separate JavaScript / React process on port 8265; talks to GCS for state.

Insights

Workers have their own import overhead (cold Python startup ~50–200 ms), which is why Ray caches import state across tasks within the same worker (the runtime_env mechanism).

4. RLlib's Production-Grade Distributed RL (Anyscale Blog)

Author: Sven Mika · 2021-08-04 · anyscale.com/blog/scaling-reinforcement-learning-with-ray-and-rllib

Problem Statement

RL is structurally harder to scale than supervised learning: rollouts are sequential within an episode, learners need fresh policy weights after every gradient step, and exploration vs exploitation introduces noisy gradients.

Solution Details

  • IMPALA / APPO: a centralised learner pulls trajectories from many rollout workers; weight updates are broadcast back asynchronously (V-trace off-policy correction).
  • Workers as Actors: each rollout worker is an actor running the simulator (e.g., Atari env, robotics env); the learner is a separate actor.
  • Ray's placement groups: pack the learner + GPU workers on a single high-memory node; spread rollout actors across many CPU-only nodes for simulator parallelism.

Benchmarks

  • ~1000 rollout actors, 1 learner, 1 GPU; ~10× sample throughput vs single-node baseline
  • Used by Ant Group for production-scale RL (paper: Ray + RLlib at Ant Group)

5. Ray Serve LLM Guide: Productionising vLLM on Ray

Author: Anyscale engineering · 2024 (continuously updated) · docs.ray.io/serve/llm/serving-llms

Problem Statement

vLLM is the state-of-the-art open-source LLM serving engine (PagedAttention, continuous batching). Running vLLM in production requires autoscaling, request routing, multi-replica deployment, observability. These are exactly Ray Serve's strengths.

Solution Details

  • LLMServer Serve deployment: wraps vLLM's LLM engine; supports any HuggingFace model; tensor-parallel across multiple GPUs in a single replica via vLLM's own tensor_parallel_size.
  • Multi-LoRA serving: a single replica can serve multiple LoRA adapters; Ray Serve's request routing picks the right adapter per request.
  • Autoscaling on queue depth: autoscaling_config.target_num_ongoing_requests_per_replica.
  • Streaming responses: SSE; vLLM's streaming output is exposed via Serve's streaming response API.

Benchmarks

  • ~10–20k tokens/s/GPU on Llama-3-70B with TP=4 on H100
  • Comparable to standalone vLLM serving; adds multi-replica + autoscaling + observability
  • Cold start: ~30–60s to load a 70B model on 8× H100 (limited by model load time, not Ray)

Source: Ray Serve LLM guide; vLLM v0.2.

5.2 Ray's Distinct Strengths

  1. The open-source community and contributor base. Ray has 1,200+ contributors on GitHub, 30k+ stars, an annual Ray Summit conference (1,500+ attendees), and adoption at 6 of the top 10 tech companies.
  2. Cross-cutting AI lifecycle coverage: training, serving, tuning, RL, data preprocessing — all on the same runtime, with shared primitives (actors, objects).
  3. Zero-copy data sharing: the Plasma / Arrow-Flight object store means no extra serialization when models, tensors, or dataframes pass between tasks.
  4. Native Kubernetes integration via KubeRay: same Ray code runs on a single laptop, a 1000-node cluster, or a managed Kubernetes deployment.
  5. Backed by the Spark lineage: the founding team has built distributed systems before; the engineering culture is mature.

5.3 Ray's Distinct Weaknesses

  1. DX is not as streamlined as Modal: you still need to think about clusters, placement groups, runtime envs. Modal hides all of this.
  2. Cold start for serving is poor: Ray Serve cold-start (30–60s for a 70B model) is much slower than Modal's checkpointed snapshot approach. Modal explicitly markets against this.
  3. GCS is a SPOF: GCS failure takes the cluster down. KubeRay + redundant raylets mitigate but don't eliminate this.
  4. Anyscale Endpoints failure: proves the hosted-API business is hard. Anyscale is now competing with hyperscaler cloud platforms (AWS, GCP, Azure) — not directly with OpenAI.
  5. Documentation is uneven: Ray has many libraries; each has its own docs; the quality varies. The KubeRay docs in particular lag behind the Anyscale product docs.
