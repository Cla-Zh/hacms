0. AI Agent 沙箱 + 沙箱编排 — 范式跃迁

0.1 从「容器云原生」到「沙箱云原生」的根本性转移

过去十年云计算的工作负载范式是「微服务 + 长生命周期容器 + K8s 编排」。2025-2026 年 AI Agent 浪潮正打破这个范式:

维度 传统微服务容器 (Docker/K8s) AI Agent 沙箱
生命周期 长周期(数小时-数天) 秒级/亚秒级(单次工具调用)
冷启动 5-60s(镜像拉取+启动) <125ms(Firecracker SnapStart)
并发密度 单机 10-100 Pod 单机 1000+ microVM
状态模型 无状态为主(Stateless) 树状分支有状态(MCTS Rollout)
执行模式 同步请求-响应 异步、分叉、循环、Suspend/Resume
隔离强度 Namespace/cgroup(共享内核) MicroVM(独立内核) / WASM(强沙箱)
可观测性 日志 + Metrics + Trace 加 LLM 推理 trace + Tool call tree

0.2 沙箱与沙箱编排的关系(为什么两者必须协同)

沙箱解决的是「安全边界 + 资源占用」:

  • MicroVM: 强隔离,启动 ~125ms(Firecracker v1.17),单 guest <5MiB
  • WASM: 弱隔离但毫秒级,Wasmtime v48 启动 <90μs(Dandelion/CHERI)
  • 进程级: 中等隔离,gVisor 拦截 syscalls

沙箱编排解决的是「高频派生 + 树状分支」:

  • MCTS 树探索: 1000 个子环境在 718ms 内派生(Sandlock)
  • RL rollout: 1000 个 rollout worker 并发,RL-aware scheduler
  • Checkpoint/Resume: 树状分支暂停 / 恢复,内存不爆(CRIU + SnapStart)

核心张力:

  • 沙箱越强隔离 → 启动越慢 → 不适合高频 fork
  • 沙箱越快启动 → 隔离越弱 → 不适合不可信代码
  • 解决路径: 快照(Snapshot) + 派生(Fork) + CoW(零拷贝) 三件套

0.3 2026 H2 沙箱产业的五个非共识假设

H1:沙箱与沙箱编排会分裂成两条独立产业链

  • 沙箱产业链: Firecracker / Cloud Hypervisor / gVisor / Wasmtime / StratoVirt / Kuasar(纯运行时优化)
  • 沙箱编排产业链: Modal Snapshots / E2B Firecracker 自研调度 / forkd / Sandlock / Dandelion(纯调度优化)
  • 两者不直接竞争,而是上下游关系 — 但开源项目会同时做两边(Kuasar 同时管运行时 + 多 runtime 调度)

H2:脱离 K8s 的「自研调度器」会成为 SaaS 沙箱主流

  • Modal / E2B / Fly.io / Vercel Sandbox / Cloudflare Sandbox 全部自研调度器
  • 原因: K8s 默认调度 234 pods/s vs Modal 自研 1.05s 启动 import torch(差距 100×+)
  • 即使 K8s 1.34 引入 sandbox-runtime(2025-08 SIG Apps 起),也无法在编排层追上自研调度器

H3:开源 MicroVM 的「商业化」会发生剧烈分化

  • Firecracker: AWS Lambda 锁定 + Fly.io / Modal / E2B 集成(无明显商业化)
  • Cloud Hypervisor: Intel 主导 + StratoVirt 后端(开源中立)
  • gVisor: Google Cloud Run 锁定(开源但商业路径明确)
  • 结论:没有商业化的 MicroVM 会被锁定到某一家云厂商

H4:RL Rollout 会催生「RL-aware scheduler」新赛道

  • OpenRLHF / verl / TRL 的 tree rollout 与 K8s 默认调度器特性不兼容
  • Sandlock / Zeroboot / Dandelion 都是为了这个场景专门设计
  • 未来 3 年会出现「RL-aware scheduler」专属赛道

H5:中国沙箱会走「双轨」路线(轻量 + 自研)

  • 字节 Kuasar: StratoVirt 后端(开源路线,CNCF Sandbox)
  • 阿里袋鼠: 自研 MicroVM + 函数计算 FC(闭源路线,商业化)
  • 腾讯 CubeSandbox: 60ms 冷启动,2026-04 开源(技术跟随 + 性能领先)
  • 华为 StratoVirt: Kuasar 后端(开源主导)
  • 蚂蚁 Mosdic / 火山 Agent Sandbox: 公开资料不足(待读者核实)

全文结论与展望

1. 终局预判(2027-2028)

  1. 沙箱终局: MicroVM + WASM 混合 — Firecracker 内部跑 WASM runtime,既保留 microVM 强隔离又享 WASM 毫秒级启动
  2. 编排终局: 自研调度器分裂 — Modal/E2B/Fly.io/Vercel 各守一方,K8s 在 AI Agent 沙箱编排市占 <20%
  3. RL-aware scheduler 分化 — Sandlock / Zeroboot / Dandelion 演化出独立赛道
  4. 开源 vs 闭源双轨 — Firecracker / gVisor / Wasmtime 仍是开源事实标准,但商业自研调度器会形成 5-10 家独角兽

2. 风险与反向证伪

  • 若 Firecracker 出现严重逃逸 CVE → 微内核路线重新评估,QEMU / crosvm 受益
  • 若 Anthropic / OpenAI 推出"纯端侧 Agent"(on-device) → 整个云原生执行环境栈需求需求腰斩
  • 若 Sandlock / forkd 等开源调度器被 Modal / E2B 收购 → 开源路线分化风险

3. 给中国本土的启示

  • 阿里袋鼠: 国内市占第一,但闭源路线,需警惕 AWS Lambda 式锁定

1.1 MicroVM 路线(重点展开)

MicroVM 是当前 AI Agent 沙箱的事实标准,核心思路是用专用 VMM(Virtual Machine Monitor)替代 QEMU/VMware 等通用 hypervisor,只保留云工作负载必须的最小设备集(virtio-net、virtio-blk、virtio-console、virtio-rng),通过 KVM 在 Linux 内核态虚拟化基础上提供 guest kernel 隔离。冷启动 60-300 ms,内存基线 < 50 MB,同时保留 VM 的安全性与 Linux syscall 兼容性。

MicroVM 与传统 VM 的核心区别:

  1. 设备集裁剪:传统 QEMU 默认支持数百种设备(USB/PCI/声卡/光盘等),MicroVM 只保留 4-6 类 virtio 设备,降低 I/O 攻击面
  2. 无 BIOS / 直接 PVH 启动:绕过 UEFI / BIOS,直接以 PVH(Paravirtualized Hypervisor)入口进入 guest kernel
  3. guest kernel 与 rootfs 镜像管理分离:AWS Lambda 把 guest kernel 维护在 host 端,sandbox API 只接受 rootfs 镜像
  4. API 化:Firecracker 提供 RESTful API(socket),所有 VM 生命周期通过 HTTP 请求驱动
  5. 与 OCI / containerd 集成:通过 firecracker-containerd、containerd-shim-kata-v2 等 shim 进入云原生生态

1.2.1 gVisor(Google,应用内核代表)

gVisor 是 Google 在 2018 年开源的「用户态应用内核」沙箱,核心设计哲学与 Firecracker / Kata 截然不同:不启动 guest kernel,而是用 Go 重写一个 Linux-like syscall 接口,在用户态拦截并执行所有 syscall。这一设计牺牲了部分 syscall 兼容性(70-80%),换取了:

  1. 零 guest kernel 启动开销(无需加载 guest kernel + init),冷启动 <100 ms
  2. 攻击面收窄:guest 看不到真实 Linux kernel,即使 syscall 被实现错也只是 panics,host kernel 仍隔离在外
  3. 更小的镜像(无 guest kernel,rootfs 直接以用户态文件访问)
  4. 与 OCI 完全兼容:runsc 是 OCI runtime spec 实现,与 Docker / Kubernetes / containerd 零摩擦集成

项目状态

  • 仓库:https://github.com/google/gvisor(Apache-2.0)
  • 当前最新:20260831.0 release(2026-09-04 发布);前序 20260824.0(2026-08-27)
  • 累计 377+ 个 release,约每周发布
  • Stars:19.2K(releasealert.dev 2026-09)
  • 来源:https://github.com/google/gvisor、https://releasealert.dev/github/google/gvisor

核心架构

  • 用户态应用内核:用 Go 重写 Linux-like syscall 接口
  • 不复用 host kernel,而是拦截 syscall(走 ptrace 或 KVM)在自己的 Sentry 中实现
  • 子组件:Sentry(应用内核,最大组件)+ Gofer(文件系统访问,每容器一个独立 Gofer 进程)
  • 提供 OCI runtime runsc,与 Docker / Kubernetes / containerd 无缝集成
  • 性能权衡:启动快(<100 ms)、内存占用低,但 syscalls 兼容性 ~70-80%,部分 IO/网络性能劣于原生
  • 生产使用:Google Cloud Run、Anthropic Claude Code Web sandbox(2026-08 自托管公测)、Modal Sandboxes

真实案例

  • Modal Sandboxes:AI Agent 代码执行平台,gVisor 隔离,Python-first,GPU 加速 ML workload——https://modal.com/blog
  • Google Cloud Run:托管容器执行环境底层是 gVisor
  • Anthropic Claude Code on the Web:每个 session 在 Anthropic 管理的 VM 中运行,网络代理强制 default allowlist——https://code.claude.com/docs/en/sandbox-environments
  • Northflank:提供 gVisor-based 沙箱选型

1.3.2 Wasmtime(Bytecode Alliance Core Project)

Wasmtime 是 Bytecode Alliance 在 2019 年开源的 WebAssembly 运行时,2025-04-30 升格为 Bytecode Alliance 首个 Core Project(与 WAMR、WASI、Component Model 并列,但 Wasmtime 是第一个升到 Core)。它既可作为 CLI 工具运行 .wasm 文件,也是 Spin / wasmCloud / WasmEdge / Cosmonic Control 的底层引擎。其设计哲学是「生产级 WASM 运行时 + 标准合规 + 内存安全」,代码以 Rust 实现,使用 Cranelift JIT(默认)+ Winch baseline AOT(快速编译、低内存)双 codegen 后端。

关键特性(深度展开)

  • Cranelift(主流 JIT)+ Winch(baseline AOT)双 codegen 后端。Cranelift 经过形式化验证(ACM 2024 论文 + 跟进工作 + Zenodo artifact),其 lowering 规则可形式化证明正确性——但 CVE-2026-34971 显示形式化验证模型必须随代码同步更新,否则验证失效
  • Pooling allocator:大批量实例的内存复用,适合 serverless 高密度场景(可减少 80%+ 内存分配)
  • Epoch-based interruption:从外部中断 runaway loop,避免单 guest 长时间占用 CPU
  • Pre-compilation(.cwasm):跨 cold start 复用编译结果,冷启动可压到亚毫秒级(对比 Firecracker 125 ms)
  • ASYNC + Tokio 集成:Component Model async 支持 Wasmtime 41+
  • Fuel metering:每个 wasm 模块可配置 fuel 上限,执行到上限 trap,实现「按调用计费」语义
  • WASI Preview 2 / Component Model:v25.0 起完整支持 WASI 0.2.1;v46+ 启用 WASI 0.3(2026-06-11 启动)
  • wasm-nn 后端:PyTorch / ONNX / OpenVINO 后端,支持 ML inference(WasmEdge 也有 wasi-nn)
  • gas / interruption:可配置全局 epoch interruption

Hopper 单 GPU CC vs Blackwell 多 GPU CC 差异(关键技术差异)

  • Hopper H100/H200:
    • 单 GPU CC(per-GPU CC)模式:GPU 自身 TEE 隔离,GPU memory 加密,本地 attestation
    • 多 GPU CC 通过 Protected PCIe(PPCIE) —— H100/H200 Protected PCIe 在 PCIe 层面加硬件保护,使多卡组成 CC 域;需要在 host 打 nvidia.com/cc.mode=ppcie label,Pod 同时请求 nvidia.com/pgpu 和 nvidia.com/nvswitch 资源
    • NVSwitch 配合 PPCIE:通过 NVSwitch fabric 扩展 CC 域到多 GPU,适用于 LLM 训练
  • Blackwell B200/B300:
    • 多 GPU 直通(MPT) —— Blackwell 原生支持 GPU-to-GPU TEE 通信,无需 PPCIE hack
    • HGX B300 平台支持(NVIDIA CC 1.1.0 起,2026-08-11 GA):单机 8 × B300 NVLink 全互联 + GPU CC
    • 更简单的 attestation:Blackwell TEE attestation 简化了 SEV-SNP / TDX + GPU attestation 之间的互信链

  • CPU TEE:AMD SEV-SNP(Genoa / Milan,3rd Gen+)或 Intel TDX(Emerald Rapids / Granite Rapids)

  • Trustee / KBS:Key Broker Service 协议 0.4.0;负责 attestation evidence 收集 + secret delivery
  • containerd:2.2.2 / 2.3.x

Cloud Hypervisor ✅ ✅ ✅ ✅(via Kata)
Kata Containers(QEMU) ✅ ✅ ✅ ✅(NVIDIA CC 1.0/1.1 GA)
gVisor 受限 ❌ ❌ ❌
Wasm / WAMR ❌(走 wasi-nn 抽象) ❌ ❌ ❌

结论:对 AI Agent 训练 / 大模型推理场景,MicroVM + vfio-pci + MIG / MIG-Backed vGPU 是 2026 年的事实标准;机密 AI 则走 Kata + NVIDIA CC + Hopper/B200 PPCIE。

2.1 沙箱编排的核心问题(高频 fork / 树状探索)

2.1.1 为什么传统 K8s 在 1000+ Pod 并发场景下"撑不住"

Agent 工作流把 Kubernetes 推到能力边界之外。Agent 一次探索循环可能产生:

  • 一次代码解释器调用 → 1 个 sandbox;
  • 一次 MCTS 树搜索展开 1000 个候选动作 → 1000 个 sandbox;
  • 一次 RL rollout 评估 10,000 个轨迹 → 10,000 个 sandbox。

这要求调度器在秒级内 fork 出千个独立、带状态的、带 checkpoint 的 sandbox,而 K8s 默认控制链路上没有这个数字。

Preferred Networks 的权威基准 (tech.preferred.jp/en/blog/kubernetes_scheduler_benchmark,2025-12-08)复现了 Kubernetes 上游 scheduler_perf 框架,在 500 节点 / 500 已有 Pod / 测 1000 新 Pod 场景下给出三组数字:

调度器配置 调度吞吐 (pods/s) 平均单 Pod 延迟
标准 kube-scheduler(无插件) 234.20 pods/s(current)/ 267.29(previous) ~4.3 ms/pod
PFN 自研 scheduler(含 Gang + GPU 拓扑) Lua 版 26.51 pods/s ~37.7 ms
PFN 自研 scheduler Lua→Go 重写后 374.08 pods/s ~2.7 ms
PFN Gang Pod scheduling(Lua→Go 后) 19.59 pods/s ~51 ms

关键观察:Gang 调度(RL/分布式训练必须)把 throughput 直接砍到默认的 1/12——这是裸 K8s 调度器在 RL/agent 场景的致命瓶颈。PFN 把 Lua 插件改写成 Go 后,标准 throughput 提升 ~14 倍(26→374),但 Gang 路径只能从 4.08 升到 19.59(提升 4.8 倍)。这印证了Kubernetes Gang Scheduling 文档 中描述的 "all-or-nothing" 语义带来的额外开销成本——1.37 beta 起 PodGroup 引入,默认仍需 GenericWorkload feature gate。

2.1.2 镜像拉取 vs Snapshot 的根本差距

冷启动时间链:

[标准 K8s + DaemonSet 预拉镜像]
  image pull (cached) ~50ms
  + kubelet start      ~500ms
  + CRI runc create    ~200ms
  + container start    ~500ms (含 app init)
  + readiness probe    ~3000ms
  ──────────────────────────────
  总计 P50             ~5s+ (来源:[阿里云袋鼠对比文章](https://developer.aliyun.com/article/1497978) 报告同等规格下袋鼠沙箱 5s vs KataContainer)

[自研调度器 + 预 fork Firecracker snapshot]
  snapshot mmap         <1ms
  + VM create + restore ~150ms (E2B) / 0.79ms (Zeroboot)
  + app resume from PID1 ~10ms
  ──────────────────────────────
  总计 P50             80–200ms (E2B/Modal) / ~150ms (forkd)

关键差距:

  • 镜像拉取 是 IO 带宽瓶颈,即使在缓存命中下仍有 ~50ms 序列化延迟,且无法跨 fork 共享;
  • Snapshot fork 走 mmap(MAP_PRIVATE) 走 page-fault CoW,父进程内存页被数千 child 共享,直到 child 写入才复制——这是 forkd/Zeroboot 能达到 0.79ms 的根本原因;
  • Checkpoint 进一步压缩"应用初始化时间":Modal 把 import torch 的 5s 冷启动压到 1.05s @ p50、0.69s @ p0,靠的是把内存里 import 完成那一刻的进程状态序列化保存(modal.com/blog/mem-snapshots, 2025-01-28)。

2.1.3 K8s 1.34 仍无原生 Checkpoint/Restore API

K8s 1.25 引入 container checkpoint 作为仅 forensic 取证用的 alpha feature(由 kubelet /checkpoint API 暴露),1.30 升 beta 并默认开启 ContainerCheckpoint feature gate(criu.org/Kubernetes)。但 K8s 至今没有:

  • Pod 级别的 snapshot restore API(只能把 checkpoint 转 OCI 镜像再用普通 Pod 创建);
  • Snapshot fork/branch API;
  • 与 snapshot 一体的 fork 语义;
  • 父子 sandbox 的内存/状态继承 API。

这些必须由 sandbox 编排器在 K8s 之上自研——这就是 2.3 节所有"脱离 K8s 自研调度器"存在的根本理由。

2.1.4 微沙箱编排 vs 传统容器编排的根本差异

维度 传统 K8s Pod Agent 微沙箱
生命周期 长期运行(Deployment)、短批(Job) 短到中期(几秒到几天)
状态共享 无(每个 Pod 独立) 父子继承(CoW fork)
资源画像 静态(Pod spec 决定) 动态(运行时按工具调用变化)
调度粒度 Pod 级(分钟级反应) Sandbox 级(秒级反应)
拓扑结构 星型/无 树状(MCTS 派生)
GPU 调度 整卡 / MIG 单 sandbox 内 GPU 推理 + checkpoint
典型数 万级 Pod 10w+ sandbox/分钟(RL rollout)

这意味着传统 K8s 控制面不是"加速一下就能用",必须重新设计调度器 + 引入 sandbox 概念 + 加入 fork/branch 原语——这是 2.4 节树状探索专用的出发点。

2.1.5 "为什么 Agent 不直接复用 Lambda / Cloud Run / Cloud Functions"

这一节是面向"熟悉传统 Serverless 但不熟 Agent"的读者的常见疑问。Lambda/Cloud Run/Cloud Functions 与 Agent 微沙箱的根本差距:

  • 冷启动语义不同:Lambda 设计为"事件触发 → 启动 → 退出",最长 15 分钟,镜像固定、代码 immutable,无法在 runtime 暂停后"分支"——而 agent 的探索循环恰恰需要"暂停 → fork → 多个 child 并行 → 比较结果 → 选 best branch"这种语义;
  • 无法表达父子关系:Lambda / Cloud Run 都是无状态 worker,parent / child 仅通过消息传递;Agent 需要"fork 后 child 继承 parent 的内存页面"(CoW),这是消息协议层做不到的;
  • 生命周期与价格模型错位:Lambda 按 GB-second 计费,鼓励"长跑大实例";Agent 沙箱按秒级 sub-second 频繁创建销毁,需要"千个 sandbox × 毫秒级"而不是"1 个 sandbox × 几小时";
  • 网络与凭证模型不同:Lambda 把凭证放在环境变量(在 sandbox 内),适合 stateless worker;Agent 长会话需要 Connectors(Fly.io 模式)或 Durable Object per agent(Cloudflare 模式),让凭证留在平台层;
  • GPU 调度粒度:Lambda GPU 实例是"整卡 + 长租",无法做"千次/秒 fork 出一个 microVM 并共享父 snapshot"——这是 forkd/Zeroboot/Dandelion 共同瞄准的空白。

简单说:Serverless 是"无状态函数的弹性",Agent 微沙箱是"有状态探索树的弹性",二者在调度目标、fork 语义、状态保留、价格模型上都不在同一维度。这也是为什么头部 Agent 平台全部选择"自研",而不是"用 Lambda + 改一改"。

2.2.1 K8s 1.30-1.34 关键 KEP

(1) Native Sidecar Containers — KEP-753,1.28 alpha,1.32 GA。 1.32(2024-12 发布)将 sidecar 从 init 容器 hack 提升为一等公民:只要 restartPolicy: Always 的 init 容器就会在主容器生命周期内保持运行,并在主容器结束后按相反顺序优雅退出。直接收益是修复 Job 完成 bug——此前 sidecar 经常在主容器完成前被驱逐,导致 Job 永远不结束 (Kubernetes Docs: Sidecar Containers)。

(3) In-Place Pod Vertical Scaling — KEP-1287,1.32 beta。 允许修改 CPU/Memory requests/limits 而不重建 Pod(devstarsj 1.32 深度文章),对长时运行的推理服务极有价值。

(4) Gang Scheduling (KEP-3063 关联) — 1.37 beta。 K8s Gang Scheduling 文档显示:Feature state Beta since Kubernetes v1.37; disabled by default——这意味着即使到 1.37(2026 年中后期),Gang 仍是 opt-in。这反衬出 Volcano 在 1.11+ 已经成熟(volcano v1.11 release blog)。

(5) Opportunistic Batching:1.31+ 的默认特性,让调度器在 0.5s 窗口内复用过滤/打分结果。

2.2.5 三层预热的代价对比与何时该选哪一层

不同"预热"路径的代价与适用场景完全不同:

预热方式 资源代价 启动延迟 适用场景 局限
DaemonSet 镜像预拉 每节点一份镜像缓存(~GB×N) 容器启动 ~500ms 通用、长跑 service 镜像大时仍 IO 受限
SOCI(Sealed OCI) 镜像 metadata cache 容器启动可"提前"启动 大模型/数据集镜像 SOCI 索引构建需时间
Karpenter warm node 整节点常驻(贵!) Pod 调度立即 Spot / 异构机型混部 不解决 sandbox fork latency
SandboxWarmPool N 个 warmed pod 常驻 ~100ms(单 sandbox) AI agent runtime、RL 受 warmed pod 数量限制
Memory Snapshot(Modal) 一份 warmed image + checkpoint 1.05s import torch AI/ML Python workload gVisor 用户态内核(非 VM)
GPU Memory Snapshot GPU 内存快照 2s(NeMo) GPU 推理 cold start 多 GPU + CUDA graph 兼容差
forkd / Zeroboot(snapshot CoW) 一份 warmed parent snapshot 0.79ms fork MCTS/RL 高频 fork 单 vCPU / 局部网络

经验法则:延迟预算 ≥ 5s → 任何方案都行;1–5s → 预热池 + Memory Snapshot;<1s → 必须 forkd/Zeroboot/Dandelion 这种"内存页表级"调度;亚 100ms → 接受 fork 的"局部副作用"(无网络、单 vCPU、共享 CSPRNG)。

2.4 Agent 树状探索专用沙箱调度(重点)

本节核心问题:Agent 的 MCTS 搜索 / RL rollout / ReAct 多分支探索要求"在一个 warmed parent 的状态下派生数千个 children",传统 K8s 既无 snapshot fork 语义也无内存 CoW 共享。本节是本章真正的核心——2025–2026 出现了一个独立的"树状调度"赛道。

2.4.1 Locality-Aware Fork(就地派生)

概念:在 fork 时优先选择与父 sandbox 同一物理节点、同 NUMA、同 GPU 拓扑 的目标机,最大化 page cache / KV cache 复用。

代表实现:

  • forkd ——见 2.4.5,父 snapshot 在同节点 mmap,child 自动 locality-aware;
  • Dandelion(ETH)——见 2.4.8,把"父子"约束在同一个 microVM 上下文内,通过 MMU worker 复用地址空间。

2.4.2 Tree Branching 调度

概念:agent 不仅要 fork,还要 在运行中 pause → snapshot → resume(即 branching),把探索树中间节点变成 fork 的源头。

代表实现:

  • forkd v0.4 BRANCH mode ——56–150ms(live mode),允许 branch_sandbox(parent_id, mode="live", wait=False),返回 ~10ms 后 background copy 继续;
  • Sandlock fork ——纯 process fork(无 VM),1000 clones 718ms / 680μs/clone;
  • Modal Memory Snapshot——runsc restore 创建新 sandbox(非 in-place branch)。

2.4.3 Checkpoint/Resume 调度

概念:与 K8s 的 ContainerCheckpoint(Kubelet API only)不同,Agent 需要:

  • Periodic checkpoint ——每 N 步自动 dump 进程状态;
  • Resume on demand ——断点续跑,不必从头 init;
  • Snapshot as branch ——把 checkpoint 当 branch point 派生 child。

代表实现:

  • RayTurbo Native Sandboxing (2026-08 Anyscale blog)——把 sandbox 做成 Ray actor 一等公民,可 checkpoint;
  • Agent RL 训练:verl / OpenRLHF 的 ray.train.report(metrics, checkpoint=...) 模式;
  • SandboxWarmPool(agent-sandbox K8s)——预热 pod 池,降低 fork latency。

2.4.4 父子环境 CoW 共享

核心机制:用 Linux 的 mmap(MAP_PRIVATE) 把父 snapshot 文件以 copy-on-write 方式映射到 child;父的所有内存页被 children 共享,直到 child 写入才 page-fault 复制。

2.4.10 这条赛道的"非共识判断"

为什么 forkd/Zeroboot/Sandlock/Dandelion/CubeSandbox 在 2025–2026 集中出现?背后的非共识是:

  • RL rollout 是 2026 最大的 sandbox 需求方——一个 PPO iteration 要 fork 数千 verifier sandbox;一个 SWE-bench 评估要 fork 数千 code execution sandbox;一个 MCTS agent 决策要 fork 数千 tool-call sandbox;
  • 传统 microVM cold-boot 太慢——即使 Firecracker 也要 ~150ms;Modal 的 gVisor restore 要 1s;对于"100ms 内 fork 100 个"的需求完全不够;
  • 内存是真正的瓶颈,不是 CPU——RL eval 里 2 GB reward model + 1 GB dataset,若每个 sandbox 独立加载 → 1000 sandbox 就是 3 TB;而 forkd/Zeroboot/Dandelion 用 CoW fork 把这压到 ~2 GB(parent)+ KB 级(child);
  • 学术与工业的合流——Dandelion(ETH SOSP 2025)论文里的"每个请求 cold-start"在工业上由 forkd/Zeroboot/Sandlock 实现为"fork from warmed parent";二者殊途同归。

反共识风险:

  • 单 vCPU / 无网络 / 共享 CSPRNG 这些"fork 副作用"在生产 RL 场景是否能容忍,取决于 RL 框架本身——verl HybridEngine 已经做了 in-place resharding,能容忍;OpenRLHF 在 actor pool 之间走 Ray object store,不依赖 fork;而 SWE-bench 类评估则完全不依赖网络和 CSPRNG,fork 是天然选择;
  • 国产项目(CubeSandbox、袋鼠)与海外(forkd、Zeroboot)在同一时间窗口内独立做出类似选择,意味着 CoW fork 已经不再是"学术原型",而是工程共识。

2.4.11 "fork from warmed parent" 与 "snapshot cold-boot" 的本质差异

理解 forkd/Zeroboot/Dandelion 与 Modal Memory Snapshots / E2B snapshot fork 之间的关键差异,对选型至关重要:

共同点:都是"复用某个预先准备好的状态",避免从头初始化。

差异:

维度 Snapshot cold-boot(Modal/E2B 风格) Fork from warmed parent(forkd/Zeroboot 风格)
状态来源 预存的 image/snapshot 文件 运行中的 process(PID 1 已 warmed)
状态保留 文件系统 + 部分内存(runsc restore) 完整内存 + heap + stack + fd + threads
延迟 几十到几百毫秒 亚毫秒
副作用 几乎无(独立进程) 单 vCPU / 共享 CSPRNG / 共享网络命名空间
隔离强度 强(独立 microVM) 弱到中(KVM 隔离但共享父 page cache)
适用场景 长跑 + 高隔离 + GPU 推理 RL rollout / MCTS / SWE-bench 评估
代表项目 Modal Memory Snapshots, E2B forkd, Zeroboot, Sandlock, Dandelion

选型建议:

  • 如果 sandbox 需要长时间运行(几小时到几天)+ 强隔离 → Modal / E2B 风格;
  • 如果 sandbox 是短生命周期(秒到分钟)+ 高频 fork → forkd / Zeroboot 风格;
  • 如果 sandbox 是纯 process 级别(无需完整 Linux kernel)+ 极低开销 → Sandlock 风格;
  • 如果需要学术界验证的微秒级弹性 + 可投入生产 → Dandelion 风格(但目前仍是学术原型)。

这一分野也是为什么本章把 2.4 节作为"重点"——它代表了 2025–2026 调度层最重要的"新原语"。

2.7.6 中国厂商与海外厂商的差异

中国云厂商的"沙箱编排"路径与海外有三个明显差异:

  1. "调度器 + AI 平台"是耦合的——海外 Modal / E2B / Fly.io 是单纯的"沙箱 + 调度"产品;阿里 PAI / 华为 ModelArts / 腾讯 TI-ONE / 火山引擎是"沙箱 + 调度 + 训练 + 推理 + 模型市场"的端到端 AI 平台。这一区别来自中国云厂商的客户习惯:大企业客户希望"一个平台搞定一切",而海外开发者习惯"每个组件单独选最强者";
  2. "国产开源"作为对外宣传重点——CubeSandbox(腾讯云,Apache-2.0,11,813 stars)2026-04 开源时明确以"兼容 E2B SDK + 改一个环境变量迁移"为卖点,反映中国厂商对"开源标准"的话语权追求;阿里袋鼠、华为 StratoVirt、字节 Kuasar 均沿同一路径;
  3. 自研硬件协同——阿里 CIPU / 华为 CIPool / 字节自研 NIC / 腾讯黑石都把"调度器 + 自研硬件"垂直整合,这是海外大云不容易复制的优势(海外更偏通用硬件 + 开源软件)。

章节小结

2025–2026 的沙箱编排层演进可以归结为四条主线:

  1. Kubernetes 主线在"补作业":通过 Sidecar GA、DRA、InPlacePodVerticalScaling、agent-sandbox CRD(2025-08 起的官方子项目)把 AI / 长生命周期 workload 的硬伤一个个补上,但单 scheduler 200 pods/s 上限没有根本突破;Gang scheduling 在 1.37 才进入 beta,且仍 disabled by default。
  2. 自研调度器用"快照 + Firecracker fork + sub-second cold start"重新定义 SLO:Modal 1.05s、E2B 150ms、forkd 100 forks in 101ms、Zeroboot 0.79ms fork latency——这些数字已经超出 K8s 一个数量级;2025-11 Cloudflare 收购 Replicate、2025-12 Akamai 收购 Fermyon、2026-07 Nscale 收购 Anyscale($1.65B),三笔收购共同把"自研调度器"从创业赛道变成大厂基座。
  3. 树状探索专用调度是 2025–2026 真正的"新赛道":forkd / Sandlock / Zeroboot / Dandelion(ETH SOSP 2025)/ CubeSandbox(腾讯)——五个项目用 mmap CoW + fork 把"派生 1000 sandbox"压到亚秒级,把 sandbox 调度从"基础设施服务"重定义为"内存页表操作"。
  4. 两级调度 + RL rollout 专用路径成熟:Kueue → Volcano → KubeRay → KServe / llm-d → GIE 已是 2026 年"开源最佳实践栈";verl 3D-HybridEngine 用 in-place CUDA IPC resharding 把 70B 模型切换延迟压到 <1% iteration 时间;RLHF/GRPO 训练对调度器的真实压力点已从"如何跑满 GPU"转移到"如何让 rollout 与 training 共享同一片 GPU 而不互踩"。

对读者的选型建议:

  • 如果你做的是短跑 RL rollout / MCTS 探索 / SWE-bench 评估 → 直接 forkd 或 Zeroboot(Dandelion 关注但暂不投入生产);
  • 如果你做的是长跑 agent runtime + GPU 推理 → Modal 或 E2B;
  • 如果你需要多云 / BYOC / 异构 GPU → Northflank;
  • 如果你需要长会话 + 浏览器端 → Fly.io Sprites + Cloudflare Durable Objects;
  • 如果你已经重度依赖 K8s → 在 K8s 之上叠 Kueue + Volcano + KubeRay + agent-sandbox SandboxWarmPool;
  • 如果你在中国 + 需要合规 → 阿里 ECI/袋鼠、华为 CCE Turbo、字节火山、腾讯 CubeSandbox。

本章遗留的开放问题(留给下一版):

  1. agent-sandbox SandboxWarmPool 在生产环境下的 fork latency 数据——目前仅有 spec,缺独立 benchmark;
  2. forkd / Zeroboot / Sandlock 在 RL 框架(verl / OpenRLHF / TRL)中的真实集成情况——均为独立项目,尚未看到与 RL 框架的标准 API;
  3. Dandelion 何时进入生产——目前仍是 ETH 学术原型(35 stars),距离工业可用还有 1–2 年;
  4. Cloudflare Sandboxes GA 与 Durable Object Facets 的 SLA 与价格——2026-04 才 GA,公开数据尚少;
  5. 国产项目(袋鼠、Kuasar、CubeSandbox、Mosdic) 与海外项目的 fork latency / memory overhead 横向比较——本调研未找到完整对比表;
  6. Anyscale Native Sandboxing in Ray(2026-08 发布) 与 KubeRay / Ray actor pool 的实际集成深度——Anyscale 已被 Nscale 收购,后续路线尚不明朗;
  7. Kubernetes Gang Scheduling 1.37 GA——目前 beta 且 disabled by default,正式 GA 时间未定。

4.7 小结:对沙箱 / 编排研究方向的启示

  1. 沙箱启动时间已不是瓶颈:Dandelion (90 μs) + PhoenixOS (600 ms 级 GPU C/R) + Medusa (53% TTFT) 三条线共同把「冷启动」从 10s of ms 压到 μs / 100s of μs 级。
  2. 编排粒度下沉:
    • 空间上:LithOS → per-kernel spatial share
    • 时间上:XSched → preempt at Lv3 (running command)
    • 网络上:BlitzScale → compute fabric 当 storage fabric
    • 内存上:TrEnv-X → CXL/RDMA 跨 sandbox 复用
  3. 底层栈成熟:
    • 流式镜像(Stargz / Nydus / SOCI)已是事实标准,90%+ 加速
    • Firecracker snapshot + dirty-page + uffd 流水线完备
    • CRIU 仍是进程级 check-point 首选,LLM inference / JVM 都在用
  4. 安全不可省:TDXdown / GhostRace / Reptar 三类 CVE 提示硬件 TEE ≠ 完整安全,编排器仍需在 seccomp / Landlock / netns / attestation 层做纵深防御。
  5. 多轮 agent 时代的特殊点:Continuum 把 KV cache 当成「沙箱内一类可调度资源」,与 TrEnv-X 的 sandbox-env 复用互补,共同构成 agent 时代的沙箱内存管理新范式。
