0.2 为什么 MCTS/RL Rollout 在 K8s 下会性能坍塌

Agent 树状探索(Monte Carlo Tree Search / RL Rollout)的核心特征是:

  • 高频 fork: 单次决策可能派生 4-32 个并行子环境(MCTS),RL rollout 可能 100-1000 并发
  • CoW 内存共享: 父子环境共享只读内存(SYSTEM_PROMPT + TOOL_SCHEMA),子环境只写自己修改的部分
  • checkpoint/resume: 树状分支需要在任意节点暂停/恢复,以便利用 GPU 资源

K8s 默认调度的三大瓶颈(数据来源:Preferred Networks K8s Scheduler Benchmark):

  1. Per-Pod 调度开销: 1000 Pod 部署场景,K8s 默认调度器约 234 pods/s,Gang scheduling 仅 19 pods/s(2026 数据)
  2. 镜像拉取延迟: 1GB 镜像 cold pull 30-60s,即使有 image pre-staging 也难以应对突发 fork
  3. 检查点缺失: K8s 1.34 仍无原生 checkpoint API(KEP-2008 还在 Stage Alpha)

0.3 新范式的核心特征(四个根本性变化)

  1. Sandbox-as-a-Service: 沙箱成为可计量的 API(Modal/E2B/Fly.io Sprites),不再绑定具体镜像
  2. Memory-as-a-Fabric: CXL/CRIU/userfaultfd 让内存成为可"派生/快照/恢复"的资源
  3. Snapshot-as-a-Primitive: Firecracker SnapStart / Lambda SnapStart 把"冷启动"压缩到 <200ms
  4. Confidential-by-Default: TDX/SEV-SNP 让"不可信 Agent 代码"在受保护硬件中运行

0.5 五个核心非共识假设(H1-H5)

  • H1: MicroVM 与 WASM 不收敛 — 长 session 多租户 microVM 不可替代,边缘/短任务 WASM 占优,未来 5 年是混合形态(microVM-of-WASM = WASI Preview 2 + Firecracker)
  • H2: 协议(MCP/A2A)正在架空编排层 — Agent 框架正在降级为 tool-router,真正的"智能"在 LLM 与协议,不在调度器
  • H3: 存储/内存协同才是 Agent 性能瓶颈 — 不是沙箱启动时延,而是 fork/branch 时内存页表/CoW 共享效率
  • H4: TDX/SEV-SNP 成为 AI Agent 标配 — 2026 起,所有 SaaS 沙箱(Modal/E2B/Fly.io)会默认开启 confidential 模式
  • H5: RL Rollout 调度会分化出专用调度器 — OpenRLHF/verl 的 tree rollout 与通用 K8s 调度器特性不兼容,未来 3 年会出现"RL-aware scheduler"专属赛道

一、沙箱隔离层深度剖析

调研时间:2026-09-06 适用对象:AI Agent 系统的代码执行环境选型与架构设计 资料来源:全部声明均附 URL 引用,关键数字与 CVE 通过 web 搜索交叉验证(详见 §1.7 反幻觉校验清单)

摘要

AI Agent 在 2024-2026 年从「对话式 LLM」跃迁到「自主执行型 LLM」,催生了对安全、低时延、可水平扩展的沙箱执行层的刚性需求。当前业界形成四条主线:

  1. MicroVM 路线(Firecracker / Cloud Hypervisor / Rust VMM / crosvm / QEMU microvm / StratoVirt):提供硬件级 guest kernel 隔离,冷启动 60-300 ms;
  2. 进程级 / 应用内核路线(gVisor / Kata Containers / Nabla Containers / nsjail / bubblewrap):进程级沙箱,启动 <100 ms,但系统调用兼容性各异;
  3. WASM 路线(Wasmtime / Wasmer / WAMR / WasmEdge / Spin / wasmCloud):用户态 capability 隔离,WASI 0.2(Preview 2)于 2024-01-25 GA,冷启动可压到亚毫秒级;
  4. 新兴 / 实验路线(字节 Kuasar / 阿里 Bagualu & Agent Sandbox / StratoVirt / Docker VMM Profile / E2B / Fly.io Sprites / Modal / Northflank):围绕 CNCF Sandbox API 重新设计,强调「按工作负载挑选沙箱类型」。

1.1.3 Rust VMM / StratoVirt / QEMU microvm

Rust VMM 共享库生态

  • 组织:https://github.com/rust-vmm,提供 kvm / vhost / vfio / vm-virtio / mshv / xen 等基础 crate
  • 由 Firecracker / Cloud Hypervisor / crosvm / StratoVirt 共同维护
  • 价值:避免各 VMM 重复实现 virtio / KVM bindings,统一内存安全基础
  • 数据来源:https://github.com/rust-vmm、https://www.cloudhypervisor.org/docs/prologue/introduction.html

QEMU microvm machine type

  • 官方文档:https://www.qemu.org/docs/master/system/i386/microvm.html
  • 灵感直接来自 Firecracker:无 PCI、无 ACPI,仅 virtio-mmio + 极简 ISA 子集(可选 PIT / PIC / RTC / serial)
  • 默认 BIOS 为 qboot(https://github.com/bonzini/qboot),可换 SeaBIOS
  • 不支持:PCI-only 设备、任何热插活、跨 QEMU 版本的 live migration
  • Ubuntu Server 团队实测:从标准 QEMU 切到 microvm 启动快 ~282 ms;再叠 qboot 额外快 ~526 ms——https://ubuntu.com/server/docs/explanation/virtualisation/qemu-microvm
  • QEMU microvm 主要意义:研究 / 基准测试基线,生产场景多走 Firecracker 或 Cloud Hypervisor

StratoVirt(openEuler / 华为云主导)

  • 项目:https://gitee.com/openeuler/stratovirt、https://github.com/openeuler-mirror/stratovirt(Mulan PSL v2)
  • 镜像:GitHub mirror 显示 stars ≈ 417(2026-09)
  • 一套架构同时支持标准虚拟机、容器、Serverless 三种场景
  • 集成进 Kuasar 作为 MicroVM sandboxer 后端(与 Cloud Hypervisor、QEMU 并列)
  • openEuler 25.03 已提供 StratoVirt 预编译 rootfs 与 vmlinux: https://mirrors.huaweicloud.com/openeuler/openEuler-25.03/stratovirt_img/x86_64/

2.1 K8s 体系对 Agent 场景的演进

2.1.1 K8s 1.30-1.34 关键 KEP（Sidecar GA / DRA / Job 策略）

近四个版本的 Kubernetes 主线，针对长任务、AI 异构资源、Sidecar 生命周期做出了三件决定性事情：

(1) Native Sidecar Containers — KEP-753，1.28 alpha，1.32 GA。 Kubernetes 1.32 在 2024 年 12 月发布，将 sidecar 容器从"伪 init 容器 hack"提升为一等公民：只要 restartPolicy: Always 的 init 容器就会在主容器生命周期内保持运行，并在主容器结束后按相反顺序优雅退出。Kubernetes 官方文档明确指出，这一改动的直接收益是修复 Job 完成 bug——此前 sidecar 经常在主容器完成前就被驱逐，导致 Job 永远不结束 (Kubernetes Docs: Sidecar Containers)。KEP 仓库保留了完整的实施历史与 GA 门槛 (kubernetes/enhancements KEP-753)。第三方解读见 Greenpepper Software 2026。

(2) Dynamic Resource Allocation (DRA) — KEP-3063 / 3064 / 4382，1.30 alpha，1.34 默认开启。 DRA 把"GPU / NPU / FPGA 等异构设备的选择与配置"从 Device Plugin 时代「先报告整数资源再抢占式分配」改为「声明式 ResourceClaim + CEL 表达式选择」。NVIDIA 维护的 dra-driver-nvidia-gpu 要求 K8s ≥ 1.32，并在 1.34 后默认开启 feature gate DynamicResourceAllocation；它还提供 ComputeDomain 抽象，用于 Multi-Node NVLink（GB200/GB300 NVL72 等）（NVIDIA GPU Operator 文档）。这一改动使 GPU 调度摆脱了"整数 nvidia.com/gpu 资源 + 拓扑管理器"的两难，为推理专家并行（EP）、prefill/decode 分离铺路。

(3) Job 成功/失败策略 (KEP-2187) 与 in-place pod resize (KEP-1287)：1.32 Beta 引入 InPlacePodVerticalScaling (devstarsj 1.32 深度文章)，允许修改 CPU/Memory requests/limits 而不重建 Pod，对长时运行的推理服务极有价值。Job 的 success/failure policy 则让 PPO/RL 训练这种「某些 exit code 算成功、某些算失败」的场景不必再写外层 wrapper。

(4) Opportunistic Batching (Scheduler Performance Tuning)：1.31+ 的默认特性，让调度器在 0.5s 窗口内复用过滤/打分结果，把批调度吞吐显著抬高（见下文 2.1.4 数字）。

2.1.3 K8s 预热池与 Warm Pool 模式

K8s 自身的 cold start（拉镜像 + kubelet 启动 + readiness 通过）在 agent 场景下太慢。生产实践普遍采用"预拉镜像池 + 节点 warm pool"两种策略：

  • Image Pre-pull (DaemonSet / SOCI / Kwokt)：在节点 bootstrap 阶段由 DaemonSet 把常用 agent runtime 镜像预先拉取；EKS 推荐做法是 Sealed OCI for Images (SOCI)，可以在镜像完整下载前就启动容器 (EKS AI/ML Cluster Setup)。
  • Warm Node Pool (Karpenter)：Karpenter 在 2024 年 GA 后已成为 EKS 默认弹性方式。它直接读 unschedulable Pod 的 spec，自行决策 instance type / zone / capacity type (EKS Best Practices: Karpenter)。2026 年起 EKS Auto Mode 把 Karpenter / Node Monitoring Agent / SOCI / NVIDIA Device Plugin 全部预装 (EKS ML Node Pools)。
  • EKS Pod Identity（IRSA 替代品，2024 GA）让 Pod → S3/Vault 等下游访问无需静态凭证，配合 Karpenter 让"节点 + 权限 + 镜像 + GPU 驱动"全自动化。

2.1.4 关键延迟数据：原生 K8s 在 1000+ fork 场景的瓶颈

这是本章必须正面回答的问题：默认 kube-scheduler 在 1000 个并发 fork 场景下的延迟到底是多少？

最权威的数据来自 Kubernetes 上游的 scheduler_perf 集成基准。Preferred Networks 在 2025 年发布的 Benchmark Testing of the Kubernetes Scheduler 复现了上游基准并给出三种场景的数字：

场景 调度吞吐 (pods/s) 平均单 Pod 调度延迟
标准 kube-scheduler（500 节点 / 500 已有 Pod / 测 1000 新 Pod） ~234 pods/s ~4.3 ms/pod（按 1000/234 折算）
PFN 自研 scheduler（含插件） ~26 pods/s（早期 Lua 版）→ 374 pods/s（Go 重写后） ~2.7 ms
PFN Gang Scheduling ~19 pods/s（Lua→Go 后） ~52 ms/pod

对应的 upstream JSON 输出（来自 Preferred Networks 同一篇文章）记录了「SchedulingBasic 500Nodes / namespace-2」的延迟分布：Average = 213.96 pods/s、P50 = 55.99 pods/s、P90 = 371.93 pods/s、P95 = 371.93 pods/s、P99 = 371.93 pods/s。

社区给出的 SchedulingBasic 5000Nodes_10000Pods 阈值约为 270 pods/s，低于即说明 PR 引起回归。这意味着：

  • 裸 kube-scheduler 单 scheduler 实例在数千节点规模下大约只能稳定吃掉 200–300 pods/s。对一个 1 秒内 fork 1000 个 sandbox 的 agent，这是做不到的。
  • Gang scheduling（多 Pod 必须同时起）会把吞吐降到 1/10。
  • 字节跳动内部同样印证了这一数字：字节火山引擎公开博客 报告其自研调度器 "1w 台机器、40w+ 容器数"，Gang 语义下10 秒内拉起 5k 容器（即 ~500 pods/s），且在 20k 节点 / 1000k Pods 规模、1k+ incoming Pods/s 下稳定运行——这是裸 K8s 远不能及的。

结论：原 K8s 调度器对 agent 而言有两个不可绕过的瓶颈——(a) 单 scheduler 200 pods/s 上限、(b) 单 Pod 创建要走 API Server + etcd + scheduler + kubelet + CRI 五段链路，端到端 P50 ≥ 5s（无 image pull），这两个数字直接催生了 2.2 节所有脱离 K8s 的自研方案。

2.2 脱离 K8s 的专用自研调度器

这一组平台的共同特征：自研控制面 + Firecracker/gVisor MicroVM 池化 + 快照/镜像复用，从而把 cold start 压到 sub-second、把 fork 1000 个 VM 压到秒级。

2.2.1 Modal

Modal 一直是最透明公开数据的玩家。关键技术节点：

  • gVisor + 自定义 OverlayFS 提供 sandbox 隔离（不是 Firecracker）。
  • Memory Snapshots（2025-01）：基于 gVisor 的 runsc restore 实现 checkpoint/restore，跨 cold start 复用 Python import、torch 加载等状态。其 官方博客 给出数据：
    • 简单 import torch 程序 cold start：~1.05s @ p50、0.69s @ p0（对比普通 runsc run 5s）。
    • Stable Diffusion Function：~13s → ~3.5s（2.5× 提升）。
  • GPU Memory Snapshots（2025-07）：把 GPU 状态也写入 snapshot，进一步降低 GPU 推理 cold start (GPU Memory Snapshots 博客)。
  • Cold start 社区基准对比（dev.to 2026-09 测评）：Modal A100 (40GB) median cold start 1.8s，对比 RunPod Serverless 4.2s、Replicate 6.5s、Lambda Labs ~45s。

Modal 调度层公开资料较少，公开口径强调"自动 scale-to-zero + 多区域部署 + min_containers/buffer_containers/scaledown_window 三参数控制 warm pool" (Modal Cold Start 文档)。

2.2.2 E2B

E2B 专注于"agent 代码解释器"细分。架构关键：

  • 基于 Firecracker fork 的自研 runtime，每个 sandbox 一个独立 Linux guest kernel。
  • 预 fork microVM snapshot：cold start ~125–150ms（jacar.es、llms.blog 2026-08 比较）。
  • 公开 SDK：Python/JS Code Interpreter + Desktop Sandbox（computer-use agent）+ 自托管 OpenAPI（Apache 2.0）。
  • 计费：公开报价约 $0.05/vCPU-hour（reactify-solutions 2026）。

E2B 控制面文档明确说："每个 sandbox 由 REST Sandbox API + 控制面调度"，由 e2b-dev/infra 仓库（Apache-2.0）维护 (deepwiki E2B System Architecture)，调度协议为「API 提交 → Orchestrator → Firecracker host 分配 → snapshot fork」。

(A) 快照 + CoW Fork 路线

2.4 两级调度协同机制（Global Scheduler + Actor 级本地分派）

三、存储与物理内存协同层深度剖析

本章聚焦 AI Agent 大规模执行环境对存储栈 + 物理内存栈提出的全新耦合约束:从一页 page 的写时复制 (CoW),到一个 microVM 冷启动时的镜像按需取回,再到跨机房的 CXL 内存池化与内存去重。所有结论均来自 2024-2026 年可验证的一手资料(内核文档、项目 README、ISCA/OSDI/ATC 论文、厂商技术披露),未能溯源的细节一律标注「未公开」。

3.1 内存端机制

3.1.1 CoW 与 Fork

机制本质:fork(2) 后子进程与父进程共享匿名页,内核把双方 PTE 标为只读,任一方写入时通过 do_wp_page()(源码 mm/memory.c)分配新 folio、复制原页并刷 TLB。该机制自 1970s 起就是 UNIX 进程模型的基石,Linux 5.19 (2022) 引入 PG_anon_exclusive 进一步把 anon-only 的 PTE 用一个 bit 区分,避免在 fork 后立即父子都写时仍要走完整 COW 流程(kernel-internals.org/mm/cow/)。

关键限制(给具体数字 + 来源):

  • fork 只复制页表,不复制物理页。对于稀疏大地址空间进程,页表本身可能就是几十到几百 MB(kernel-internals.org "Page table overhead")。
  • 2MB THP 在 COW 时会被先打散成 4KB 再复制,单字节写也要复制 2MB;Linux 6.15 (2025) 在 THP COW 路径上做了改进(kernel-internals.org/mm/cow/ 引用 "THP COW improvements (v6.15, 2025)")。
  • vfork 跳过页表拷贝,但父子共用栈,只可在子进程立即 _exit()/exec() 时使用(kernel-internals.org)。

Sandlock 实战数字(2026 年 3 月公开基准):Multikernel Technologies 在《1,000 Sandboxes in 718 Milliseconds》一文中给出在单一 Linux 进程上以 fork(2) 派生 1,000 个子沙箱:

  • 端到端 718 ms,每克隆 ~680 µs。
  • 10,000 个克隆共享同一份 2 GB 模型权重,总驻留内存仍是 ~2 GB(每克隆仅 ~4 KB 页表开销),而非 20 TB。
  • 对比:容器冷重启需 ~200 ms × 1000 = ~200 s,Firecracker 快照派生 ~150 ms × 1000 = ~150 s。
  • 来源:https://multikernel.io/2026/03/19/sandlock-cow-fork。

在容器 / MicroVM 中 Fork 的差异:

  • Linux 容器 通过 mount/PID/net/user 命名空间隔离,这会打破父进程与子容器之间的页表共享。从宿主外部对容器内进程直接 fork() 是不可能的——必须借 CRIU 检查点/恢复或 unionfs + cold start。
  • Firecracker MicroVM 提供 guest 内的 CoW(fork 在 guest 内依旧工作),但跨 microVM 实例只能共享「预拷贝的内存文件」和「只读块设备」——MAP_PRIVATE + 文件后端让所有 guest 起始页指向同一物理页,首次写时复制(firecracker/docs/snapshotting/snapshot-support.md)。

3.1.2 userfaultfd 与按需缺页加载

userfaultfd(2) 自 Linux 4.3 (2015) 引入,把 page fault 路径导出到用户态;Linux 4.11 (2017) 增加 non-cooperative 模式,使 CRIU 可在不知道目标进程语义的情况下做 lazy restore;Linux 5.13 (2021) 引入 UFFDIO_REGISTER_MODE_MINOR(hugetlbfs),5.14 (2021) 增加 shmem minor 模式(参考 man7.org/linux/man-pages/man2/userfaultfd.2.html 和 docs.kernel.org/admin-guide/mm/userfaultfd.html)。

三种关键模式:

模式 触发条件 Linux 版本 用途
UFFDIO_REGISTER_MODE_MISSING 虚拟页表项不存在 4.3+ QEMU post-copy live migration、Firecracker snapshot 的 Uffd backend、CRIU lazy restore
UFFDIO_REGISTER_MODE_MINOR 物理页存在,但 PTE 未建立 5.13/5.14 shmem/hugetlbfs 上的按需 PTE 填充
UFFDIO_POISON 用户态主动投毒,让后续访问者收到 SIGBUS / MCE 4.11+ 模拟硬件内存故障、QEMU live migration 中的内存传染模拟(docs.kernel.org/admin-guide/mm/userfaultfd.html "Memory Poisioning Emulation")

UFFD_FEATURE_WP_ASYNC 异步写保护:配合 UFFDIO_REGISTER_MODE_WP 使用时,写操作不会再产生 message,只能从 /proc/pagemap 的 uffd-wp bit 读出"是否写过"——适合批量记账而非同步拦截。

实战用法:

  • Firecracker 提供两种 snapshot 后端:File(让内核 MM 负责 page fault)和 Uffd(用独立进程接管,适合必须用 2MB hugetlb 的场景,firecracker/docs/snapshotting/snapshot-support.md)。
  • CRIU --lazy-pages 把 restore 时未填充的 VMA 用 UFFD 注册,启动一个 criu lazy-pages 守护进程响应缺页;支持本地 image、远程 page server 两种来源(criu.org/Userfaultfd)。社区反复验证的代价:lazy-pages 本身比普通 restore 慢,所以最适合「必须最快 resume、运行后可接受持续 page fault」的场景,比如 LLM 推理冷启动。

3.1.3 KSM / UKSM / 内存去重

KSM 由 CONFIG_KSM=y 启用,ksmd 内核线程定期扫描 madvise(MADV_MERGEABLE) 注册的 VMA,stable tree + unstable tree 维护,Linux 2.6.32 (2009) 起可用(docs.kernel.org/admin-guide/mm/ksm.html)。KSM 最初为 KVM overcommit 设计,核心约束:

  • 必须进程主动 madvise(MADV_MERGEABLE);
  • 不扫描未注册区域(Kubernetes 容器需在运行时显式启用,否则无收益);
  • 共享页一旦被任一写方触发 COW,就会 unmerge;频繁写入的工作负载(KSM 称之为 COW-broken)几乎没收益;
  • 用户态可调: pages_to_scan、sleep_millisecs、max_page_sharing(默认 256)、stable_node_chains_prune_millisecs 等。

UKSM (FAST '18, Nai Xia 等):在 KSM 之上做了三层贡献——

  1. 全系统扫描:不再需要 madvise,自动遍历所有匿名 VMA;
  2. rich-area 检测:对重复率高的热区全速扫描,对稀疏区采样;
  3. thrashing 过滤:主动跳过 COW-broken 区域。

关键基准数字(来源 usenix.org/system/files/conference/fast18/fast18-xia.pdf):

  • 同 CPU 开销下(2/10/20% one core),UKSM 节省内存是 KSM 的 3~5 倍;
  • 在 25 个 KVM VM 启动场景中,UKSM 合并 5.3 GB,KSM 仅 1.7 GB,约 3×;
  • Docker 容器无法被 KSM 处理(Docker 镜像层不 madvise),UKSM 可直接合并;
  • native 场景 UKSM 性能惩罚 < 3%,虚拟化场景 < 1.8%。

Para-KSM (USENIX ATC '25):用 Intel DSA(Data Streaming Accelerator)做并行 hash + 多页比较,每 CPU cycle 去重吞吐比 KSM 高 31-50%,性能退化降低到原来的 1/1.3~1/2.7(usenix.org/system/files/atc25-ji.pdf)。

腾讯 KSMRT:腾讯云基于 KSM 的生产实践,腾讯在 KVM 集群启用 KSM 后报告宿主利用率显著提升(具体规模未在公开论文披露完整数字,但被多次复述;本报告不引用未核实百分比,标注「腾讯 KSMRT 在大规模 KVM 集群有公开案例,具体节省数字以厂商原始资料为准」)。

反幻觉校验:所谓"100 个 VM 共享 90% 内存"是营销话术——具体数字取决于工作负载的可去重页比例,基线 25 VM 实验中 UKSM 也只是把 5.3 GB / N 拼凑出来,而不是 N×2 GB → N×0.1 GB。

3.1.5 持久内存 PMEM(Intel Optane 已停产 + 替代方案)

关键事实:Intel 在 2022 年 Q2 财报(2022-07-29) 中确认将逐步退出 Optane 业务,减值 5.59 亿美元库存;Micron 早在 2021 年就将 3D XPoint 工厂出售给德州仪器(datacenterdynamics.com/en/news/intel-kills-off-optane-memory-...,tomshardware.com/news/intel-kills-optane-memory-business-for-good,intel.com/content/www/us/en/support/articles/000091826/...)。当时主要受影响的下游厂商:Vast Data(用 Optane 做写缓冲)、Oracle(Exadata)、MemVerage(Big Memory 软件定义内存池)。

替代方案:

  • CXL Type-3 + DRAM 是当下最主流:DRAM 容量大、延迟低、可池化,但失去字节级持久性;
  • CXL Type-3 + NAND/QLC 提供「内存命名空间 + 后端 NAND」的廉价大容量,延迟比 DRAM 高 ~200-400 ns;
  • Samsung CMM-H(3.1.4 节)是 DRAM+NAND hybrid 的代表,DRAM 写入持久化、NAND 做容量后备(storagenewsletter.com/2024/03/22/...);
  • KIOXIA / Samsung 在开发的 CXL-NAND type-3 设备,目标替代 Optane 的「内存语义 + 大容量」定位。

Optane PMEM 时代的遗产:DAX(Direct Access)、mmap(MAP_SYNC)、fsdax / devdax 三种访问模式仍保留,只是底层介质由 Optane 换成 CXL-attached DRAM 或 Compute Memory。

3.2 存储端机制

3.2.1 NVMe-oF 与 RDMA

NVMe-oF(NVMe over Fabrics)用三种传输承载 NVMe 命令:TCP、RDMA(RoCEv2 / InfiniBand)、Fibre Channel。

  • TCP:标准以太网上跑,无需专用 NIC;Kubernetes 事实首选。CPU 占用高于 RDMA,但部署简单(simplyblock.io/glossary/nvme-over-fabrics-transport-comparison/)。
  • RDMA:最低延迟、CPU 占用最低,但要求无损以太网(RoCEv2 需要 PFC + ECN)、支持 RDMA 的 NIC(Mellanox ConnectX 系列、Intel E810)。SPDK 24.01 性能报告同时给出 Mellanox ConnectX-5 Ex 和 Intel E810-CQDA2 的 NVMe-oF TCP 测试数据(spdk.io/news/2024/03/07/Performance_Report_Update/)。
  • FC:沿用现有 SAN 运维流程,适合传统大型机/SAN 客户。

关键参考实现:SPDK 提供用户态 NVMe-oF target,2025-2026 仍持续演进 —— v25.05 (2025-05) 加入 NVMe PCIe 中断模式;v25.09 (2025-09) 加入 NVMe 1.4 / NSSR;v26.01 LTS (2026-01) 支持 NVMe 2.0 target;v26.05 (2026-05) 加入 NVMe KV 与 JSON-RPC schema 生成(spdk.io/ 首页与 release notes)。

3.2.2 用户态块驱动:SPDK / io_uring / XDP

SPDK(BSD-3-Clause):用户态 NVMe 驱动,poll-mode + thread-per-core + 无锁队列,通过 uio/vfio 把 PCI BAR 直接 MMIO 给用户态进程。SPDK v26.01 LTS 自称 1 年支持期(spdk.io/)。

SPDK vs io_uring vs libaio 实测(来源:ijraset.com/research-paper/evaluating-the-performance-of-spdk-based-io-uring-and-aio-block-device,spdk.io/doc/userspace.html):

  • SPDK 在 4KB 随机读场景可获 2.6× IOPS/core(vs fio+kernel);
  • io_uring 用 2× SPDK 核心数时性能可逼近 SPDK——证实 io_uring 是「内核可承受的近似用户态」折中;
  • libaio 引入 kernel 上下文切换与 page cache,在高并发下劣势明显。

XDP(eXpress Data Path):在内核 NIC driver hook 处跑 eBPF 程序,早于 socket 层做包处理,通常用于 L3/L4 加速而非块存储,但与 SPDK/DPDK 同属「绕过内核协议栈」理念。

io_uring(Linux 5.1, 2019):SQE/CQE 环形队列 + 用户态提交,内核 6.x 持续扩展(io_uring-cmd 支持 NVMe 命令直接提交、io_uring_enter 标志、registered buffers 零拷贝)。Linux 6.10+(2024-2025)新增 futex2、multishot accept 等。io_uring 与 CRIU 不兼容:checkpoint/restore 时 ring file descriptor 状态难序列化,需 seccomp 关闭 io_uring(chopratejas/gpu-checkpoint-benchmarks/setup.sh 显示在 seccomp profile 里禁用 io_uring)。

3.2.3 流式加载:Stargz / SOCI / nydus / Dragonfly

问题:传统 docker pull 顺序为「下载 layer → 解压 → 合并 rootfs → start container」,FAST '16 论文给出 pull 占容器启动时间 76%(stargz-snapshotter README)。2 GB 镜像在 100 Mbps 网络下最少 160 s + 解压时间。

三家 lazy-pulling snapshotter 横向对比(数据综合自 pistack.xyz/posts/2026-05-10-...-guide/、stargz-snapshotter README、dragonflyoss/nydus README):

指标 Standard Pull Stargz (eStargz) Nydus SOCI
500 MB 冷启动 ~45 s ~3 s ~2 s ~4 s
2 GB 冷启动 ~180 s ~5 s ~3 s ~6 s
Index 开销 N/A ~5% ~2% ~3%
首次拉取带宽 100% ~15% ~10% ~12%
后启动命中缓存 100% ~5% ~3% ~5%

对应「冷启动减少 ~90%+」「带宽节省 85-90%」量级。

eStargz(containerd/stargz-snapshotter,CNCF):gzip 兼容,通过 tar footer + 预计算索引让 OCI registry 无需修改即可承载;ctr-remote image optimize 支持 workload-based prefetch hit prediction。 Nydus(dragonflyoss/nydus,CNCF,出自阿里 Ant Group):RAFS 二进制格式,默认 128 KB chunk,bootstrap(几 KB) + blob 双文件,chunk 级去重跨层/跨镜像生效;Rust 编写;生产环境网络延迟降低 80%+(dragonflyoss/nydus README)。 SOCI(awslabs/soci-snapshotter,AWS):保留原 OCI 层完全不变,额外加一个 zTOC(zstd Table of Contents)层作为单独 OCI manifest;与 ECR 深度集成;面向「零图像格式改动」诉求。

3.2.4 按需块级分发:lazypull / sparse-page

  • containerd 把 snapshotter 设计成 proxy plugin,通过 gRPC 与外部 snapshotter 通信,因此三种实现均可不改 containerd 主干即接入;
  • ctr-remote 提供远程 lazy pull,只下载 manifest + 必要 chunks;
  • Firecracker demand-paging + MAP_PRIVATE(firecracker/docs/snapshotting/snapshot-support.md):guest 内存文件 mmap 为只读私有映射,page fault 时再从 backing file 载入,写入走 CoW 到匿名内存。代价:memory file 必须全程保留——这是设计取舍,不是 bug。
  • NBD(Network Block Device):qemu-nbd 把 QCOW2 镜像以 NBD 协议导出,支持 -B bitmap 选项把 qcow2 持久 dirty-bitmap 通过 qemu:dirty-bitmap:<name> 元数据上下文推送;NBD client 借此只读被修改过的块(qemu.org/docs/master/interop/nbd.html、manpages.ubuntu.com/.../qemu-nbd.8.html)。NBD + dirty-bitmap 是真正在生产中使用的「增量分发」通道(QEMU 增量备份、Proxmox、Ceph)。

3.3 快照与恢复机制

3.3.1 Firecracker snapshot

Firecracker 快照由两份文件构成:snapshot_file(VM 状态 + 设备模型)和 mem_file(guest 物理内存)。两种 mem_backend:

  • File:对 mem_file 做 MAP_PRIVATE,内核按需分页,写时 CoW;
  • Uffd:用独立用户态进程响应 page fault,支持 2MB hugetlb。

官方性能基线(firecracker/docs/snapshotting/snapshot-support.md):Intel m5d.metal、2vCPU/512MB/1 block/1 net device,snapshot resume p50 < 8 ms,p90 < 5 ms;ARM m6g.metal p50 < 3 ms。Diff snapshot 通过 KVM dirty page log 自动只保存上次快照后被修改的页。

AWS Lambda SnapStart(docs.aws.amazon.com/lambda/latest/dg/snapstart.html、systeminternals.dev/aws/lambda/、dataa.dev/2026/04/21/...):

  • 发布版本时 Lambda 用 Firecracker 拍下「init 完成后」的内存+磁盘快照,加密落 cache;
  • Cold start 时直接 restore + 跑 handler,典型 Java/C# cold start 从 ~6 s 降至 < 200 ms 量级;
  • 2026-04 数据 dataa.dev:2 GB Java 单体端点 + SnapStart → 约 150 ms 从 0 到可响应;
  • SnapStart 仅对 Java(首发)、Python、.NET(2024-2025)开放;Python 必须用 @register_before_snapshot / @register_after_restore 钩子重新初始化随机数、网络连接、临时凭据(dev.to/aws-builders/.../59mn)。

3.1.1 节 Sandlock fork 数字与本节对比:同样派生 1000 个隔离环境,Sandlock fork 在单进程内 718 ms(每 clone 680 µs,共享 ~4 KB 页表),Firecracker 快照派生约 150 s 量级(每 VM ~150 ms + 网络/资源初始化)。量级差 ~200×,但前者受困于 host kernel,后者提供 guest kernel 隔离。

3.3.2 CRIU 用户态检查点

CRIU 自 Linux 2.6.x 时代起就在持续演进,把进程状态(内存映射、寄存器、fd 表、socket、信号量、timerfd、pidfd…)dump 到 image 集合,然后用相同 image 还原。

  • 增量 checkpoint 由 --track-mem 实现(KSM 风格周期性扫描)但生产用例少见;
  • lazy-pages 自 Linux 4.11 起可用——criu restore --lazy-pages 注册 UFFD VMA,criu lazy-pages 守护进程响应缺页,可从本地 image 或远程 criu dump --lazy-pages 启的 page server 取页(criu.org/Userfaultfd)。

实战基准(github.com/chopratejas/gpu-checkpoint-benchmarks README,vLLM + Qwen2-1.5B-Instruct):

指标 Baseline cold start CRIU restore Speedup
TFFT (Time-to-First-Token) 30-50 s 1-3 s 10-30×
Container Start 1-2 s – –
Restore – 0.3-1 s –
Model Load 25-45 s – –
Reinitialization – 0.5-2 s 15-30×
Inference TFFT 0.5-1 s 0.3-0.8 s 1.5-2×

扩展性:7B 模型 15-30×,13B+ 模型 20-50×(README 经验值)。核心收益 = 跳过 model load(权重已在 GPU VRAM)+ 跳过 CUDA context init + 跳过 Python runtime 预热。

生产案例:ContainerCheckpoint / restore 在 Kubernetes 上已有官方 guidance(oneuptime.com/blog/post/2026-02-09-container-checkpoint-restore-criu/),Podman podman container checkpoint 走 runc → CRIU 链路。

3.3.3 VM live migration

QEMU live migration 三阶段:load + dirty page bitmap + 反复迭代至 dirty < 阈值 + 最后 stop-and-copy;存储侧用 NBD + dirty-bitmap 做「只迁 dirty 块」(详见 3.2.4)。 AWS EBS 快照:S3 持久化,新 EBS 卷从快照恢复是懒加载——访问未拉取的块首次延迟会升高;Fast Snapshot Restore (FSR) 预热可在创建时即全部 hydrate(aws.amazon.com/blogs/storage/addressing-i-o-latency-when-restoring-amazon-ebs-volumes-from-ebs-snapshots/)。 Ceph RBD 快照克隆:父快照 + COW clone,创建即瞬时,与大小无关;只存 divergent block(docs.ceph.com/en/latest/rbd/rbd-snapshot/、oneuptime.com/.../rook-clone-rbd-images-from-snapshots-copy-on-write/)。Kubernetes PVC 从 VolumeSnapshot 恢复本质是 RBD clone。 Longhorn / OpenEBS 类似:RBD-clone 风格在 Longhorn 的「base image + snapshot」,OpenEBS cStor/Jiva 也都用 thin snapshot + CoW。

4.1 L7 应用层语义防御

4.1.1 为什么 L7 防御在 AI Agent 场景被重新定义

AI Agent 与传统 Web 服务的最大区别在于:它把"用户输入"和"工具返回 / RAG 检索文档"放在同一个上下文窗口里,并把这段文本直接拼接到具有工具调用能力的系统提示词之后。这使得 Prompt Injection 不再是"绕过聊天机器人的越狱",而是直接面向 RAG、工具调用、代码执行的运行时攻击面。OWASP 在 2024 与 2025 持续把 LLM01 Prompt Injection 列为大模型应用的首要威胁。

L7 语义防御的目标是把攻击者在"数据通道"塞进来的恶意指令,在进入模型上下文之前拦截;同时把模型输出里违反策略的内容,在出栈时拦截。这一层并不替代底层隔离,而是与 VMM/TEE/内存加密构成纵深防御。

4.3 硬件内存加密与控制流完整性

4.3.1 内存加密矩阵

  • AMD SME(Secure Memory Encryption):Milan 起全栈默认开启,使用单一 AES-XTS 密钥。SEV 是其 VM 级扩展,SNP 增加完整性。
  • Intel TME(Total Memory Encryption) / MKTME(Multi-Key TME):Ice Lake / Sapphire Rapids 起支持 TME;MKTME 提供每域密钥,TDX 直接基于 MKTME 的子集实现多 TD 隔离。
  • Apple Secure Enclave(题外但常被对照):独立 SoC,与主 CPU 物理隔离,自研 SEP。

4.3.2 控制流完整性(CFI)

  • Intel CET(Control-flow Enforcement Technology):从 Tiger Lake / 12th Gen Core 起正式落地,包含 Shadow Stack(返回地址硬件副本,RET 时比对)+ IBT(Indirect Branch Tracking),ENDBR64/ENDBR32 标记合法间接跳转目标。Alder Lake(12 代)Datasheet 明确列出 CET 支持。
  • ARM PAC(Pointer Authentication):Armv8.3-A 引入,用 QARMA 算法对返回地址签名;BTI(Branch Target Identification) 是 Armv8.5-A 引入,与 Intel IBT 类似,要求目标指令为 BTI。
  • AMD:Zen 4 起支持 CET Shadow Stack 与 IBT(与 Intel 二进制兼容)。

NVMe Sanitize(Block Erase / Crypto Erase / Overwrite) NVMe 1.3+ SSD Block Erase 分钟级;Crypto Erase 秒级 NVMe 1.3 引入,最彻底
TCG OPAL / IEEE 1667 Crypto Erase 自加密 SSD(SED) 秒级 仅在硬件加密可信实现时有效

4.4.3 HDD 与物理销毁

  • ATA Secure Erase(传统 HDD)、Degauss(仅对磁性介质有效,>5,000 Oe 对现代高矫顽力 HDD,>7,000 Oe 对 LTO 磁带)、Shredding(NSA 对刚硬磁盘要求 ≤ 2mm 颗粒)、Disintegration / Pulverization / Melting(高保密级)。
  • 对企业级 SSD 的 DoD 5220.22-M 多遍覆盖是错误方法:覆盖不能触达 wear-leveled 与 over-provisioned 区域,必须用 NVMe Sanitize 或 Crypto Erase。

4.4.4 云端"加密粉碎"(Crypto-shredding)

  • AWS:EBS 默认加密;客户可用 KMS 自管密钥,删除密钥即可"粉碎"该密钥保护的所有快照与卷。
  • GCP:Persistent Disk 默认 CMEK/SSE-KMS,删除密钥版本即擦除对应数据;同时支持 Application-layer CMEK。
  • Azure:Disk Encryption Set(CMK)+ Azure Key Vault HSM,删除 key version 等同销毁。

4.4.5 AI Agent 场景的合规映射

GDPR Article 17(被遗忘权)、HIPAA、CPRA 均要求"不可恢复地销毁"。对 agent 而言,模型权重、训练数据缓存、日志、checkpoint 都需要在租户退出时执行 crypto-shredding + NVMe Sanitize 双重流程。

4.5 2024-2026 关键 CVE 与安全事件

4.5.1 CPU 侧信道/微架构

  • Spectre v2 变种(BHI / Spectre-BHB,2022):Linux 内核 6.5+ 引入 BHI 缓解(spectre_bhi=off)。2024-2025 期间未发现新的 Spectre v2 大规模武器化样本,但仍是多租户场景的关键风险。
  • CVE-2022-40982 Downfall:2023-08 披露,6-11 代 Core 与 1-4 代 Xeon Scalable,影响几乎所有 Intel 主流消费/服务器线。Tom's Hardware 2023-08-10 报道缓解使某些 AVX-512 工作负载性能下降最高 39%。
  • CVE-2023-23583 Reptar:2023-11 披露,Google Tavis Ormandy 在 Project Zero 报告。Intel 评估CVSS 8.8 High。
  • CVE-2024-2193 GhostRace:2024-03 披露,USENIX Security 2024 收录,Linux 944d5fe50f3f 补丁 + AMD SB-7016 + Xen XSA-453。
  • CVE-2024-27457 TDXDown:CCS 2024 论文,Intel 在 TDXModule 1.5.06 加入单步防御增强,但StumbleStepping 仍需应用层缓解(OpenSSL/wolfSSL 已修复 ECDSA nonce 问题)。

4.5.2 虚拟化与 microVM

  • Firecracker:2020 历史 CVE-2020-27174(串口缓冲内存泄漏)、CVE-2020-16843(网络栈 DoS);2024-2026 新增 CVE-2026-1386(jailer symlink,AWS Lambda/Lambda@Edge 修复)、CVE-2026-5747(virtio PCI OOB write,1.13.0-1.14.3、1.15.0)。AWS 自家 Lambda/Fargate 不受影响(2026-003 公告明示)。
  • QEMU:QEMU 在 2024-2025 持续披露多个 VM 逃逸类 CVE(典型如 VIRTIO/IOMMU 越权),影响 gVisor/kata 等用户态 hypervisor 形态。
  • gVisor:Google 在 2024-2025 持续为 GKE Sandbox 推送安全更新,核心 send/recv syscall filter 多次加固。
