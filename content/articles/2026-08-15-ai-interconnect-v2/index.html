Part 1内存墙 4.0 + 互联必要性

2026 年 LLM 训练/推理遇到的根本性瓶颈不是算力, 而是数据如何在硬件单元间流动. 这一节建立"为什么需要互联"的物理基础.

1.1 Memory Wall 4.0 是什么

Memory Wall (内存墙) 是 1989 年 Wulf & McKee 提出的概念. 2026 年的"Memory Wall 4.0"有 4 层含义:

  1. 1.0 (1989-2010): CPU 与 DRAM 之间的速度差距 (CPU GHz vs DRAM ns).
  2. 2.0 (2010-2020): GPU 出现后, GPU 算力增长远快于 HBM 带宽增长 (DeepSeek-V3 paper 论证).
  3. 3.0 (2020-2024): 大模型 KV Cache 显存爆炸, 单卡 HBM 装不下 70B 模型长上下文 KV.
  4. 4.0 (2025+): 单卡 HBM 装不下 V4-Pro 1.6T 模型 KV (1M ctx 时 2300+ MiB/req), 必须跨卡池化 KV Cache.

💡 为什么 Memory Wall 4.0 必须用跨卡互联? V4-Pro 1.6T 模型 KV Cache 1M ctx 单请求 ~2300 MiB, batch=32 即 ~73 GB. B200 单卡 192 GB HBM, 看似装得下, 但: (1) 模型权重 ~3 TB 占 HBM; (2) batch=128 时 KV ~290 GB > 192 GB; (3) 多用户共享 batch. 物理层结论: KV Cache 必须跨卡/跨节点/跨域池化, 不是单卡优化. 这就是 2026 互联方案爆发的根本原因.

1.2 为什么 KV Cache 必须跨卡 — 数学推导

KV Cache 大小公式: 2 × L × B × S × H_kv × d_h × bytes. V4-Pro 真实参数:

参数数值含义
L (层数)~80 (估, V4)Transformer 层数
B (batch)32 (生产)并发请求数
S (sequence)1M ctx上下文长度
H_kv~128 (V4 MLA 压缩后)KV 头数
d_h576 (MLA latent)每头维度
bytes2 (FP16) / 1 (FP8) / 0.5 (FP4)每元素字节

FP16: 2 × 80 × 32 × 1M × 128 × 576 × 2 ≈ 73 GB (batch=32). FP8 → 37 GB. 配合 MLA 压缩到 10% → 3.7 GB/req.

1.3 互联 4 层 — 从硬件到协议

AI 互联按"距离"分 4 层, 每层解决不同问题:

  1. 层 1 (intra-GPU): SRAM↔HBM↔HBM3e, NVLink-C2C (Grace Hopper) — 芯片内, 不算"互联"
  2. 层 2 (intra-node): NVLink 5/6 / NVSwitch / Infinity Fabric — 8 卡单 node, 1-10 TB/s 域
  3. 层 3 (inter-node): CXL / InfiniBand / RoCE / 灵衢 UB / NVLink-C2C over PCIe — 跨 node, 100-200 GB/s 域
  4. 层 4 (inter-DC): 800G/1.6T Optical / Edge Cache (Cloudflare AI Gateway) — 跨 DC, ms 级域
📌 阅读指南 本文按"协议家族 → 硬件代表 → 软件栈 → KV Cache 落地" 4 维组织. 每章末尾有"为什么这样设计"物理层分析, 不只是列产品参数.

Part 2CXL 全家族 (3.0 / 3.1 / 3.2 / 4.0) — 内存池化协议

CXL[1] (Compute Express Link) 是 2019 年 Intel 提出的开放标准, 目标是让 CPU/GPU/加速器/CXL 内存设备共享统一内存地址空间. 2026 是 CXL 3.0+ 商用元年.

2.1 CXL 协议栈 — cache / mem / io 三合一

CXL 在 PCIe 物理层上跑 3 个独立子协议:

子协议作用等价于典型延迟
CXL.io设备发现 + DMA + 中断PCIe~500 ns
CXL.cache设备侧缓存 CPU 内存类似 CCIX / OpenCAPI~150 ns
CXL.memCPU 访问设备侧内存 (内存池化)类似 NUMA 远端访问~80-120 ns

CXL.mem 是内存池化的核心. CPU 通过 load/store 指令直接访问远端 CXL 设备的内存, 无需软件介入 (透明).

CXL.io (设备发现) + CXL.cache (设备缓存) + CXL.mem (内存共享). 基于 PCIe 5.0 / 6.0 物理层, 2025+ 用 PCIe 6.0 PAM4.
💡 为什么 CXL.mem 比 NVLink-C2C 慢? NVLink-C2C (Grace Hopper) ~150 ns, CXL.mem ~80-120 ns (HBM 等价延迟 80-100 ns). CXL.mem 接近 HBM 延迟 的关键: (1) 基于 PCIe 5.0/6.0 物理层 (vs NVLink-C2C 自研 SerDes); (2) 用一致性协议 (类似 MESI) 而非 DMA. 物理层原因: CXL 走标准 PCIe 信号完整性, 不需要 NVIDIA 自研 PCB 材料, 延迟略低但开放生态优势巨大.

Part 3NVIDIA CMX (Context Memory Storage) + Dynamo + BlueField-4

CMX[6] (Context Memory Storage) 是 NVIDIA 2025-GTC 公布的 KV Cache 跨域池化方案. 核心创新: 把 KV Cache 当作 Context Memory (上下文记忆), 不是 "GPU 临时缓存".

CMX 由 4 层组成:

  1. L0 (GPU HBM): 模型权重 + 当前 batch KV, 30-100 TB/s, ~100 GB/GPU
  2. L1 (CMX Memory Tile): 跨 GPU 共享的 Context Memory, ~10 TB/s, ~100 TB (整个 CMX 池)
  3. L2 (CPU DRAM): 1-2 TB/node, 80 GB/s, 冷 KV 备查
  4. L3 (NVMe SSD): 10-100 TB/node, 7 GB/s, 持久化 KV 历史

💡 为什么 CMX 5× TPS 而不是 1.5× 或 2×? 数学推导: KV Cache 命中率 80% (CMX 池化前 40% 单卡) × decode 加速比 4× (KV miss 时延 4ms → 1ms) × prefix reuse 节省 prefill 6× → 综合 TPS 提升 5×. 物理层: CMX 让 GPU 不再"等 KV 计算" (传统 70% decode 时间在等 KV 读 HBM), 而是"等 KV 传输" (CMX RDMA ~1ms), 时间差 5×.

3.2 BlueField-4 DPU — CMX 的计算心脏

BlueField-4[7] (2026-Q3 量产, 估) 是 CMX 的 DPU 端:

  • 16 核 ARM Neoverse + 16 GB DDR5
  • ConnectX-8 400 GbE 网络
  • PCIe 6.0 ×16 主机接口
  • DOCA Memos SDK 提供 Context Memory API

BlueField-4 在 CMX 中的角色: 把 CPU DRAM + NVMe SSD 暴露为 GPU 可直接访问的 Context Memory 抽象, 类似 NVIDIA GPUDirect Storage 但语义层更高 (不是"存储", 是"记忆").

3.3 Spectrum-X SN6800 — 102.4 Tb/s 首个 CPO POD 互联

Spectrum-X SN6800[8] (2026-Q1 量产) 是业界首个 CPO (Co-Packaged Optics) POD 互联 switch:

  • 102.4 Tb/s 总带宽 (vs SN5600 51.2 Tb/s, 2× 提升)
  • CPO 光学: 51.2 Tb/s 光引擎集成到 switch ASIC (vs 传统可插拔光模块)
  • 512 × 800G 端口 或 1024 × 400G 端口
  • 功耗: 30W/port (vs 传统可插拔 15W/port 但距离 2m → CPO 距离 100m+)
💡 为什么 Spectrum-X 用 CPO 而不是可插拔光模块? CPO 把光引擎集成到 switch ASIC 内部, 距离从 2m (可插拔) → 100m+ (CPO). 物理层: 可插拔光模块信号完整性损失随距离指数增长, 2m 后衰减 6 dB. CPO 距离 100m+ 后衰减仍 < 1 dB. 代价: switch ASIC 必须支持光引擎 (工艺复杂), 量产难. NVIDIA 2025 解决.

3.5 5× TPS 数学 + STX 部署路径

5× TPS 数学推导 (NVIDIA GTC 2025 keynote 给的公式):

# 5× TPS 推导 (简化) 传统部署: TPS_base = 1 / (TTFT + decode_len × TPOT) CMX 部署: TPS_cmx = (1 - miss_rate) × TPS_cache_hit + miss_rate × TPS_miss = 0.7 × 5 × TPS_base + 0.3 × TPS_base # 70% hit 5×, 30% miss 1× = 3.5 × TPS_base + 0.3 × TPS_base ≈ 5× × TPS_base

STX (Spectrum-X Trade) 部署路径: NVIDIA 推荐 3 阶段部署 CMX:

  1. Stage 1 (评估期): 单 node 内 CMX 试点, 1 个 SN6800 + 8 个 BlueField-4
  2. Stage 2 (Pod 期): 跨 node CMX 池化, 16 个 SN6800, 1024 个 BlueField-4
  3. Stage 3 (Zone 期): 跨 DC CMX 池, 256 个 SN6800, 全 zone 共享 Context Memory

Part 4华为灵衢 UnifiedBus 2.0 + Atlas 950 SuperPoD

灵衢 (UnifiedBus)[9] 是华为自研的统一互联协议, 2025-09-18 HC2025 公布 2.0 版本. 配套硬件 Atlas 950 SuperPoD (8,192 NPU, 8 EFLOPS FP8).

4.1 灵衢 4 层协议架构

灵衢协议栈 4 层:

  1. 物理层: 200 Gbps SerDes × 64 lanes = 12.8 Tbps/port
  2. 链路层 (UB-LLC): credit-based flow control + retry + CRC
  3. 传输层 (UB-TL): RDMA-like + DCQCN 拥塞控制
  4. 应用层 (UB-AL): 集合通信 (AllReduce/AllGather/All-to-All) + KV Cache 传输 + 内存语义
💡 为什么灵衢单 port 带宽是 NVLink 6 的 3.5×? 灵衢 2.0 用 200 Gbps SerDes × 64 lanes, NVLink 6 用 200 Gbps × 18 lanes. 华为选择"少 lanes 高频率"路线, NVIDIA 走"多 lanes 中频率"路线. 物理层原因: 高频率 SerDes 信噪比劣化更快, 灵衢用更先进的 PCB 材料 (low-loss CCL) + 更好的 DSP, 让 200 Gbps/lane 在更长距离稳定.

Part 5Google TPU ICI + OCS (Ironwood 9,216 chip)

Google TPU 互联方案从 v4 开始独立发展, ICI (Inter-Chip Interconnect) 是核心, OCS (Optical Circuit Switch) 是杀手锏.

5.1 TPU 历代互联演进

TPU 版本年份ICI 单 chip 带宽典型 Pod 规模OCS
v22017~500 Gb/s (估)256 chip无
v32018~656 Gb/s1024 chip (2D torus)无
v42021~1.2 Tb/s4096 chip (3D torus + OCS)✓ 首次

v6 Trillium2024~900 Gb/s (估)1024 chip✓
v7 Ironwood2025-111.2 Tb/s9,216 chip (24×24×16 3D torus)✓ 多级
💡 为什么 TPU v7 ICI 带宽反而比 v5p 略低? v7 Ironwood 是推理旗舰, 不是训练. 推理 KV Cache 已压缩 (MLA + FP8), ICI 带宽需求 < 训练 (训练需要 AllReduce). 物理层: 推理 workload 70% 时间在等 KV 读 HBM, ICI 带宽需求相对降低. Google 故意压低 ICI 成本, 提升单 chip HBM (192 GB) 和算力.

5.2 Ironwood 3D torus + OCS 推理架构

  • 3D torus: 24 × 24 × 16 chip 拓扑 (chip 排列在 3D 网格, 每 chip 6 个邻居)
  • ICI: 1.2 Tb/s/bidirectional, 全双工
  • OCS: 物理层光交换, 可动态重配置 torus 拓扑

5.3 OCS 工作原理

OCS[10] 用 MEMS (Micro-Electro-Mechanical Systems) 微镜阵列实现光路切换:

  • switch 时延 ~10ms (机械微镜旋转到位时间)
  • 单 OCS 端口带宽 1.6 Tb/s
  • 物理层: 无 packet 处理, 纯物理层切换
  • Gemini 3 不同任务 (长 ctx / 短 ctx / batch / streaming) 自动用不同 torus shape

5.4 TPU ICI vs NVLink — 域大小 vs 延迟

维度TPU v7 ICINVIDIA NVLink 6
最大域9,216 chip (3D torus)576 chip (Rubin Ultra 估)
拓扑3D torus + OCS 动态Fat-Tree + NVSwitch
switch 数量~400 (估)144 (Rubin Ultra)
ICI 延迟~500 ns (跨 1 chip) → ~5 μs (跨 pod)~150 ns (同 switch)
OCS 切换延迟10 ms (一次性)N/A
总带宽 (单 pod)11 Pbps (9,216 × 1.2 Tb/s)207 TB/s (576 × 3.6 Tb/s / 8)
💡 为什么 Google 选 3D torus + OCS 而不是 NVLink 风格的 Fat-Tree? Fat-Tree switch 数量 O(N log N) 增长. 3D torus switch 数量 O(N^(2/3)) — 9,216 chip 只需 ~400 switch (15× 优势). 物理层: torus 让每个 chip 既做 compute 又做路由, 总硬件成本降 60%. 代价: 长距离延迟高, OCS 解决 — 按 workload 动态切拓扑, 让短距离通信走最少 hop.

Part 6阿里 AI 互联 (PPU + ICN + 磐久 + ALink + EIC + CIPU)

阿里在 AI 互联方案上最复杂, 涉及 6 大子系统, 跨芯片/网络/存储/容器/数据库. 这一节讲清"为什么阿里需要这么多层".

6.1 真武 PPU + ICN Switch 1.0

真武 PPU (阿里自研 GPU, 2025-09 公布) + ICN Switch 1.0 (阿里自研互联 switch):

  • 真武 PPU: ~2 PFLOPS FP16 (估), 80 GB HBM, HBM2e (阿里第一代 GPU, 不算 SOTA)
  • ICN Switch 1.0: 6.4 Tbps 单 port, 256 port, 1.6 Pbps 交换容量
  • 对标 NVIDIA NVLink + Spectrum-X, 但阿里生态 (Qwen / 灵骏 / 磐久)
💡 为什么阿里做真武 PPU 而不是只用 NVIDIA? 三个原因: (1) 成本: NVIDIA H100 单价 ~$30k, 真武 PPU 估 ~$10k, 3× 优势; (2) 国产化: 阿里承担"国产替代"国家战略任务; (3) 供应链安全: 美国出口管制 H100/H200 高端 GPU 给中国, 真武 PPU 不受限. 物理层: 真武 PPU 用 HBM2e 而非 HBM3/HBM4, 落后 NVIDIA 一代, 但 性价比 3× 是中国市场的关键.

6.2 磐久 AL128 + ALS/ALink + EIC + CIPU + 灵骏

阿里 5 大 AI 基础设施:

ALink 单 port 3.2 Tbps/GPU 是关键 (vs NVLink 4 900 GB/s). 这是阿里"自研 + 高带宽"策略的胜利.

6.3 阿里 KV Cache 共享 — PAI FlashKV + Tair KVCache

阿里 KV Cache 方案 (与 NVIDIA CMX 思路类似, 但用自研软件):

  • PAI FlashKV: 阿里云 PAI 平台的 KV Cache 池化 (类似 Mooncake), 2026-Q1 GA
  • Tair KVCache: 基于 Tair (阿里自研 Redis 兼容 KV 存储) 的 KV Cache 持久层, 100+ TiB
  • 百炼 Session Cache: 兼容 Anthropic Prompt Caching API, 1h TTL, 50% off

💡 为什么 UALink 1.0 比 NVLink 6 慢但域更大? UALink 1.0 是联盟标准, NVLink 是NVIDIA 私有. 联盟标准必须平衡所有成员的需求, 性能不及最强者. 物理层: UALink 用标准 PCIe 6.0 PAM4 信号 (成熟工艺), NVLink 6 用 NVIDIA 自研 SerDes (更快但非标). 域更大是因为多家厂商可生产 ASIC (Broadcom / Marvell / Cisco).

7.3 Ultra Ethernet 800G/1.6T

Ultra Ethernet[12] (UEC 联盟 2025-06 发布 1.0 spec) 是 AI 专用以太网:

  • 800G/1.6T 标准, 2026 H1 商用 ASIC 三足鼎立: Broadcom Tomahawk 6 / Marvell Inphi / Cisco Silicon One
  • 延迟 ~500 ns (vs InfiniBand HDR 200 Gb/s ~600 ns)
  • 适合大规模 training/inference, 1.6T 用于跨 rack
  • RDMA-like 传输层, 软件兼容 RoCE
💡 为什么 Ultra Ethernet 1.6T 延迟比 InfiniBand HDR 还低? InfiniBand 是 1999 年的标准, 信号路径长 (~600 ns PHY + 协议栈). Ultra Ethernet 1.0 用 PCIe 6.0/7.0 PAM4 信号 (成熟) + 简化协议栈 (RDMA-like 而非完整 IB transport), 物理层延迟 ~500 ns. 代价: Ultra Ethernet 不支持 IB 的可靠传输特性, 软件层需补.
