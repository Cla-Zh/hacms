2.1 V1 引擎核心：三进程职责分离

V1 的运行时是明确的三角色进程模型：前端进程持有 AsyncLLM（async_llm.py:80），内含 InputProcessor（input_processor.py:41）与 OutputProcessor（output_processor.py:464）；EngineCoreClient 按部署形态五选一——Inproc(:343) / SyncMP(:906) / AsyncMP(:1086) / DPAsyncMP(:1366) / DPLBAsyncMP(:1550)，由 make_async_mp_client 按 DP+LB 模式裁断（core_client.py:155-170）。引擎进程是 EngineCoreProc（core.py:1088）包裹 EngineCore（core.py:111）：主线程跑 run_busy_loop（:1473），另起两个 daemon ZMQ IO 线程（:1178-1199）专职收发，保证主循环不被 IO 阻塞。

EngineCore.step() 逐行拆解（core.py:633-662，主线亲验） 
def step(self) -> tuple[dict[int, EngineCoreOutputs], bool]:
    """Schedule, execute, and make output."""
    if not self.scheduler.has_requests():          # 641 无请求直接空转
        return {}, False
    scheduler_output = self.scheduler.schedule(    # 643 ① 调度（L3 全部智慧）
        self._should_throttle_prefills())
    future = self.model_executor.execute_model(    # 644 ② 派发执行（非阻塞 Future）
        scheduler_output, non_block=True)
    grammar_output = self.scheduler.get_grammar_bitmask(  # 645 ③ 结构化输出掩码
        scheduler_output)      #     —— 与模型前向"重叠"计算
    with (self.capture_iteration_details(scheduler_output) as iteration_details,
          self.log_error_detail(scheduler_output)):
        model_output = future.result()             # 650 ④ 等执行结果
        if model_output is None:                   # 651 异步流水线模式
            model_output = self.model_executor.sample_tokens(grammar_output)
    self._process_aborts_queue()                   # 656 ⑤ 先处理执行期到达的 abort
    engine_core_outputs = self.scheduler.update_from_output(  # 657 ⑥ 状态推进
        scheduler_output, model_output)
    return engine_core_outputs, scheduler_output.total_num_scheduled_tokens > 0

四个设计细节值得品味：① 调度与执行通过 Future 解耦，为 async_scheduling 的"调度-执行重叠"留下接口；② 结构化输出的 grammar bitmask 在等 future 期间计算——把 CPU 工作塞进 NPU/GPU 前向的影子里；③ abort 在更新状态之前处理，避免已死请求占用新一步资源；④ 返回值的第二分量（本步是否真的跑了模型）喂给 post_step 决定是否提取草稿 token（core.py:664-671）。

2.2 执行器与数据契约：一切归约到 collective_rpc

Executor.get_class（abstract.py:52-96）按 backend 选 uniproc/multiproc/ray/external_launcher；所有执行器把 execute_model 归约到 collective_rpc 原语。MultiprocExecutor（:111）用共享内存消息队列 rpc_broadcast_mq 广播调度输出、worker_response_mq 回收结果，且仅 output_rank 回传（:340-351）——TP 组内只让一名 worker 说话。Worker 链路：WorkerBase（worker_base.py:44）→ WorkerWrapperBase（:212）→ gpu_worker.Worker（gpu_worker.py:182）。

2.4 DP 协调：波次锁步的代价与设计

3.2 三个值得驻足的设计细节

  • EngineCoreRequest ≠ Request：前端产物（跳 5）是传输 DTO；调度侧 Request 在 EngineCore 输入线程里由 from_engine_core_request 重建（跳 6-7）——两个类的分离让前端无法污染调度不变式。前缀缓存键（block hashes）在 Request 构造时就算好（request.py:283-288），不等首次调度。

4.0 核心不变式：没有 prefill/decode 阶段之分

Woosuk 注释（scheduler.py:559-568，主线亲验）

"There's no 'decoding phase' nor 'prefill phase' in the scheduler."——每个请求只有 num_computed_tokens 与 num_tokens_with_spec（= len(prompt)+len(output)+len(spec)，request.py:299-300），调度器每步让前者追赶后者。这个不变式统一覆盖了 chunked prefill、prefix caching、speculative decoding，乃至未来的 jump decoding——阶段模型的消亡正是 V1 调度器比 V0 简洁的根本原因。

4.2 RUNNING 循环：五道跳过闸门与抢占（:624-857）

RUNNING 优先于 WAITING（连续批处理的"老人先走"）。循环内五类跳过：① input_budget 耗尽即 break；② 异步 max_tokens 预判（:631-645，确定已达上限就不多排一步）；③ PP cadence（:647-651，同请求 decode 须隔 pp_size 步对齐广播槽环）；④ DP defer 的 prefill chunk 让位；⑤ 多模态 encoder cache 未就绪让位。

num_new_tokens 钳制链（:670-718）：基值 = num_tokens_with_spec + num_output_placeholders − num_computed_tokens → long-prefill 截断 → min(token_budget, input_budget − draft_slots) → max_model_len 钳制 → Mamba 块对齐 → encoder 调度 → MTP lookahead 预留（chunk 边界不落在 lookahead 内）。为 0 则越过（不堵队，Woosuk 注释 :734-736：调度非严格 FCFS）。

抢占机制全解：重算式抢占（V1 无 swap）与 victim 回滚

allocate_slots 失败进入抢占循环（:741-747）：victim 选择按策略分两路——PRIORITY 取 max(running, key=(priority, arrival_time))（优先级最低且最晚到者，:761-765），FCFS 直接取队尾 running[-1]（:767）。两道保险：延迟释放闸门 _request_blocks_can_be_freed 为否则放弃本轮（:769-771）；PRIORITY 下若 victim 本步已被排过，须回滚其预算/spec/encoder 记账（:773-797）。

_preempt_request（:801-805 → :1539-1582）：释放全部块与 encoder cache、num_computed_tokens=0——V1 是重算式抢占，没有 V0 的 swap-to-CPU；恢复时靠 prefix cache 命中减算（若开 connector 可换出）。被抢占请求 prepend 回 waiting 队首（:1581）保证下一轮最先 reconsider。victim 即自身或无块可腾 → break。

4.3 WAITING 循环：准入、前缀命中与 connector 协商（:868-1352）

仅当本步无抢占且未暂停才接纳新请求（:869）——抢占过的步先消化存量。准入上限 len(running) + num_waiting_for_streaming_input < max_num_active_reqs（:877-879）。

V1 的 KV 管理是清晰的四层：KVCacheManager（对外门面）→ KVCacheCoordinator（多类型协调：full-attention/MLA/滑窗/mamba 混合模型各管一摊）→ SingleTypeKVCacheManager 族（单类型策略）→ BlockPool（物理块池）。核心入口 allocate_slots（kv_cache_manager.py:371-608）分三阶段：① 释放滑窗外块 + 容量检查（watermark / full_sequence_must_fit 准入门）；② 挂载前缀命中块（refcnt+1，不重算）；③ 从 BlockPool 弹新块并 cache 提交——分配上限按 request.num_tokens 计算，不含投机草稿 token。

6.2 前缀缓存：块级哈希链与 LRU 驱逐

块哈希默认 sha256（cache.py:144），采用链式输入：父块哈希 + 本块 token ids + extra_keys（LoRA / 多模态 / cache_salt / prompt_embeds，kv_cache_utils.py:650-680）——链式结构保证"相同前缀的后续块哈希必然相同"，这是跨请求共享的数学基础；cache_salt 混入让租户间无法互相命中，是多租户隔离的暗桩。BlockPool 的空闲队列是双向链表：无哈希块 prepend 队首（LIFO 立即复用），带哈希块 append 队尾（FIFO，最久未命中者先被驱逐）（block_pool.py:776-807），驱逐发生在新分配无块可用时（:668-702）。

6.3 块表与寻址：从 slot 公式到 as_strided 显存池

Worker 侧的 BlockTable（v1/worker/block_table.py:57）以"行=请求、值=物理块 id"组批，经 append_row → commit_block_table（H2D）→ Triton kernel 生成 slot_mapping。寻址公式：slot = block_table[req][pos // B] * B + pos % B（kernel 实现 :466-476）。显存本体是扁平 int8 大池，按 dtype/层数/头数 as_strided 解释成 [L,B,H,N,C]（kv_cache_interface.py:1388-1407）——dtype 可换而池布局不变，这是 fp8 KV cache 零成本切换的根基。块大小默认 16（cache.py:71），后端选择优先级 FLASH_ATTN > FLASHINFER > TRITON_ATTN > FLEX（platforms/cuda.py:83-179）。

CH.08分布式通信与 PD 分离：HCCL 一肩挑的世界

8.1 通信底座：没有 Custom AllReduce 的取舍

vLLM CUDA 侧的通信是一条 7 级选择链（cuda_communicator.py:335-408），顶端是自研 CustomAllreduce IPC kernel（custom_all_reduce.cuh：1-stage :9 / 2-stage :32）——在小消息 TP all-reduce 场景绕过 NCCL 以压低延迟。Ascend 侧的答案截然不同：NPUCommunicator 显式 ca_comm=None（npu_communicator.py:57），不覆写 all_reduce，全部集合通信交给 HCCL（华为集合通信库）：pyhccl_wrapper 仅绑定 6 个 HCCL 函数（HcclGetRootInfo/CommInitRootInfo/AllReduce/Broadcast 等，pyhccl_wrapper.py:113-250），其余走 torch_npu 的 ProcessGroup(hccl)。设备初始化处以后端字符串 "hccl" 调用 init_distributed_environment（worker.py:1243-1245，主线亲验）。

在此之上，Ascend 还创建了若干专用通信组：_MC2（MoE 通算融合）、_DYNAMIC_EPLB（专家动态均衡）、_P_TP（PD 分离）与细粒度 TP 组（distributed/parallel_state.py:132-133），并带 HCCL ProcessGroup 复用补丁（patch_distributed.py:58-76）。

拓扑发现去哪了？

代码库中不存在 HCCS/RoCE/rank_table 的 Python 拓扑发现逻辑（全仓仅 1 条注释命中）——昇腾集群的链路发现完全下沉到 CANN/HCCL 运行时。对开发者意味着：TP/PP/EP 的物理亲和性优化在 Python 层无可调抓手，只能靠通信组划分与算子选择间接影响。

CH.11前沿演进预测：从代码事实出发的外推

⚠ 阅读须知

本章全部内容为预测标注的前瞻判断，不是代码事实。每条预测先列出其外推所依据的代码事实（带锚点），再给出 1-3 年尺度的演进判断与依据说明。事实与观点的边界是本报告的反幻觉纪律。

11.1 CXL 与内存池化：已有抽象的性能拐点

代码事实：① kv_offload 已把存储抽象为二维矩阵 Medium{CPU, STORAGE} × Locality{LOCAL, REMOTE} + TierMatcher 层级匹配（base.py:46-70），tiering/ 下已有 fs/kvcr/obj/p2p 多后端与 ARC/LRU 双策略；② host 注册路径已为超大内存基设计（HiSparse 以 256GiB 为块注册 host memory，hisparse/runtime.py:30）；③ 磁盘后端已做到 GPU DMA 与 pwritev/preadv 双缓冲流水（simple_kv_offload/disk_backend.py:50,294-323）。

预测（1-2 年）：Medium 枚举将出现第三态（CXL/池化内存语义），但 vLLM 无需大改——Locality.REMOTE + p2p tier 已完成"远端内存池"的延迟建模，CXL 池只是新后端注册。真正的变化在调度层：KV 分层从 GPU→本地 CPU→磁盘 三级变为"GPU→CXL 近端池→集群池→存储"四级，TierMatcher 二维匹配成为容量-延迟联合调度核心；块大小（10.4 的 128 vs 16 之争）将被重新拉小——CXL 带宽使小块传输成本下降、碎片收益放大。依据：抽象维度已预留（事实①）；256GiB 大块 host 注册说明设计者在为"内存池远大于单卡 HBM"的世界做准备（事实②）；DMA 流水证明设备旁路拷贝已产品化（事实③）。CXL 对 vLLM 是"已有抽象的性能拐点"，而非新功能。

11.2 超大规模 MoE 专家并行与 Ascend 集群

代码事实：① Ascend EPLB 跑在独立进程（EplbWorker 基于 Process/Queue，经 shared_dict 收发热度、支持 D2D 权重搬迁，eplb_worker.py:29-59），策略插件化 5 种；② MoE 通信四路并存可运行期切换，FusedMC2 内含 MegaMoe HCCL 上下文失效/重建逻辑（moe_comm_method.py:295-339），并已处理"EPLB 动态重排 × 未量化权重未按专家拆分"的冲突（routed_experts.py:188）；③ 编码器缓存已引入 cost-aware 淘汰（score = 频率 × 重算成本，score_ec_manager.py:13-39）。

预测（1-3 年）：三方向将兑现——(a) 专家放置从周期性 rebalance 走向在线连续迁移：EPLB 已是独立进程异步决策（事实①），闭环将从步级收敛到层内流水级，flashlb 类策略会与 mc2 的 512-token 上限联动做容量感知路由；(b) 通信库状态管理成为一等公民：FusedMC2 已在手工维护 HCCL 上下文失效/重绑（事实②），说明 EP 组动态重构（扩缩容、故障切换）是真实负载，将沉淀为类似上游 reconfigure 的正式接口；(c) EPLB 与 EC/KV 缓存策略合流：score-based 淘汰（事实③）证明"重算成本感知"已被接受，专家冷热与 KV 冷热将共用一套成本模型联合调度。依据：三条事实链都显示 Ascend 已把"动态资源重配置"当常态路径在工程化。

11.3 零拷贝 token streaming 与全异步流水线

代码事实：① V1 全部进程间消息为 msgspec.Struct（70+ 处，v1/engine/__init__.py:110-302），msgpack 编解码是显式热路径；② 设备侧已实现"token 不出 GPU"：async 模式 sampled token 驻留 GPU、下步直接注入（gpu_model_runner.py:3741-3747），PP 场景直接 GPU 广播绕过 scheduler 回传（scheduler.py:1679-1694）；③ 但 token 流最后一棒仍是 per-request Python list 拼接（gpu_input_batch.py:77-87），detokenizer 经 msgpack 逐 token 搬运。

预测（1-2 年）：零拷贝沿"GPU→pinned 环形缓冲→IPC 共享内存"路线推进，分两步：(a) EngineCore→detokenizer 的 token 流改走共享内存 + 事件通知，msgpack 只承载控制消息——当前唯一必须序列化的是 token id 数组本体，而 sampled token 在 worker 侧已是连续 device 张量（事实②），落 pinned buffer 后可被同机 consumer 直接 mmap；(b) 调度器"盲调度"范围扩大——async_scheduling 已让 scheduler 用占位符 [-1] 先行（10.2），下一步 stop 判定也异步化/推测化，CPU 流水线容忍 1-2 步投机深度，调度-执行重叠从"单步"扩为"多步流水线"。依据：事实①证明序列化已是被精细管理的显式边界；事实②证明设备侧零拷贝已在关键路径落地；事实③指出剩余瓶颈在 Python 对象模型。风险点：增量 detokenize 需文本边界，纯 id 流将迫使 detokenizer 改为状态机式增量消费。

11.4 稀疏/线性注意力：从模型支持到一等运行时

代码事实：① 上游已出现专用稀疏 KV 数据面 vllm/v1/hisparse/（"resident, host, and hot-cache data plane"，runtime.py:3），调度侧有 resident/hot/source 三层 page 管理器，已支持 fp8 DS-MLA 行格式（656B/行）；② Ascend 全硬件线（A2/A3/A5）Dockerfile 默认安装 flash-linear-attention-npu（Dockerfile:136-150 等三处）；③ vllm_ascend/attention/ 已有 sfa、dsa（v1 与 v41 两代）、sparse_flash_mla、sfa_kv_offload 五个稀疏后端；csrc/attention 下 30+ 算子目录中稀疏/线性族占多数（lightning_indexer 系、sparse_flash_*、recurrent_gated_delta_rule、chunk_kda_fwd 等）。

预测（1-3 年）：(a) "稀疏注意力 + KV 分层"将合并为一个子系统——hisparse 已把稀疏 page 的 resident/host 迁移做成数据面（事实①），下一步稀疏 index（lightning indexer 类）将决定 KV 页在 GPU/CXL/磁盘间的驻留策略："注意力稀疏度"成为分层调度的输入信号而非独立特性；(b) 线性注意力（gated delta rule/KDA 族）在 Ascend 上从"模型支持"变为"一等运行时"——recurrent/chunk 两条 kernel 线并行演进（事实③）且 Dockerfile 全系预装 FLA（事实②），说明在为 hybrid（linear+full 交错）模型常态化备货；mamba 式定长状态缓存会与 KV 管理进一步融合，page 体系需同时容纳"变长 KV 页"与"定长 state 页"；(c) DSA 双版本并存（dsa_v1/dsa_v41）预示快速迭代期，接口稳定后将向上游 MLA sparse 路径收敛。依据：事实①证明上游已接受"稀疏 KV 需要专用调度/数据面"；事实②③的投入强度超出实验性质；block_size=128（10.4）与稀疏块注意力的天然块粒度一致，更像协同设计而非巧合。

12.1 总结论：十个一句话判断

  1. 双核解耦成立且优雅：vLLM 用"契约 + 字符串 qualname + entry_points"把硬件差异完全挡在主干之外，vllm-ascend 以 5 个注入面运行期接管——这是同形态硬件插件（TPU/XPU 之外）最成熟的一个。
  2. V1 调度器是本代引擎的心脏："无 prefill/decode 阶段"不变式 + 双预算 + 统一推进游标，把连续批处理、chunked prefill、投机解码、前缀缓存收敛进一个 961 行函数。
  3. monkeypatch 是被工程化治理的临时契约：58 项补丁逐条登记上游 PR 与移除计划——补丁密度指示的正是 OOT 接口的缺口地图（调度器/EngineCore/配置 schema）。
  4. PagedAttention 在 Ascend 上契约不变、实现全换：块表语义与寻址公式完全一致，消费方从 FlashAttention 换成 FIA；KV 保持 ND 布局，NZ 分形只作用于权重。
  5. Ascend 算子世界三通道并存、自研为重：155 处 _C_ascend 调用 + 30+ 目录的 CANN vendor 包，稀疏/线性注意力算子占比已超半数——押注下一代模型结构。
  6. 通信策略分野清晰：TP 无融合 allreduce（HCCL 一肩挑），通信-计算重叠全部押在 MoE（MC2/FusedMC2 单算子三元融合），但 512 tokens/rank 上限让大批量 prefill 退回 All2All。
  7. PD 分离生态远超单点实现：11+ connector 全契约实现，llmdatadist 已被 mooncake/MemFabric 体系取代；kv_offload 四层体系正在为 CXL/池化内存铺路。
  8. 显存管理两条互斥路线：expandable_segments（常规推理碎片治理）与 CaMemAllocator（RL sleep/wake 让位）硬断言互斥，platform 层自动切换。
  9. 主要技术债务集中在三处：编译栈双轨（eager 退化 + 自研 aclgraph）、块大小决策错位（128 vs 16 的相反权衡 + 位置错误 TODO）、PP 体系原始（无 interleaved、draft 压末 rank）。
  10. 未来已写在目录名里：hisparse/kv_offload/kv_hints/v2 runner/稀疏后端五族——稀疏化、分层化、零拷贝化、V2 执行层，是双仓共同的下一站。
