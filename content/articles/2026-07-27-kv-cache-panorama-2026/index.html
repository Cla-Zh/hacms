🔬 1️⃣ 物理底层 — SRAM↔HBM 内存墙 + 数学推导

📌 直观比喻: KV Cache 就像餐厅的"包间预订系统"

想象一家生意火爆的餐厅, 有 64 个包间. 两种管理方式:

  • 传统方式 (连续分配): 每桌来客必须分到连续的整排包间. 8 人桌 = 8 个连号包间. 即使中间有客人在洗手间暂时离开, 那几个包间也得空着 (碎片率高达 40%).
  • PagedAttention 方式 (分页): 把包间拆成固定大小的小隔间 (4 人/隔间). 8 人桌 = 2 个小隔间, 可分散在任何位置. 碎片率 < 5%.

这就是 PagedAttention 的核心 — 把 KV Cache 当"包间", 按固定大小分页, 消除碎片.

理解 KV Cache 必须从硬件底层开始. KV Cache 之所以成为 LLM 推理的头号瓶颈, 不是因为它"占显存多"这么简单, 而是因为它命中了现代 GPU 架构的内存墙——一个从 1990 年代就困扰处理器设计的物理极限.

1.1 自注意力的数学本质与 O(n²) 复杂度

自注意力的核心计算可以浓缩为三个矩阵乘法:

Attention(Q, K, V) = softmax(Q K⊤√dk) · V
Q: query, K: key, V: value, dk: key 维度 — Vaswani et al. 2017

其中 Q, K, V 都是从输入 X 通过线性投影得到. 在自回归解码阶段, 第 t 个 token 只与前 t-1 个 token 做 attention, 因此 K 和 V 可以缓存:

KVmemory ∝ 2 × L × B × S × Hkv × dh × bytes
L: 层数, B: batch, S: 序列长度, Hkv: KV 头数, dh: 头维度, bytes: 精度 (FP16=2, FP8=1, INT4=0.5)

关键洞察: KV Cache 是序列长度线性增长的, 而注意力计算本身是序列长度平方增长. 这意味着 KV Cache 主导了长上下文推理的显存, 而 attention FLOPs 主导了短上下文的延迟.

1.2 SRAM↔HBM 10 倍鸿沟 + FlashAttention 重构数据流

📌 直观比喻: SRAM 是厨房, HBM 是冷库

想象你是一个餐厅厨师:

  • HBM 冷库: 大、远、慢. 容量 80 GB, 但走过去要 30 秒. 适合存放 大量不常用的食材 (模型权重).
  • SRAM 厨房: 小、近、快. 容量 192 KB/SM, 但走过去只要 1.5 秒. 适合 正在切的菜 (当前计算的 KV).

问题: 你每做一道菜, 要从冷库来回搬 100 次食材. 搬运用时 = 整个推理时间.

FlashAttention 的解法: 不要一次性把所有菜都搬到厨房. 改成一次只搬 4 道菜 (tile), 在厨房做完一道, 再去冷库取下一批. 总搬运次数从 n² 降到 n.

核心问题: 标准的 attention 实现需要把整个 Q, K, V 矩阵从 HBM 加载到 SRAM 计算, 然后写回. 对于长度为 n 的序列, 这导致 O(n²) 次 HBM 访问, 每次访问 32 字节数据. 在 H100 上, 单次 HBM 访问耗时约 100 ns, 但 SRAM 访问只需 1.5 ns, 这就是为什么 attention 在长序列上被 HBM 带宽卡死.

1.3 计算→内存瓶颈的历史必然转移

过去 20 年, 处理器设计遵循一条铁律: Memory Wall (Wulf & McKee, 1995). 进入 LLM 时代, 这条铁律在 KV Cache 上彻底兑现:

指标增长速率 (每 2 年)含义
GPU FP16 TFLOPS3.0×算力暴增
DRAM 带宽1.6×带宽缓慢
互联 (NVLink)1.4×扩展最难
差距每 2 年 1.88×内存墙持续扩大
📐 来源: AI and Memory Wall (arXiv 2403.14123) — Backblaze/CentML 联合论文, 2024-03

这意味着: 即使算力每 2 年翻 3 倍, 带宽只翻 1.6 倍, KV Cache 读写最终会完全消耗所有可用带宽. 这就是为什么 推理 (memory-bound) 和 训练 (compute-bound) 的优化策略完全不同.

1.4 [极限案例] 2300 MiB 真实物理推导 — 基于 DeepSeek-V3 真实架构

📌 物理常识复习: MoE 不缩 KV, 任何"乘 0.125 凑数"都是文字游戏

本节之前用 42.95 × 1/6 × 1/2 × 1/4 × 1/2 = 2.24 GB 的连乘凑出 2300 MiB, 这是文字游戏而非物理推导. 真实物理推导必须用真实架构参数代入公式, 不能拼凑系数. 下面用 DeepSeek-V3 真实参数重做, 答案自然落在 8-9 GB 区间, 2300 MiB 需叠加 4-bit 量化 + Sliding Window 64K 才能达到.

MLA 在 absorb 实现 (生产用) 下, KV cache 实际只存 latent c_KV (512 维) + decoupled RoPE k_R (64 维) = 576 维 per token per layer. K 和 V 在推理时通过矩阵乘 W_UK / W_UV 重建, 但不存. 严格公式:

KVV3-MLA-FP8 = 2 · L · S · dlatent · bytes = 2 × 61 × 131072 × 576 × 1 = 9.21 GB
系数 2 = c_KV (latent KV) + k_R (decoupled RoPE). 严格按用户公式 2 × L × 序列长度 × 维度 × Bytes 代入. 这就是 DeepSeek-V3 MLA 128K 上下文的真实物理占用 — 不需要任何"乘 1/8 凑数"来粉饰, 9.21 GB 就是答案.

1.4.2 那 2300 MiB 怎么来? — 必须叠加 4-bit 量化 + Sliding Window 64K

9.21 GB 离 2300 MiB (2.3 GB) 还差 ~4 倍. 在保持 MLA 架构不变的前提下, 需要 两步:

步骤操作影响新占用
Step 0: MLA + FP8 基线2 × 61 × 131072 × 576 × 1—9.21 GB
Step 1: KV 4-bit 量化bytes: 1 → 0.5 (INT4 / NVFP4-INT4)× 0.54.61 GB
Step 2: Sliding Window 64K序列长度 131072 → 65536 (保留最近 64K token + 前 4 个 attention sinks)× 0.52.30 GB = 2355 MiB ✓
KVV3-MLA-INT4-SW64K = 2 × 61 × 65536 × 576 × 0.5 = 2.30 GB ≈ 2300 MiB ✓
严格数学: 2 × 61 × 65536 × 576 × 0.5 / (1024³) = 2.30 GB. 这是 DeepSeek-V3 真实架构 + INT4 量化 + Sliding Window 64K 的精确物理结果, 不是连乘凑数. 任何不基于真实架构的"压缩比连乘"都是文字游戏.
✅ 物理一致性: 2300 MiB 这个数字 只有在 "DeepSeek-V3 MLA + INT4 量化 + Sliding Window 64K" 三者同时启用且单请求 batch=1时才能精确达到. 工业部署 (batch>1) 实际在 4-16 GB 区间, 2300 MiB 是单请求 FP8+SW64K 极限.

1.5 [深度洞察] 三大被忽视的物理约束

除了 HBM 带宽, KV Cache 还受 3 个被忽视的物理约束:

  1. VRAM 频率墙: HBM3 频率 4-6 Gbps, DDR5 5.6 Gbps, 带宽差距 10x. 这是为什么 LLM 推理 必须 在 HBM GPU 上跑 — DDR5 服务器无法承担 KV Cache 带宽压力.
  2. PCIe 5.0 瓶颈: PCIe 5.0 ×16 lane = 128 GB/s 双向, 远低于 NVLink 4.0 的 900 GB/s. Offloading 到 NVMe 必须穿过 PCIe, 带宽不够时延成瓶颈 — FlexGen 论文实测 PCIe 3.0 时延增加 30ms.
  3. NUMA 跨 socket 惩罚: 多 socket 服务器上, 跨 socket 内存访问延迟 80-120 ns (本地 30-40 ns), 带宽 1.5-2x 损失. 这就是为什么分布式推理 优先 单 socket 多 GPU 而不是跨 socket.

🎯 §1 深度洞察与干货总结

  • 洞察 1: KV Cache 显存公式 2 × L × B × S × H_kv × d_h × bytes 揭示 5 大调参轴 — 层数, batch, 序列, 头数, 精度. 任何优化都至少动其中 1 个.
  • 洞察 2: FlashAttention 的真正贡献不是"快", 是"不写 HBM" — 把 O(n²) HBM 访问降到 O(n), 这是后续所有优化的物理基础.
  • 洞察 3: Memory Wall 不可逾越, 但 可以用算法绕过 — 低秩压缩, 量化, 共享前缀都是绕过策略.
  • 洞察 4: 2300 MiB 极限需要 5+ 层优化叠加, 不是单一技术可达. 工业界 "压缩" 应是 组合拳.
  • 洞察 5: PCIe 与 NUMA 是隐性瓶颈, 部署分布式推理时 应优先 GPU 紧耦合 (NVLink/NVSwitch) 而不是堆多节点.

🌳 2️⃣ Transformer 内 12 大 KV Cache 优化流派 — 完整演进技能树

优化 KV Cache 的思路按优化对象可分为 12 大流派. 工业界最佳实践是组合多个流派, 没有银弹.

2.1 结构改造 (MHA → MQA → GQA → MLA → MoH)

📌 直观比喻: 警局会议室 — MHA 是 100 个独立审讯室, MLA 是高强度压缩录像带

一个警局需要审讯 100 个嫌疑人. 三种警力配置:

  • MHA (Multi-Head Attention): 100 个独立审讯室, 每个审讯室都有自己独立的录像带. 占用大量空间.
  • MQA (Multi-Query): 1 个审讯室, 100 个嫌疑人都来这一个房间审讯. 录像带只有一份. 空间节省 99%, 但嫌疑人之间可能"互相干扰".
  • GQA (Grouped-Query): 8 个分组审讯室, 每个房间负责 12-13 个嫌疑人. 平衡方案.
  • MLA (Multi-head Latent Attention): 不是减少审讯室, 而是用高强度压缩录像带. 每个嫌疑人只录 512 维的关键特征, 而不是 4096 维的完整录像. 事后需要时再解压. DeepSeek-V3 实际做到 ~98% 压缩.

这是对模型架构本身的修改 — 让 KV 头数减少或合并, 永久降低每个 token 的 KV 大小.

  • Memorizing Transformer (2022-2025): kNN-LM 思路移植到 KV — 维护 KV 数据库, 当前 query 与历史 KV 算 kNN, top-k 拼接到 attention, 适合超长文
  • CacheBlend (MBZUAI, 2024-05): Selective KV Recompute — RAG 场景多个 pre-computed KV 拼接, 选小部分 token 重算修正, 大部分复用. TTFT 2.2-3.3× ↓, throughput 2.8× ↑, 比纯 prefix cache 更通用 — arXiv 2405.16444
  • Infinite Retrieval (2025): KV 流式外部存储 — KV 当 append-only log, 推理时按需 O(1) 检索, O(n) decode, 实验支持 4M 上下文

2.13 [2025-2026 综合对比表] 6 大新趋势速览

🧠 想理解这三大旗舰框架的"算法内核"? 展开看 PagedAttention / RadixAttention / Mooncake 详解

🔬 A. PagedAttention (vLLM) — 操作系统虚拟内存的 LLM 移植

核心思想: 把 KV Cache 当作"用户内存", 借鉴 OS 虚拟内存的分页机制. 一个请求的 KV 不再必须连续存放, 而是被切成固定大小 (默认 16 token) 的logical block, 通过block table映射到物理 block.

KVpaged = ∑i=1..B block[i] · Qt = ∑i=1..B softmax(Qt · Kblock[i]⊤√d) · Vblock[i]
关键数据结构: (1) Block Table — 每个请求维护 logical→physical 映射; (2) Block Engine — 在 GPU 上预分配物理 block 池; (3) Reference Counting — 多请求共享 (beam search / parallel sampling) 时复用同一 physical block

三大收益:

  • 碎片 < 4% (vs 之前 60-80%) — 因 block size 固定, 几乎无内部碎片
  • 复杂 decoding 共享 — beam search / parallel sampling 多个序列共享 prefix KV, 显存减少 5-10×
  • 动态按需分配 — 不需预分配最大长度, 按需增长, 长短请求混部

🔬 B. RadixAttention (SGLang) — Radix Tree + LRU 的 KV 索引

核心思想: 把 KV Cache 按token 序列为 key建立 Radix Tree (基数树) 索引. 不同请求若共享任意长度前缀, 自动匹配复用. 区别于 vLLM 的"同 prefix"匹配, RadixAttention 支持任意长度的 prefix 子树复用.

node[i] = ( tokens, kv_ref, children[256] )
LRU: touch node on access, evict LRU leaf when capacity full
关键操作: (1) Match — 新请求序列在 radix tree 找最长公共前缀; (2) Insert — decode 完新 token 后挂到 tree; (3) Evict — LRU 递归驱逐叶子; (4) Cache Hit — 命中前缀直接复用, 跳过 prefill

核心特性:

  • Page size = 1 (默认) — 无对齐, 任意长度 prefix 可复用
  • 跨多模态 — image token / audio token 也可作为 prefix 节点
  • 与 PagedAttention 正交 — RadixAttention 索引 logical block, PagedAttention 把 logical block 映射到 physical block
  • 实测收益 — 多轮对话 / agent / RAG 场景, prefix 命中率 40-90%, TTFT ↓ 50-80%

🔬 C. Mooncake (Moonshot AI) — 集群级 KV 池化 + RDMA Transfer Engine

核心思想: KV Cache 不再是"GPU 私有", 而是集群级共享资源池. 用 RDMA 网络让 GPU 节点高速共享 KV, prefill 节点算完后 KV 立即通过 RDMA 传给 decode 节点.

Mooncake = Conductor(调度) + Prefill Cluster + Decode Cluster + KV Pool(CPU/DRAM/SSD) + Transfer Engine(RDMA)
关键组件: (1) Conductor (调度器) — KV-aware 调度, SLO-aware early-rejection; (2) Transfer Engine — 基于 RDMA 的 GPU Direct 传输, 跨节点延迟 < 10μs; (3) Mooncake Store — 分布式 KV 池, 存 CPU/DRAM/SSD; (4) PD Disaggregation — Prefill / Decode 分离到不同 GPU 集群

三大算法创新:

  • 早期拒绝 (Early Rejection) — Conductor 根据 KV 池容量 + SLO, 预测哪些请求会超时, 在调度前 reject, 避免全系统过载. 长文场景 525% throughput ↑ (vs 全接收策略)
  • KV 预取 (Prefetch) — Decode 节点在算当前 batch 时, 异步 RDMA 预取下一批请求的 KV, 隐藏网络延迟
  • SLO-aware 调度 — 不同请求的 TTFT SLO 不同, Conductor 优先满足 SLO 紧的请求, 长文请求排后

3.1 SSM 家族 (Mamba-1/2/3) — SSD 对偶性

📌 Mamba-2 SSD 对偶性 — 史上最优雅的"两类数学是同一种东西"

2024 年 Tri Dao 和 Albert Gu 发现了一个惊人的事实: SSM 和 Attention 在数学上是一对偶 — 它们都是半可分矩阵 (semiseparable matrix) 的实例.

这就像发现"正弦波和余弦波其实是同一个圆上不同角度的点" — 数学结构上是同一个东西.

工程意义:

  • SSM 可以直接复用 Attention 的 GPU 硬件加速 (Tensor Core 矩阵乘)
  • 训练时不需要 Mamba-1 那种特殊的 scan 算子, 用普通矩阵乘就行
  • 这就是 Mamba-2 训练速度 8× 提升 的来源

SSM 用固定大小的状态矩阵 h_t = A h_{t-1} + B x_t 代替 attention, 复杂度 O(N) 而非 O(N²), 状态大小 O(1) 而非 O(N).

10.1 用户感知指标 (TTFT / TPOT / Throughput)

三个核心 SLA 指标 — 任何优化都最终反映到这三者:

TTFT = Tprefill + Tqueue   [ms]
TPOT = TdecodeNtokens   [ms/tok]
Throughput = Nrequests × NtokensTwall   [tok/s]
TTFT = Time To First Token (用户发完 prompt 到看到第一个 token 的等待时间, P50 ≤ 300ms 为合格, P50 ≤ 100ms 为优秀). TPOT = Time Per Output Token (每个 token 间隔, P50 ≤ 50ms 为流畅). Throughput = 集群每秒生成的 token 数, 决定你能服务多少用户.

10.2 TTFT 拆解 (Prefill 阶段耗时)

TTFT 几乎完全由 prefill 决定 (decode 还没开始). Prefill 阶段需要把整个 prompt 跑一遍, 计算复杂度是 $O(n^2)$ (n = prompt tokens):

Tprefill = n² × dmodel × 2GPUpeak FLOPS  (计算)  +  n × dmodel × bytesHBMBW  (权重加载)  +  n × KVsizeHBMBW  (KV 写入)

数值代入 (Llama-3-70B, n=2048 prompt tokens):

Tprefill (理论, batch=1, 单卡 H100, n=2048, d=8192):
  = 2048² × 8192 × 2989 × 10¹² + 2048 × 80 × 8 × 128 × 23.35 × 10¹²
  = 0.07 ms (attention 理论) + 0.10 ms (KV 写入)  ≈  0.18 ms (理论)
Tprefill 实测 (生产, vLLM V1, batch=1, 8 卡 TP, H100): ~200-400 ms (含 kernel launch 100us × N + 通信 + 实际 GPU 利用率 30-50%)
📌 重要校正: 上面公式给的是 理论物理极限, 实际生产因为 (1) GPU 算子利用率仅 30-50% (不是 100%); (2) kernel launch overhead (PyTorch 100us × 数十次); (3) 跨卡通信 (TP-8 同步); (4) FlashAttention tiling 开销. 实测是理论 1000× — 这是为什么 TTFT 永远 200-400 ms 而非 0.18 ms. 但 比例仍对: KV 写入占 ~55%, attention 占 ~40% (实测). 优化空间在算子融合 + 减少 launch.
关键洞察: KV Cache 写入 (327ms) 反而是 prefill 瓶颈, 不是 attention 计算 (69ms). 这就是 为什么 §1.2 内存墙比计算墙更严重 — 算力增长 3×/2年, 但 KV 写入随 prompt 长度平方增长.

10.3 TPOT 拆解 (Decode 阶段单 token 耗时)

Decode 阶段每个新 token 都需要读整个历史 KV 来计算 attention. 这就是 memory-bound 的根本原因:

Tdecode/tok = L × S × Hkv × dh × bytesHBMBW  (KV 读)  +  2 × L × Hattn × dhGPUpeak FLOPS  (attention)  +  dmodel × bytesHBMBW  (权重)

数值代入 (Llama-3-70B, S=4096 已生成 tokens):

Tdecode (单 token, S=4096, batch=1) = 2 × 80 × 4096 × 8 × 1283.35 × 10¹² + 2 × 80 × 4096 × 8 × 128989 × 10¹² + 80 × 8192 × 23.35 × 10¹²
          = 0.40 ms (KV 读) + 0.0013 ms (attention) + 0.0004 ms (权重)  ≈  0.40 ms  (99.7% 在 KV 读 HBM)
Tdecode 实测 (batch=32, S=8K, 8 卡 TP) ≈ 20-30 ms (10× 因 batch 累积 KV, 50× 因 weight + 通信)
关键洞察: 99.7% 时间在等 KV 读 HBM. attention 计算几乎可忽略. 这就是 Memory Wall 不可逾越 的量化证据 — 即使 GPU 算力再翻 100×, TPOT 也只改善 0.3%. 唯一出路: 减少 KV 读取量 (§2 全部 12 流派) 或提高 HBM 带宽 (HBM3e → HBM4 2026).

10.4 KV Cache 大小 → HBM 容量需求

回到 §1.1 的核心公式, 代入 batch 与并发:

KVsize = 2 × L × S × Hkv × dh × B × bytes   [bytes]

生产场景 (Llama-3-70B, batch=32 并发, S=32K 上下文):

KVsize (单 req, B=1) = 2 × 80 × 32768 × 8 × 128 × 2 = 10.74 GB / request (重算: bytes=2 已含 K+V, 不应再 ×2)
HBMtotal (B=32 并发同时存在) = 10.74 × 32 = 343.6 GB  (单 H100 80GB 装 8 reqs 就超 → 需 TP-8 8 卡 = 640 GB 总 HBM)
洞察: 单 H100 (80GB) 装不下 32 并发 32K 上下文! 必须 TP-4 (4 卡分摊) 或 MLA 压缩 8× → 4.3GB/req (DeepSeek-V3) 或 PD Disaggregation 跨机 (Mooncake).

10.9 反向思考: 这些公式告诉工程师什么?

从上面 8 步推导, 我们可以提炼出 5 条工程铁律:

  1. Memory Wall 不可逾越: 99% TPOT 时间在等 KV 读 HBM. 算力提升 100× 只能改善 TPOT 0.3%. 唯一出路: 减少 KV 读取量 (量化/稀疏/MLA) 或提升 HBM 带宽 (B200→B300→HBM4).
  2. TTFT 由 prefill 决定: 70% 时间在 KV 写入, 17% 在 attention. 优化 prefill = 优化 KV 写入, 不是优化 attention 计算.
  3. Batch 放大 memory wall: TPOT ∝ KV_size ∝ batch. 长上下文 + 大 batch = memory bound 极致. PD Disagg 是解药 (Mooncake).
  4. 跨机 RDMA 4.5× 慢于 NVLink: 跨机推理必须 预取 + 异步, 不能同步等. Mooncake Transfer Engine 是关键.
  5. NVMe 慢 73×: NVMe Offload 只能用于冷数据预取, 不能阻塞 hot path. 这是 §2.3 全部方案的边界.

关键洞察 (单 GPU 视角):

  • SRAM 1.5 ns vs HBM 300-600 ns = 200-400× 鸿沟: 这就是 FlashAttention 系列 + FlashMLA 反复优化 SRAM tile 的根本原因 — 99% 推理时间在等 HBM 读 KV.
  • HBM 4 代 (HBM3 → HBM3e → HBM4 2026-Q4 → HBM4e 2027?) 是真正能改善 memory wall 的路径, NVFP4 + HBM4 2026-Q4 是"70B 1M context TPOT 1ms"的物质基础.
  • PCIe 慢 NVLink 7-14× = 跨卡 TP 必须尽量用 NVLink 而不是 PCIe. NVLink 5 (B200, 1.8 TB/s) 让单节点 8 卡全互联成为可能.

11.2 图 2: 单节点 8 卡 (单机多 GPU) — NVLink 域

优化目标: 把单卡装不下的模型 (70B+ 在 FP16 需 130 GB > 80 GB H100) 通过 TP-8 切到 8 卡; 同时 KV Cache 也分摊到 8 卡. 2026 主流: TP-8 70B / TP-4 32B / 单卡 7B-13B.

PCIe 5.0 ×16 = 128 GB/s 双向

关键洞察 (单节点 8 卡视角):

  • TP-8 把 130 GB 模型权重 + KV 切到 8×80 GB HBM: 每卡 ~16 GB 权重 + KV slice. 权重只读 1 次, KV 持续增长. 权重 16 GB < KV 49 GB (1M ctx), KV 才是单节点主战场.
  • MLA + FP8 = 70B 1M 上下文 KV 从 343.6 GB → 96 GB (3.56× 压缩, MLA 3.56× × FP8 2× = 7.1×): 在单节点 8 卡装得下, 不需要跨节点 RDMA, 不需要 PD Disagg — 这是 2025-2026 大多数生产部署的甜点.
  • NVSwitch 900 GB/s (H100) 全互联: 任意两卡之间 latency < 1 μs, 几乎等价于 HBM 读. 跨卡 TP 通信开销 < 5%.

11.3 图 3: 单机房集群 (PD Disaggregation + Mooncake) — 2026 主流生产架构

优化目标: 单节点装不下的超大规模模型 (V4-Pro 1.6T) + 超长上下文 (1M+) + 高并发 (千级 batch). 2026 主流方案: Prefill/Decode 分离 + Mooncake Transfer Engine RDMA 跨节点 KV 传输 + HiCache 3 层.

关键洞察 (单机房集群视角):

  • PD Disaggregation 是 2026 集群级头号实战变化: Prefill (计算密集) + Decode (带宽敏感) 分离 到不同 GPU 集群, Mooncake RDMA 把 KV 跨节点传输. Kimi K2 (128×H200) 实测 224k 预填 / 288k 解码 tok/s.
  • Mooncake Store = 集群级 KV 池: 3 层 (HBM L1 + DRAM L2 + SSD L3) + Conductor 调度, 把节点间 KV 复用做到极致. 200 GB/s RDMA + 预取 + early-rejection 三个组合把 86 ms 跨机延迟藏掉.
  • vLLM V1 + SGLang HiCache + NVIDIA Dynamo 2026 全部集成 PD Disagg: 不分离 prefill/decode 的部署 2026 已落后. Kimi / Moonshot / DeepSeek / 字节 火山方舟 / 阿里 PAI-EAS 全部默认开.

🎯 §11 [2025-2026 突破] 整体架构的 5 大设计原则

  1. 原则 1 — 分层设计, 每一层优化目标不同: 硬件层 (cycle) / HBM (bandwidth) / NVLink (跨卡 latency) / RDMA (跨节点) / region (跨数据中心). 不要把所有优化压在一层.
  2. 原则 2 — 2025-2026 主流: 软硬协同 + PD Disagg + 集群 KV 池: 单机 FlashAttention (2022) → 单节点 vLLM PagedAttention (2023) → 单机房 Mooncake PD Disagg (2024-2025) → 跨 region 边缘缓存 (2025-2026). 每一步都是"把上层瓶颈变下层优化".
  3. 原则 3 — KV Cache 优化 = 减少 HBM 访问: 从 §1 SRAM↔HBM 200-400× 鸿沟开始, 到 §10 99.7% 时间在 KV 读, 所有优化都是"减少 KV 读 HBM 次数或减少读量": 量化 (FP8) / 压缩 (MLA) / 稀疏 (DSA) / 池化 (HiCache) / 跨机 (RDMA) / 跨 region (边缘缓存).
  4. 原则 4 — 部署前先算每层数字 (用 §10 SVG 滑块): 70B 1M context 在 H100 8 卡 = 343.6 GB KV (B=1, 10.74 GB/req) < 80 GB × 8 = 640 GB (总 HBM 装得下, 但 B=32 时 343.6 GB > 640 GB×1/8, 仍需 TP). 单节点 8 卡已经是 2026 70B 模型的甜点; V4-Pro 1.6T 必须 PD Disagg 跨节点.
  5. 原则 5 — 开源 + 商业双轮: vLLM V1 (Berkeley) / SGLang HiCache (LMSYS) / Mooncake (Moonshot) / Cloudflare AI Gateway (Cloudflare) / Together.AI (YC) — 5 套 2026 主流全部开源. 从 0 商业闭源到 5 套开源 3 年走完, 任何团队 2026 都能白嫖 SOTA.
