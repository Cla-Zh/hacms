Executive Summary — What Modal Is (and Isn't)

Modal Labs, Inc. 是 Erik Bernhardsson(CEO,Spotify 推荐系统之父,IOI 2003 金牌)和 Akshat Bubna(CTO,Scale AI 前 Staff Engineer,IOI 2014 金牌)于 2021 年 1 月在纽约创立的 AI 基础设施公司。(erikbern.com/about.html; LinkedIn)

Modal 是什么:一个 从 Rust 容器运行时起、把 CPU/GPU 内存快照、内容寻址 FUSE 文件系统、Multi-cloud LP 资源求解器全部自研的"AI-native cloud"。开发者写 @app.function(gpu="H100") 一个 decorator,Modal 替你处理 container build、image distribution、function-as-a-service 调度、auto-scaling、checkpoint/restore。

Modal 不是什么:不是 Firecracker 派 microVM(用 gVisor runsc),不是 Anyscale 派 Ray-as-a-service(更接近"DX 极致的 serverless"),不是 hyperscaler 的 serverless GPU 套壳(GCP Cloud Run 的 L4 only、AWS Lambda 无 GPU)。

"We decided to not build this on top of tools like Docker/Kubernetes because we want infrastructure to be fast. ... Modal has no problem building a 100GB container, and then booting up 100 of those containers — you can do the whole thing in a few seconds."
— Erik Bernhardsson, "What I have been working on: Modal", 2022-12-07

Why This Research Brief Is Worth Reading

Modal 是 2026 年 AI infra 赛道最值得拆解的公司之一,因为:

  1. 它解决的不是 GPU 不够的问题,而是 GPU 等得不耐烦的问题 — 大部分 hyperscaler 卖的是 raw GPU hours,Modal 卖的是"GPU 在你需要时立即可用"
  2. 它从 runtime 开始重写 — 不在 Docker/K8s 上套壳,而是把 container scheduler、image builder、filesystem 全部用 Rust 重写;这种赌注在 hyperscaler 内部都很少有人敢做
  3. 它的 ARR 在 8 个月 5× 是有公开信源支撑的(Reuters 引述 Erik + Sacra 估算匹配),不是 paper round
  4. 它的 Sandboxes 业务单独构成 1/3+ 收入(Series C 自述),这是 agent 算力市场第一波变现的少数公开案例

2.2 Infrastructure-from-Code 范式

    ↓ docker build

    ↓ kubectl apply (Helm chart, ConfigMap, Deployment YAML)

Modal 范式

import modal

image = modal.Image.debian_slim().pip_install("torch")
app = modal.App("inference")

@app.function(
    gpu="H100",
    memory=4096,
    enable_memory_snapshot=True,
    scaledown_window=120,
)
def predict(prompt: str) -> dict:
    import torch, transformers
    model = transformers.pipeline(
        "fill-mask",
        model="bert-base-uncased",
        device="cuda",
    )
    return model(prompt)

# Deploy
# $ modal deploy app.py

# Call (from anywhere)
# predict.remote("The capital of France is [MASK].")
# OR (from local)
# predict.local("The capital of France is [MASK].")  # runs locally

"We decided to not build this on top of tools like Docker/Kubernetes because we want infrastructure to be fast. I met a lot of VCs and other people while I was still just working alone on a prototype and most of them told me I was nuts when I started talking about building custom file systems and container engines. But we built it and it's working beautifully!"

为什么不用 Docker/runc?

runc 容器直接与 host kernel 共享 syscall surface,对执行 LLM 生成的 hostile 代码不够安全。Modal 选 gVisor 是为了在不需要硬件虚拟化开销的前提下获得强隔离。

为什么不用 Firecracker?

  • Firecracker 是 KVM-backed microVM,启动 ~125ms,有 ~5MB memory overhead
  • 每个 Firecracker microVM 有一个完整的 guest kernel,对 CUDA / GPU passthrough 不友好
  • Modal 需要在数十万并发 sandbox 中提供 GPU,Firecracker 的硬件虚拟化路径与 NVIDIA GPU passthrough 摩擦更大
  • Firecracker 适合 CPU-only serverless(AWS Lambda 的设计点),不适合 AI workloads

为什么 runsc 让 checkpoint/restore 变简单?

"Checkpoint/restore is actually especially easy for runsc. A container in the runsc runtime is straightforwardly a state machine. That is, the runtime is architected (in Go) as a collection of tasks with cooperative preemption, as in most other systems with async/await-style concurrency. The system is already being interrupted and then continued at every await point, so it's 'only' a matter of serializing that state into a checkpoint."
— truly-serverless-gpus, 2026-05-12

Modal 在这篇 canonical post 中明确说出为什么选 gVisor 而非 Firecracker:因为 gVisor 的 Go 实现本身就是一个 async state machine — checkpoint/restore 只需把 state machine 序列化。这是 Firecracker 做不到的事,因为 Firecracker 的 guest kernel 是独立 Linux kernel,必须用 CRIU / DMTCP 这种"冻结 guest kernel state" 的笨办法。

3.4 GPU Memory Snapshot — NVIDIA CUDA Checkpoint API

(gpu-mem-snapshots, 2025-07-30, by Luis Capelo + Colin Weld; NVIDIA CUDA Driver API docs)

触发条件

NVIDIA 在 driver 分支 570 / 575 中加入 cuCheckpointProcessLock / cuCheckpointProcessRestore / cuCheckpointProcessUnlock 三件套。这是 NVIDIA 2024-2025 加的相对较新的功能,Modal 是最早产品化的玩家之一。

Snapshot 流程

  1. Lock CUDA processes — cuCheckpointProcessLock() 防止 snapshot 期间发起新 GPU 操作
  2. 等待所有进程进入 CU_PROCESS_STATE_CHECKPOINTED 且无活跃 CUDA sessions
  3. Snapshot CPU memory + GPU memory — 一个统一的 pages 文件
  4. Restore 时反向: cuCheckpointProcessRestore() → cuCheckpointProcessUnlock()

  • 不需要再分 snap=True / snap=False lifecycle
  • 不同 worker host 间硬件兼容性检查 → fallback to CPU-only snapshot

4. How we achieved truly serverless GPUs

作者: Modal engineering (Erik cross-posted) · 发布: 2026-05-12 · modal.com/blog/truly-serverless-gpus

Problem Statement

GPU allocation utilization 对 inference 工作负载常 10-20%(用户 over-provision 应对 burst)。四个 bottleneck: instance acquisition / machine boot / image+FS loading / app host+device init。

Solution Details — 四大 ingredient

  1. Multi-cloud capacity orchestrator (Resource Solver): 13+ cloud providers, LP via GLOP; capture H200 < H100 时点的 arbitrage
  2. Cloud buffers: small idle GPU pool to absorb new load
  3. Custom filesystem (ImageFS): lazy, content-addressed, multi-tier cache
  4. Checkpoint/restore: CPU (CRIU + gVisor) + GPU (NVIDIA CUDA checkpoint API)

关键洞察 — 为什么 runsc 让 checkpoint 简单

"Because applications only interface with this emulated kernel [gVisor Sentry], they can be checkpointed and restored by it without cooperation from the host kernel. Checkpoint/restore is actually especially easy for runsc. ... The system is already being interrupted and then continued at every await point, so it's 'only' a matter of serializing that state into a checkpoint."

Benchmarks

  • 40× spin-up improvement(50s vs 2000s)
  • vLLM Qwen3-0.6B boot:CPU+GPU snapshots reduce 95th-percentile restore time materially
  • AWS g6.12xlarge 缺 pclmulqdq 指令 → 不能接受带该指令 host 上做的 snapshot
  • RDMA weight server 可以让 model load 带宽提升 3-10×(in-AZ / in-rack),但尚未产品化
  • "We use the same basic storage affordances as in the custom filesystem to load model weights, and so model weights are loaded at a few gigabytes per second"

5. Scaling to 1 million concurrent sandboxes in seconds

作者: Colin Weld, Connor Adams · 发布: 2026-07-16 · modal.com/blog/scaling-to-1-million-concurrent-sandboxes-in-seconds

Problem Statement

Run a million concurrent sandboxes(数十万 nodes)。K8s 不可行:O(n × p) 调度算法默认串行化,每个 pod 多次 etcd writes,heartbeat O(nodes),etcd 在 keyspace 内不可分片。Modal 原架构也有同样问题:Postgres 在 critical path 上,O(sandboxes) writes;每个 finished sandbox 触发 durable workflow。

Solution Details

  1. 水平扩展的 scheduling servers,并发处理 create 请求
  2. In-memory cached worker state(不是单一 source of truth)
  3. Workers 自己是 source of truth — workers 周期性把状态 publish 到 Redis stream
  4. Schedulers 消费 Redis stream 异步,根据 in-memory cache 做调度决策
  5. 选定 worker 后,scheduler 直接 RPC 该 worker,worker accept(有 free resources)/ reject
  6. Sandbox 对象存 Redis,不在 critical path
  7. 只两个网络 hop + 一个便宜 CPU op

关键 bug — rtnl lock 竞争

新调度器推 sandbox 到 worker 太快,worker 上大量 sandbox 创建在设置容器网络规则时竞争 Linux 内核的 rtnl lock → 容器启动 tens of seconds → Modal 重做容器网络设置。

Benchmarks

  • 1,000,000 sandboxes <60 秒
  • p50 time-to-interactivity <500ms
  • 单一 Redis stream 可用至 >100k workers;可加更多 streams

6. Linear programming for fun and profit (Resource Solver)

作者: Colin Weld, Irfan Sharif · 发布: 2025-05-07 · modal.com/blog/resource-solver

Problem Statement

找最优云厂 instance type 组合满足动态需求,given per-instance price + capacity limit across 13+ providers + demand variability + buffer headroom + per-region mix + GPU performance equivalence。

Solution Details

  • Pre-prune instance types 启发式(cut solve time 10×,lose a bit accuracy)

5.2 Architecture Trade-offs

Modal 为极致 DX 牺牲了什么

  1. Vendor Lock-in: Modal Functions 只能在 Modal 上跑。不可 self-host,不像 Daytona / microsandbox 那样提供 on-prem / VPC 选项。Modal 的 deliverable 是"Modal runtime",不是 open-source stack。
  2. No BYOC / VPC: Modal 是完全 managed-only,客户的数据/计算不能跑在客户自己的 VPC(除非 Enterprise 谈 specific deal,未公开)。
  3. gVisor syscall coverage: gVisor 不能 100% 模拟 Linux kernel;某些 features(eBPF, raw sockets, Docker-in-Docker, custom cgroups, systemd)需要新的 alpha VM Sandboxes。
  4. Snapshot portability: snapshot 绑定 host CPU instruction set + CUDA driver branch + GPU model。Modal 多云架构 → 一个 Function version 需要多个 snapshot,storage / metadata 开销更高。
  5. Pricing opacity: region 1.15-1.75×、non-preemptible 3×、Sandbox CPU/memory 3× standard,产能规划比 hyperscaler 难。
  6. Static IP / Custom domain: 仅 Team 计划以上可用,且为 proxy-based,不是原生 L4/L7 LB。
  7. Multi-node DDP: closed beta — 不适合超大规模 pretraining

Modal 的架构优势

  1. 冷启动最优化(端到端): ImageFS lazy load (~100ms index mount) + CRIU+gVisor CPU snapshot (2.5-7×) + NVIDIA CUDA GPU snapshot (10×) = Stack 在一起 40× 整体
  2. 统一 Python DSL 覆盖全工作流: 同一 @app.function() 装饰器可写 inference、batch、RL、sandboxes、training、notebook — 没有"infra switch tax"
  3. Multi-cloud arbitrage via LP solver: 通过 Resource Solver,Modal 可以持续用最优成本组合服务用户,这是 hyperscaler 永远做不到的
  4. gVisor isolation + ephemeral-by-default sandboxes: hostile agent code 安全
  5. 1M concurrent sandboxes 验证: scheduling 已证明可扩展到客户级 50k+ concurrency

5.3 Bottlenecks

1. InfiniBand/RoCE 暂未产品化

Modal 自述:RDMA weight server 可以让 model load 带宽提升 3-10×,但"expensive and gnarly, especially when scaling to many models and dynamic worker pools. We're working on it!" — 后果:超大模型(>50 GB weights)在多 worker 间 distributed inference 时,model loading 是主要Bottlenecks;不是 LLM inference 本身的Bottlenecks,而是 cold start 时加载 weights 的Bottlenecks。影响:trillion-parameter 模型 serving 不友好。

2. 多 GPU 训练 production-readiness 不足

Modal docs 自述:"Multi-node training in closed beta (contact us for access)"。Multi-GPU 8 GPU per node 支持,但 DDP across nodes 是 closed beta。影响:不适合超大规模 training workload,定位 inference / fine-tune / RL 而非 pretraining。

3. GPU 供应链依赖上游云厂

Modal 自报 13+ 云厂(AWS, GCP, Oracle, CoreWeave, Lambda 等)。Erik 接受 Reuters 采访时说:"we work with 13 cloud providers, up from 5 last year"。Modal 自身是 GPU 净买方,受 NVIDIA 产能 / 云厂分配 / 区域 quota 影响。

4. Snapshot 兼容性约束

100% restore 成功率无法保证:host CPU instruction set、CUDA driver version、GPU model 任一不匹配都会触发 fallback 到 cold start。在 heterogeneous fleet 上,一个 Function version 需要多个 snapshot → storage / metadata 开销。影响:p99 冷启动延迟仍可能 hit worst case(几十秒)。

5. 毛利率压制 [Analyst Estimates]

GPU 上游成本 + 区域 multiplier + 3× Sandbox premium → 客户被引导用 preemptible / 多区域 mix。Hyperscaler 持续降价(AWS 在 2025 年降价 45% GPU price)。推论:Modal 长期毛利率可能压缩到 25-35%(vs 短期 35-50%)— 除非 LP arbitrage 持续产生超额价值。

6. 监管/合规

SOC 2 Type 2 + HIPAA(Enterprise)已有。ISO 27001、FedRAMP 未公开 — 在高度监管行业(政府、银行、医疗机构)GTM 阻力。HIPAA 删除合规仅在 Volumes v2。

7. Modal 自家发现的 rtnl lock 风险

这是一个 Modal 自己公开承认的 Linux kernel level 问题:大规模 burst sandbox 创建会触发 worker 内核 rtnl lock 竞争,容器启动 tens of seconds。意味着 Modal 的调度系统在某些极端负载下必须重做容器网络 setup。这是已经发生的 production 事故,而非"潜在"风险。

反共识 1:Modal 不该跟 Fireworks / Together / Baseten 直接对比

技术Glossary — 穿透 Modal 报告的 OS / 内核概念

术语含义在 Modal 语境
OCI runtime Open Container Initiative 定义的容器运行时规范。Docker / containerd 都通过 shim 调用 OCI-compatible runtime Modal 用 runsc(gVisor)和 runc 都是 OCI runtime
runc Docker 默认的容器 runtime,直接使用 host kernel 的 syscall surface。轻量但隔离弱 Modal 不用
runsc / gVisor Sentry Google 写的 Go-implemented application kernel;用户态拦截 syscall,自己实现大部分 Linux system call surface Modal Functions / Sandboxes 默认 runtime
Firecracker Amazon 写的 VMM(Virtual Machine Monitor),在 KVM 上跑 microVM。每个 microVM 有独立 guest kernel AWS Lambda / E2B / Vercel Sandbox 选这个;Modal 不用
KVM Linux Kernel-based Virtual Machine,Linux 内核的硬件虚拟化模块,提供 CPU / memory 虚拟化 Modal VM Sandboxes(alpha)底层用 KVM + 真实 Linux kernel
CRIU Checkpoint/Restore In Userspace,Linux kernel 项目,把运行中进程冻结到磁盘再恢复 Modal CPU memory snapshot 的理论根基(虽然实际实现是 gVisor 自家)
CUDA Checkpoint API NVIDIA 在 driver 570/575 分支加的 API,允许冻结 CUDA process 状态(包括 GPU vRAM) Modal GPU memory snapshot 的实现机制
FUSE Filesystem in Userspace,允许用户态进程实现 filesystem 并通过 kernel module 暴露 Modal ImageFS 和 Volumes 用 libfuse
content addressing 文件内容由 hash(SHA-256 等)命名,而不是路径。同 hash = 同内容,自动 dedup ImageFS 的核心设计 — chunk 由 hash 命名 → dedup + immutable cache
overlayfs Linux kernel 的 union mount filesystem,支持 lower(read-only) + upper(writable) + work 目录叠加 Modal 容器使用 overlayfs 挂载,lower 是 ImageFS 的 FUSE mount
read_ahead_kb Linux 内核 block layer 参数,指定顺序读时 kernel 预读多少 KB Modal 调到 32 MiB(默认 128 KiB),1 GiB 引发灾难
rtnl lock Linux kernel routing/netlink 子系统的全局锁,序列化对 routing table / interface 的修改 Modal 1M sandbox 测试时把 worker 内核 rtnl 干爆,容器启动 tens of seconds
MIG / Multi-Instance GPU NVIDIA Ampere+ GPU 的硬件分片功能,一张 H100 可切成最多 7 个 isolated instances Modal 未产品化
vGPU NVIDIA 的虚拟 GPU,hypervisor 把一张物理 GPU 暴露给多个 VM 看 Modal 未产品化
MIG-backed vGPU 在 MIG 切出的实例上再叠加 vGPU,实现"硬件分片 + 软件虚拟"双层 Modal 未产品化
RDMA Remote Direct Memory Access,允许机器 A 直接读写机器 B 的内存,绕过 OS / TCP。InfiniBand / RoCE 是物理实现 Modal 自述 in-rack RDMA 可让 model load 带宽 10× — 未产品化
NVLink / NVSwitch NVIDIA 的 GPU-to-GPU 高速互联,NVSwitch 是交换机芯片 Modal 在多 GPU node 内用 NVLink,NCCL all-reduce 测试用于 GPU health
RoCE RDMA over Converged Ethernet,在标准以太网上跑 RDMA。比 InfiniBand 便宜 Modal 提过 RoCE weight server 作为优化方向
Xid / sXid errors NVIDIA driver / GPU 硬件错误码,Xid 是 driver-level,sXid 是 system-level Modal 维护"the best GPU error resource on the internet" — Xid 字典
GLOP Google 的 LP(Linear Programming)solver,在 OR-Tools 库中 Modal Resource Solver 用 GLOP 求最优云厂 instance 组合
Simplex algorithm 1947 年 George Danzig 提出的 LP 求解算法。Modal Resource Solver 用的就是它 Modal 提到"computer scientists and mathematicians have been producing algorithms to solve these problems for nearly two hundred years"
Service Mesh / RPC 微服务间通过 RPC 通信的架构模式 Modal 调度器用 RPC 直接联系 worker(不走 service mesh,显式 RPC)
vsock / virtio-vsock host ↔ guest VM 间的高效通信通道 Modal VM Sandboxes(alpha)可能用
Multi-tenant 多个客户共享同一硬件资源 Modal 是 multi-tenant,需要 gVisor 隔离保障安全

冷启动优化的完整Timeline — 从 ~2000s 到 ~50s

Modal 在 truly-serverless-gpus 一文中给出了一个 inference replica 从 idle 到 ready 的完整Timeline。原始 4 步:

StepNaiveModalModal 的优化
1. Acquire machine + GPUs 分钟级 — 云厂 quota / capacity ~10-30s — 多云 LP solver + cloud buffers Resource Solver 实时从 13+ 云厂挑最便宜的可用 instance
2. Boot machine + start container ~30s — K8s pod start + container runtime + image pull ~1-2s — 自研 boot 路径 Container 已经在 runsc,boot 在 ~1s 量级
3. Load filesystem (image + code + models) ~1 minute — 8 GiB image pull + decompress + unpack ~100ms — ImageFS lazy load(index only) 5 MiB index FUSE mount + 按需 fetch
4. App host + device init(imports, model load) 10s-几分钟 — 26k syscalls in import torch + model load ~1-5s — CRIU CPU snapshot + CUDA GPU snapshot Snapshot restore ≈ 直接跳到 `f(x)` 调用点
TOTAL ~2000s (33 分钟) — 主要是 step 4 + capacity wait ~50s — 全栈叠加 40× speedup

逐步对Bottlenecks的应对

Bottlenecks 1:Capacity 等待

Modal 自述:用户在 spike 时需要等云厂分配 instance。Modal 的解法是 LP solver + cloud buffers — 预先 spin-up 一些 idle instances 当 buffer,同时 solver 持续优化 instance 组合。

Bottlenecks 2:文件系统

这是 Modal 在 2024 年集中攻克的Bottlenecks(ImageFS)。8 GiB Python image 在 naive `docker run` 流程下需要 1 分钟(2 GiB/s 下载 + 80 MiB/s 单线程 gzip 解压)。Modal ImageFS 把这个降到 ~100ms 挂载 + 按需 fetch — 详情见 M3.2。

Bottlenecks 3:Python 应用初始化

即使文件系统准备好了,Python 进程仍然要执行 `import torch` 等 26,000 syscalls。这是 Modal 在 2025 年 1 月用 CRIU+gVisor snapshot 攻克的。Snapshot restore ≈ 直接跳到 import 完成后的状态,跳过所有 syscalls。详情见 M3.3。

Bottlenecks 4:GPU 应用初始化

CPU snapshot 不能 save GPU state,所以 `model.to('cuda')` 必须在 snapshot restore 后重做。Modal 在 2025 年 7 月用 NVIDIA CUDA checkpoint API 攻克。详情见 M3.4。

剩余 50s 在哪里?

Modal 自述(图示数据):从 ~2000s 到 ~50s 是 40×。剩余的 ~50s 主要是:

  • Cloud buffer spin-up(~10-30s)— 如果 buffer 中没有合适的 instance
  • GPU weights load(~1-50s)— model 越大越慢;Modal 自述"a few GB/s to a few hundred seconds"
  • vLLM / SGLang 的额外 init — Modal 提过需要 weight offloading 等调整

冷启动优化的"递归性" — 还有优化空间吗?

Modal 自述在 2026 年的几个方向:

  1. RDMA weight server(M3.6 提过)— 3-10× model load 带宽提升
  2. Multi-region pre-warming(2026-08 blog "Bringing serverless functions closer to the speed of wire")— Function Call 数据路径 >50ms 提速
  3. Multi-GPU snapshot— 当前仅单 GPU;多 GPU NCCL 还在 hack
  4. Snapshot storage tiering— hot snapshot in NVMe, warm in S3, cold in glacier

Blog 2/6 — Memory snapshots: Checkpoint/restore for sub-second startup

发布日期: 2025-01-28 · 作者: Jonathon Belotti · 来源: modal.com/blog/mem-snapshots

作者原话 — 为什么 gVisor 让 checkpoint 简单

"Container snapshotting functionality is an outgrowth of the 'checkpoint/restore in userspace' (CRIU) kernel technology. ... CRIU was first presented in 2011 by some 'mad Russians' as a method for live migration of containers between physical servers."

"CRIU is developed for the runc container runtime, but for security reasons Modal uses the gVisor container runtime runsc. While runc has containers run on the host kernel, gVisor implements a userspace kernel and gives the guest container access to that. ... While a runc snapshotting solution cooperates with the host Linux kernel to save container state—the kernel exposes, via /proc VFS, details about a process's memory maps, open files, children processes—gVisor controls the userspace kernel serving a snapshotted container guest."

Snapshot 文件结构

  • 容器文件系统 mutations(overlayfs upper)
  • 整个进程树
  • 每个进程的 state:memory mappings、file descriptor table、registers、environment variables、PID
  • 不包括:live network connections、NVIDIA GPU state(后续 blog 单独处理)
  • Snapshot 文件 = 单个 'pages' 文件(100 MiB - 10 GiB)

Restore 实现细节

gVisor 的 prioritized background page loading + Modal FUSE 的 aggressive preload 协同工作:

  • gVisor 在 snapshot 时序列化它自己的 async state machine
  • Modal 把 pages 文件预加载到 host page cache
  • restore 时,gVisor 在 background 加载 pages(不需要全部 ready 才能开始)
  • 如果 page fault 命中 host page cache → 立即可用
  • 如果 page fault 没命中 → FUSE server 从 network 拉取(10s of ms)

Blog 3/6 — GPU Memory Snapshots

发布日期: 2025-07-30 · 作者: Luis Capelo, Colin Weld · 来源: modal.com/blog/gpu-mem-snapshots

作者原话 — 痛点

"While memory snapshots significantly improved cold start times for many functions, they had an important limitation for GPU workloads—GPU state could not be included in the snapshot. Until now. ... For example, this meant that you had to copy model weights from CPU to GPU after restore."

实现机制 — CUDA Checkpoint API

NVIDIA 在 driver 分支 570 / 575 加入的 CUDA checkpoint/restore API:

  • cuCheckpointProcessLock() — 锁定 CUDA process 防止 snapshot 期间发起新 GPU 操作
  • 等待所有进程进入 CU_PROCESS_STATE_CHECKPOINTED 且无活跃 CUDA sessions
  • Snapshot CPU memory + GPU vRAM 一起
  • Restore 时:cuCheckpointProcessRestore() → cuCheckpointProcessUnlock()

Snapshot 包含

  • Device memory contents(GPU vRAM)— model weights
  • CUDA kernels
  • CUDA objects(streams, contexts)
  • Memory mappings 和 addresses

Blog 4/6 — How we achieved truly serverless GPUs

作者原话 — 为什么 serverless GPU 难

"Inference workloads are more variable and less predictable than the training workloads that previously dominated. That makes them a natural fit for serverless computing, where applications are defined at a level above the (virtual) machine so that they can be more readily scaled up and down to handle variable load."

Blog 5/6 — Scaling to 1 million concurrent sandboxes in seconds

发布日期: 2026-07-16 · 作者: Colin Weld, Connor Adams · 来源: modal.com/blog/scaling-to-1-million-concurrent-sandboxes-in-seconds

作者原话 — 为什么 K8s 不可行

"For Kubernetes, as an example:
  • The scheduling algorithm is O(n × p) for n nodes and p pods in the worst case, and scheduling is serialized by default.
  • Each pod causes multiple writes to etcd (the central Kubernetes durable store) over its lifetime, which can create serious issues under high pod creation rates or high pod churn, and etcd is not natively shardable within a keyspace
  • Each node must write to etcd at least once per heartbeat interval to signal liveness, so baseline etcd write load is O(nodes) completely independent of pod creation"

Modal 旧架构的同样问题

Modal 自述:"Modal's original sandbox architecture has similar issues. Like Kubernetes, we rely on strong consistency throughout our backend, so creating and scheduling sandboxes requires global coordination, and O(sandboxes) writes to Postgres, which we cannot trivially shard."

新架构的关键决策

  • Trading global consistency for scalability and performance on the critical path
  • 调度服务器是 fleet,不是单一 scheduler
  • 每个调度服务器用 in-memory cache(不是中央 durable store)
  • Workers 自己是 source of truth → publish state to Redis stream
  • 调度器 RPC worker 直接创建 — worker accept/reject

实测数字

  • 1,000,000 sandboxes 创建 < 60 秒
  • p50 time-to-interactivity < 500ms
  • 两个网络 hop + 一个 cheap CPU op
  • Sandbox objects 存在 Redis(不在 critical path)
  • Single Redis stream viable past 100k workers

作者原话 — LP 的 dual mandate

# Modal 自述(改写):
# 1. 创建 100k sandboxes 同时在同一个 worker
# 2. 每个 sandbox 创建时调用 netlink API 设置 network namespace
# 3. 所有调用都需要 rtnl lock → 串行化
# 4. rtnl lock held time ≈ 10ms per netlink call
# 5. Total time = 100k × 10ms = 1000s 启动时间
#
# Solution: pre-create network namespaces in batches,
# or use alternative networking setup (e.g. CNI plugins
# that batch operations).

M3.14 · ImageFS Detail

ImageFS 生产细节 — 从 modal-client 到 worker 的完整路径

ImageFS 5 tier cache 详解

Modal 在 jono-containers-talk 中给出 5 tier 的延迟 / 吞吐 / 成本(参考 M4.1 完整摘录):

  1. Memory(10-40 GiB/s,$2/GiB/月)— 同一 worker 上的 page cache
  2. SSD(4 GiB/s,$0.10/GiB/月)— worker 本地 NVMe, RAID-0
  3. AZ Cache Server(10 GiB/s,$0.15/GiB/月)— Availability Zone 级 cache, Modal 自建
  4. Regional CDN(3-10 GiB/s)— 跨 AZ 共享,无明确 $/GiB
  5. Blob Storage(3-10 GiB/s,$0.015/GiB/月)— S3 / GCS / Azure Blob,长期存储

Worker 上的 cache 命中模式

Modal 自述: "Our distributed file system uses a series of caches to store, directly in the worker memory, the most popular files used across Modal users."

关键数字:

  • Worker memory cache 命中:通常 70-90% (典型 workload)
  • AZ cache 命中:次优 tier,5-15%
  • Blob storage:5-15%(冷数据, 比如不在常用 image 中的 dependencies)

Modal 经验:哪些文件命中最高

Belotti 公开:"if torch is imported in one program, another program benefits because the torch files are now in the worker cache. This has a substantial impact in performance, usually 3-5x faster than when downloading files without a cache."

最热文件(粗略估计):

  • Python 解释器 + 标准库
  • PyTorch / TensorFlow 共享 library
  • CUDA runtime libraries
  • Hugging Face transformers
  • NumPy / pandas / scikit-learn
  • vLLM / SGLang / llama.cpp

Cache invalidation 策略

Modal 用 content-addressed chunk 命名,意味着:

  • 同一 chunk hash = 同一内容 → 不需要 invalidation
  • 新版本 image → 新的 chunks → 自动 dedup 旧版本 chunks(如果还在用)
  • 不需要"cache flush"操作 — 这跟 Docker 的 layer-based cache 模型形成鲜明对比

Content addressing vs Docker layer 的差异

维度Docker layer-basedModal content-addressed
Cache keyLayer digest + parent chainFile content hash
Dedup granularityLayer(粗)Chunk(细, 通常 4 KiB - 1 MiB)
更新 image重新 build 整个 layer chain只改 chunks,其他 unchanged
Cache invalidation显式 layer prune无需(无 invalidation)
Network transfer整个 layer只按需 chunk
Container startpull 整个 image → 几 GB / 几 minutepull 5 MiB index → 100ms

这是 Modal ImageFS 设计哲学的本质 — chunks by content, not layers by build order。这是容器生态一个根本性的范式转移。

Modal 为什么不用 SOCI / stargz / Nydus?

OCI 生态已经有几个 lazy-loading 方案:

  • containerd/stargz-snapshotter(NTT, 2019)— gzip + seekable table
  • AWS SOCI(2023)— OCI referrer + FUSE
  • Dragonfly Nydus(2021)— chunk-based + FUSE

Modal 的 ImageFS 自研(2022-2024),可能是 Nydus 风格但更紧密集成。原因可能包括:

  • Modal 想控制 5 tier cache 的具体实现(不是为了 OCI 标准)
  • Modal 不想绑定 containerd(snapshotter 模式)
  • Modal 想 integrate 到 gVisor runsc 直接(OCI 标准 snapshotter 在 containerd 层)
GPU Strategy

GPU 共享策略对比 — Modal 在哪一档

GPU 共享是 AI infra 行业最被讨论的设计选择之一。本节比较主要 serverless GPU 玩家采用的策略。

5 种 GPU 共享策略

A. 整块物理 GPU per workload(per Function / per Sandbox)

代表玩家: Modal, Fireworks, Together, Baseten, RunPod

优点: 简单、CUDA 全兼容、inference engine 兼容性好

缺点: 利用率低 — 小 workload 浪费大 GPU 容量

B. MIG(Multi-Instance GPU,硬件分片)

代表玩家: NVIDIA AI Enterprise / vGPU 方案中

原理: 把 H100 / A100 切成 7 个 isolated instances,每个 1/7 算力 + memory

优点: 硬件级隔离、QoS 保证、并行执行

缺点: CUDA compatibility profile 受限、inference engine 兼容性差、Modal 未产品化

信源: NVIDIA MIG

C. vGPU(time-slicing)

代表玩家: NVIDIA vGPU 许可产品

原理: 多个 VM 时间片轮转使用同一 GPU

优点: 简单、CUDA 兼容

缺点: 没有真正并行,QoS 弱

信源: NVIDIA vGPU

D. CUDA MPS(Multi-Process Service)

代表玩家: 一些 hyperscaler 内部使用

原理: 同一 GPU 上多个 CUDA context 并发

优点: CUDA 兼容

缺点: 不隔离 — 一个进程 crash 可能影响其他进程

E. rCUDA / vCUDA(API-level virtualization)

代表玩家: rCUDA 开源项目,一些研究项目

原理: 在 user-space intercept CUDA API,转发到远端 GPU

优点: 可以跨机器共享 GPU

缺点: 性能开销大、CUDA 兼容性差

Modal 当前在哪个位置?

Modal 采用 策略 A(整块物理 GPU) + 不依赖 GPU 共享技术。这是务实的选择:

  • Modal 的客户绝大多数用 vLLM / SGLang / TGI 等 inference engine,这些 engine 对 MIG 不友好
  • Modal 用 sandbox 多容器的方式做"OS 层共享"(在同一物理 GPU 上跑多个容器)
  • Modal 在 GPU Glossary 描述 MIG 但不产品化 — 等 NVIDIA 生态更成熟

多 GPU 节点内部互联

Modal worker 是 8-GPU node,内部互联方式:

  • NVLink(GPU-to-GPU, ~900 GB/s on H100)— Modal docs 自述 multi-GPU training 在同一物理机
  • NVSwitch(switch chip)— 8-GPU 全互联
  • PCIe(GPU-to-CPU)— fallback

这是 NCCL all-reduce 等 collective 操作的基础。Modal 在 weekly active check 中跑 NCCL all-reduce 来验证 NVLink 性能(gpu-health)。

跨节点 GPU 互联 — 当前的局限

Modal 自述在 truly-serverless-gpus blog 中提到跨节点的Bottlenecks:

"It's tough to elevate this bottleneck when you load across clouds or cloud regions like we do. You might >3x this speed by running a weight server within an AZ or >10x it by running an RDMA weight server over RoCE/InfiniBand. This is doable, but expensive and gnarly, especially when scaling to many models and dynamic worker pools. We're working on it!"

这意味着:

  • Modal 当前 不支持 跨节点 NCCL all-reduce over RDMA
  • 跨节点 weight transfer 是当前最大Bottlenecks(尤其 trillion-parameter model serving)
  • RDMA weight server 是 2027 路线图

Conclusion

结语 — Modal 是 2026 年最值得跟踪的 AI infra 公司之一

这份研报试图回答一个问题:Modal 到底是一家什么样的公司?

回答是:Modal 是一家 从 OS / 容器 / GPU 调度底层开始重写整个 serverless AI 栈 的公司。它的赌注是 — 传统的 Docker + Kubernetes + Helm + YAML 体系是为 web 服务设计的,不适合 AI 工作负载的 burst pattern。Modal 把整套替换成 Rust runtime + Python DSL + LP 资源求解器 + multi-cloud arbitrage。

从结果看,这个赌注在 2026 年获得兑现:

  • GPU cold-start 从 ~2000s → ~50s (40× speedup)
  • ImageFS 2.5 GB/s sustained throughput
  • GPU snapshot 10× speedup(Parakeet NeMo)
  • 1M concurrent sandboxes <60s
  • 1B+ sandbox lifetime 启动
  • ARR 9 个月 5×(从 $60M → $300M)
  • Sandboxes 占收入 1/3+

客户的 quote 是最直接的证据 — Cognition / Suno / Ramp / Lovable / DoorDash / Reducto / Physical Intelligence / Meta — 几乎覆盖了 2026 年最热的 AI 应用场景。

Modal 不是没有弱点:

  • self-hosted 缺位
  • multi-node DDP 还在 closed beta
  • RDMA weight server 未产品化
  • 毛利率压力(hyperscaler 降价)
  • vendor lock-in(不可 self-host)

但 Modal 的真正护城河不是单点技术,而是 "三层叠加 + 1 个商业化":

  1. 运行时层(gVisor + CRIU + CUDA checkpoint)
  2. 文件系统层(Rust + FUSE + content addressing + 5 tier cache)
  3. 调度层(LP + Redis stream + in-memory cache)
  4. 商业化层(1B+ sandboxes + 顶级 customer logos)

竞争对手必须同时做到这 4 件事才能追赶,而非单点突破。这是 Modal 在 AI infra 赛道的真正壁垒。

Competitor Deep Dive

竞品深度分析 — Modal 在 AI infra 生态中的位置

1. Fireworks AI — $17.5B @ $1B+ ARR(2026-07 Series D)

定位:Speed-focused open-model inference API。40T tokens/day,5000+ 客户。

关键差异:

  • Fireworks 是 "inference API marketplace" — 用户给 prompt,平台返回 token
  • Modal 是 "serverless GPU execution substrate" — 用户给 Python 函数,平台跑任意 Python
  • Fireworks 强在 closed-loop latency 优化;Modal 强在 DX + cold start

估值倍数: 17.5× ARR — 比 Modal 略高,但 Fireworks ARR($1B+)远大于 Modal($300M)

信源: Sacra, valueaddvc.com

2. Together AI — $8.3B @ $1.15B bookings(2026-07 Series C)

定位:Open-model inference + dedicated GPU clusters。即时集群(Instant Clusters)+ Blackwell GPUs。

关键差异:

  • Together 既有 API serving 也有"卖整机"模式 — 双重 GTM
  • DX 不如 Modal(Together 没有 Python DSL;用户写 model server 模板)
  • Bookings $1.15B 但 不是 ARR,实际收入可能更低

信源: valueaddvc.com Fireworks analysis

3. Baseten — $13B @ $600M ARR(2026-06 Series F)

定位:Enterprise inference engineering platform。Truss YAML 配置,可自部署。

关键差异:

  • Baseten 提供 self-hosted 和 hybrid deployment in customer VPCs — 这是 Modal 没有的
  • 1B+ inference calls/day,87 clusters,18 clouds(infra 规模大)
  • YAML Truss 配置 — DX 弱于 Modal 的 Python DSL
  • 2025 年 cold start 16-60s — Modal 的 sub-second 优势显著

信源: valueaddvc.com Baseten profile

4. Replicate

定位:Massive catalog of pre-trained models + private model deployment。数千 paying 客户。

关键差异:

  • Replicate 强在 catalog(无需写代码部署预训练模型)
  • 弱在 private deployment(冷启动长,billed idle)
  • 不是 Modal 的直接竞品 — Replicate 偏 catalog,Modal 偏 compute substrate

信源: beam.cloud benchmark

5. RunPod

定位:Docker-first GPU cloud。Cold start 6-12s(FlashBoot <1s)。

关键差异:

  • RunPod 更像传统 IaaS(per-pod pricing)+ serverless overlay
  • Docker 接口 → 学习曲线陡
  • 便宜(up to 40% GPU 节省),适合成本敏感型 workload

信源: beam.cloud benchmark

6. Anyscale

定位:Managed Ray OSS — 分布式 Python 计算平台。

关键差异:

  • Ray 生态基础(Modin、XGBoost-Ray 等)
  • 更像"managed Ray"而非 serverless DX
  • infra burden 仍高于 Modal

信源: Modal 自述对比(TBPN digest)

7. Beam — 开源 beta9 runtime + Python SDK

定位:Python-native serverless GPU。开源 beta9 runtime(类似 Modal 自研 Rust runtime)。

关键差异:

  • Beam 也用 lazy container loading(GPU snapshot restore)
  • Cold start ~2-3s(比 Modal 慢)
  • 比 Modal 小很多 — 不是 enterprise scale

信源: beam.cloud

8. Hyperscalers — AWS Lambda / Google Cloud Run / Azure

AWS Lambda:

  • Firecracker microVM,sub-second cold start,但 无 GPU 支持
  • 适合 serverless compute,不适合 AI workload

Google Cloud Run:

  • gVisor runtime(同 Modal),但 cold start 20-30s
  • GPU 支持限制 L4(mid-2025),不能 serve 大模型

Azure:

  • Azure Container Apps 2026 才补齐 serverless GPU
  • DX 仍弱于 Modal

Hyperscalers 的 serverless GPU 是 Modal 的最大潜在威胁 — 当他们的 DX 追上 Modal,客户可能不会切换。
