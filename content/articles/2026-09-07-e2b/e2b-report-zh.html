执行摘要

E2B 卖的是 Agent 计算的管道工程——一套开源 SDK,用于快速启动一个隔离的 Firecracker microVM,在其中运行 LLM 生成的代码,任务完成后立即销毁。与 AWS Lambda 同一套 VMM;同一套 SDK 也在 Anthropic、Hugging Face、Perplexity、Groq、Manus、LMArena 内部使用。两位捷克创始人,原本经营一款开发者工具产品 DevBook,于 2023 年转向 E2B,先后完成 $2.5M Pre-Seed、$11.5M Seed(Decibel,2024 年 10 月)与 $21M A 轮(Insight Partners,2025 年 7 月)。累计融资约 $32M。

技术护城河并不在于 microVM 本身——任何人都可以跑 Firecracker——而在于其快照恢复流水线:每次创建模板本质上是恢复一个预先启动好的 memfile,通过 userfaultfd 按需供给页,rootfs 通过 NBD COW overlay 提供,快照差异相对于父模板异步上传。结果是 5–30 ms 的热启动,以及 150–800 ms 的从对象存储冷启动。

商业风险是结构性的:E2B 最大的客户恰恰是 LLM 实验室本身,后者随时可以——也确实有报道称在 Anthropic 的案例中如此——进行垂直整合。乐观的一面则是开源 SDK 带来的锁定效应、BYOC 企业销售(SOC 2 + HIPAA + 美国/欧盟区域),以及 Desktop/Computer-Use 这条增长曲线,Claude / GPT 正在推出更多 Agent。

3.0.1 · envd 守护进程 —— 每个 microVM 内部跑的是什么

envd 是 E2B 在 VM 内部的守护进程,监听 :49983,协议为 Connect-RPC(Buf 的 HTTP/2 RPC 框架)。它是 SDK 在沙箱内部唯一会交互的、由 E2B 控制的进程。综合 ARCHITECTURE.md 与 ggprompts 架构图:

envd RPC 接口

API 组方法用途
Process APIStartProcess、SignalProcess、ListProcesses、StreamOutput在 VM 内部执行 shell 命令;捕获 stdout/stderr;信号(SIGTERM/SIGKILL)
Filesystem APIReadFile、WriteFile、MakeDir、Remove、Stat对沙箱 rootfs 的直接文件操作
Init API/init首次握手;接收 sandbox ID、envd 访问令牌(来自 MMDS)、环境变量

envd 与某个模板版本是绑定的。一个长期暂停的沙箱在整个生命周期内都停留在该 envd 版本上,除非用户显式执行一次 FS-only 的恢复-暂停循环(此时可通过 debugfs 替换 envd)。

envd 令牌 —— 哪些能力被它守门

Orchestrator 签发一个限定范围的短效 JWT,作用域为 team + sandbox,通过 MMDS 在 init 阶段注入 envd。envd 在每一次 RPC 调用时都会校验令牌。其 audience 声明为 https://api.——为一个集群签发的令牌不会被另一个集群接受。

3.1 运行时基底 —— Firecracker microVM

E2B 直接构建在 Firecracker 之上 —— 与 AWS 为 Lambda/Fargate 开发的 VMM 同款。证据已在多处交叉验证:

  • E2B 自己的 Firecracker-vs-QEMU 博客(2025-03-03)
  • 开源架构文档(ARCHITECTURE.md)
  • 第三方深度分析(Spheron)
  • Firecracker 上游安全设计(DeepWiki)

Firecracker 基准数字(来自 Northflank 与 Firecracker 设计文档的交叉确认):

~50,000 行 Rust 代码(对比 QEMU 的约 200 万行 C)
~125 ms 每个 microVM 的冷启动
<5 MiB 每个 microVM 的内存开销
每个 VMM 一个 Rust 进程(外加 jailer 线程)
KVM 硬件虚拟化
纵深防御:VMM 进程自身启用 seccomp + Landlock + cgroups

E2B 的增值并不在于更快的 microVM 启动 —— 而在于确保每一次沙箱创建本质上都是一次快照恢复,而不是从零启动。比 125 ms 更快?仅当快照已经在本地缓存中(5–30 ms)。否则 Orchestrator 仍要付出 UFFD + NBD + VM-resume 的代价。

3.2 "创建一个沙箱"的戏法 —— 为什么比 125 ms 更快

flowchart LR A[SDK: Sandbox.create] --> B[API: gRPC Create] B --> C[Orchestrator: fetch template] C --> D{Cache hit?} D -- yes --> E[local memfile] D -- no --> F[GCS/S3 + NFS chunk cache + peer-to-peer] E --> G[UFFD lazy memory restore] F --> G G --> H[NBD COW rootfs overlay] H --> I[Firecracker: resume VM] I --> J[envd /init → ready] style A fill:#0e7490,color:#fff style J fill:#10b981,color:#fff

五项架构设计让这一切变快(ARCHITECTURE.md):

  1. 模板 = 预先启动的快照。构建阶段运行一个 VM,并在构建时捕获 memfile(内存)、rootfs.ext4(磁盘)、snapfile(VM 状态)、metadata.json(配置)。这些产物按 {buildID}/... 路径存储在 GCS/S3/本地。
  2. Sandbox.create() 内部即是一次恢复。Firecracker 的 LoadSnapshot 在不预先加载内存的情况下恢复 VM;userfaultfd (UFFD) handler 按需从模板的 memfile 提供 page fault。只有被触碰的页才会被读取。
  3. 通过 NBD 实现 COW rootfs。模板 rootfs 保持只读;写入落到一个 per-sandbox 的 COW 缓存,该缓存以 Network Block Device 的形式暴露给 Firecracker,由 Orchestrator 内部一个用户态 NBD server 提供。
  4. 优先在原节点恢复。调度器会优先把请求路由到最近一次使用过该快照的节点;若该快照仍在本地磁盘缓存中,则完全不需要读对象存储。
  5. 预取会预热已知的热点页;Orchestrator 还支持一个共享 NFS chunk cache以及节点间 P2P 获取(在上传完成前即可使用)。

实际延迟:

  • 本地缓存的热恢复:5–30 ms(Spheron)
  • 从对象存储冷恢复:150 ms(Spheron)/300–800 ms(Morph,因模板而异)
  • 真正的冷启动(仅文件系统/全新构建):Firecracker 自身约 125 ms + UFFD 页面错误遍历

3.3 快照模型与暂停/恢复 —— 暂停本身就是一次快照

每次暂停都会上传相对于父模板的差异(内存 diff + COW rootfs diff),按 buildID 索引,并通过 .header 索引文件沿 diff 链回溯解析。

sequenceDiagram participant Client as SDK participant API as API Server participant Node as Orchestrator (node) participant OS as Object storage participant VM as Firecracker Client->>API: pause(sandboxId) API->>API: snapshot row → Postgres API->>Node: gRPC Pause Node->>VM: Pause VM (dirty-page tracking) Node->>Node: diff memory + rootfs vs template Node->>OS: async upload (memfile diff, rootfs diff, .header) VM-->>Node: state persisted Node-->>API: ack API->>Client: paused

延迟的 rootfs 导出(功能开关)

Orchestrator 在暂停时不再对 rootfs 做 diff,而是在暂停期间弹出可写的 COW 缓存,并在后台(reflink)封存它。优点:把 diff 的延迟从面向用户的 pause 调用中剥离。缺点:在封存完成前,该 diff 的后续读取会被阻塞;封存失败是永久性的,上传会立即失败,不再重试。

仅文件系统快照(pause({keepMemory:false}))

丢弃内存,保留磁盘。恢复时通过 RebootSandbox 进行冷启动。自动恢复(auto-resume)永远不走这条路径——它做不到(恢复运行中的进程必须用到内存)。通过 fs-only-resume-api 功能开关按 team 维度开启;API 会在不匹配时直接拒绝,而不是悄悄降级。来源

启动前的文件系统恢复

如果某 rootfs 在暂停时没有执行 fs_quiesced(遗留的同步回退路径,或仅文件系统恢复),那么 VM 启动前会跑一次在 jail 中的 e2fsck -p -E journal_only——只重放 journal,与客机内核挂载时的行为一致。memory: false 的恢复会挂载一份一致的磁盘;任何持久化状态都不会被改写(内存快照原样保留)。

envd 替换(envd 离线升级)

在一次 fs_quiesced 快照的冷启动恢复过程中,可通过 debugfs 将 envd 二进制替换为更新版本(并非以宿主内核挂载租户镜像)。最佳努力;按快照的构建版本作为键;在重新暂停重新烘焙运行版本之前,该操作会幂等地反复触发。受 envd-offline-upgrade-target 开关控制。

自动暂停 / 自动恢复

空闲的沙箱会被暂停;入站流量通过 client-proxy 恢复它们。这正是让按秒计费看起来像 serverless 计费的原因——直到你的 Agent 在用户多轮交互之间陷入空闲。

3.4 存储与 I/O —— 沙箱内部到底装着什么

  • Rootfs:基于 Ubuntu 的最小化 Linux;基线约 200 MB;每个沙箱通过 COW overlay。
  • 块设备:由 Orchestrator 内部 NBD server 提供、NBD 后端的 COW overlay;底层是节点上的本地 NVMe;在 pause 时以 diff 形式上传到 GCS/S3。
  • 内存:每个模板构建一个 memfile;每次暂停生成 per-sandbox 内存 diff。
  • 对象存储:GCS(GCP 主用)、S3(AWS beta)、本地磁盘回退。按 buildID 索引。来源
  • 网络:每个沙箱一个 TAP 接口接入宿主机 bridge;每个沙箱一个 /30 子网;NAT + iptables 出站;通过 physdev 模块实现 per-tap 的出站隔离。来源

3.5 GPU —— 缺失的托管能力

E2B 托管层对 Code Interpreter + Desktop 仅提供 CPU。GPU 访问仅在开源自托管模式下可用,通过裸金属上的 VFIO-PCI passthrough 实现:

  • 宿主机内核持有 GPU;客机直接看到该设备。
  • 需要在 BIOS 中开启 IOMMU(Intel VT-d / AMD-Vi)。
  • Firecracker VFIO 设备:在 VM config 中配置 "vfio": [{"host_dev_path": "/dev/vfio/N"}]。
  • 已确认在 NVIDIA A100 80GB PCIe(PCI 10de:20b5)与 H100 上工作正常。
⚠ 注意事项(Northflank + Spheron):Firecracker 的 PCIe 相关工作在 2025 年被 AWS 上游暂停。开启嵌套虚拟化的云 VM 会带来 5–15 ms 的额外开销,并会破坏 PCIe passthrough。在托管型 GPU 推理这一场景下,Modal / Replicate 仍是更强的选择。来源 来源

3.6.2 Seccomp / Landlock / cgroups —— Firecracker jailer 强制了什么

Firecracker VMM 本身运行在一个加固过的 jailer 沙箱中。引自 Firecracker 安全子系统文档:

  • 进程隔离:每个 microVM 作为一个独立进程运行,由 jailer 实施严格的沙箱约束。
  • 系统调用过滤:细粒度的 seccomp filter 限制 VMM 与宿主内核的交互。
  • 文件系统访问限制:Landlock LSM(Linux 内核提供的可叠加文件系统沙箱)。
  • 资源控制:cgroups v1/v2 对 CPU、内存、PIDs、blkio、devices 的配额限制。

3.9 · 冷启动数学 —— 为什么 150 ms 对 Agent 来说胜过 800 ms

按秒计费让冷启动延迟成为一项直接的收入成本项。下面是单次沙箱创建事件的算账:

场景冷启动执行时间计费总时长实际每次成本
从本地缓存做快照恢复30ms5s5.03s × $0.000014 = $0.0000704~$0.00007
从 GCS 恢复,无 NFS300ms5s5.30s × $0.000014 = $0.0000742~$0.000074
冷启动(无模板)800ms5s5.80s × $0.000014 = $0.0000812~$0.000081
两次工具调用间空闲 30s(交互式 Agent)—5s + 30s idle35s × $0.000014 = $0.00049~$0.00049(约为头版价 7 倍)

在每月一百万沙箱的规模下,5 倍的速度提升(快照恢复 vs 冷启动)带来的差异只有大约每年 $100;但"计费的空闲时间"与"计费的执行时间"之间的差异,折合每百万沙箱每年大约 $4,200。这就是为什么 E2B 的对外叙事重点放在工具调用延迟故事上,而不是按秒费率本身。

3.11 · 快照产物剖析

根据 ARCHITECTURE.md 的定义,模板构建与一次已暂停沙箱的快照具有相同的产物形态——快照本质上就是一个新的构建,其 memfile/rootfs 以相对于来源模板的 diff 形式存储。

{buildID}/
├── memfile              # 原始内存镜像(通过 UFFD 惰性加载)
├── rootfs.ext4          # 文件系统镜像
├── snapfile             # Firecracker VM 状态
├── metadata.json        # sandbox ID、template、envd 访问令牌哈希
└── .header              # 索引文件:沿 diff 链一路回溯到基础模板

diff 链通过 .header 文件解析。如果你先暂停沙箱 A(来自模板 T),再暂停一个子沙箱 B(来自已暂停的 A),B 的产物就是相对于 A 的 diff,.header 一路回溯到 T。

5.2 Firecracker 与 WASM 的权衡——为什么 E2B 没有选 WASM

Firecracker 启动约 125ms;WASM 冷启动 1–5ms——快 20–100 倍。E2B 选了更慢的那个原语。为什么?

  • Linux ABI 兼容性。沙箱需要真实的 Python/Node/Rust/CUDA/PyTorch/x86 二进制、完整的 glibc、完整的系统调用。WASM = 只有 WASI(POSIX 覆盖正在增长但仍不完整)。
  • GPU + VFIO。Firecracker 支持 VFIO 设备透传(存在 2025 年 PCIe-pause 风险)。WASM 除了 WebGPU 之外没有真正的 GPU 路径。
  • 既有生态。E2B 的客户(Anthropic、Hugging Face、Perplexity、Manus)产出的 agent 会执行 pip install、npm i、shell 命令。WASM 重写了用户的使用模型。
  • 运维对称性。microVM 本质上是一个迷你的 Linux VM——SRE、系统管理员与安全团队都已经知道怎么对它进行推理。

简而言之:WASM 胜在冷启动;Firecracker 胜在里面能跑什么。E2B 赌的是 AI agent 沙箱的瓶颈是里面跑的东西,而不是箱子出现得多快。src src

5.3 瓶颈与风险

  • 托管 GPU 不是 E2B 的强项。Modal 和 Replicate 主导着托管 GPU 沙箱品类;E2B 的 GPU 故事仅限于裸金属自托管。src
  • 客户去中介化风险。头部客户都是 LLM 实验室,具备纵向整合的能力。Anthropic 被广泛报道其 Claude Code 制品运行在 E2B 之上(landscape 资料,二手来源)。任何一家这样的客户单方面的产品路线决策,都可能让 E2B 一大块收入崩塌。
  • 平台分叉风险。Vercel Sandbox(2024–2025)与 Google Cloud Run Sandboxes(2026 Preview)都在 Firecracker/gVisor 之上交付同样的原语。超大规模云厂商可以通过价格与捆绑进行竞争碾压。
  • 按秒计费中的"闲置时间税":当交互式 AI agent 在两次工具调用之间等待用户回复 30 秒时,计费时钟仍在走。【分析师估算】 根据 Morph 的分析 (src),计费秒数中有 15–30% 是 agent 闲置时间。这恰恰伤害了 E2B 想要切入的用例。
  • "财富 100 强注册率达 88%"是一个漏斗顶端指标,而不是 ARR。注册 ≠ 活跃部署。
  • 上线初期单一区域集中。最初仅美国区域;欧洲区域随 Enterprise 才上线。

5.4 战略判断

  • 切入点是真实的。E2B 是"AI agent 安全 Linux 沙箱"的最便捷路径——三行代码、AWS Lambda 级别的隔离、对工具调用延迟足够快的快照恢复。Apache-2.0 开源优先的打法意味着,即使超大规模云厂商匹配上同款原语,Anthropic / Hugging Face / Perplexity 仍会继续使用它,因为 SDK 体验与开源护城河已经足够深。
  • 天花板是有界的。E2B 卖的是 agent 计算的管道。管道是云的一个特性,而不是云之上的一个层级。真正可守得住的护城河是模板 + SDK 生态 + 闲置时间优化,而不是 microVM——任何人都能跑 Firecracker。
  • 上行空间在哪里:Pause/resume 效率(已较强)、BYOC + 本地化企业销售(Rogo、StackAI、Effective AI、Genspark 早期有进展)、GPU-on-bare-metal 服务于 RL rollout(Paper Instruments、Replicas)、Desktop + computer-use,配合 Anthropic/OpenAI 推出更多 agent。A 轮资金($21M)能买到约 24 个月,把注册量转化为付费企业收入。

5.5.1 为什么 Firecracker 的 PCIe 暂停很重要

AWS 在 2025 年暂停了上游的 PCIe 透传相关工作。这意味着:

  • E2B 托管层在 code interpreter 场景下只能停留在 CPU。
  • 在 E2B 上跑 GPU 工作负载需要裸金属自托管,并配合 IOMMU + VFIO-PCI 绑定。
  • Modal 的托管 GPU(T4、A10G)在这一块有先发优势——但它没有 H100/B200,没有自托管,也没有快照恢复。

Spheron 和 Northflank 都指出,这是 2026 年基于 Firecracker 的沙箱产品在架构上单一最大的约束。

5.5.2 E2B 想在 GPU 上挑战 Modal 需要改变什么

  1. 在 AWS 裸金属或 GCP 裸金属上跑起托管 GPU microVM。
  2. 增加 H100 / B200 实例类型,支持 MIG 切片。
  3. 把按秒计费重构为"GPU-active-second"定价(Modal 的模式)。
  4. 让企业客户承诺 GPU 用量(Anthropic、Meta、Mistral 内部都需要这个)。

截至 2026 年中,以上这些都还没有公开动作。
