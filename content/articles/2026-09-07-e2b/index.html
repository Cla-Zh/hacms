Executive Summary

E2B sells the plumbing of agent compute: an open-source SDK that spins up an isolated Firecracker microVM, runs LLM-generated code inside it, and tears it down. Same VMM as AWS Lambda; same SDK at Anthropic, Hugging Face, Perplexity, Groq, Manus, LMArena. Two co-founders out of Czechia who pivoted from a developer-tools product (DevBook) in 2023, took $2.5M Pre-Seed, $11.5M Seed (Decibel, Oct 2024), and $21M Series A (Insight Partners, Jul 2025). Total ~$32M.

The technical moat is not the microVM — anyone can run Firecracker — it's the snapshot-resume pipeline: every template create is internally a resume of a pre-booted memfile, pages served via userfaultfd on demand, rootfs via NBD COW overlay, snapshot diffs against the parent template uploaded asynchronously. The result is 5–30ms warm start and 150–800ms cold start from object storage.

The commercial risk is structural: E2B's biggest customers are the LLM labs themselves, who can — and reportedly do, in the case of Anthropic — vertically integrate. The upside is the open-source SDK lock-in, the BYOC enterprise motion (SOC 2 + HIPAA + US/EU), and the Desktop/Computer-Use vector as Claude / GPT ship more agents.

3.0.1 · The envd daemon — what's running inside every microVM

envd is E2B's in-VM daemon, exposed on :49983 over Connect-RPC (Buf's HTTP/2 RPC framework). It is the only E2B-controlled process the SDK interacts with inside the sandbox. From ARCHITECTURE.md and the ggprompts architecture map:

envd RPC interface

API groupMethodsPurpose
Process APIStartProcess, SignalProcess, ListProcesses, StreamOutputShell commands inside the VM; captures stdout/stderr; signals (SIGTERM/SIGKILL)
Filesystem APIReadFile, WriteFile, MakeDir, Remove, StatDirect file ops in the sandbox rootfs
Init API/initFirst handshake; receives sandbox ID, envd access token (from MMDS), env vars

envd is pinned to a template version. A long-lived paused sandbox stays on that envd version for its whole lifetime unless the user does an explicit FS-only resume cycle (which can swap envd via debugfs).

envd token — what gates what

The orchestrator mints a short-lived JWT scoped to team + sandbox and presents it to envd via MMDS on init. envd validates the token on every RPC call. The audience claim is https://api.<BYOC or default domain> — a token minted for one cluster's origin is not accepted by another.

3.1 Runtime substrate — Firecracker microVM

E2B is built directly on Firecracker, the same VMM AWS built for Lambda/Fargate. Verified end-to-end across:

  • E2B's own Firecracker-vs-QEMU blog (2025-03-03)
  • The OSS architecture doc (ARCHITECTURE.md)
  • Third-party deep dive (Spheron)
  • Firecracker upstream security design (DeepWiki)

Firecracker baseline numbers (cross-confirmed from Northflank and the Firecracker design doc):

~50,000 lines of Rust (vs. QEMU's ~2M lines of C)
~125 ms cold boot per microVM
<5 MiB memory overhead per microVM
Single Rust process per VMM (with jailer thread)
KVM-backed hardware virtualization
Defense-in-depth: seccomp + Landlock + cgroups on the VMM process itself

E2B's value-add is not faster microVM boot — it's making sure every sandbox create is already a snapshot resume, not a from-scratch boot. Faster than 125 ms? Only when the snapshot is in local cache (5–30 ms). Otherwise the orchestrator pays the UFFD + NBD + VM-resume tax.

3.2 The "create a sandbox" trick — why it's faster than 125ms

flowchart LR A[SDK: Sandbox.create] --> B[API: gRPC Create] B --> C[Orchestrator: fetch template] C --> D{Cache hit?} D -- yes --> E[local memfile] D -- no --> F[GCS/S3 + NFS chunk cache + peer-to-peer] E --> G[UFFD lazy memory restore] F --> G G --> H[NBD COW rootfs overlay] H --> I[Firecracker: resume VM] I --> J[envd /init → ready] style A fill:#0e7490,color:#fff style J fill:#10b981,color:#fff

Five architectural moves make this fast (ARCHITECTURE.md):

  1. Template = pre-booted snapshot. Build runs a VM and captures a memfile (memory), rootfs.ext4 (disk), snapfile (VM state), metadata.json (config) at build time. Stored under {buildID}/... in GCS/S3/local.
  2. Sandbox.create() is internally a resume. Firecracker's LoadSnapshot restores the VM without loading memory; a userfaultfd (UFFD) handler serves page faults directly from the template's memfile. Only touched pages are read.
  3. COW rootfs via NBD. Template rootfs stays read-only; writes go to a per-sandbox COW cache exposed to Firecracker as a Network Block Device, served by an in-process userspace NBD server inside the orchestrator.
  4. Origin-node resume preferred. Placement picks the node where the snapshot was last used; if the snapshot is still in local disk cache, no object-storage reads at all.
  5. Pre-fetching warms known-hot pages; the orchestrator also supports a shared NFS chunk cache and peer-to-peer fetch from other nodes before upload completes.

Latency in practice:

  • Warm resume from local cache: 5–30 ms (Spheron)
  • Cold resume from object storage: 150 ms (Spheron) / 300–800 ms (Morph, template-dependent)
  • Truly cold boot (filesystem-only / new build): Firecracker's own ~125 ms + UFFD page-fault walk

3.3 Snapshot model & pause/resume — pause IS a snapshot

Every pause uploads a diff against the parent template (memory diffs + COW rootfs diffs), keyed by buildID and resolved through .header index files that walk diff chains.

sequenceDiagram participant Client as SDK participant API as API Server participant Node as Orchestrator (node) participant OS as Object storage participant VM as Firecracker Client->>API: pause(sandboxId) API->>API: snapshot row → Postgres API->>Node: gRPC Pause Node->>VM: Pause VM (dirty-page tracking) Node->>Node: diff memory + rootfs vs template Node->>OS: async upload (memfile diff, rootfs diff, .header) VM-->>Node: state persisted Node-->>API: ack API->>Client: paused

Deferred rootfs export (feature-flagged)

Instead of diffing the rootfs on the pause critical path, the orchestrator ejects the writable COW cache during pause and seals it (reflink) in the background. Pro: moves diff latency off the user-facing pause call. Con: blocks subsequent reads of the diff until the seal completes; seal failures are permanent and the upload fails fast rather than retrying.

Filesystem-only snapshots (pause({keepMemory:false}))

Drops memory, keeps disk. Resume performs a cold boot via RebootSandbox. Auto-resume never takes this path (it can't — memory is needed to restore the running process). Per-team gating via fs-only-resume-api feature flag; the API rejects rather than silently downgrades. src

Pre-boot filesystem recovery

If a rootfs was not fs_quiesced at pause (legacy sync-fallback or filesystem-only rescue), a jailed e2fsck -p -E journal_only runs before the VM boots — journal replay only, identical to what the guest kernel would do at mount. memory: false resumes mount a consistent disk; nothing durable is mutated (the memory snapshot survives untouched).

envd swap (envd offline upgrade)

On cold-boot resume of a fs_quiesced snapshot, the envd binary can be swapped to a newer version via debugfs (NOT a host-kernel mount of the tenant image). Best-effort; keyed on the snapshot's built-with version; re-fires idempotently until a re-pause re-bakes the running version. Gated by envd-offline-upgrade-target flag.

Auto-pause / auto-resume

Idle sandboxes pause; inbound traffic resumes them via the client-proxy. This is what makes the per-second clock feel like serverless billing — until your agent idles between user turns.

3.4 Storage & I/O — what's actually inside the sandbox

  • Rootfs: minimal Ubuntu-derived Linux; ~200 MB base; COW-overlaid per sandbox.
  • Block device: NBD-backed COW overlay served by the orchestrator's in-process NBD server; backed by local NVMe on the node; uploaded as diffs to GCS/S3 on pause.
  • Memory: memfile per template build; per-sandbox memory diffs on pause.
  • Object storage: GCS (primary GCP), S3 (AWS beta), local-disk fallback. Keyed by buildID. src
  • Network: per-sandbox TAP interface into a host bridge; /30 subnet per sandbox; NAT + iptables egress; physdev module isolates per-tap egress. src

3.5 GPU — the missing managed feature

E2B managed tier is CPU-only for Code Interpreter + Desktop. GPU access is OSS self-host only, via VFIO-PCI passthrough on bare metal:

  • Host kernel owns the GPU; the guest sees the device directly.
  • Requires IOMMU (Intel VT-d / AMD-Vi) in BIOS.
  • Firecracker VFIO device: "vfio": [{"host_dev_path": "/dev/vfio/N"}] in the VM config.
  • Confirmed working with NVIDIA A100 80GB PCIe (PCI 10de:20b5) and H100.
⚠ Caveat (Northflank + Spheron): Firecracker PCIe work was paused in 2025 by AWS upstream. Cloud VMs with nested virtualization add 5–15 ms overhead and break PCIe passthrough. Modal/Replicate remain stronger for managed GPU inference. src src

3.6.2 Seccomp / Landlock / cgroups — what the Firecracker jailer enforces

The Firecracker VMM itself runs in a hardened jailer sandbox. From the Firecracker security subsystems doc:

  • Process isolation: each microVM runs as a separate process, managed by the jailer that enforces strict sandboxing.
  • System call filtering: fine-grained seccomp filters restrict the VMM's interaction with the host kernel.
  • Filesystem access restrictions: Landlock LSM (the Linux kernel's stackable filesystem sandbox).
  • Resource control: cgroups v1/v2 quotas for CPU, memory, PIDs, blkio, devices.

3.6.3 In-VM security — envd token model

Each microVM gets an access token delivered via the Firecracker MMDS (Microvm Metadata Service). The orchestrator mints a short-lived JWT signed by the API, scoped to the team + sandbox, with an aud claim bound to https://api.<domain> so a token for one cluster is not accepted by another.

3.6.4 Network isolation — what egress is allowed

Spheron's reproduction of the E2B-style sandbox network setup (cross-checked with ARCHITECTURE.md):

# Create bridge for sandbox networking
ip link add br0 type bridge
ip link set br0 up
ip addr add 10.100.0.1/16 dev br0

# TAP device per sandbox
ip tuntap add tap0 mode tap
ip link set tap0 master br0
ip link set tap0 up

# Egress NAT
iptables -t nat -A POSTROUTING -o eth0 -j MASQUERADE
iptables -A FORWARD -i br0 -o eth0 -j ACCEPT

# Per-sandbox egress restriction (physdev module — tap0 enslaved to br0)
iptables -I FORWARD -i br0 -m physdev --physdev-in tap0 -o eth0 -j DROP

Sandboxes can be created in "no internet" mode — useful for code-interpreter use cases where the agent doesn't need external API access. The flag is exposed at the SDK level (lifecycle / network config).

3.9 · Cold-start math — why 150ms beats 800ms for agents

The per-second clock makes cold-start latency a direct revenue line item. Here's the math for a single sandbox creation event:

ScenarioCold-startExecution timeTotal billedEffective $/exec
Snapshot resume from local cache30ms5s5.03s × $0.000014 = $0.0000704~$0.00007
Resume from GCS, no NFS300ms5s5.30s × $0.000014 = $0.0000742~$0.000074

At a million sandboxes per month, the difference between a 5× speedup (snapshot resume vs cold boot) is on the order of $100/year — but the difference between billed idle time vs billed execution time is ~$4,200/year per million sandboxes. This is the structural reason E2B's customer-facing narrative focuses on the tool-call latency story, not the per-second rate.

Auto-resume on inbound trafficFull snapshot ONLYAuto-resume restores memory (running process)

3.11 · Snapshot artifact anatomy

Per the ARCHITECTURE.md spec, a template build and a paused-sandbox snapshot have the same artifact shape — a snapshot is just a new build whose memfile/rootfs are stored as diffs against the template it came from.

{buildID}/
├── memfile              # raw memory image (lazy-loaded via UFFD)
├── rootfs.ext4          # filesystem image
├── snapfile             # Firecracker VM state
├── metadata.json        # sandbox ID, template, envd access token hash
└── .header              # index file: walks the diff chain back to base template

Diff chains are resolved through the .header files. If you pause sandbox A (from template T), then pause a child sandbox B (from paused A), B's artifacts are diffs against A's artifacts, and .header walks back to T.

5.2 The Firecracker-vs-WASM trade-off — why E2B didn't go WASM

Firecracker boots in ~125 ms; WASM cold-starts in 1–5 ms — 20–100× faster. E2B chose the slower primitive. Why?

  • Linux ABI compatibility. Sandboxes need real Python/Node/Rust/CUDA/PyTorch/x86 binaries, full glibc, full syscalls. WASM = WASI only (with growing but partial POSIX coverage).
  • GPU + VFIO. Firecracker supports VFIO device passthrough (with the 2025 PCIe-pause caveat). WASM has no real GPU path beyond WebGPU.
  • Existing ecosystem. E2B's customers (Anthropic, Hugging Face, Perplexity, Manus) ship agents that pip install, npm i, and shell out. WASM rewrites the user model.
  • Operational symmetry. A microVM is just a tiny Linux VM — SREs, sysadmins, and security teams already know how to reason about it.

In short: WASM wins on cold-start; Firecracker wins on what fits inside. E2B bet the bottleneck for AI-agent sandboxes is what runs inside, not how fast the box appears. src src

5.3 Bottlenecks & Risks

  • Managed GPU is not E2B's strength. Modal and Replicate dominate the managed-GPU sandbox category; E2B's GPU story is self-host-only on bare metal. src
  • Customer disintermediation risk. Top customers are LLM labs that can vertically integrate. Anthropic is widely reported to run Claude Code artifacts on E2B (landscape profile, secondary source). A single product roadmap decision at any one of them collapses a material revenue slice.
  • Platform fork risk. Vercel Sandbox (2024–2025) and Google Cloud Run Sandboxes (Preview 2026) ship the same primitive on top of Firecracker/gVisor. Hyperscalers can out-compete on price and bundling.
  • The "idle-time tax" on per-second billing: when an interactive AI agent waits 30s for a human response between tool calls, the meter keeps running. 【分析师估算】 15–30% of billed seconds are agent-idle, per Morph's analysis (src). This hurts exactly the use case E2B sells into.
  • "88% of Fortune 100 signups" is a top-of-funnel metric, not ARR. Signup ≠ active deployment.
  • Single-region concentration at launch. US-only initially; EU regions came with Enterprise.

5.4 Strategic Verdict

  • The wedge is real. E2B is the cheapest path to "secure Linux sandbox for AI agent" — three lines of code, AWS-Lambda-grade isolation, snapshot-resume fast enough for tool-call latency. The OSS-first Apache-2.0 play means Anthropic / Hugging Face / Perplexity will keep using it even if a hyperscaler matches the primitive, because the SDK ergonomics and OSS runway are already deep.
  • The ceiling is bounded. E2B sells the plumbing of agent compute. Plumbing is a feature of the cloud, not a layer above it. The defensible moat is templates + SDK ecosystem + idle-time optimization, not the microVM — anyone can run Firecracker.
  • Where the upside lives: Pause/resume efficiency (already strong), BYOC + on-prem enterprise sales (early traction with Rogo, StackAI, Effective AI, Genspark), GPU-on-bare-metal for RL rollouts (Paper Instruments, Replicas), Desktop + computer-use as Anthropic/OpenAI ship more agents. The Series A war chest ($21M) buys ~24 months to convert signups into paid enterprise revenue.

5.5.1 Why Firecracker's PCIe pause matters

AWS paused PCIe passthrough upstream work in 2025. The implication:

  • E2B's managed tier stays CPU-only for code interpreter.
  • GPU workloads on E2B require bare-metal self-host with IOMMU + VFIO-PCI binding.
  • Modal's managed GPU (T4, A10G) has a lead here — but no H100/B200, no self-host, no snapshot-resume.

Spheron and Northflank both note this is the single biggest architectural constraint on Firecracker-based sandbox products in 2026.

5.5.2 What E2B would have to change to challenge Modal at GPU

  1. Bring up managed GPU microVMs on AWS bare-metal or GCP bare-metal.
  2. Add H100 / B200 instance types with MIG slicing.
  3. Refactor the per-second clock into "GPU-active-second" pricing (Modal's model).
  4. Get enterprise customers to commit to GPU volumes (Anthropic, Meta, Mistral all need this internally).

None of these are happening publicly as of mid-2026.
