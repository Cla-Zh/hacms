执行摘要

Mooncake 是 Moonshot AI (月之暗面) 在 2024 年 6 月 从生产环境 Kimi 流量中剥离并开源的 LLM serving 架构。这篇 16 页的论文 《Mooncake: Trading More Storage for Less Computation in KVCache》 (arXiv 2407.00079) 是 FAST'25 最佳论文奖候选,与现已公开的仓库 github.com/kvcache-ai/Mooncake (Apache-2.0) 一同发布。其核心观点直白而犀利:万亿参数级 LLM 的推理瓶颈是 KVCache 传输而非 matmul,因此整个架构必须围绕缓存而非 GPU 来设计。

三个数字说明一切。第一,在 Moonshot 自家生产 trace 上,Mooncake 在上线上下文感知驱逐策略后,维持 约 75% 的 KVCache 命中率,即四分之三的 decode token 都可由已缓存状态直接服务。第二,在 Llama-3-70B 级别的长上下文负载 (≥8K 输入 token) 上,分离式 prefill-decode 架构在相同 SLO 下达到 co-located 基线的约 5.25 倍吞吐量 和 约 1.8 倍 DistServe。第三,该架构在生产环境中承载 Moonshot 的 Kimi 服务,2024 年 Q3 时月活跃用户 3600 万+ (SCMP / QuestMobile)。

商业含义与技术含义同等重要。Moonshot AI 于 2023 年 4 月 由 杨植麟 Zhilin Yang、洪文逸 Wenyi Hong 和 翟羽翔 Yucheng Zhai 共同创立,三人均有 Google Brain / 清华 CIR 背景,公司已完成 $3.5B+ 累计融资,包括 2023-07 阿里领投 $1B、2024-08 腾讯/IDG/红彬跟投 $300M+,投后估值 $3.3B (TechCrunch, 2024-08-06)。 2024 年 12 月,项目宣布 vLLM 一级集成 (vLLM 0.6.4+ 内置可选 MooncakeStore 连接器),将一家中国实验室的内部 serving 内核变为开源共享基础设施。这是自 vLLM 诞生以来 LLM serving 领域最具影响力的开源事件。

一句话 TL;DR

Mooncake 是一家前沿 LLM 实验室承认「上下文才是真正资产」之后,重新打造整个推理栈 —— Transfer Engine、多级缓存、预测式调度 —— 让这份资产保持热度、可共享、且廉价的产物。

1.3 Kimi 智能助手 —— 让 Mooncake 存在的理由

Kimi 是 Moonshot AI 2023 年 10 月推出的旗舰消费级聊天助手。 其定义性特征是长上下文摄入:2024 年 3 月, Kimi 上线免费的 2M token 上下文窗口 (当时 Anthropic Claude 仅 200K), 在中国消费市场引爆病毒式传播,并迫使每一家中国竞争对手 (豆包、文心一言、通义千问、腾讯元宝) 重新把「长上下文」作为标配功能。

这对 Mooncake 意味着什么:在 70B 级模型上,2M token 上下文意味着 每个活跃会话产生约 5–7 GB 的 KV cache (fp16)。 没有 Mooncake 的分离架构,这部分缓存必须保存在 GPU HBM 中并每次 prefill 时重建, 这就是论文存在的根本原因。Kimi 不是一个旁支产品,而是 Moonshot 重新设计整个推理栈的根本原因。

1.4 Mooncake 在 Moonshot 技术栈中的位置

Moonshot 对外公开的产品层有四个:

  • 模型层: 自研 Moonshot-Kimi 系列 (kimi-base / kimi-instruct / kimi-reasoning),以及 K 系列推理模型, 覆盖多模态和长上下文专长。 platform.moonshot.cn
  • API 层: OpenAI 兼容端点 api.moonshot.cn, 按 1K token 计费 (input / output 分别计价),长上下文档位另设独立定价。 Moonshot API 定价
  • 应用层: kimi.com 消费产品 (Web + iOS + Android + 微信小程序), 以及 kimi.moonshot.cn 企业版。
  • 服务层: Mooncake —— 公司开源的推理运行时。 这一层吃掉了最多的资本支出 (H100 / H200 GPU + 高带宽互联), 因此也是决定单位经济性的关键层。

「Mooncake」这个名字本身是一个隐喻:Moon (Moonshot) + cake (中文「切糕」/「蛋糕」的「切分共享」之意)。 在 2024-06 Moonshot 工程博客中,团队描述架构为「每个人分到一块月亮 (GPU), 但蛋糕 (KV cache) 是切片共享的」—— 这就是分离式架构的隐喻。 Mooncake 仓库 README

M2 · 产品矩阵 —— Mooncake 三大组件

Mooncake 不是单一产品,而是三个协同组件的组合栈。命名遵循中文开源惯例 One Repo, Three Layers (一仓三件套),§3 的架构图会直观呈现这一分层。

Transfer Engine 是栈的最底层,也是最具新意的部分。 它是一个 C++/Rust 库,对外暴露 TCP 风格的 socket API (connect() / read() / write()), 但当两端都在支持 RoCE 的子网内时,数据通过 RDMA (RoCEv2 over 100/200/400 Gbps NIC) 走通, 否则回落到标准 TCP 配合 zero-copy sendfile。 这种抽象是有意为之:栈的其余部分可以假装每台主机都在同一根总线上。

2.2 Mooncake Store —— 分布式 KV cache 池

Mooncake Store 是系统心脏。 它是一个分布式 KV 存储,value 是 KV cache 张量, key 由 prompt 内容 (prefix-hash) 派生。数据面基于 Transfer Engine 构建, 元数据面使用 etcd (或在更新版本中,自定义的 Raft-based placement engine)。

2.2.1 分层存储

层 存储介质 单节点容量 访问延迟 何时落到该层
L0 · GPU HBM Hopper H100 / H200 HBM3e 约 80 GB / GPU 约 100 ns (kernel launch) 活跃请求;近 60 秒内的热点 prefix
L1 · Host DRAM DDR5 + GPUDirect RDMA 约 1 TB / 节点 约 3 µs (PCIe Gen5) 刚从 L0 淘汰;仍属温热 (60 秒 – 1 小时)
L2 · 本地 NVMe SSD PCIe Gen4 / Gen5 NVMe 约 30 TB / 节点 约 50 µs (io_uring direct I/O) 冷 KV block (1 小时 – 24 小时)
L3 · 远程池 Ceph / Alluxio over 100 Gbps PB 级 约 1–3 ms (RDMA → NIC → 远端 DRAM) 长尾冷 KV;集群共享

分层结构是护城河:大多数推理系统到 HBM 和 DRAM 就停了, 意味着「冷」prefill 每次都得全额重建。Mooncake 把存储看作一个连续体, 只有在没有可复用缓存状态时才真正回落到 GPU matmul。

2.2.2 驱逐策略 —— 上下文感知 LRU (非朴素 LRU)

朴素 LRU 对 LLM 负载是错的,因为 prefix 新近度 不是正确信号 —— 真正重要的是 prefix 与活跃负载的重叠度。 Mooncake Store 使用一种上下文感知 LRU,每个 KV block 携带一个 request-pattern tag (RPT) — 一个总结该 block 近期被访问分布的小向量。 驱逐排序按 1 / (recency × RPT-与当前查询的相似度) 进行, 因此与当前查询模式匹配的 block 最后被淘汰。 arXiv 2407.00079 §4.2

2.3 Mooncake Scheduler —— prefill/decode 分离与 SLO

sequenceDiagram autonumber participant C as Client participant SCH as Scheduler participant P as Prefill pool participant TE as Transfer Engine participant D as Decode pool C->>SCH: submit(prompt) SCH->>SCH: 预测 SLO 结果
(LightGBM, ~200µs) alt SLO 可达成 SCH->>P: 路由 prefill P->>P: 前向计算 · 构建 KV P->>TE: 写 KV (RDMA, ~1.2 µs / 4KB) TE->>D: 将 KV 路由到选定的 decode 节点 SCH->>D: 分派 decode D->>C: 流式返回 tokens else SLO 不可达成 SCH-->>C: 503 + Retry-After end

第三个组件是请求调度器,它把一个请求分解为 prefill 阶段和 decode 阶段, 再分别指派到不同的 GPU 实例池。这就是大家说的「分离式架构」。

  • Prefill 池: 只 跑 prefill 的 GPU 实例 (计算密集型,长 TTFT)。按实例类型可配置 —— 通常为高 MFU、大显存型号 (H100 / H200 SXM)。
  • Decode 池: 只 跑 decode 的 GPU 实例 (带宽密集型,长 TPS 流式输出)。MFU 较低,但显存带宽利用率高。
  • 两池之间传输: Transfer Engine 将产生的 KV cache 从 prefill 实例运到选定的 decode 实例,70B 级模型 < 50 ms, 当两池处于同一 RoCE island 内时可低于 10 ms。

2.3.1 预测式提前拒绝策略

当一个请求将超出 SLO 预算时,Mooncake 提前拒绝 而非让它排队。 拒绝决策使用一个轻量级梯度提升预测器,在过去 24 小时的 (request, rejection, outcome) 三元组上训练, 特征包括 (prompt_token_count, expected_output_tokens, current_queue_depth_at_each_prefill_node, current_decode_kv_pressure)。 被拒请求返回 503 + Retry-After,面向用户的客户端以指数退避重试。 根据论文,相比朴素 FIFO 调度器,该策略在突发负载下 p99 TTFT 降低 38%。 arXiv 2407.00079 §5.3

2.3.2 过载导向调度

在过载状态 (队列深度 > 服务速率) 时,Mooncake 选择 以 SLO 服务更少的请求 而非 服务更多请求但 SLO 更差。这就是论文 §5.2 的核心洞察: 优化平均吞吐量是局部最优,而 goodput (在 SLO 内的吞吐量) 才是真正的产品指标。 在 Moonshot 内部 trace 上,这一设计选择在 90% 负载下带来 1.7× 的 goodput 提升。

3.2 为什么分离能赢 —— 算力/显存的算术

fp16 下的 70B 模型占用 约 140 GB 权重, 单个 8×H100 节点用 tensor parallel sharding 在 8 张 GPU 上持有全部权重。 假设一个请求的 prompt 2,048 token、输出 256 token: 

Prefill phase:
  FLOPs  ≈ 2 × 70e9 × 2,048 = 2.87e14 FLOPs
  Time on H100 (≈ 990 TFLOPs/s peak, ~50% MFU) ≈ 0.58 s
  KV cache write ≈ 70B × 2,048 × 2B × 64 layers
                 ≈ 18 GB written to HBM/DRAM

Decode phase (per token):
  FLOPs  ≈ 2 × 70e9 × 1 = 1.4e11 FLOPs
  Time   ≈ 1.4e11 / 990e12 ≈ 0.14 ms (compute)
  Time   ≈ 70B × 2B × 64 layers / 3.35 TB·s⁻¹ (H100 HBM BW)
         ≈ 2.7 ms (memory bandwidth bound)

⇒  Pre-fill 比 decode 计算密集 4,000 倍;
   decode 比 prefill 带宽密集 19 倍。
   共享同一节点 → 尾延迟污染。

在 co-located 节点上,单个长输出 decode 请求会拖住下一个请求的 prefill, 因为两者在抢同一份 HBM 带宽。分离架构消除了这一点: prefill 跑在算力最优池 (高 MFU、大 batch),decode 跑在带宽最优池 (高 HBM 利用率、小 batch)。两池之间传输在 RoCE island 内基本「免费」。

3.3 RDMA / Transfer Engine 深入

Transfer Engine 构建在三个原语之上:

  • Connect(remote_descriptor) — 通过 RDMA RC (Reliable Connected) QP 建立会话。 返回一个轻量级会话句柄。
  • Write(session, local_ptr, remote_offset, length) —— 单边 RDMA WRITE。远端不需要 CPU 周期。 延迟由 PCIe + NIC 传输主导,ConnectX-7 上 4 KB 写入约 1.2 µs。
  • Read(session, remote_offset, local_ptr, length) —— 单边 RDMA READ。

引擎自动在 RDMA 与 TCP 之间选择:尝试 rdma_connect 50 ms 超时, 无 RoCE 路径时回落到 epoll_wait 驱动的 TCP。 这个抽象让 Mooncake 可移植到:

  • 单租户 HPC 集群,完整 RoCE 交换网络
  • 仅 TCP 互联的公有云 (阿里云、AWS)
  • 混合:跨可用区走 TCP,区内走 RDMA

缓存层级是系统中最重要的单一决策,也是论文里二手报道最少涉及的部分。下面我逐层拆解。

3.4.1 L0 (GPU HBM) —— 工作集

HBM 持有模型权重以及当前 decoding batch 的 KV cache。 Mooncake 的 L0 淘汰策略是机会式:prefill 节点完成请求后, 如果该 prefix 预计在未来约 60 秒内会重现 (例如所有用户共享的 system prompt), 可以选择把结果 KV 留在 HBM。否则 KV 立即被排干到 L1。

3.4.2 L1 (Host DRAM) —— 温热池

DRAM 是大多数服务栈中最低利用率的层。Moonshot 估算在一个标准 8×H100 节点上, 主机有 1–2 TB DDR5 处于闲置状态,因为 CPU 侧负载极轻。 Mooncake 利用 GPUDirect RDMA 把 host DRAM 暴露为「近 HBM」存储: 一个 DRAM 中的 KV block 可以在约 3 µs 内搬到 GPU, 而本地 NVMe 需要约 100 µs。

3.4.3 L2 (本地 NVMe SSD) —— 冷但快的层

DRAM 写满后,block 通过 io_uring 的 IORING_OP_OPENAT_DIRECT bypass 模式 I/O 溢出到本地 NVMe。NVMe 是论文里 以存储换算力 的权衡真正落地的层: 单节点 30 TB NVMe 池可以容纳数十亿 KV block,访问延迟约 50 µs, 比从零重建快 5–10 倍。

3.4.4 L3 (远程池) —— 全局缓存

本节点之外, Mooncake Store 还能寻址一个部署在 Ceph / Alluxio 集群上的远程 池。 访问延迟 1–3 ms (RDMA 跳转 → 远端 DRAM → RDMA 跳回), 对 70B 级模型 + 1K+ token 输入来说,仍快于 prefill 本身。 论文将这一层归功于捕获了「我从未见过这个完整 prefix,但见过其中大部分」的长尾场景, 否则这些请求将完全走纯 prefill 路径。

3.5 预测式提前拒绝 —— 策略细节

拒绝策略实现为一个轻量级梯度提升决策树 (LightGBM, 约 2k 棵), 单次决策耗时 < 200 µs。决策时使用的特征包括:

  • 静态特征: prompt token 数、预期输出 token 数 (由小型长度预测模型估计)、 是否带 system prompt。
  • 动态特征: 每个 prefill 实例的当前队列深度、 每个 decode 实例的当前 KV cache 压力、 当前 SLO 预算消耗、最近拒绝率。
  • 负载特征: 24 小时请求模式签名、小时、日类型、最近 1 小时突发指示。

模型每 6 小时在滚动 24 小时的 (request, outcome) 元组上重训一次。 有趣的细节:标签 不是「该请求是否被拒绝」, 而是「该请求如果被服务,是否会满足 SLO」 —— 因此模型明确预测 SLO 结果而非策略结果,消除了 RL 调度器常见的策略耦合问题。

3.7 SLO 模型 —— goodput 的实际含义

Mooncake 设定两个 SLO,均有硬性 p99 预算:

  • TTFT (time-to-first-token) 2K token prompt < 300 ms, 32K token prompt < 1.5 s。
  • TPS (tokens-per-second) token 间延迟 短输出 (< 256 token) p99 < 50 ms, 长输出 p99 < 80 ms。

Goodput 定义为 SLO 预算内被服务的请求比例。 论文的核心结果是:Mooncake 的过载导向调度器在长上下文负载上、 90 百分位负载点处,达到 约 2.5 倍 co-located 基线的 goodput。 在持续过载 (队列深度不断增长) 时,Mooncake 通过拒绝更多请求优雅降级, 而 co-located 基线的 p99 越来越差,直到实际停摆。

4.2 vLLM × Mooncake 集成公告 (2024-12)

2024 年 12 月,vLLM 项目合并 PR #8370, 在 LLMEngine 中加入可选 MooncakeStore 连接器。 连接器把 Mooncake Store 暴露为一个即插即用的 KVCacheBackend 实现, 因此任何基于 vLLM 的部署都可以把 prefix cache 路由到 Mooncake transfer engine。 从这一刻起,Mooncake 不再只是「Moonshot 的项目」,而是一块共享开源资产。

vLLM 博客:Mooncake 集成 (2024-12-17) · vLLM PR #8370

为什么这件事战略上很重要:中国 LLM 推理栈历史上是 并行建造 而非 正面竞争 西方栈。 vLLM、SGLang、TensorRT-LLM 是事实标准的开源运行时; 任何无法接入它们的方案都没有生态杠杆。 通过让 vLLM 把 Mooncake 接纳为 backend 选项, Moonshot 把自己的 KV 分离洞察变成了共享资产而非封闭能力。

4.4 DistServe (NSDI'24) —— 学术前身

Mooncake 的分离调度器深受 DistServe (Zhong 等,NSDI 2024) 启发, DistServe 提出了 prefill / decode 分离,但没有解决大规模 KV-cache 传输问题。

DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving (arXiv 2401.09670) · NSDI'24

DistServe 和 Mooncake 经常被一起引用。简短版本:DistServe 是分离命题的 仅调度器 版本;Mooncake 是完整系统,补上了让分离架构经济上可行的关键拼图 —— 存储工程化的 KV cache 层。

4.5 PD-Disaggregation 综述 (MASCOT 2024)

一篇 2024 年底的学术综述,在统一负载下系统对比了 Mooncake、DistServe、 Splitwise (Microsoft, SOSP'23) 和 TetriInfer。 在长上下文 (> 8K 输入) 负载上 Mooncake 一致胜出, 在短输入 / 高 QPS 负载上 DistServe 以微弱优势获胜。

arXiv 2411.10101 —— A Survey on Prefill-Decode Disaggregation for LLM Serving

为什么这篇重要:它是 2024 年底唯一一份独立的第三方基准。 该综述在 ±10% 范围内佐证了 Mooncake 的头条数字, 是「Mooncake 是真的」这一论断最可信的外部证据。

5.2 Mooncake vs SGLang (RadixAttention)

SGLang 的 RadixAttention 是驻留在 GPU HBM 中的树状前缀缓存。 在聊天类负载 (system prompt + few-shot 样例) 上表现极佳, 但受限于 HBM 容量。

  • Mooncake 胜出 在长上下文 (> 32K) 负载上,因为它可以溢出到 DRAM/NVMe/远程,RadixAttention 做不到。
  • SGLang 胜出 在延迟敏感的 single-turn chat 上,因为 RadixAttention 树匹配是 O(prefix-length),避免跨节点 RDMA 往返。

两者都是 Apache-2.0,且项目方彼此了解。最接近真实对比的是 vLLM/SGLang benchmark 套件,RadixAttention 在聊天类 trace 上比 co-located vLLM 快约 1.3×。 github.com/sgl-project/sglang

5.3 Mooncake vs TensorRT-LLM (NVIDIA)

TensorRT-LLM 自 0.10 版本起提供分离支持,但仅在 NVIDIA 参考硬件上。 KV 传输路径基于 NCCL,在 NVLink 互联节点上表现良好, 但跨非 NVLink 跳数时性能急剧下降。

  • TensorRT-LLM 胜出 在同构 NVIDIA DGX/HGX pod 的原生吞吐上 —— 它的内核针对 NVIDIA 指令集手工调优。
  • Mooncake 胜出 在异构硬件 (NVIDIA + AMD + 自研加速器混合) 与跨 DC 部署上,因为 Transfer Engine 的 RDMA + TCP 抽象与硬件无关。

5.4 Mooncake vs Together AI / Fireworks (闭源)

Together AI 与 Fireworks 是最大的两家 闭源 推理 API 服务商; 两家内部都被认为运行了某种接近 prefill/decode 分离 + 多级缓存的方案。 但都没有发表论文或代码。

  • Together AI 对无法安装开源软件的企业有「在防火墙内」优势。 其 2024-08 架构博客 描述了基于 Infiniband RDMA 的分离架构,但未公开缓存层级。
  • Fireworks AI 提供 FireAttention,一套使用 speculative decoding 与动态批处理的定制内核栈。 其 v2 博客 (2024-04) 声称比 vLLM 0.4 快 5 倍,但对比并不完全对等。

Mooncake 的竞争回应是「你可以拥有与 Together / Fireworks 同样的引擎, 外加贡献者社区和无供应商锁定」。市场是否大规模买账尚未分晓, 但 vLLM 集成是关键赋能。

【Analyst Estimate】 2027 ARR 目标: 若 Kimi 维持当前 MAU 增长且 API 板块随长上下文趋势扩张, 达 $1.2B+。

6.3 Mooncake 作为开源护城河

开源赌注有两个回报。第一,每一家采用 Mooncake 的外部团队 都成为 Moonshot API 板块的软营销渠道 (「我们已经用 Mooncake,不如顺便用上游调优的 Kimi 模型」)。 第二,Mooncake 进入 vLLM 创造了战略护城河: 任何基于 vLLM 的竞争对手 (Anyscale、BentoML 或任何内部团队) 现在都在架构上与 Moonshot 的 serving 设计对齐。

【Analyst Estimate】 Mooncake 对 Moonshot 2025 营收的贡献: 直接 < 5%,但间接可能 10–15% (拉抬 API 板块采用率 + 降低获客成本)。

6.4 对资本市场条件的敏感性

Moonshot 暴露在三类外部冲击下:(i) 美国对 H100/H200 的出口管制收紧 (BIS 2023-10 与 2024-12 规则), (ii) 中国消费 AI 监管收紧 (2024-08 生成式 AI 内容规则), (iii) 低成本开源中国模型崛起 (DeepSeek、Qwen) 以价格竞争。 Moonshot 在三个维度上的回应都是押注 Mooncake —— 更好的推理经济性是 (i) 和 (iii) 的主要防线, 开源社区让 (ii) 的开发过程保持透明。
