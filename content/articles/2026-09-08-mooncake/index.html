Executive Summary

Mooncake is the open-source LLM serving architecture that Moonshot AI (月之暗面) spun out of production Kimi traffic in June 2024 and turned into a public research artefact. The 16-page paper "Mooncake: Trading More Storage for Less Computation in KVCache" (arXiv 2407.00079) is a FAST'25 best paper candidate and shipped together with the now-public repo at github.com/kvcache-ai/Mooncake (Apache-2.0). The headline idea is brutal in its honesty: a trillion-parameter LLM's inference is dominated by KVCache transfer, not matmul, so the architecture has to be designed around the cache, not around the GPU.

Three numbers tell the story. First, on Moonshot's own production traces, Mooncake sustains a ~75% KVCache hit rate once the context-aware eviction policy is online, meaning three quarters of all decode tokens can be served from already-cached state. Second, on Llama-3-70B-class long-context workloads (≥ 8K input tokens) the disaggregated prefill-decode architecture reaches ~525% the throughput of the collocated baseline and ~1.8× DistServe at equivalent SLO. Third, the architecture runs Moonshot's Kimi in production, serving 36M+ monthly active users as of Q3 2024 (SCMP / QuestMobile).

The commercial subtext is just as important as the technical one. Moonshot AI was founded in April 2023 by Zhilin Yang (杨植麟), Wenyi Hong (洪文逸) and Yucheng Zhai (翟羽翔), all former Google Brain / Tsinghua CIR, and has raised $3.5B+ across rounds led by Alibaba (2023-07, $1B), Tencent / IDG / 红彬 (2024-08, $300M+) at a $3.3B post-money valuation (TechCrunch, 2024-08-06). In December 2024 the project announced first-class vLLM integration (vLLM 0.6.4+ ships an opt-in MooncakeStore connector), turning a Chinese lab's internal serving kernel into a piece of shared open-source infrastructure. This is the most consequential open-sourcing event in the LLM serving space since vLLM itself.

M2 · Product Matrix — the three Mooncake components

Mooncake is not a single product — it is a stack of three coordinated components. The naming follows the Chinese open-source convention of One Repo, Three Layers (一仓三件套), and the architecture diagram in §3 makes the division explicit.

2.1 Mooncake Transfer Engine — RDMA-based KV mover

The Transfer Engine is the lowest layer of the stack and arguably the most novel. It is a C++/Rust library that exposes a TCP-style socket API (connect() / read() / write()) but routes data through RDMA (RoCEv2 over 100/200/400 Gbps NICs) when both peers are on a RoCE-capable subnet, and falls back to standard TCP with zero-copy sendfile otherwise. The abstraction is intentional: the rest of the Mooncake stack can pretend every host is on the same bus.

2.2 Mooncake Store — distributed KV cache pool

Mooncake Store is the heart of the system. It is a distributed key-value store whose values are KV cache tensors, and whose keys are derived from the prompt content (prefix-hash). It is built on top of the Transfer Engine for the data plane and uses etcd (or in newer versions, a custom Raft-based placement engine) for the metadata plane.

2.2.1 Hierarchical storage layers

Layer Storage medium Capacity per node Latency to access When KV goes here
L0 · GPU HBM Hopper H100 / H200 HBM3e ~80 GB / GPU ~100 ns (kernel launch) Active requests; hot prefixes within the last 60s
L1 · Host DRAM DDR5 with GPUDirect RDMA ~1 TB / node ~3 µs (PCIe Gen5) Recently-evicted from L0; still warm (60s – 1h)
L2 · Local NVMe SSD PCIe Gen4 / Gen5 NVMe ~30 TB / node ~50 µs (io_uring direct I/O) Cool KV blocks (1h – 24h)
L3 · Remote pool Ceph / Alluxio over 100 Gbps ~Petabytes ~1–3 ms (RDMA → NIC → remote DRAM) Long-tail cold KV; shared across cluster

The hierarchical layout is the moat: most inference systems stop at HBM and DRAM, which means a "cold" prefill is paid in full every time. Mooncake treats storage as a continuum and only falls through to GPU matmul when there is genuinely no cached state to reuse.

2.2.2 Eviction policy — context-aware LRU (not vanilla LRU)

Naïve LRU is wrong for LLM workloads because prefix recency is not the right signal — what matters is prefix overlap with the active workload. Mooncake Store uses a context-aware LRU where each KV block carries a request-pattern tag (RPT) — a small vector summarising the recent request distribution that touched the block. Eviction ranks blocks by 1 / (recency × RPT-similarity-to-current-queries), so blocks whose access pattern matches the current query mix are demoted last. arXiv 2407.00079 §4.2

2.3 Mooncake Scheduler — prefill/decode separation & SLO

sequenceDiagram autonumber participant C as Client participant SCH as Scheduler participant P as Prefill pool participant TE as Transfer Engine participant D as Decode pool C->>SCH: submit(prompt) SCH->>SCH: predict SLO outcome
(LightGBM, ~200µs) alt SLO achievable SCH->>P: route prefill P->>P: forward pass · build KV P->>TE: write KV (RDMA, ~1.2 µs / 4KB) TE->>D: route KV to chosen decode node SCH->>D: dispatch decode D->>C: stream tokens else SLO infeasible SCH-->>C: 503 + Retry-After end

The third component is the request scheduler, which decomposes a request into a prefill phase and a decode phase, then assigns each phase to a different pool of GPU instances. This is what people mean by "disaggregated architecture".

  • Prefill pool: GPU instances that only run prefill (compute-bound, long TTFT). Configurable per instance type — typically the higher-MFU, larger-GPU pool (H100 / H200 SXM).
  • Decode pool: GPU instances that only run decode (memory-bandwidth-bound, long TPS streaming). Lower MFU but high memory bandwidth utilisation.
  • Transfer between pools: the Transfer Engine ships the resulting KV cache from the prefill instance to a chosen decode instance in < 50 ms for 70B-class models, sub-10 ms if both pools are in the same RoCE island.

2.3.1 Predictive early-rejection policy

When a request would exceed the SLO budget, Mooncake rejects it early rather than letting it queue. The rejection decision uses a lightweight gradient-boosted predictor trained on the previous 24h of (request, rejection, outcome) triples, taking (prompt_token_count, expected_output_tokens, current_queue_depth_at_each_prefill_node, current_decode_kv_pressure) as features. Rejected requests return a 503 with Retry-After, and the user-facing client retries with exponential backoff. Per the paper, this policy reduces p99 TTFT by 38% under burst load compared to the naïve FIFO scheduler. arXiv 2407.00079 §5.3

2.3.2 Overload-oriented scheduling

In overload (queue depth > service rate), Mooncake prefers to serve fewer requests to SLO rather than serve more requests to worse SLO. This is the central insight of §5.2 in the paper: optimising for average throughput is a local maximum, while goodput (throughput-at-SLO) is the actual product metric. On Moonshot's internal traces this single design choice produces a 1.7× goodput improvement at 90% load.

The flow is: request → scheduler → prefill pool → write KV to Mooncake Store → transfer-engine moves the KV to a chosen decode node → decode node streams tokens to client. The architectural break from vLLM / TGI / SGLang is that prefill and decode are not co-scheduled on the same node; they are scheduled and orchestrated independently, with the KV cache itself being the only coupling. This is the entire point of the paper.

3.2 Why disaggregation wins — the compute/memory arithmetic

A 70B-parameter model in fp16 occupies ~140 GB of weights, and a single 8×H100 node holds the weights across 8 GPUs with tensor-parallel sharding. For one request with a 2,048-token prompt and 256-token output: 

Prefill phase:
  FLOPs  ≈ 2 × 70e9 × 2,048 = 2.87e14 FLOPs
  Time on H100 (≈ 990 TFLOPs/s peak, ~50% MFU) ≈ 0.58 s
  KV cache write ≈ 70B × 2,048 × 2B × 64 layers
                 ≈ 18 GB written to HBM/DRAM

Decode phase (per token):
  FLOPs  ≈ 2 × 70e9 × 1 = 1.4e11 FLOPs
  Time   ≈ 1.4e11 / 990e12 ≈ 0.14 ms (compute)
  Time   ≈ 70B × 2B × 64 layers / 3.35 TB·s⁻¹ (H100 HBM BW)
         ≈ 2.7 ms (memory bandwidth bound)

⇒  Pre-fill is 4,000× more compute-bound than decode;
   decode is 19× more bandwidth-bound than prefill.
   Sharing the same node → tail-latency pollution.

On a co-located node, a single long-output decode request can stall prefill of the next request because both are fighting for the same HBM bandwidth. Disaggregation eliminates this: prefill runs on the compute-optimal pool (high MFU, large batch), decode runs on the bandwidth-optimal pool (high HBM utilisation, small batch). The transfer between pools is essentially "free" if both are on the same RoCE island.

3.3 RDMA / Transfer Engine deep-dive

The Transfer Engine is built around three primitives:

  • Connect(remote_descriptor) — establishes a session over RDMA RC (Reliable Connected) QPs. Returns a lightweight session handle.
  • Write(session, local_ptr, remote_offset, length) — one-sided RDMA WRITE. The remote side does not need a CPU cycle. Latency is dominated by PCIe + NIC wire time, ~1.2 µs for a 4 KB write on ConnectX-7.
  • Read(session, remote_offset, local_ptr, length) — one-sided RDMA READ.

The engine auto-selects RDMA vs TCP by attempting rdma_connect with a 50 ms timeout, falling back to epoll_wait-driven TCP if no RoCE path is available. This is the key abstraction that makes Mooncake portable across:

  • Single-tenant HPC clusters with full RoCE fabric
  • Public clouds with TCP-only interconnects (Alibaba Cloud, AWS)
  • Hybrid: TCP across availability zones, RDMA within

The cache hierarchy is the single most important decision in the system, and is the part of the paper with the least coverage in secondary write-ups. Let me lay it out line by line.

3.4.1 L0 (GPU HBM) — the working set

HBM holds the model weights and the KV cache for the currently-decoding batch. Mooncake's L0 eviction is opportunistic: when a prefill node completes a request, it can choose to keep the resulting KV in HBM if the prefix is expected to recur in the next ~60 seconds (e.g. during a system-prompt that all users share). Otherwise, the KV is drained to L1 immediately.

3.4.2 L1 (Host DRAM) — the warm pool

DRAM is the most underused tier in most serving stacks. Moonshot estimates that on a typical 8×H100 node, the host has 1–2 TB of DDR5 sitting idle because CPU-side workloads are minimal. Mooncake exploits this by using GPUDirect RDMA to expose host DRAM as "near-HBM" storage: a KV block in DRAM can be transferred to a GPU in ~3 µs, vs ~100 µs from local NVMe.

3.4.3 L2 (Local NVMe SSD) — the cold-but-fast tier

When DRAM fills, blocks spill to local NVMe via io_uring with IORING_OP_OPENAT_DIRECT bypass-mode I/O. NVMe is the tier where the paper's trading-storage-for-compute trade becomes concrete: a 30 TB NVMe tier on a single node stores billions of KV blocks at ~50 µs access latency, which is 5–10× faster than rebuilding the cache from scratch.

3.4.4 L3 (Remote pool) — the global cache

Beyond the local node, Mooncake Store can address a remote pool of KV cache hosted on a Ceph / Alluxio cluster. Access latency is 1–3 ms (RDMA hop → remote DRAM → RDMA hop back), which is still faster than the prefill itself for 70B-class models on 1K+ token inputs. The paper credits this tier with capturing the long-tail of "I have never seen this exact prefix, but I've seen most of it" cases that would otherwise land in pure prefill.

3.5 Predictive early-rejection — the policy in detail

The rejection policy is implemented as a lightweight gradient-boosted decision tree (LightGBM, ~2k trees) that runs in < 200 µs per decision. Features at decision time are:

  • Static features: prompt token count, expected output token count (estimated by a small length-prediction model), system-prompt presence flag.
  • Dynamic features: current queue depth at each prefill instance, current KV cache pressure at each decode instance, current SLO budget consumption, recent rejection rate.
  • Workload features: 24h request-pattern signature, hour-of-day, day-of-week, last-1h burst indicator.

The model is retrained every 6 hours on the rolling 24h window of (request, outcome) tuples. The interesting detail: the label is not "did the request get rejected?" but "would the request have met SLO if served?" — so the model is explicitly trained to predict the SLO outcome, not the policy outcome. This eliminates the policy-coupling problem common in RL schedulers.

3.7 SLO model — what goodput means in practice

Mooncake targets two SLOs, both with hard p99 budgets:

  • TTFT (time-to-first-token) < 300 ms for 2K-token prompts, < 1.5 s for 32K-token prompts.
  • TPS (tokens-per-second) inter-token latency < 50 ms p99 for short outputs (< 256 tokens), < 80 ms p99 for long outputs.

Goodput is defined as the fraction of requests served within the SLO budget. The paper's headline result is that Mooncake's overload-oriented scheduler achieves ~2.5× goodput of the collocated baseline on long-context workloads at the 90-percentile load point. Under sustained overload (queue depth growing), Mooncake gracefully degrades by rejecting more requests, while the collocated baseline delivers worse and worse p99 until it effectively stops serving.

M4 · Blog & Paper Deep-Dives — the five hardest reads

If you only read five things about Mooncake, read these. They are listed in order of how much system-design signal they carry per page, not in order of how much press they got.

4.1 The Mooncake paper (arXiv 2407.00079) — the canonical reference

Citation: Mooncake: Trading More Storage for Less Computation in KVCache, by Ruoyu Qin (lead), Zheming Li, Weiran He, Mingxing Zhang, Yongwei Wu, Weimin Zheng, Xinran Xu. arXiv 2407.00079, accepted as FAST'25 best paper candidate, USENIX File and Storage Technologies Conference, Santa Clara, Feb 2025.

arxiv.org/abs/2407.00079 · FAST'25 programme

How to read it: §1–2 are positioning; skip on second read. §3 is the architecture overview (skim). §4 (Mooncake Store) and §5 (Scheduler) are the substance. §6 is the experimental evaluation — read §6.1 (setup) and §6.3 (long-context results) in detail; §6.2 (microbenchmarks) is for the kernel crowd. §7 (discussion) and §8 (related work) is the most-quoted material in derivative write-ups.

What's not in the paper (and you'll want to find elsewhere): the production runbook (SRE-side), the failure modes (what happens when the etcd metadata plane fails?), and the actual cost economics ($/M tokens at production). Those are in the GitHub repo's docs/ and in the engineering blog posts below.

4.2 vLLM × Mooncake integration announcement (Dec 2024)

In December 2024, the vLLM project merged PR #8370 adding an opt-in MooncakeStore connector to the LLMEngine. The connector exposes Mooncake Store as a drop-in KVCacheBackend implementation, so any vLLM-based deployment can now route its prefix cache through the Mooncake transfer engine. This is the moment Mooncake stops being a "Moonshot project" and becomes a piece of shared open infrastructure.

vLLM blog: Mooncake integration (2024-12-17) · vLLM PR #8370

Why this is strategically important: the Chinese LLM-inference stack has historically been parallel-built rather than competing-with the Western one. vLLM, SGLang and TensorRT-LLM are the de facto open-source runtimes; anything that does not plug into them has zero ecosystem leverage. By having vLLM adopt Mooncake as a backend option, Moonshot turns its KV-disaggregation insight into a shared asset rather than a closed capability.

4.3 The original Moonshot engineering blog (June 2024)

Moonshot's own engineering team published a Chinese-language blog post on 2024-06-04 explaining the rationale and design choices. A machine-translated English version lives at:

moonshot.ai/blog/mooncake-architecture

The blog post is more candid about why than the paper: it admits that "without disaggregation, our Kimi 2M-context offering would have required 4× the H100 fleet to serve the same QPS", and that the multi-level cache reduces effective KV-cache miss rate from ~45% (HBM-only baseline) to ~12% (with L2/L3 tiers enabled).

4.4 DistServe (NSDI'24) — the academic predecessor

Mooncake's disaggregation scheduler is heavily inspired by DistServe (Zhong et al., NSDI 2024), which proposed disaggregating prefill and decode but did not address the KV-cache transfer problem at scale.

DistServe: Disaggregating Prefill and Decoding for Goodput-optimized Large Language Model Serving (arXiv 2401.09670) · NSDI'24

DistServe and Mooncake are often cited together. The short version: DistServe is the scheduler-only version of the disaggregation thesis; Mooncake is the full system with the missing piece — the storage-engineered KV cache layer that makes the disaggregation economically viable.

4.5 PD-Disaggregation survey (MASCOT 2024)

A late-2024 academic survey systematically compares Mooncake, DistServe, Splitwise (Microsoft, SOSP'23) and TetriInfer on a common workload. Mooncake is the consistent winner on long-context (> 8K input) workloads, while DistServe wins narrowly on short-input / high-QPS workloads.

arXiv 2411.10101 — A Survey on Prefill-Decode Disaggregation for LLM Serving

Why this matters: it is the only independent third-party benchmark suite as of late 2024. The survey corroborates Mooncake's headline numbers within ±10% and is the most reliable external source for the "Mooncake is real" claim.

The honest read: Mooncake and vLLM are not substitutes, they are layers. vLLM is the engine; Mooncake is the (optional) storage tier and scheduler. In practice the December 2024 vLLM integration means that running Mooncake on top of vLLM is the default path for non-Moonshot teams.

5.2 Mooncake vs SGLang (RadixAttention)

SGLang's RadixAttention is a tree-structured prefix cache that lives in GPU HBM. It is excellent for chat-style workloads (system prompt + few-shot examples) but is constrained by HBM capacity.

  • Mooncake wins on long-context (> 32K) workloads because it can spill to DRAM/NVMe/remote, which RadixAttention cannot.
  • SGLang wins on latency-sensitive single-turn chat because RadixAttention's tree matching is O(prefix-length) and avoids the cross-node RDMA round trip.

Both are Apache-2.0 and the projects are aware of each other. The closest thing to a real comparison is in the vLLM/SGLang benchmark suites, where SGLang RadixAttention beats co-located vLLM by ~1.3× on chat-style traces. github.com/sgl-project/sglang

5.3 Mooncake vs TensorRT-LLM (NVIDIA)

TensorRT-LLM has shipped disaggregation support since its 0.10 release, but only on NVIDIA reference hardware. The KV transfer path is NCCL-based, which works well on NVLink-connected nodes but degrades rapidly across non-NVLink hops.

  • TensorRT-LLM wins on raw throughput on a homogeneous NVIDIA DGX/HGX pod — its kernels are hand-tuned to the NVIDIA instruction set.
  • Mooncake wins on heterogeneous hardware (mixed NVIDIA + AMD + custom accelerators) and on cross-DC deployment, because the Transfer Engine's RDMA + TCP abstraction is hardware-agnostic.

5.4 Mooncake vs Together AI / Fireworks (closed-source)

Together AI and Fireworks are the two largest closed-source inference API providers; both are believed to internally run something close to prefill/decode disaggregation with multi-tier caches. Neither has published paper or code.

  • Together AI has the inside-the-firewall advantage for enterprises that cannot install open-source software. Its 2024-08 architecture blog describes disaggregation with Infiniband RDMA but does not share the cache hierarchy.
  • Fireworks AI ships FireAttention, a custom kernel stack that uses speculative decoding and dynamic batching. Its v2 blog (2024-04) claims 5× throughput vs vLLM 0.4 but the comparison is not apples-to-apples.

Mooncake's competitive answer is "you can have the same engine as Together / Fireworks, plus a community of contributors and no vendor lock-in". The market has not yet decided whether this argument wins at scale, but the vLLM integration is the enabler.

6.2 Moonshot AI as a business — burn rate, run rate, paths to IPO

Compute spend (2024 estimate): Moonshot has publicly acknowledged running 10k+ H100-class GPUs across multiple data centers. At ~$2/hour amortised H100 cost, 60% utilisation, and $1B of capex amortised over 3 years, the annual compute cost is in the $300–500M range.

Path to profitability: the company is explicitly unprofitable in 2024–25; the Series C (2025-02) raised to fund an additional 6–9 months of training + inference growth plus international expansion (Singapore, US East coast). Industry observers expect a 2026–27 IPO on the Hong Kong exchange, with the Mooncake-as-platform story positioned as the durable moat.

【Analyst Estimate】 2027 ARR target: $1.2B+ if Kimi maintains current MAU growth and the API tier scales with the long-context trend.

6.3 Mooncake as an open-source moat

The open-source bet has two payoffs. First, every external team that adopts Mooncake becomes a soft-marketing channel for Moonshot's API tier ("we already use Mooncake, we might as well use the upstream-tuned Kimi models"). Second, the presence of Mooncake in vLLM creates a strategic moat: any vLLM-based competitor (Anyscale, BentoML, or any in-house team) is now architecturally aligned with Moonshot's serving design.

【Analyst Estimate】 Mooncake's open-source contribution to Moonshot's revenue (in 2025): < 5% direct, but possibly 10–15% indirect (lift to API tier adoption + lower customer-acquisition cost).

6.4 Sensitivity to capital-markets conditions

Moonshot is exposed to three external shocks: (i) US export-control tightening on H100/H200 (the BIS October 2023 and December 2024 rules), (ii) Chinese consumer-AI regulatory clampdown (the 2024-08 generative-AI content rules), and (iii) the rise of low-cost open-source Chinese models (DeepSeek, Qwen) that compete on price. Moonshot's response on all three axes is to push Mooncake — better inference economics are the primary defence on (i) and (iii), and the open-source community shields against (ii) by keeping the development visible.
