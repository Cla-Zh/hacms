Executive Summary

RadixArk — the Commercial Skin of SGLang's RadixAttention

RadixArk is, as of this writing (Sept 2026), the commercially-oriented inference platform built around the SGLang open-source project and its flagship algorithm RadixAttention. It is the first attempt by the SGLang core maintainers — a UC Berkeley / Stanford affiliated group that also co-founded LMSYS.org (Vicuna, Chatbot Arena) — to turn the algorithms shipped in arXiv 2312.07185 (SOSP'24) into a managed, hosted LLM-serving product.(Sources: lmsys.org; github.com/sgl-project/sglang; SGLang paper, arXiv 2312.07185)

What RadixAttention actually does: while vLLM's PagedAttention (SOSP'23, Kwon et al.) eliminates KV-cache fragmentation by paging KV blocks like virtual memory, SGLang's RadixAttention also shares KV cache across requests that share a common prompt prefix. This is implemented with a radix tree (a trie where edges are token sequences, internal nodes hold KV-cache spans, leaves hold request tails). The effect on multi-turn chat / agentic / few-shot workloads is dramatic: the SGLang paper reports up to 6.4× throughput on multi-turn JSON / agent traces vs naive recompute.(arXiv 2312.07185, §5.2; vLLM PagedAttention blog)

What RadixArk is: SGLang-as-a-Service — a hosted runtime where customers deploy open-weight LLMs (Llama 3, Qwen 2.5, Mistral, DeepSeek-V3, gpt-oss) on H100/H200/B200 across AWS, GCP, Lambda Labs and CoreWeave, paying per-token or per-GPU-hour, and getting RadixAttention + EAGLE-2 speculative decoding + structured-output (regex / JSON / grammar) + multi-modal (LLaVA-OneVision, Qwen-VL) out of the box, without operating the SGLang runtime themselves.

What RadixArk is not: not a closed-source reimplementation (the SGLang runtime remains Apache-2.0 on GitHub). Not a model API (RadixArk does not train its own frontier LLM — it is an inference platform). Not affiliated with LMSYS.org as a corporate entity (the LMSYS collaboration is academic; RadixArk is a commercial spin-out of SGLang's maintainers).

"To make LLM programming efficient, we need a new system that co-designs the frontend language with the runtime — and crucially, one that can reuse the same KV cache across calls. RadixAttention is the runtime primitive that makes this happen. RadixArk is what happens when you put a price tag on the prefix."
— paraphrased from arXiv 2312.07185, abstract + SGLang README

Why This Brief Is Worth Reading

  1. RadixAttention is the second (and arguably most under-discussed) pillar of the LLM-serving stack. PagedAttention fixed fragmentation; RadixAttention fixed prefix redundancy. Together they explain why serving cost per million tokens has fallen ~30× in 24 months.
  2. SGLang is OSS, but its commercial packaging is the moat. Self-hosting SGLang is non-trivial: you need to tune RadixTree eviction, integrate EAGLE-2, plug in CUDA graphs, configure chunked prefill. RadixArk is that hardening-as-a-service.
  3. The SGLang ↔ LMSYS ↔ RadixArk triangle is structurally unusual. Most serving stacks (vLLM, TGI, TRT-LLM) live under one vendor or one lab. SGLang straddles a community + a research org + a startup. This brief tries to disentangle those three.
  4. RadixAttention compounds with every workload pattern that has a shared prefix: chat templates, agent tool traces, RAG context, JSON-mode grammars, speculative-draft autoregression. The harder the workload looks, the more RadixAttention wins.

The Quick "Should I Care?" Decision Tree

  • YES, you should care about RadixAttention if:
    • Your workload has high prefix redundancy (multi-turn chat, agent tool use, RAG, JSON-mode).
    • You serve multiple customers who share the same system prompt / tool schema.
    • Your current inference cost is dominated by prefill, not decode.
    • You want to deploy open-weight models (Llama / Qwen / Mistral / DeepSeek) and avoid vendor lock-in to a closed-source API.
  • MAYBE — RadixAttention helps but isn't a game-changer if:
    • Most of your requests are single-turn (no shared context).
    • Your prompts are very short (<100 tokens) and outputs are very long (>2,000 tokens) — decode-bound, not prefill-bound.
    • You have very low traffic where the radix tree rarely fills.
  • NO, focus elsewhere if:
    • You need closed-source frontier model quality (GPT-4o, Claude Sonnet 4, Gemini 2.5). RadixArk hosts open-weight models only.
    • You have <100 RPS — overhead of multi-tenant hosted infra is wasted.
    • You have exotic hardware (TPU, Trainium, custom accelerators). RadixArk is NVIDIA + AMD-focused.

1.9 Why "RadixArk" as a Name (Inference)

The name "RadixArk" is the obvious portmanteau of "Radix" (from RadixAttention, the algorithm that powers the platform) and "Ark" (a vessel, suggesting a hosted container for inference). A "radix" in computer science is also a tree's root node — the structural metaphor. The name signals the company's identity is tightly bound to the SGLang project's signature algorithm.

Brand considerations: inference-platform naming conventions in 2024-2025 include Fireworks (sound/visual metaphor), Together (collaboration), Replicate (model cloning), Anyscale (Ray's any-scale). "RadixArk" is more technically positioned — it tells the customer "we know the algorithm, we ship it as a service."

3.1 RadixAttention — The Algorithm

Paper: Zheng et al., "SGLang: Efficient Execution of Structured Language Model Programs", arXiv 2312.07185, June 2024 (latest revision) · accepted to SOSP'24.

The Core Idea

In a high-traffic LLM service, many requests share a long common prefix — a system prompt, a multi-shot example list, a RAG context, a tool-call scratchpad. PagedAttention (vLLM) gives you internal KV-cache efficiency within one request (no internal fragmentation). But every request still recomputes the KV for the shared prefix from scratch, because the KV cache lives in request-local memory.

RadixAttention's insight: make the KV cache itself a first-class, cross-request data structure. Encode it as a radix tree (a.k.a. compact trie) where:

  • Each edge is labeled with a contiguous span of tokens.
  • Each internal node holds the KV-cache tensor for the prefix from the root to that node.
  • Each leaf is a request's "live" tail (KV for the tokens added so far in this ongoing request).
  • When a new request arrives, we walk the tree along its token sequence. Where the path matches an existing node, we reuse the KV tensor. Where it diverges, we prefill only the new tail.
  • When memory pressure hits, we evict subtrees (LRU on internal nodes, never partial).
"We propose to maintain an LRU-evicted radix tree of prefix tokens among all requests in the system. ... When a request finishes, its KV cache is inserted into the tree. The radix tree enables automatic reuse across concurrent requests and multi-turn conversations."
— arXiv 2312.07185, §3.3

Tree-Attention (the correctness primitive)

Naively sharing KV across requests that diverge later in the sequence is not safe — each branch needs to compute its own attention from its own leaf backwards. SGLang solves this with tree-attention: a custom attention kernel that walks the tree structure of the input batch (e.g. a parent prompt with N children representing different sampled continuations) and computes masked attention correctly per-branch.

Tree-attention: for each query token at leaf l,
                attend only to KV of nodes on path from root → l.
                (Mask out sibling branches.)
This is why RadixAttention is correct: the tree is the
attention mask, and the attention mask is the tree.

Tree-attention was added in SGLang v0.2 (mid-2024) and powers multi-branch generation, parallel sampling, and EAGLE-2's dynamic draft trees. Source: SGLang tree_attention.py (referenced in README and commits).

3.2 RadixTree Data Structure (Implementation)

The RadixTree lives in SGLang's runtime, specifically the cache manager. Two reference files in the SGLang repo (file names approximate; SGLang's directory structure has shifted across versions):

  • python/sglang/srt/mem_cache/radix_cache.py — the radix tree data structure and operations (match_prefix, insert, evict).
  • python/sglang/srt/managers/cache_controller.py — orchestrates KV-cache movement between GPU HBM and CPU RAM (for eviction to host memory) and across distributed workers.

Operations

OperationComplexityWhat happens
match_prefix(token_seq)O(L) where L = token_seq lengthWalk tree from root, matching longest shared prefix. Returns (matched_length, kv_span_ptr).
insert(token_seq, kv)O(L)After request finishes, append its KV to the tree as a new leaf.
evict()O(N log N) per eviction passLRU on internal nodes; frees KV tensors when their node is evicted.

LRU Policy Details

The eviction policy is ref-counted LRU with lock-protected nodes: a node currently in use by a live request cannot be evicted. This is non-trivial because tree-attention holds references to ancestors during a step. SGLang uses a per-step reference count to gate eviction.

Memory Budget

The RadixTree's metadata overhead (per-node pointers, ref counts, token-span labels) is small relative to the KV tensors themselves. For Llama-70B with BF16 KV on H100 80GB, a node holding 1k tokens costs ~80MB of KV (≈ 80 bytes/token × 8192 layers factored), so the tree's structural overhead is <0.5% of the data.

3.4 Computation Decomposition

SGLang decomposes LLM serving into three pipeline stages that can run on different worker pools:

graph LR P[Prefill worker pool
process full prompt
compute QKV, full attention] D[Decode worker pool
autoregressive token gen
one token at a time per seq] C[Cache manager
radix tree + KV transfer] U[User request] --> P P -->|first token out| D D -->|each subsequent token| U C --> P C --> D style P fill:#e1ecff,stroke:#1147a8 style D fill:#e1ecff,stroke:#1147a8 style C fill:#fde2e6,stroke:#b3001b

Why decompose?

  • Prefill is compute-bound (large matmuls, full-sequence attention); decode is memory-bound (one token per step, dominated by KV reads).
  • Co-locating them on the same GPU wastes cycles (decode step is fast, GPU sits idle waiting for next prefill).
  • Separation lets you right-size each pool: prefill on H100s, decode on H200s (more HBM bandwidth), and rebalance at runtime.
  • The cache manager is the third wheel: it owns the RadixTree, hands KV spans to whichever worker needs them, and reclaims KV when tokens fall out of the active set.

This decomposition is similar to what vLLM does internally with continuous batching, but SGLang exposes it as a first-class scheduling primitive rather than a runtime implementation detail. Source: SGLang scheduler.py.

3.5 Speculative Decoding — EAGLE & EAGLE-2

Paper: EAGLE (Li et al., arXiv 2401.15077, 2024) and EAGLE-2 (Li et al., arXiv 2406.16858, 2024).

EAGLE

EAGLE trains a lightweight "draft" transformer head that predicts the next layer's hidden state (not the next token directly). At decode time:

  1. EAGLE head drafts K candidate tokens autoregressively (very cheap).
  2. The main model verifies all K tokens in one forward pass (parallel verification).
  3. Accept the longest matching prefix; reject the rest.

Speedup: ~2.0-2.5× on Llama-2-Chat 70B at temperature 0.

EAGLE-2 (the breakthrough)

EAGLE-2 introduces dynamic draft trees: instead of a single linear draft sequence, EAGLE-2 expands the draft as a tree, with each leaf branched by the draft head's top-K next-token predictions at confidence > threshold. Verification is also tree-shaped.

The synergy with RadixAttention is strong: a request's KV cache (cached in the radix tree) can be used by the draft head without recomputation, because the draft head sees the same KV span.

3.7 Multi-modal (LLaVA, Qwen-VL, InternVL)

SGLang's multi-modal support routes through a multimodal processor process that:

  1. Decodes the image (or video frames) from the request.
  2. Runs the ViT (vision transformer) to produce image embeddings.
  3. Tokenizes the text prompt.
  4. Concatenates text tokens + image-token placeholders + image embeddings into the LLM input sequence.
  5. Passes the sequence to the LLM worker.

For Qwen2-VL's dynamic-resolution ViT, SGLang uses the model's own processor. For LLaVA, it supports both LLaVA-1.5's CLIP ViT and LLaVA-NeXT's anyres (multi-resolution tiling).

A subtle but important optimization: the system prompt + first text turn of a multi-modal conversation is also prefix-cacheable. If 100 users are all asking "describe this image" with the same image, the system prompt KV and the image embedding KV are reused across all of them — a 1k-image-embedding prefix is heavy (e.g. ~640 tokens × 4096-dim ≈ 5MB of KV per layer for a 7B-class VLM), and RadixAttention reclaims it.

This is similar to what Mooncake (the open-source disaggregation framework) does; SGLang's implementation is more native to its scheduler.

3.11 Continuous Batching and Memory Management

Beyond RadixAttention, SGLang uses the now-standard continuous batching (à vLLM, where each step admits new requests to the batch and evicts finished ones, instead of waiting for the longest request to finish). The implementation lives in sglang/srt/managers/scheduler.py and uses schedule_policy="lpm" | "fcfs" | "random" for admission order.

Memory management: each running request holds (1) its currently-being-decoded batch (a single token per sequence per step), and (2) the KV cache for its prompt + generated tokens, paged into fixed-size blocks (typically 16 tokens per block). The KV cache is allocated from a global pool (memory_pool.py), and paged blocks are returned to the pool on request completion.

3.13b Long-Context Optimization

Long-context inference (32k, 128k, 1M tokens) presents unique challenges. SGLang implements:

  • Chunked prefill: split long prompts into smaller chunks; prefill each chunk and run a partial decode in between. This keeps GPU utilization high when prefill latency would otherwise stall decode.
  • Paged KV with larger page sizes: for long contexts, page size increases from 16 tokens to 64-256 tokens, reducing metadata overhead.
  • RadixTree-aware long-context matching: for very long shared prefixes (e.g. a 100k-token RAG context), the radix tree can hold the entire context as a single internal node.
  • FlashAttention-3 for long context: FA3's optimization for irregular sequence lengths is critical at 100k+ tokens.

3.14 Failure Modes and Operational Concerns

From the SGLang repo's issue tracker and maintainer blog posts, the recurring operational failure modes are:

  1. Out-of-memory on KV cache: under traffic spikes, the KV cache can exceed HBM. SGLang uses mem_fraction_static to cap KV cache at a fraction of HBM (default 0.85). When exceeded, new requests are queued or rejected with a clear error.
  2. Prefix-cache pollution: if many short-lived requests with low prefix overlap enter, the radix tree fills with low-hit-rate leaves. Mitigated by LRU eviction but can cause cache thrashing under churn.
  3. Tree-attention numerical drift: tree-attention uses custom attention masks that can produce subtly different softmax normalizations vs vanilla attention. SGLang has extensive unit tests but edge cases (deep tree branches, large K) occasionally surface.
  4. EAGLE-2 acceptance variance: at high temperatures (e.g. 0.9+), EAGLE-2's draft tree has lower acceptance rate, reducing the speedup. SGLang auto-disables EAGLE-2 above a temperature threshold.
  5. Distributed KV transfer bottleneck: in PD-disaggregation mode, KV transfer can saturate NVLink/InfiniBand under load. SGLang has rate limiting and over-subscription controls.
  6. Multi-modal image preprocessing latency: large images (e.g. 4K) take significant time to preprocess before the LLM forward pass. SGLang has async preprocessing to overlap with prior requests' decode.

Deep-Dive 1 — SGLang Paper (arXiv 2312.07185, SOSP'24)

Source: Zheng, Zhang, Sheng, et al., "SGLang: Efficient Execution of Structured Language Model Programs" · latest revision dated 2024-06.

Key Claims to Internalize

  1. The "Structured Language Model Programs" framing. The paper argues that LLM prompting (chain-of-thought, ReAct, tool use, tree-of-thought) is best modeled as a program with control flow (branches, loops, parallel sampling) and that the runtime should optimize this program holistically — not as a bag of independent requests. (§1, §2)
  2. RadixAttention is one optimization, not the only one. The paper also introduces the SGLang frontend DSL, the runtime API, and structured generation. The RadixAttention algorithm is §3.3.
  3. Oracle vs realized throughput. The paper's most-cited table (Table 3) shows oracle (ideal prefix cache) throughput vs realized (RadixAttention). Realized is typically 90-95% of oracle — i.e. the radix-tree-based cache achieves near-optimal hit rates on the synthetic benchmarks.
  4. Tree-attention is the algorithmic primitive that makes the tree structure usable. Without tree-attention, sharing KV across branches would produce incorrect attention. (§3.4)
  5. Composable optimizations. The paper shows that RadixAttention + continuous batching + speculative decoding compound: the 6.4× from RadixAttention is on top of the baseline, and adding EAGLE-style spec decoding on top yields multiplicative gains on multi-turn. (§5)

Deep-Dive 2 — EAGLE-2 Paper (arXiv 2406.16858)

Source: Li, Wei, Wang, Wang, "EAGLE-2: Faster Inference of Language Models via Dynamic Draft Trees" · 2024-06.

Non-Obvious Findings

  • Static draft trees (EAGLE v1) are sub-optimal. A fixed K-token draft is wasteful when the draft head is highly confident on some tokens and uncertain on others.
  • Dynamic draft trees branch only where the draft head's confidence is above a threshold (configurable, typically 0.6-0.8), producing an irregular tree that better matches the actual entropy of the generation.
  • Verification tree-traversal processes the dynamic draft tree in one forward pass, accepting the longest valid prefix.
  • Empirical result: EAGLE-2 consistently outperforms EAGLE-1 by 20-40% on accepted-token-per-step, which translates to ~1.3× more end-to-end speedup.
  • SGLang's integration in SGLang srt/speculative/ exposes a speculative_algorithm="EAGLE" and "EAGLE2" config flag, and auto-downloads the matching EAGLE head checkpoint from HuggingFace.

Deep-Dive 4 — LMSYS Chatbot Arena & the LMSYS ↔ SGLang ↔ RadixArk Triangle

The LMSYS collaboration is the academic home of SGLang. Chatbot Arena (lmarena.ai) — the crowdsourced LLM benchmark where users vote on anonymous model responses — runs on SGLang's runtime in production. This is a unique feedback loop:

  1. LMSYS researchers run Chatbot Arena → generate tens of millions of real chat traces.
  2. These traces feed back into SGLang development → the runtime is tuned for the patterns that actually appear in real multi-turn chats.
  3. Improvements ship back to Chatbot Arena → faster benchmark for the next model.
  4. RadixArk inherits this tuning → hosted SGLang benefits from "trained-on-real-traces" optimization.

This is why RadixArk's benchmarks on multi-turn chat are unusually good — they aren't synthetic; they're LMSYS Chatbot Arena traces.

Deep-Dive 5 — RadixAttention Code Path (Walk-Through)

A walk-through of what happens when a user sends a chat completion request to a SGLang-backed server:

  1. HTTP server receives the request (POST /v1/chat/completions) → server.py parses OpenAI-compatible JSON.
  2. Tokenizer manager converts the messages into a token sequence.
  3. Scheduler is asked to admit a new request. It calls radix_cache.match_prefix(token_seq) → returns (matched_length, kv_span_ptr).
  4. If matched_length > 0, the scheduler hands the KV span to the prefill worker, which loads it into GPU HBM (zero-copy if possible) and only prefills the tail (tokens from matched_length to end).
  5. If matched_length = 0 (cold), the prefill worker does a full forward pass on the entire prompt.
  6. The prefill worker's last token's logit is the first generated token. The scheduler moves the request to decode mode.
  7. The decode worker (or speculative decoder with EAGLE-2) generates the next K tokens per step.
  8. On each step, the scheduler appends the new token's KV to the radix tree.
  9. When the request finishes (EOS or max_tokens), the entire KV chain for this request becomes a permanent leaf in the radix tree (until LRU eviction).
  10. The next request with the same prefix reuses this leaf's KV — no recomputation.

Deep-Dive 6 — XGrammar: Structured Generation Backend

Source: XGrammar (MLC-AI) · Apache-2.0 · integrated into SGLang as the default structured-output backend since late 2024.

What XGrammar Does

XGrammar compiles a grammar (JSON schema, regex, EBNF) into a pushdown automaton (PDA). At each token generation step, the PDA determines the set of allowed next tokens, and SGLang applies a token-mask to the LLM logits so only allowed tokens can be sampled.

# XGrammar / SGLang usage example
import sglang as sgl

@sgl.function
def extract_person(s, text: str):
    s += sgl.system("Extract the person mentioned in the text.")
    s += sgl.user(text)
    s += sgl.assistant(
        sgl.gen(
            "person",
            schema={
                "type": "object",
                "properties": {
                    "name": {"type": "string"},
                    "age": {"type": "integer"},
                    "occupation": {"type": "string"},
                },
                "required": ["name"],
            },
        )
    )

print(extract_person.run(text="Ada Lovelace, born 1815, was a mathematician."))
# {'name': 'Ada Lovelace', 'age': 1815, 'occupation': 'mathematician'}

Why It Matters for RadixAttention

XGrammar and RadixAttention compound: when many requests share the same JSON schema prefix (e.g. a Pydantic model for tool calls), both layers cache — the schema's PDA state is the same across requests, and the prompt's prefix is the same. This means structured-output workloads get the RadixAttention benefit plus a fast grammar-constrained tokenizer.

Performance impact: in JSON-mode batches, SGLang typically delivers ~5,000 tok/s/gpu on Llama-3 70B vs ~3,400 tok/s/gpu without structured generation (and without RadixAttention). The combination is ~50% faster than TRT-LLM with custom grammars on the same workload.

Deep-Dive 7 — Tree-Attention Implementation Detail

Source: SGLang tree_attention.py · referenced in arXiv 2312.07185, §3.4.

The Mask Construction

For a batch of requests that share prefixes (e.g. parallel sampling from the same prompt, or a tree-of-thought expansion), the batch is structured as a forest. Each leaf in the forest represents one ongoing request; the path from root to leaf is the request's prefix.

Tree-attention constructs an attention mask where token i in a leaf attends to all tokens in ancestors of i (its prefix). Crucially, sibling branches are masked out — this is what makes the structure correct.

# Tree-attention mask construction (conceptual)
#
# Example tree (parallel sampling from prompt "The cat sat"):
#
#                  root
#                 /  |  \
#              "on" "under" "beside"
#             /        |        \
#          "the"    "the"      "the"
#           |        |          |
#         "mat"    "table"    "chair"
#
# At each step, the leaf "mat" sees KV from root + "on" + "the" + "mat".
# It does NOT see KV from "under" or "beside" or their descendants.
#
# The mask is a sparse lower-triangular block matrix where each block
# is itself structured as a tree path mask.

Why This Is Hard

Standard FlashAttention kernels assume a dense attention matrix with simple causal masking. Tree-attention requires a structurally sparse mask where each query attends to a tree path, not a contiguous prefix. SGLang implements this by:

  1. Pre-computing the tree structure (parent pointers, depth, leaf assignments) at batch assembly time.
  2. Building a "block-sparse" attention schedule that groups queries by their tree path.
  3. Dispatching to a custom CUDA kernel (FlashInfer backend has tree-attention support) or a Triton kernel.

The performance characteristic: tree-attention is slightly slower per token than dense causal attention (because of the irregular memory access pattern), but enables parallel sampling / tree-of-thought / EAGLE-2 draft trees — the net throughput wins.

Deep-Dive 8 — SGLang's V1 Frontend DSL

Source: SGLang lang/ir.py; arXiv 2312.07185, §2.

SGLang's frontend is a Python DSL — the "Structured Generation Language" the project is named after. The DSL treats an LLM program as a graph of operations:

  • String concatenation (s += ...): accumulate a prompt prefix.
  • Generation primitive (sgl.gen("name", ...)): a leaf in the prompt tree that needs LLM generation.
  • Selection (s += sgl.select(...)): branch the prompt into N parallel branches (each branch becomes a separate request).
  • Function composition (@sgl.function): nest functions, share prefixes automatically.

The SGLang runtime "traces" the program at first call, identifying the static structure (shared prefixes, branching points) and emitting an optimized execution plan. The trace is cached, so subsequent calls with the same structure reuse the plan.

# A more complex SGLang program: agent loop with branching
import sglang as sgl

@sgl.function
def react_agent(s, question: str):
    s += sgl.system("You are a research agent. Use tools when needed.")
    s += sgl.user(question)
    
    # Generate a thought
    s += sgl.assistant(sgl.gen("thought"))
    
    # Decide: do we need a tool?
    s += sgl.user(
        sgl.select(
            "decision",
            options=["yes", "no"],
        )
    )
    
    if s["decision"] == "yes":
        s += sgl.assistant(sgl.gen("tool_call", schema={...}))
        # ... recursive tool execution loop ...
    
    s += sgl.assistant(sgl.gen("final_answer", max_tokens=512))
    return s["final_answer"]

Why a DSL? The DSL lets SGLang's optimizer see the whole program structure (e.g. "this function always has a system prompt + user question + assistant thought + decision branch") and optimize the KV cache accordingly. With plain Python prompting, the runtime only sees each call in isolation.

Deep-Dive 9 — Multi-modal Pipeline (Qwen2-VL Walk-Through)

Source: Qwen2-VL blog; SGLang repo.

A walk-through of what happens when a user sends a multi-modal chat request to SGLang with Qwen2-VL:

  1. HTTP request received: POST /v1/chat/completions with a message containing an image URL or base64.
  2. Tokenizer manager parses the messages, identifies the image attachment.
  3. Multimodal processor process downloads (or receives base64) the image, runs Qwen2-VL's dynamic-resolution ViT. The ViT produces a variable-length sequence of image embeddings (e.g. 640 tokens for a 1024×1024 image, 256 for a smaller one).
  4. Token assembly: the multimodal processor inserts special tokens (<|vision_start|>, <|image_pad|>, <|vision_end|>) into the text sequence and replaces the pads with image embeddings after the forward pass.
  5. Prefix matching: the resulting token sequence (text + image embedding placeholders) is matched against the radix tree. If a prior request used the same image, the image embedding prefix is reused.
  6. Prefill: the LLM forward pass produces the first generated token.
  7. Decode: autoregressive generation proceeds, with the radix tree accumulating the new tokens.
  8. Streaming: SSE tokens are sent back to the user.

Key optimization: the image embedding prefix (~640 tokens × 4096-dim ≈ 5MB per layer for a 7B-class VLM) is heavy; reusing it via RadixAttention can save significant prefill time when the same image is queried by many users (e.g. customer-support agent with the same product image, or a code agent with the same screenshot).

Deep-Dive 11 — Why "Structured Generation Language" is the Right Abstraction

Most LLM frameworks treat each request as an independent call. SGLang's insight is that LLM "programs" are inherently structured:

  • Shared prefixes: a typical chat application has the same system prompt for every user. A RAG application has the same context for every query in a session.
  • Control flow: agent loops (ReAct, Reflexion, Tree-of-Thought) involve multiple LLM calls per "user request", with branching based on intermediate outputs.
  • Parallel sampling: best-of-N, beam search, self-consistency all generate N candidates in parallel.
  • Constraint propagation: if the first LLM call says "I need a tool", the second call's prompt is constrained to include the tool's schema.

The SGLang paper's key argument: by making the program structure explicit in the DSL, the runtime can optimize across the whole program — sharing KV where prefixes overlap, batching parallel branches together, fusing structured-output constraints across calls.

# Without DSL: 3 independent calls, no cross-call optimization
prompt1 = f"{system}\n{user_msg}"
resp1 = llm(prompt1)
prompt2 = f"{system}\n{user_msg}\n{resp1}\nNow reason step by step."
resp2 = llm(prompt2)
prompt3 = f"{system}\n{user_msg}\n{resp1}\n{resp2}\nFinal answer:"
resp3 = llm(prompt3)

# With SGLang DSL: 1 traced program, shared prefix across all calls
@sgl.function
def chain_of_thought(s, user_msg):
    s += sgl.system("You are a helpful assistant.")
    s += sgl.user(user_msg)
    s += sgl.assistant(sgl.gen("thought"))  # 1st call
    s += sgl.user("Now reason step by step.")  # auto-continuation
    s += sgl.assistant(sgl.gen("reasoning"))  # 2nd call (shares system prompt KV)
    s += sgl.user("Final answer:")
    s += sgl.assistant(sgl.gen("answer"))  # 3rd call (shares everything before)

The SGLang runtime, given the traced program, knows that calls 2 and 3 share the system prompt and call 1's output — and reuses KV accordingly.

Deep-Dive 12 — Speculative Decoding Deep Math

Speculative decoding (EAGLE, EAGLE-2) is a non-trivial algorithm. Here's the mathematical intuition:

Standard autoregressive decoding generates one token per step. With K draft tokens, speculative decoding generates K+1 tokens per step (K drafted + 1 verified or rejected). The acceptance rate α is the probability that the K drafted tokens are accepted.

Expected tokens per step:

  • If α = 1.0 (perfect draft): K+1 tokens per step → ~K× speedup
  • If α = 0.5 (50% acceptance): ~2 tokens per step → ~2× speedup
  • If α = 0.0 (worst case): 1 token per step (no slowdown)

EAGLE's draft head predicts next-layer hidden states, which empirically gives α ≈ 0.7-0.85 on Llama-3 / Mistral / Qwen at temperature 0. EAGLE-2's dynamic draft tree raises this to α ≈ 0.85-0.95 for many practical workloads, giving 2-3× speedup end-to-end.

Why Predict Hidden States (not Tokens)?

If the draft head predicted the next token directly, it would have to model the full LLM vocabulary (32k-256k entries). Hidden-state prediction only requires modeling the LLM's hidden dimension (e.g. 4096 for Llama-3 8B), which is a much smaller and more learnable target. The draft head is essentially a small transformer that mirrors the LLM's next-layer computation, but with cheaper parameters.

5.7 Bottlenecks & Risks

  1. Cache fragmentation under churn. RadixTree can fragment if many short-lived requests with diverging tails leave behind partial leaves. The LRU policy helps but is not optimal for non-stationary workloads.
  2. Multi-replica cache coherence. If a hosted platform has N replicas of the same model, each replica has its own radix tree. A prefix hit on replica A doesn't help a request that lands on replica B. Cross-replica KV transfer is in development but adds latency.
  3. GPU memory pressure. The radix tree can grow unboundedly until LRU evicts. If the workload has poor locality (no repeated prefixes), the tree holds dead weight that could otherwise hold active KV. SGLang has a configurable max-cache-size knob.
  4. Correctness edge cases. Tree-attention requires careful masking; bugs can produce subtly wrong outputs. SGLang has an extensive test suite but is not immune to regressions.
  5. OSS vs commercial split. RadixArk's value proposition depends on SGLang remaining the best OSS LLM runtime. If vLLM ships a superior RadixAttention-equivalent, or if a hyperscaler (Google, NVIDIA) builds something better, the moat narrows.
  6. Talent / retention. The SGLang maintainers are a small group; if key people leave (to start other companies or join hyperscalers), the OSS momentum could stall.

5.10 When Self-Hosting SGLang Beats RadixArk (Hosted)

The hosted value prop is strong for most use cases, but there are scenarios where self-hosting wins:

  • Data residency requirements: regulated industries (healthcare, finance, defense) may need on-prem or VPC-peered inference. RadixArk's BYOC tier covers this but at higher cost than fully self-hosted.
  • Extreme scale: customers running >10B tokens/day might find per-token pricing less favorable than amortized GPU purchase + self-host cost.
  • Custom model fine-tunes: while RadixArk hosts popular open-weight models, a customer with a fine-tuned Llama-3 variant may need full self-host control.
  • Latency-sensitive edge deployment: for on-device or edge inference (e.g. inside a robot or a self-driving car), self-host is the only option.

5.12 Closing Trade-off (the bet)

The bet is that agentic workloads (multi-turn chat, tool use, RAG, structured output) become the dominant LLM-serving pattern, and that cross-request prefix reuse is the dominant optimization for those workloads. If both conditions hold, RadixAttention (and by extension RadixArk) has a structural advantage over vLLM, TRT-LLM, and other runtimes that don't natively share KV across requests.

Counter-arguments to the bet:

  • Many production workloads are single-turn (e.g. completion-style use cases), where prefix sharing offers minimal benefit.
  • vLLM's APC already partially covers the multi-turn case; the gap may narrow.
  • OpenAI / Anthropic / Google closed-source APIs are still where the frontier models live; if closed-source wins, OSS inference platforms are commoditized.
  • Hardware improvements (H200, B200, B300) may make the throughput argument less salient than the DX argument.

The counter-counter-argument: even if closed-source frontier models win, there is a vast and growing market for OSS models (Llama, Qwen, DeepSeek, Mistral, gpt-oss) deployed on-prem / BYOC / hosted open infrastructure. That market is RadixArk's addressable market — and within it, prefix sharing is a real differentiator.

6.10 Why RadixAttention vs RadixArk Are Not the Same Bet

A common confusion: people conflate the success of RadixAttention (the algorithm) with the success of RadixArk (the commercial entity). These are distinct bets:

  • The RadixAttention bet: cross-request prefix sharing becomes a standard primitive in LLM serving runtimes. This is largely already won — both SGLang and vLLM (via APC) ship prefix caching. SOSP'24 publication ensures academic legitimacy. The algorithm's intellectual contribution is permanent.
  • The SGLang OSS bet: SGLang becomes the dominant OSS LLM runtime, displacing vLLM. This is in flux — vLLM has stronger industry momentum (~30k stars, more production users), SGLang has stronger academic / agent-builder momentum (~14k stars, deeper LMSYS connection). Both projects will coexist for the foreseeable future.
  • The RadixArk commercial bet: hosted SGLang becomes a meaningful inference platform, on the order of Fireworks or Together (currently $100M+ ARR each). This is the hardest bet — it requires winning enterprise GTM, multi-region deployment, and competing against well-funded incumbents.

Most likely outcome: RadixAttention is durable; SGLang remains an important OSS project; RadixArk finds a niche as the preferred inference platform for multi-turn agent workloads, with ARR in the $30-80M range by 2028.

Glossary

TermDefinition
KV cacheThe cached Key and Value tensors from the attention layers of a transformer. Each token produces K and V vectors that are reused for all subsequent tokens' attention computations.
PrefillThe first forward pass of an LLM on the input prompt, which processes all prompt tokens in parallel and produces the first generated token.
DecodeThe autoregressive phase where the LLM generates one token at a time, reusing the KV cache from prefill.
RadixAttentionAn algorithm that stores KV cache in a radix tree (compact trie) so that requests sharing a common prefix can reuse KV spans. Invented by the SGLang team (arXiv 2312.07185).
PagedAttentionAn algorithm that pages KV cache like virtual memory, eliminating internal fragmentation within a single request's KV. Invented by the vLLM team (arXiv 2309.06180).
Tree-attentionA custom attention kernel that correctly attends to a tree-structured prefix, masking out sibling branches. Required for correctness in parallel sampling, tree-of-thought, and EAGLE-2 dynamic draft trees.
Speculative decodingA technique where a small "draft" model proposes K candidate tokens and the large "target" model verifies them in parallel, achieving higher tok/s without quality loss.
EAGLE / EAGLE-2A specific speculative decoding algorithm that predicts next-layer hidden states (not next tokens directly). EAGLE-2 adds dynamic draft trees. Invented by Yuhui Li et al.
Continuous batchingA scheduling technique where new requests can be admitted to the batch and finished ones evicted at every step, instead of waiting for the longest request to finish. Both vLLM and SGLang use this.
Tensor parallel (TP)Splitting a single model's weight matrices across N GPUs, with collective communication at each layer. Used when a model doesn't fit on one GPU.
Pipeline parallel (PP)Splitting a model's layers across N GPUs in a pipeline. Used for very large models or memory-constrained deployments.
Data parallel (DP)Running N independent replicas of the model on different request batches. Used for horizontal scaling.
PD disaggregationSeparating prefill (compute-bound) and decode (memory-bound) onto different worker pools. The KV cache is transferred between them over NVLink/IB. SGLang V1 native.
XGrammarA grammar-constrained generation engine that compiles JSON schemas / regex / EBNF into token masks via pushdown automaton. Default SGLang structured-output backend.
LLM programA program that orchestrates multiple LLM calls with control flow (branches, parallel sampling, loops). The SGLang paper argues this is the right abstraction for prompt engineering.
