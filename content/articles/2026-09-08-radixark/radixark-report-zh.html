RadixArk —— SGLang RadixAttention 的商业化外衣

RadixArk 截至本简报撰写时(2026 年 9 月)是围绕 SGLang 开源项目及其旗舰算法 RadixAttention 构建的面向商业的推理平台。这是 SGLang 核心维护者(隶属于 UC Berkeley / Stanford 的研究团队,同时也是 LMSYS.org(Vicuna、Chatbot Arena)的联合发起方)首次尝试将 arXiv 2312.07185(SOSP'24)中发表的算法,转化为托管式的 LLM serving 产品。(来源:lmsys.org;github.com/sgl-project/sglang;SGLang 论文,arXiv 2312.07185)

RadixAttention 真正在做什么:虽然 vLLM 的 PagedAttention(SOSP'23,Kwon 等)通过将 KV block 按虚拟内存分页消除了 KV cache 的碎片化,SGLang 的 RadixAttention 还额外在共享同一 prompt 前缀的请求之间共享 KV cache。这是通过一棵基数树(radix tree)实现的(一种 trie,边为 token 序列,内部节点保存 KV-cache 跨度,叶子节点保存请求的尾部)。在多轮对话 / agentic / few-shot 负载下,效果非常显著:SGLang 论文报告,在多轮 JSON / agent 轨迹上相对朴素重算可达 6.4× 吞吐。(arXiv 2312.07185, §5.2;vLLM PagedAttention blog)

RadixArk 是什么:SGLang-as-a-Service —— 一个托管式 runtime,客户可以在 AWS、GCP、Lambda Labs 和 CoreWeave 上,把开源权重 LLM(Llama 3、Qwen 2.5、Mistral、DeepSeek-V3、gpt-oss)部署在 H100 / H200 / B200 上,按 token 或 GPU·小时付费,开箱即用 RadixAttention + EAGLE-2 投机解码 + 结构化输出(regex / JSON / grammar)+ 多模态(LLaVA-OneVision、Qwen-VL),而无需自行运维 SGLang runtime。

RadixArk 不是什么:不是闭源重实现(SGLang runtime 在 GitHub 上仍是 Apache-2.0)。不是模型 API(RadixArk 并不自己训练前沿 LLM —— 它是一个**推理**平台)。与 LMSYS.org 不存在公司层面的关联(LMSYS 协作是学术性质,RadixArk 是 SGLang 维护者的商业化衍生)。

“要让 LLM 编程变得高效,我们需要一个全新系统,把前端语言和运行时协同设计 —— 关键是,这个系统能够在多次调用间复用同一份 KV cache。RadixAttention 就是让这件事发生的运行时原语。RadixArk 则是当你在前缀上贴上价格标签时会发生的事情。”
—— 改写自 arXiv 2312.07185 摘要 + SGLang README

为什么值得读这份简报

  1. RadixAttention 是 LLM serving 技术栈中第二根(也是被讨论最少)支柱。PagedAttention 解决了碎片问题;RadixAttention 解决了前缀冗余问题。两者共同解释了为什么 24 个月内单位 token 的 serving 成本下降了约 30×。
  2. SGLang 是开源的,但其商业化封装才是护城河。自托管 SGLang 并非易事:你需要调优 RadixTree 淘汰策略、集成 EAGLE-2、接入 CUDA graphs、配置 chunked prefill。RadixArk 正是这种“硬化即服务”。
  3. SGLang ↔ LMSYS ↔ RadixArk 的三角结构并不常见。大多数 serving 技术栈(vLLM、TGI、TRT-LLM)都依附于单一厂商或单一实验室。SGLang 横跨社区 + 研究机构 + 创业公司三方。本简报试图厘清这三者之间的关系。
  4. RadixAttention 与每一种共享前缀的负载模式叠加产生复利:对话模板、agent 工具轨迹、RAG 上下文、JSON-mode 语法、投机解码 draft 自回归。工作负载越“难”,RadixAttention 优势越大。

“我该不该关心?”决策树

  • 是的,你应该关心 RadixAttention,如果:
    • 你的工作负载有高前缀冗余(多轮对话、agent 工具调用、RAG、JSON-mode)。
    • 你服务多个共享同一 system prompt / 工具 schema 的客户。
    • 你当前的推理成本主要来自 prefill,而不是 decode。
    • 你想部署开源权重模型(Llama / Qwen / Mistral / DeepSeek),避免被闭源 API 锁定。
  • 也许 —— RadixAttention 有帮助但不是决定性的,如果:
    • 你的请求大多是单轮(没有共享上下文)。
    • 你的 prompt 很短(<100 token)而输出很长(>2,000 token)—— 受 decode 限制而非 prefill。
    • 流量很低,基数树很少有机会填满。
  • 不需要,把精力放在别处,如果:
    • 你需要闭源前沿模型的品质(GPT-4o、Claude Sonnet 4、Gemini 2.5)。RadixArk 只托管开源权重模型。
    • 你的 RPS <100 —— 多租户托管基础设施的开销被浪费了。
    • 你有异构硬件(TPU、Trainium、自研加速器)。RadixArk 聚焦 NVIDIA + AMD。

1.12 为什么 RadixArk 衍生是合理的(即使没有公开融资)

考虑到开源 LLM serving 市场的规模(预计到 2028 年达 $15-30B)以及 SGLang 团队算法的深度,商业化衍生是顺理成章的。标准的开源→公司打法:

  1. 开源项目获得关注(SGLang 自 2024 年起)→ 社区使用,贡献者增长。
  2. 企业客户想要托管版本→ 不想自己运营 GPU 基础设施。
  3. 创始人衍生出托管商业实体(RadixArk ~2024)→ 捕获运营层的价值。
  4. 商业实体反哺开源开发→ 形成飞轮。
  5. 实体融资扩大规模→ 2026-2027 年的 A 轮。

这一打法已被验证:Databricks(Apache Spark → 托管 Databricks)、Confluent(Apache Kafka → 托管 Confluent Cloud)、MongoDB(Apache 风格许可 → MongoDB Atlas)、Elastic(Apache Elasticsearch → Elastic Cloud)、Hugging Face(transformers 库 → HF Inference API)。

RadixArk 的问题:团队是否足够大、GTM 是否准备好执行这一打法?从公开信号(SGLang README、维护者活跃度)看,团队技术上很深但规模小。执行风险高。

2.3 开发者体验(DX)

SGLang(自托管)与 RadixArk(托管)暴露相同的前端 DSL —— “Structured Generation Language”这个名字。DSL 是 Pythonic 的;你编写一个描述 prompt 组装、分支、函数调用与并行采样的程序。

import sglang as sgl

@sgl.function
def multi_turn_qa(s, question: str):
    # The system prompt is identical across calls — RadixAttention will
    # reuse the KV for this prefix on the next request.
    s += sgl.system("You are a helpful, concise assistant.")
    s += sgl.user(question)
    s += sgl.assistant(sgl.gen("answer", max_tokens=256))

# SGLang's `frontend` runs this as a graph of sub-calls.
# RadixAttention caches each (system prompt, prior turns) node.
print(multi_turn_qa.run(question="What is RadixAttention?"))

3.1 RadixAttention —— 算法

论文:Zheng 等,“SGLang: Efficient Execution of Structured Language Model Programs”,arXiv 2312.07185,2024 年 6 月(最新修订)·被 SOSP'24 接收。

核心思想

在高流量的 LLM 服务中,许多请求共享一个很长的公共前缀 —— system prompt、multi-shot 示例列表、RAG 上下文、tool-call scratchpad。PagedAttention(vLLM)给出了单个请求内的 KV cache 效率(无内部碎片)。但每个请求仍然需要从头重算共享前缀的 KV,因为 KV cache 处于请求本地的内存中。

RadixAttention 的洞察:让 KV cache 本身成为跨请求的一等数据结构。将其编码为一棵基数树(radix tree)(又名压缩 trie),其中:

  • 每条边用一段连续的 token 序列作为标签。
  • 每个内部节点保存从根到该节点的前缀对应的 KV-cache 张量。
  • 每个叶子节点是某个请求的“实时”尾部(到目前为止该请求新增 token 的 KV)。
  • 新请求到达时,我们沿其 token 序列遍历树。与已有节点路径匹配的部分,复用 KV 张量。发生分叉的部分,只 prefill 新的尾部。
  • 内存压力出现时,对子树进行淘汰(内部节点用 LRU,从不部分淘汰)。
“我们提议在系统中所有请求之间维护一棵 LRU 淘汰的基数树来管理前缀 token。...当一个请求完成时,它的 KV cache 被插入到树中。基数树使得跨并发请求与多轮对话的自动复用成为可能。”
—— arXiv 2312.07185, §3.3

Tree-Attention(正确性原语)

在稍后发生分叉的请求间朴素地共享 KV 是不安全的 —— 每个分支需要从自己的叶子反向计算自己的 attention。SGLang 用 tree-attention 解决:一种自定义 attention kernel,沿输入 batch 的树形结构(例如同一父 prompt 派生出 N 个不同采样续写的子节点)遍历,并按分支正确计算 masked attention。

Tree-attention: for each query token at leaf l,
                attend only to KV of nodes on path from root → l.
                (Mask out sibling branches.)
This is why RadixAttention is correct: the tree is the
attention mask, and the attention mask is the tree.

Tree-attention 于 SGLang v0.2(2024 年中)加入,为多分支生成、并行采样、EAGLE-2 的动态 draft 树提供支持。来源:SGLang tree_attention.py(README 与提交记录中提及)。

3.2 RadixTree 数据结构(实现)

RadixTree 位于 SGLang runtime 中的 cache 管理器内。SGLang 仓库中有两个相关文件(文件名大致如此;SGLang 的目录结构跨版本略有变动):

  • python/sglang/srt/mem_cache/radix_cache.py —— 基数树数据结构与操作(match_prefix、insert、evict)。
  • python/sglang/srt/managers/cache_controller.py —— 编排 KV-cache 在 GPU HBM 与 CPU RAM 之间(淘汰到主机内存)以及跨分布式 worker 的迁移。

操作

操作复杂度说明
match_prefix(token_seq)O(L),L = token_seq 长度从根遍历树,匹配最长公共前缀。返回 (matched_length, kv_span_ptr)。
insert(token_seq, kv)O(L)请求完成后,将其 KV 作为新叶子追加到树中。
evict()每次淘汰 O(N log N)内部节点 LRU;淘汰节点时释放其 KV 张量。
split(node, at_pos)O(split_size)内部节点管理 —— 新分支在节点中部发散时分裂该节点。

LRU 策略细节

淘汰策略是引用计数 LRU + 节点加锁保护:被活跃请求持有的节点无法被淘汰。这一点非平凡,因为 tree-attention 在一个 step 内会持有祖先节点的引用。SGLang 用每 step 的引用计数来门控淘汰。

内存预算

RadixTree 的元数据开销(每节点的指针、引用计数、token 跨度标签)相对 KV 张量本身很小。对 Llama-70B、H100 80GB 上的 BF16 KV,一个保存 1k token 的节点约 80MB KV(≈ 80 字节/token × 8192 层叠加),因此树的结构开销不到数据的 0.5%。

3.4 计算分解

SGLang 把 LLM serving 分解为 三个流水线阶段,可在不同 worker 池上运行:

为什么要分解?

  • Prefill 是计算密集型(大矩阵乘、全序列 attention);decode 是内存密集型(每步一个 token,KV 读取为主)。
  • 将它们放在同一块 GPU 上会浪费周期(decode 步骤快,GPU 在等下一次 prefill 时闲置)。
  • 分离后可以为各池选合适规模:prefill 用 H100,decode 用 H200(更大 HBM 带宽),并可在运行时重平衡。
  • Cache 管理器是第三只轮子:它拥有 RadixTree,把 KV 跨度交给任何需要的 worker,并在 token 离开活跃集时回收 KV。

这种分解与 vLLM 在内部用连续批处理所做的类似,但 SGLang 将其作为一等调度原语暴露出来,而不是 runtime 实现细节。来源:SGLang scheduler.py。

3.5 投机解码 —— EAGLE 与 EAGLE-2

论文:EAGLE(Li 等,arXiv 2401.15077,2024) 与 EAGLE-2(Li 等,arXiv 2406.16858,2024)。

EAGLE

EAGLE 训练一个轻量的 “draft” transformer 头来预测下一层的 hidden state(而非直接预测下一个 token)。解码时:

  1. EAGLE head 自回归 draft 出 K 个候选 token(非常便宜)。
  2. 主模型在一次前向中验证所有 K 个 token(并行验证)。
  3. 接受最长的匹配前缀;拒绝其余。

加速比:Llama-2-Chat 70B 在 temperature 0 下约 2.0-2.5×。

EAGLE-2(突破)

EAGLE-2 引入动态 draft 树:不是单个线性 draft 序列,EAGLE-2 将 draft 展开成一棵树,每个叶子由 draft head 在置信度 > 阈值处的 top-K 下一个 token 预测分叉而来。验证也是树形的。

与 RadixAttention 的协同效应很强:某个请求缓存在基数树中的 KV 可被 draft head 无重算地使用,因为 draft head 看到的是同一段 KV 跨度。

3.7 多模态(LLaVA、Qwen-VL、InternVL)

SGLang 的多模态支持走一个multimodal processor进程:

  1. 解码请求中的图像(或视频帧)。
  2. 运行 ViT(vision transformer)生成图像嵌入。
  3. 对文本 prompt 做 tokenization。
  4. 将文本 token + 图像 token 占位符 + 图像嵌入拼接成 LLM 输入序列。
  5. 将序列传给 LLM worker。

对 Qwen2-VL 的动态分辨率 ViT,SGLang 使用模型自带的 processor。对 LLaVA,既支持 LLaVA-1.5 的 CLIP ViT,也支持 LLaVA-NeXT 的 anyres(多分辨率分块)。

3.9 分布式 Serving —— TP / PP / DP

SGLang 支持三种可与 RadixAttention 复合的正交并行模式:

模式说明何时用与 RadixAttention 的交互
TP(张量并行)把单层权重矩阵切到 N 个 GPU(N 路分片)单模型装不下单 GPU(如 Llama-70B 在 2×H100 80GB,或 405B 在 8×H100)RadixTree 在所有 TP rank 上是相同的(它们持有同一 KV 的分片);无需协调
PP(流水线并行)把层切到 N 个 GPU(N 阶段流水线)超大模型或内存受限的节点RadixTree 在所有 PP 阶段上相同;只有 decode 步骤需要流水线气泡管理
DP(数据并行)在不同请求 batch 上跑 N 个模型副本请求量大;需要横向扩展每个副本有自己的 RadixTree —— 跨副本前缀复用需要显式 KV 传输(开发中)

对托管推理,典型部署是 H100 80GB 上 TP=8 跑 Llama-3 70B(BF16 共需 140GB VRAM,2 GPU TP=2 能放下,但 TP=8 通过更快的集合通信获得更佳 decode 延迟)。Llama-3 405B 需要 H100 80GB 上 TP=8(BF16 = 810GB ÷ 8 = 101GB 每 GPU,但考虑 KV cache 余量,实际需要 TP=8 或 TP=16)。

3.11 连续批处理与内存管理

除 RadixAttention 外,SGLang 使用现已标准的 连续批处理(类似 vLLM,每步接纳新请求、淘汰已完成请求,而不是等最长请求结束)。实现在 sglang/srt/managers/scheduler.py,使用 schedule_policy="lpm" | "fcfs" | "random" 控制接纳顺序。

内存管理:每个运行中的请求持有 (1) 当前正在解码的 batch(每序列每步一个 token),(2) 其 prompt + 已生成 token 的 KV cache,按固定大小 block 分页(通常每 block 16 token)。KV cache 从全局池(memory_pool.py)分配,请求完成时 page block 归还到池。

3.13b 长上下文优化

长上下文推理(32k、128k、1M token)有独特挑战。SGLang 的实现:

  • Chunked prefill:把长 prompt 切成小块;逐块 prefill,期间跑部分 decode。这让 prefill 延迟本会拖累 decode 时 GPU 利用率仍保持高位。
  • 页大小更大的 Paged KV:对长上下文,page 大小从 16 token 增到 64-256 token,减少元数据开销。
  • RadixTree 感知的长上下文匹配:对很长的共享前缀(如 100k-token 的 RAG 上下文),基数树可以把整个上下文作为一个内部节点。
  • 长上下文用 FlashAttention-3:FA3 对不规则序列长度的优化在 100k+ token 时至关重要。

3.13c 多 LoRA Serving

一个常见的生产需求:在单个基础模型上服务多个微调的 LoRA 适配器。SGLang 通过 SGLANG_ENABLE_LORA 标志与每请求 lora_path 参数实现 多 LoRA serving:

# Multi-LoRA serving example
# At server startup:
python -m sglang.launch_server \
    --model-path meta-llama/Llama-3.1-8B-Instruct \
    --lora-paths lora://customer_a:1 lora://customer_b:2 lora://customer_c:3 \
    --max-lora-rank 64

# Per-request:
resp = client.chat.completions.create(
    model="customer_a",  # activates customer_a's LoRA
    messages=[...],
)

这对成本高效的微调 serving 至关重要 —— 无需为每个客户部署 N 份基础模型(每个客户一份),而是部署一个基础模型 + N 个小 LoRA 适配器。即使激活不同 LoRA,RadixAttention 仍能跨请求生效。

3.14 失败模式与运维考量

从 SGLang 仓库的 issue tracker 和维护者博客,反复出现的运维失败模式:

  1. KV cache 内存不足:流量高峰时,KV cache 可能超过 HBM。SGLang 用 mem_fraction_static 把 KV cache 限制在 HBM 的一定比例(默认 0.85)。超出时,新请求排队或返回明确错误。
  2. 前缀缓存污染:若大量短生命周期、低前缀重叠的请求涌入,会留下大量低命中率的叶子,撑满树。LRU 淘汰有帮助,但在颠簸型负载下会造成 cache thrashing。
  3. Tree-attention 数值漂移:tree-attention 使用自定义 attention mask,softmax 归一化与普通 attention 略有差异。SGLang 有详尽单元测试,但极端情况(深分支、大 K)偶尔会暴露问题。
  4. EAGLE-2 接受率波动:在高温(如 0.9+)下,EAGLE-2 draft 树接受率下降,加速比降低。SGLang 在超过温度阈值时自动关闭 EAGLE-2。
  5. 分布式 KV 传输瓶颈:PD disaggregation 模式下,KV 传输可能压满 NVLink/InfiniBand。SGLang 有速率限制与超额订阅控制。
  6. 多模态图像预处理延迟:大图像(如 4K)在 LLM 前向之前预处理耗时显著。SGLang 用异步预处理与先前请求的 decode 重叠。

深度剖析 1 —— SGLang 论文(arXiv 2312.07185,SOSP'24)

来源:Zheng, Zhang, Sheng 等,“SGLang: Efficient Execution of Structured Language Model Programs”·最新修订 2024-06。

需要内化的关键主张

  1. “Structured Language Model Programs” 框架。论文认为,LLM 的 prompting(chain-of-thought、ReAct、tool use、tree-of-thought)最好被建模为一个有控制流(分支、循环、并行采样)的程序,runtime 应整体优化该程序,而不是把它当成一堆独立请求。(§1, §2)
  2. RadixAttention 只是其中一个优化,而非全部。论文还提出了 SGLang 前端 DSL、runtime API、结构化生成。RadixAttention 算法位于 §3.3。
  3. Oracle vs 实际吞吐。论文被引用最多的表格(Table 3)展示了 oracle(理想前缀缓存)吞吐 vs 实际(RadixAttention)。实际通常达到 oracle 的 90-95% —— 也就是说基于基数树的缓存在合成基准上达到近乎最优命中率。
  4. Tree-attention 是让树结构可用的算法原语。没有 tree-attention,跨分支共享 KV 会产生错误 attention。(§3.4)
  5. 可复合的优化。论文显示 RadixAttention + 连续批处理 + 投机解码 复合:RadixAttention 的 6.4× 是在基线之上,叠加 EAGLE 风格的投机解码后,多轮场景下产生乘法级增益。(§5)

深度剖析 2 —— EAGLE-2 论文(arXiv 2406.16858)

来源:Li, Wei, Wang, Wang,“EAGLE-2: Faster Inference of Language Models via Dynamic Draft Trees”·2024-06。

不显然的发现

  • 静态 draft 树(EAGLE v1)是次优的。固定 K token 的 draft 在 draft head 对某些 token 高置信、对另一些低置信时浪费。
  • 动态 draft 树只在 draft head 置信度超过阈值(可配置,通常 0.6-0.8)的分支展开,产出一个不规则树,更好地匹配生成的真实熵。
  • 验证树遍历在一次前向中处理动态 draft 树,接受最长有效前缀。
  • 经验结果:EAGLE-2 在“每步接受 token 数”上一致比 EAGLE-1 高 20-40%,转化为 ~1.3× 端到端加速。
  • SGLang 集成见 SGLang srt/speculative/,暴露 speculative_algorithm="EAGLE" 与 "EAGLE2" 配置标志,并自动从 HuggingFace 下载对应的 EAGLE head checkpoint。

深度剖析 5 —— RadixAttention 代码路径(Walk-Through)

用户向 SGLang 后端 server 发送 chat completion 请求时,端到端发生了什么:

  1. HTTP server 接收请求(POST /v1/chat/completions)→ server.py 解析 OpenAI 兼容的 JSON。
  2. Tokenizer manager 把消息转换为 token 序列。
  3. Scheduler 被请求接纳新请求。它调用 radix_cache.match_prefix(token_seq) → 返回 (matched_length, kv_span_ptr)。
  4. 如果 matched_length > 0,scheduler 把 KV 跨度交给 prefill worker,后者将其加载到 GPU HBM(尽可能 zero-copy),只 prefill 尾部(从 matched_length 到末尾的 token)。
  5. 如果 matched_length = 0(冷启动),prefill worker 对整个 prompt 做完整前向。
  6. Prefill worker 最后一个 token 的 logit 就是首个生成 token。Scheduler 把请求移入 decode 模式。
  7. Decode worker(或带 EAGLE-2 的投机解码器)每步生成下 K 个 token。
  8. 每一步,scheduler 把新 token 的 KV 追加到基数树。
  9. 请求结束时(EOS 或 max_tokens),该请求的整条 KV 链变成基数树的永久叶子(直到 LRU 淘汰)。
  10. 具有相同前缀的下一个请求复用该叶子的 KV —— 不需要重算。

深度剖析 6 —— XGrammar:结构化生成后端

来源:XGrammar(MLC-AI)·Apache-2.0·2024 年末起被集成进 SGLang 作为默认结构化输出后端。

XGrammar 做什么

XGrammar 把语法(JSON schema、regex、EBNF)编译成 下推自动机(PDA)。在每一步 token 生成时,PDA 决定允许的下一个 token 集合,SGLang 对 LLM logits 施加 token-mask,使只有允许的 token 能被采样。

# XGrammar / SGLang usage example
import sglang as sgl

@sgl.function
def extract_person(s, text: str):
    s += sgl.system("Extract the person mentioned in the text.")
    s += sgl.user(text)
    s += sgl.assistant(
        sgl.gen(
            "person",
            schema={
                "type": "object",
                "properties": {
                    "name": {"type": "string"},
                    "age": {"type": "integer"},
                    "occupation": {"type": "string"},
                },
                "required": ["name"],
            },
        )
    )

print(extract_person.run(text="Ada Lovelace, born 1815, was a mathematician."))
# {'name': 'Ada Lovelace', 'age': 1815, 'occupation': 'mathematician'}

为什么对 RadixAttention 重要

XGrammar 与 RadixAttention 复合:当许多请求共享同一 JSON schema 前缀(例如工具调用的 Pydantic 模型)时,两层缓存同时命中 —— schema 的 PDA 状态在请求间相同,prompt 的前缀也相同。这意味着结构化输出负载既受益于 RadixAttention,又有快速的语法约束 tokenizer。

性能影响:在 JSON-mode 批量下,SGLang 在 Llama-3 70B 上通常达到 ~5,000 tok/s/gpu,而不带结构化生成(也不带 RadixAttention)的同模型约 ~3,400 tok/s/gpu。同负载下比带自定义语法的 TRT-LLM 快约 50%。

深度剖析 7 —— Tree-Attention 实现细节

来源:SGLang tree_attention.py·arXiv 2312.07185, §3.4 中提及。

Mask 构造

对共享前缀的 batch(例如从同一 prompt 的并行采样,或思维树展开),batch 被组织成一片森林。每片叶子代表一个进行中的请求;从根到叶的路径就是该请求的前缀。

Tree-attention 构造的 attention mask 中,叶子 i 中的 token 只 attend 到其祖先的 token(其前缀)。关键是兄弟分支被 mask 掉 —— 这正是结构正确的原因。

# Tree-attention mask construction (conceptual)
#
# Example tree (parallel sampling from prompt "The cat sat"):
#
#                  root
#                 /  |  \
#              "on" "under" "beside"
#             /        |        \
#          "the"    "the"      "the"
#           |        |          |
#         "mat"    "table"    "chair"
#
# At each step, the leaf "mat" sees KV from root + "on" + "the" + "mat".
# It does NOT see KV from "under" or "beside" or their descendants.
#
# The mask is a sparse lower-triangular block matrix where each block
# is itself structured as a tree path mask.

为什么这很难

标准 FlashAttention kernel 假设稠密 attention 矩阵,带简单因果 mask。Tree-attention 需要结构化稀疏的 mask,每个 query attend 的是一条树路径,而不是连续前缀。SGLang 的做法:

  1. 在 batch 组装时预计算树结构(父指针、深度、叶子分配)。
  2. 构建“块稀疏”attention 调度,按树路径对 query 分组。
  3. 分发给自定义 CUDA kernel(FlashInfer 后端带 tree-attention 支持)或 Triton kernel。

性能特征:由于不规则内存访问模式,tree-attention 每 token 略慢于稠密因果 attention,但它开启了并行采样 / 思维树 / EAGLE-2 draft 树 —— 净吞吐获胜。

深度剖析 8 —— SGLang 的 V1 前端 DSL

来源:SGLang lang/ir.py;arXiv 2312.07185, §2。

SGLang 的前端是一个 Python DSL —— 即项目命名的“Structured Generation Language”。DSL 把 LLM 程序视为一张操作图:

  • 字符串拼接(s += ...):累积 prompt 前缀。
  • 生成原语(sgl.gen("name", ...)):prompt 树中需要 LLM 生成的叶子。
  • 选择(s += sgl.select(...)):把 prompt 分叉成 N 条并行分支(每个分支成为单独请求)。
  • 函数组合(@sgl.function):嵌套函数,自动共享前缀。

SGLang runtime 在首次调用时“追踪”程序,识别静态结构(共享前缀、分叉点),输出优化后的执行计划。追踪被缓存,因此后续相同结构的调用复用计划。

# A more complex SGLang program: agent loop with branching
import sglang as sgl

@sgl.function
def react_agent(s, question: str):
    s += sgl.system("You are a research agent. Use tools when needed.")
    s += sgl.user(question)
    
    # Generate a thought
    s += sgl.assistant(sgl.gen("thought"))
    
    # Decide: do we need a tool?
    s += sgl.user(
        sgl.select(
            "decision",
            options=["yes", "no"],
        )
    )
    
    if s["decision"] == "yes":
        s += sgl.assistant(sgl.gen("tool_call", schema={...}))
        # ... recursive tool execution loop ...
    
    s += sgl.assistant(sgl.gen("final_answer", max_tokens=512))
    return s["final_answer"]

为什么要有 DSL?DSL 让 SGLang 的优化器看到整个程序结构(例如“这个函数总是有 system prompt + 用户问题 + 助手思考 + 决策分支”),并相应优化 KV cache。用纯 Python prompting 时,runtime 只看到独立的单次调用。

深度剖析 9 —— 多模态 Pipeline(Qwen2-VL Walk-Through)

来源:Qwen2-VL blog;SGLang 仓库。

用户向 SGLang 发送多模态对话请求(Qwen2-VL)时,端到端会发生什么:

  1. 接收 HTTP 请求:POST /v1/chat/completions,消息中包含图像 URL 或 base64。
  2. Tokenizer manager 解析消息,识别图像附件。
  3. Multimodal processor 进程下载(或接收 base64)图像,运行 Qwen2-VL 的动态分辨率 ViT。ViT 产出一个可变长的图像嵌入序列(例如 1024×1024 图像 640 token,较小图像 256 token)。
  4. Token 组装:multimodal processor 在文本序列中插入特殊 token(<|vision_start|>、<|image_pad|>、<|vision_end|>),前向之后用图像嵌入替换 pad。
  5. 前缀匹配:得到的 token 序列(文本 + 图像嵌入占位符)与基数树匹配。如果先前的请求用过同一张图,图像嵌入前缀被复用。
  6. Prefill:LLM 前向产生首个生成 token。
  7. Decode:自回归生成继续进行,新 token 累积到基数树。
  8. 流式:SSE token 发回给用户。

关键优化:图像嵌入前缀(7B 级 VLM 下约 ~640 token × 4096 维 ≈ 每层 5MB)很重;当同一图像被多个用户查询时(例如客服 agent 用同一产品图,或代码 agent 用同一截图),通过 RadixAttention 复用能显著节省 prefill 时间。

深度剖析 11 —— 为什么 “Structured Generation Language” 是正确的抽象

大多数 LLM 框架把每个请求当作独立调用。SGLang 的洞察在于,LLM “程序”天生是结构化的:

  • 共享前缀:典型对话应用对每个用户都用相同的 system prompt。RAG 应用在同一个会话中对所有查询共享相同上下文。
  • 控制流:agent 循环(ReAct、Reflexion、Tree-of-Thought)在每个“用户请求”中涉及多次 LLM 调用,基于中间输出分叉。
  • 并行采样:best-of-N、束搜索、self-consistency 全部并行生成 N 个候选。
  • 约束传播:若第一次 LLM 调用说“我需要一个工具”,第二次调用的 prompt 就被约束必须包含工具 schema。

SGLang 论文的关键论点:通过让程序结构在 DSL 中显式,runtime 可以跨整个程序优化 —— 在前缀重叠处共享 KV,把并行分支批量到一起,跨调用融合结构化输出约束。

# Without DSL: 3 independent calls, no cross-call optimization
prompt1 = f"{system}\n{user_msg}"
resp1 = llm(prompt1)
prompt2 = f"{system}\n{user_msg}\n{resp1}\nNow reason step by step."
resp2 = llm(prompt2)
prompt3 = f"{system}\n{user_msg}\n{resp1}\n{resp2}\nFinal answer:"
resp3 = llm(prompt3)

# With SGLang DSL: 1 traced program, shared prefix across all calls
@sgl.function
def chain_of_thought(s, user_msg):
    s += sgl.system("You are a helpful assistant.")
    s += sgl.user(user_msg)
    s += sgl.assistant(sgl.gen("thought"))  # 1st call
    s += sgl.user("Now reason step by step.")  # auto-continuation
    s += sgl.assistant(sgl.gen("reasoning"))  # 2nd call (shares system prompt KV)
    s += sgl.user("Final answer:")
    s += sgl.assistant(sgl.gen("answer"))  # 3rd call (shares everything before)

SGLang runtime 在拿到追踪后的程序后,就知道调用 2 和 3 共享 system prompt 与调用 1 的输出,并相应复用 KV。

深度剖析 12 —— 投机解码深度数学

投机解码(EAGLE、EAGLE-2)是一个非平凡的算法。它的数学直觉:

标准自回归解码每步生成一个 token。用 K 个 draft token,投机解码每步生成 K+1 个 token(K 个 draft + 1 个验证或拒绝)。接受率 α 是 K 个 draft token 被接受的概率。

每步预期 token 数:

  • α = 1.0(完美 draft):每步 K+1 token → ~K× 加速
  • α = 0.5(50% 接受):每步 ~2 token → ~2× 加速
  • α = 0.0(最差):每步 1 token(无减速)

EAGLE 的 draft head 预测下一层 hidden state,在 Llama-3 / Mistral / Qwen 上 temperature 0 时经验 α ≈ 0.7-0.85。EAGLE-2 的动态 draft 树把许多实际负载的 α 提到 ~0.85-0.95,端到端 2-3× 加速。

为什么预测 hidden state(而非 token)?

如果 draft head 直接预测下一个token,它需要建模完整 LLM 词表(32k-256k 个条目)。Hidden-state 预测只需要建模 LLM 的隐藏维度(如 Llama-3 8B 为 4096),这是一个更小、更可学习的目标。Draft head 本质上是一个小型 transformer,镜像 LLM 的下一层计算,但参数更便宜。

5.7 瓶颈与风险

  1. 颠簸下缓存碎片。许多短生命周期、发散尾部的请求会让 RadixTree 留下部分叶子,造成碎片。LRU 有帮助,但对非平稳负载不是最优。
  2. 多副本缓存一致性。若托管平台对同一模型有 N 个副本,每个副本有各自的基数树。副本 A 上的前缀命中对落在副本 B 上的请求没帮助。跨副本 KV 传输在开发中,但会增加延迟。
  3. GPU 内存压力。基数树可无界增长,直到 LRU 淘汰。若负载局部性差(无重复前缀),树持有的就是死重,SGLang 有可配置的最大缓存大小旋钮。
  4. 正确性边界情况。Tree-attention 需要小心 mask;bug 可能产生微妙错误输出。SGLang 有详尽测试套,但对回归不免疫。
  5. 开源与商业拆分。RadixArk 的价值主张取决于 SGLang 保持最佳开源 LLM runtime。若 vLLM 发布更优的 RadixAttention 等价物,或某超大规模云厂(Google、NVIDIA)造出更好的东西,护城河会变窄。
  6. 人才 / 留任。SGLang 维护者是一个小群体;若关键人物离开(去创业或加入超大规模云厂),开源势头可能停滞。

5.10 自托管 SGLang 何处胜过 RadixArk(托管)

托管价值主张对大多数用例都很强,但也有自托管更划算的场景:

  • 极端规模:运行 >10B token/天的客户可能发现按 token 定价不如摊销 GPU 采购 + 自托管成本。
  • 自定义模型微调:RadixArk 托管热门的开源权重模型,但带有微调 Llama-3 变体的客户可能需要完全自托管控制。

5.12 收尾的权衡(这个赌注)

这个赌注是:agentic 负载(多轮对话、tool use、RAG、结构化输出)成为 LLM serving 的主流模式,而跨请求前缀复用是这些负载的主流优化。如果两个条件都成立,RadixAttention(以及 RadixArk)相对 vLLM、TRT-LLM 及其他不原生跨请求共享 KV 的 runtime,具备结构性优势。

对这个赌注的反方论点:

  • 许多生产负载是单轮的(例如 completion 类用例),前缀共享收益微小。
  • vLLM 的 APC 已经部分覆盖多轮场景;差距可能缩小。
  • OpenAI / Anthropic / Google 闭源 API 仍是前沿模型的归属;若闭源胜出,开源推理平台被商品化。
  • 硬件进步(H200、B200、B300)可能让吞吐论点不如 DX 论点显著。

反-反方论点:即使闭源前沿模型胜出,仍然存在一个庞大且不断增长的开源模型市场(Llama、Qwen、DeepSeek、Mistral、gpt-oss),部署在本地 / BYOC / 托管开源基础设施上。该市场就是 RadixArk 的可寻址市场 —— 而在其中,前缀共享是真实的差异化。

6.10 为什么 RadixAttention 与 RadixArk 不是同一个赌注

一个常见的混淆:人们把 RadixAttention(算法)的成功与 RadixArk(商业实体)的成功混为一谈。这是两个不同的赌注:

  • RadixAttention 赌注:跨请求前缀共享成为 LLM serving runtime 的标准原语。这一点基本已经赢了 —— SGLang 与 vLLM(经 APC)都发布了前缀缓存。SOSP'24 发表确保学术合法性。算法的智力贡献是永久的。
  • SGLang OSS 赌注:SGLang 成为主导的开源 LLM runtime,取代 vLLM。这一点还在变化 —— vLLM 行业势头更强(~30k stars,生产用户更多),SGLang 学术 / agent 构建者势头更强(~14k stars,与 LMSYS 联系更深)。两个项目在可预见的未来会共存。
  • RadixArk 商业赌注:托管 SGLang 成为有意义的推理平台,达到 Fireworks 或 Together 的量级(目前 ARR 各 $100M+)。这是最难的赌注 —— 它需要赢得企业 GTM、多区域部署,并与资金充足的存量玩家竞争。

最可能结果:RadixAttention 经久耐用;SGLang 保持重要开源项目;RadixArk 在多轮 agent 负载的首选推理平台这一利基找到位置,到 2028 年 ARR 落在 $30-80M 区间。

术语表

术语定义
KV cacheTransformer attention 层缓存的 Key 与 Value 张量。每个 token 产生 K 和 V 向量,被所有后续 token 的 attention 计算复用。
PrefillLLM 对输入 prompt 的第一次前向,并行处理所有 prompt token,产出第一个生成 token。
DecodeLLM 一次生成一个 token 的自回归阶段,复用 prefill 阶段的 KV cache。
RadixAttention将 KV cache 存储在基数树(压缩 trie)中,使共享公共前缀的请求能复用 KV 跨度的算法。由 SGLang 团队发明(arXiv 2312.07185)。
PagedAttention像虚拟内存一样对 KV cache 分页,消除单个请求 KV 内部碎片的算法。由 vLLM 团队发明(arXiv 2309.06180)。
Tree-attention一种自定义 attention kernel,正确 attend 到树形前缀,屏蔽兄弟分支。是并行采样、思维树、EAGLE-2 动态 draft 树正确性的前提。
Speculative decoding(投机解码)一种技术,用小的“draft”模型提议 K 个候选 token,大“target”模型并行验证,在不损失质量的前提下获得更高 tok/s。
EAGLE / EAGLE-2预测下一层 hidden state(而非直接预测下一个 token)的具体投机解码算法。EAGLE-2 增加动态 draft 树。由 Yuhui Li 等发明。
Continuous batching(连续批处理)一种调度技术,每步可接纳新请求到 batch、淘汰已完成请求,而不是等最长请求完成。vLLM 和 SGLang 都使用。
Tensor parallel(TP)把单模型权重矩阵切到 N 个 GPU,每层做集合通信。在模型装不下单 GPU 时使用。
Pipeline parallel(PP)把模型层切到 N 个 GPU 形成流水线。用于超大模型或内存受限部署。
Data parallel(DP)在不同请求 batch 上跑 N 个独立模型副本。用于横向扩展。
PD disaggregation把 prefill(计算密集)和 decode(内存密集)分到不同 worker 池。KV cache 通过 NVLink/IB 在两者间传输。SGLang V1 原生支持。
XGrammar通过下推自动机把 JSON schema / 正则 / EBNF 编译为 token mask 的语法约束生成引擎。SGLang 默认结构化输出后端。
LLM program编排多个带控制流(分支、并行采样、循环)的 LLM 调用的程序。SGLang 论文认为这是 prompt 工程正确的抽象。
